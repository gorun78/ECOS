## 二、现状分析

### 2.1 数据表目录分页

**文件**: `ecos_frontend/src/pages/data-workbench/tabs/ConnectionsTab.tsx` (L56, L62-71)

当前默认 `tablePageSize = 20`，且在 L62-71 有一个 `useEffect` 从 `/api/v1/engine/data/settings` 取 `catalog.page_size`（上限100）动态覆盖。数据通过 `fetchDataSourceResources` 一次性拉取全部表，前端用 `Array.slice()` 分页（L400）。

### 2.2 采集信息与Git

**后端**: `MetadataCollectTaskExecutor.execute()` 采集表清单 → 逐表 `syncResource()` 写 `td_data_resource` → `auditLog()` 写 `td_metadata_collect_log` → `updateLastCollectTime()`。**当前无Git集成、无版本差异对比。**

**Git已有能力**:
- `runtime-access` 的 `GitService`/`GitRepositoryService` 提供 `commit`/`diff`/`listCommits`/`log` 等方法
- `GatewayController.GitController` 暴露 `/api/v1/ecos/git/*`（status/commits/diff/commit/tag/rollback/branches/branch）
- `PipelineGitService` 已用 GitService 做 Pipeline YAML 版本管理（可参考其模式）

### 2.3 定时采集策略

**后端已就绪**:
- `MetadataStrategyConfig` 已支持 `scheduleCron` 字段
- `MetadataController.saveStrategy()` 已接受 `scheduleCron` 参数
- `AutoCollectScheduler` 已实现 `@Scheduled(fixedDelay=60s)` 扫描 `ON_SCHEDULE` 数据源，按 cron 触发采集

**前端缺失**: `ConnectionsTab.tsx` 的"元数据获取策略"区（L263-298）只有 trigger + countMethod 两个下拉框，**没有 cron 输入/选择控件**。`saveMetadataStrategy` API 可传 `scheduleCron` 但 UI 未暴露。

### 2.4 异步任务中心对接

**前端**: `AsyncTaskCenterView.tsx` (1137行) 是**纯 mock UI**，7条硬编码任务，`setInterval` 随机推进进度，无后端API调用。`triggerType: 'SCHEDULED'` 是假数据。
**实际采集任务**: 已走 `runtime-task`（`ITaskManagementService`），可通过 `GET /api/v1/task/list?taskType=METADATA_COLLECT` 查询真实任务列表。

### 2.5 SQL查询控制台

**根因分析**:
- 后端 `QueryController.execute()` 返回 `columns` 为对象数组: `[{name, label, type}, ...]`，`rows` 为对象数组: `[{colLabel1: val1, colLabel2: val2, ...}, ...]`
- 前端 `InlineSqlConsole`（ConnectionsTab L552-638）:
  - L574: `result({ columns: d.columns, rows: d.rows, ... })` — `d.columns` 是对象数组
  - L615: `<th key={c} ...>{c}</th>` — 把对象对象当 string 渲染 → 显示 `[object Object]`
  - L622-624: `result.columns.map(c => ... row[c])` — 用对象做键取 `row[c]` → undefined
- `sql-query-console/index.tsx` (Monaco版) 和 `SqlQueryConsole.tsx` (老版) 可能有类似问题

**修正方案**: 前端需适配后端对象格式 — 提取 `c.name`/`c.label` 作为列名，用 `columnLabel` 做行数据键。

### Task 5: 修复SQL查询控制台结果错误

**根因**: 后端 `execute()` 返回 `columns` 为对象数组 `[{name, label, type}]`，`rows` 以 `columnLabel` 为键。前端多处按字符串数组处理。

#### 5A. 修复 `InlineSqlConsole`（ConnectionsTab.tsx L552-638）

修改 result 类型定义和执行逻辑:
```tsx
// 之前: result.columns 是 string[]
// 之后: 适配对象数组
const result = {
  columns: (d.columns || []).map((c: any) => c.name || c),  // 提取 name
  rows: d.rows || [],
  rowCount: d.rowCount || 0,
  elapsedMs: d.elapsedMs || 0,
};
```

表格渲染:
```tsx
// 列头
result.columns.map((c: string) => <th key={c}>{c}</th>)

// 行数据: row 是以 columnLabel 为键的对象
// 列头 c 已提取为 name，但 row 的键可能是 label
// 兼容: row[c] 或 row[cName]
```

实际上后端 `rows` 是以 `columnLabel` 为键的。所以列头应该用 `label`（别名）而非 `name`（原始列名），因为 `row` 的键是 label。修改:
```tsx
// 提取 label 作为显示名 + key
const colLabels = (d.columns || []).map((c: any) => c.label || c.name || c);
result({ columns: colLabels, rows: d.rows || [], ... });
// 行渲染: row[cLabel]
```

#### 5B. 修复 `sql-query-console/index.tsx`（Monaco版）

检查 `ResultTable` 渲染是否正确适配对象格式的 columns。L74 `rows.slice(0, 500)` 之前未报错说明可能已适配，但需确认 `columns` 渲染方式。

#### 5C. 修复 `SqlQueryConsole.tsx`（老版）

复用 `sql-query-console/` 下的 `ResultTable`，同上检查。

#### 5D. 后端错误信息增强（可选）

`QueryController.execute()` L111: `ApiResponse.internalError("查询执行失败: " + e.getMessage())`
- 当 RLS 拒绝时，增强错误提示，明确告知"该行数据无权限访问（RLS 行级过滤拒绝）"
- 当前已有 L81: `return ApiResponse.forbidden("RLS 行级过滤不可用，查询被拒绝（默认 DENY）")` — 这个OK

## 四、假设与决策

1. **Git 仓库**: 复用 `ecos-git-repos` 目录（`sys_config.ecos_git_repo_root`），每个数据源一个子目录 `metadata/{datasourceId}/`。
2. **Diff 存储**: diff 报告 (Markdown) 存入 PG `td_metadata_collect_log` 的 `result` 字段中（`diffFile` 子字段存 git 相对路径）。
3. **不改 AsyncTaskCenterView**: 任务中心独立页面是 mock 展示，属独立功能，本次只在数据工作台内联显示任务状态+跳转链接。
4. **定时采集 cron 格式**: 标准 5 位 cron (分 时 日 月 周)。
5. **SQL 列名显示**: 使用 `columnLabel`（查询别名）而非 `columnName`，因为后端 rows 以 label 为键。
6. **不新建 Maven 模块**，不新建 Docker 容器（铁律5.1 #10）。
7. **API 只增不改**: 新增 `/collect-diff/{id}` 端点，不修改既有端点签名。
