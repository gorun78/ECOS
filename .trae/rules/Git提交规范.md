# Git 提交核心规范

> 版本: 1.1 | 2026-09-28
> 适用: ECOS 全工程（main/dev/test 分支管理 + commit message + MR/PR 流程 + 多任务并行）
> 上游依据: .trae/rules/架构铁律.md（宪法）
>
> **v1.1 变更**（2026-09-28，分模块多任务并行完善场景）：
> - 新增「五、多任务并行规则」：任务分支隔离、worktree 物理隔离、文件所有权、共享文件串行窗口、同步与冲突消解
> - 「一、核心红线」补充任务分支直推白名单例外与基线分支定义
> - Commit Message 增加并行任务 ID 标注要求；Checklist 增加并行检查维度

## 一、 核心红线与分支管理

| 规范项 | 核心要求 | 详细说明 / 示例 |
| :--- | :--- | :--- |
| **单一提交** | 一次提交只做一件事 | 单功能/单Bug，严禁多业务混杂提交。 |
| **干净安全** | 提交前强制过滤 | 严禁提交调试代码、敏感密钥、本地配置及打包产物。 |
| **分支隔离** | 严格区分分支用途 | `main/master`：严禁直接提交，仅通过 MR/PR 合入。<br>`dev`：开发主干，所有新功能/修复必须基于此拉取。<br>`test`：测试专用，仅合入自测通过的代码。<br>**基线分支**：本项目当前开发基线为 `release/v2.1-alpha`（及后续 `release/*`），规则等同 `dev`；所有任务分支从其拉取、最终合入其中。<br>**任务分支例外**：`feature/*`、`bugfix/*`、`feat/*` 等任务分支允许直推远端（作为 DONE 凭证交付），但严禁 `push -f`；合入基线必须走 MR/PR。 |
| **命名规范** | 语义化英文命名 | 从基线分支拉取，格式：`类型/模块-任务标识-描述`（描述全小写短横线）。<br>示例：`feature/data-engine-pmo61-lineage-export`、`bugfix/frontend-pmo62-hmr-context`。<br>**并行强制项**：`模块` 段必须与任务卡归属模块一致；`任务标识`（PMO 编号或任务 ID）在任务组内唯一，便于 `git log --grep` 与分支清单核对。<br>严禁拼音、中文或无意义命名。 |
| **提交凭证** | commit hash 即 DONE 凭证 | 每个 Sprint/PMO 产出必须有 Git commit hash 作为 DONE 凭证；**working tree 未提交变更一律不算交付**。worker 完成后必须按批次 clean commit（前后端分离、不夹带旧 wave 残留），验收方用 `git log --grep` 溯源，禁止仅凭 `git status` 判定完成。 |

## 二、 Commit Message 规范

| 规范项 | 核心要求 | 详细说明 / 示例 |
| :--- | :--- | :--- |
| **标准格式** | `type(模块): 动宾结构精准描述` | 示例：`feat(用户模块): 新增用户分页查询接口`<br>严禁使用“修改代码”、“update”等模糊文案。 |
| **并行任务标注** | 描述带任务标识，正文可追溯 | 并行任务组内：首行格式 `type(模块): [任务标识] 动宾描述`，如 `feat(data-engine): [PMO-61] 新增血缘导出接口`。<br>多 Task 任务组建议正文追加 `Task-Id: t_xxxx` / `Wave: A` trailer，供分组验收与回滚定位。 |
| **Type 枚举** | 严格使用以下 8 种类型 | `feat`(新功能) \| `fix`(修复) \| `refactor`(重构) \| `perf`(性能)<br>`style`(格式) \| `docs`(文档) \| `test`(测试) \| `chore`(构建/配置) |
| **拆分规则** | 无关业务必须拆分 | 多业务禁止混杂提交；功能变更与格式优化必须分两次提交。 |

## 三、 合并与推送规则

| 规范项 | 核心要求 | 详细说明 |
| :--- | :--- | :--- |
| **禁止强推** | 严禁对主干 `push -f` | 避免代码覆盖丢失，保护主干安全。并行任务分支同样严禁 `push -f`；任务分支需要改写历史时，改用新分支重命名交付或升级 PM 裁决。 |
| **规范合并** | 走 MR/PR 流程 | 功能完成后通过 MR/PR 合入基线分支（当前为 `release/v2.1-alpha`）；热修复需先在 `test` 验证。 |
| **防冲突** | 合并前同步代码 | 必须拉取远端最新代码，确保无严重冲突且代码可正常运行；并行场景下冲突只在基线分支消解，禁止在任务分支间互相 merge。 |

## 四、 多任务并行规则（v1.1 新增，🔴 强制）

> 适用场景：同一时期有 ≥2 个模块任务（PMO 任务组 / 多 worker 会话）并行开发。核心原则：**逻辑上分支隔离，物理上 worktree 隔离，共享文件串行窗口**。

| 规则项 | 核心要求 | 详细说明 |
| :--- | :--- | :--- |
| **一任务一分支** | 任务与分支一一对应 | 每个 Task 从基线分支（当前 `release/v2.1-alpha`）拉独立任务分支，命名见「一、命名规范」。**严禁在未 checkout 的分支上直接编辑**——未提交变更不属于任何分支，跨任务切换必然丢失。 |
| **worktree 物理隔离** | 并行会话各占一个 worktree | 多会话/多 Agent 并行时，每个任务用 `git worktree add <路径> -b <任务分支>` 建独立工作树，互不干扰 checkout；同一工作树内**串行**执行 checkout / add / commit / merge。任务完成后 `git worktree remove` 回收。 |
| **文件所有权** | 任务卡声明 owns-files | PM 拆分任务时每个任务必须声明可修改文件/目录清单（owner 集）；非 owner 任务**禁止触碰**。同一文件被多任务需要时，指定唯一 owner，其他任务以追加式需求交给 owner 合并修改。 |
| **共享文件串行窗口** | 高冲突文件错峰改 | `AGENTS.md`、`.trae/rules/*`、`docs/README.md`、`package.json`/`pnpm-lock`、`pom.xml`、菜单/路由注册表、i18n 词条文件、DB 迁移 SQL 为高冲突文件：只允许在约定的串行窗口内由单一任务修改；修改后立即 commit 并合入基线，其他任务 rebase 后再继续。 |
| **锁文件与产物** | 只由 rebase 触发再生 | `pnpm-lock.yaml` 等 lock 文件禁止手工编辑、禁止双任务并排生成：依赖变更任务先合入基线，后续任务 rebase 后单独跑 install 再生 lock。 |
| **同步节奏** | 每日 rebase 基线 | 任务分支开工前和每次合入基线前，必须 `git fetch` + rebase（或 merge）最新基线；在途任务分支落后基线超过 1 天视为冲突风险任务，先同步再继续开发。 |
| **合入顺序** | 低风险先行、拆小批次 | 按「chore/docs → test → 后端 → 前端 → 共享文件」的冲突梯度合入基线；每批次合入后基线必须构建通过。任务组内后合入的任务 rebase 到已含前序批次的基线，禁止并行任务各自攒大批变更最后一次性合并。 |
| **冲突消解** | 禁止丢弃对方变更 | 冲突时以语义合并解决，严禁 `checkout --ours/--theirs` 一键取舍（除非该侧确为本任务独占文件）；解决不了回到「文件所有权」裁决，必要时升级 PM。 |
| **验收与回收** | 分支即批次凭证 | 每任务完成后：任务分支 hash 作为 DONE 凭证 → MR 合入基线 → 删除任务分支与 worktree；`git branch` 中不得长期残留已完成任务的分支。 |

## 五、 提交前强制自检（Checklist）

| 检查维度 | 自检项 | 状态 |
| :--- | :--- | :--- |
| **分支检查** | 是否在合规业务分支？是否误操作主干？ | ☐ |
| **内容检查** | 是否已清除调试代码、敏感信息、冗余文件？是否属于单一变更？ | ☐ |
| **信息检查** | Type 是否准确？描述是否清晰无废话？并行任务是否已带任务标识？ | ☐ |
| **状态检查** | 是否已同步最新代码？无强制推送？代码无语法报错？ | ☐ |
| **凭证检查** | 是否已按批次 clean commit？可用 `git log --grep` 溯源到本批次 DONE 凭证？ | ☐ |
| **并行检查** | 变更是否全部落在本任务 owns-files 内？是否触碰了共享文件而未在串行窗口？是否在独立 worktree（或已确认工作树串行）？ | ☐ |
