## 一、 AI 编程最高核心准则（强制红线）
低冗余高整洁：禁止无用变量、空方法、冗余判断及无效注释，保持代码极简。
确定性原则：拒绝模糊兼容与万能兜底，精准匹配业务场景。
项目一致性：严格遵循现有架构、分层、命名及封装风格，禁止自定义新体系。
分层单一职责：Controller/Service/Dao/Entity 职责严格隔离，禁止跨层操作。
安全健壮优先：默认包含参数校验、空值判断、异常捕获、事务控制及权限判断。
禁止魔改：无明确指令，禁止修改全局配置、拦截器、统一返回体及数据库基础结构。
扩展性： 拒绝类似逻辑的代码块，尽量抽象公共方法

二、 通用代码风格规范
格式语法：缩进统一（2/4空格），排版工整；使用主流稳定语法，禁止废弃API及未使用变量。
命名规范：全英文语义化，禁拼音/缩写。
包/文件夹：全小写（如 user/controller）
类名：大驼峰（如 UserController）
方法/变量：小驼峰（如 getUserInfo）
常量：全大写+下划线（如 MAX_PAGE_SIZE）
数据库：下划线命名（如 user_info）
注释规范：类/公共方法/对外接口必须有文档注释；复杂逻辑加单行注释；禁止残留调试/废弃注释。
类、方法、成员变量需要有必要的注释。
接口不能使用Map作为入参和出参。
接口返回参数必须是ApiResult<T>方式。
所有 REST Controller 的入参和出参必须使用强类型 DTO/VO 类，禁止使用 Map<String, Object> 作为请求体参数或响应体。
所有实体使用lombok生成get和set方法。
所有 Java Entity 和 DTO 类必须使用 Lombok 消除手写样板代码。Entity 使用 @Getter + @Setter + @NoArgsConstructor（禁止 @Data，防止 JPA 懒加载/循环引用问题）。
DTO 使用 @Data，禁止手写 getter/setter/constructor，保持代码简洁一致。
所有的异常必须使用日志框架打印到日志。
花括号强制原则：所有 Java 控制流语句（if / for / while / else / else if）必须使用花括号 {}，即使只有单行语句也不得省略。省略花括号会导致 IDEA 报红色警告，且易在后续修改时引入逻辑错误。

三、 项目分层架构规范
Controller 控制层：仅负责接收参数、基础校验、调用 Service 及统一返回。禁写业务逻辑与 SQL。
Service 业务层：负责核心逻辑、参数校验、数据组装、事务及权限。禁获取 Http 请求/响应对象。
Dao/Mapper 数据层：仅负责数据库 CRUD。禁处理业务逻辑与数据拼装。
Entity/Model 实体层：仅定义字段与注解，无业务方法。
禁止跨层：禁止超大类/方法，逻辑过长必须拆分。

四、 接口开发规范
基础规范：遵循 RESTful 风格；统一使用全局返回体；分页接口统一 pageNum/pageSize。
参数校验：入参必须校验（非空/长度/格式等），非法参数统一抛出标准业务异常。
安全规范：校验登录态与 Token；敏感操作加权限校验；高频操作加防抖/幂等。
命名规范：
路由：统一 /api/模块名，全小写+短横线，资源集合用复数（如 GET /api/users）。
方法：固定动词前缀（如 getXxxDetail, addXxx, updateXxx, deleteXxx）。
实体：查询用 XxxQuery，新增/编辑用 XxxSaveDTO，返回用 XxxVO。

五、 业务逻辑与异常处理
业务逻辑：单一职责，卫语句优先；公共逻辑抽离；枚举替代硬编码；全覆盖数据判空。
异常处理：禁止裸抛原生异常与空 try-catch；使用自定义全局异常；返回友好业务提示。

六、 数据库 SQL 规范
> 详细规范见 `数据库访问规范.md`（v1.0, 2026-09-22）：IR01~06 访问 + DR01~08 命名 + EN01~03 执行 + ST01~06 三档 + DDL 模板 + MyBatis XML 模板 + DDL 审查清单。本节为精简版摘要。

SQL 强制：禁 select * 及无条件更新/删除；批量/大数据量必须分页；查询/排序字段必须有索引。
实体入库：按需赋值，禁空值覆盖有效数据；统一使用全局逻辑删除字段。
命名规范：
表名：`ecos_{module}_{business}` (新表强制 `ecos_` 前缀)，全小写下划线（如 ecos_workflow_instance）。
字段：全小写下划线；**审计 5 字段固定**：`create_time`, `update_time`, `create_by`, `update_by`, `is_deleted`。
**多租户预留**：新表必带 `domain VARCHAR(50) NOT NULL DEFAULT 'default'`。
**版本控制**：必带 `version_no VARCHAR(20) NOT NULL`（乐观锁）。
**JSONB** 字段加 `_json` 后缀；**布尔** 字段加 `is_` 前缀。
索引：普通 `idx_{表名}_{字段}`，唯一 `uniq_{表名}_{字段}`。
类型与约束：合理分配长度与类型；时间统一 datetime/timestamp；必填字段 NOT NULL。
事务规范：多表联动变更必须开启事务并处理回滚；查询禁滥用事务；单事务最多 1 个 commit 点；批量 INSERT/UPDATE 必须 `REQUIRES_NEW` 子事务 + 单批 ≤ 100。
交叉约束（继承 `数据库访问规范.md` 红线）：
- 禁 gateway / 顶层 service 直接持有 PG 连接 (IR01)
- 禁在 Engines / Runtime 自建 Driver (IR06, 走 runtime-access)
- 写操作必发 Kafka `ecos.audit` (ST06)
- 敏感列加密 + 行/列级过滤 (ST03/04/05)

七、 日志、安全与性能规范
日志规范：统一使用项目日志工具，分级记录（info/warn/error）；严禁打印密码/Token等敏感数据。
安全规范：禁硬编码密钥/密码；防 XSS 与 SQL 注入（预编译）；敏感数据返回前端自动脱敏。
性能规范：禁循环查库/第三方请求；大数据量分页/流式处理；重复查询做缓存；耗时逻辑异步处理（统一走 `runtime-task`，见第九节，禁止自建线程池/调度器）。

八、 AI 编码红线与输出要求
绝对禁止：无条件删改、吞异常、硬编码、分层混乱、未校验裸奔、冗余代码、泄露敏感数据、慢 SQL。
输出要求：代码可直接编译运行，贴合现有架构，改动精准，复杂逻辑附带说明。

九、 runtime 公共底座规范（器 · 对齐架构铁律 §2.5）
runtime 是横切底座，各引擎/服务层**必须复用，禁止重复实现**；发现公共能力缺失时先向 runtime 补强，不在引擎内自建（引擎内自建 = 验收失败）。归属判断看类定义了什么问题 Bean（`@Configuration` 定义 Driver/Client 即基础设施访问），不看被谁 import。
1. 基础设施访问（runtime-access）：PG/Neo4j/MinIO/Doris/Git 的 Driver/Client 封装统一走 `runtime-access`；引擎/服务/gateway 禁止各自 `new Driver`、禁止自建 DataSource/连接池封装（继承 IR06）。
2. LLM 调用（llm-gateway）：所有大模型调用统一走 `llm-gateway`（LLMGatewayService）；禁止引擎直连 Provider API、禁止各自封装 SDK Client / 重试 / 计量。
3. 任务与异步（runtime-task）：
   - 即时任务：业务 Controller 走 `ITaskManagementService.submitTask(desc) + executeTask(taskId)`，响应必须回**真实 `taskId`** + `status: SUBMITTED`；禁止回自造 `jobId` 当运行中任务 ID。
   - 定时/周期任务：统一 `taskManagementService.scheduleTask(desc, cron)` 注册并持有 `scheduleId`，落 `td_runtime_task_plan` + `td_runtime_task`；禁止业务侧自建 `*_scheduled_*` 表、禁止自建 `ScheduledExecutorService` / `@Scheduled` 绕过全局调度。
   - 任务级运行时状态（pending/running/succeeded/cancelled/failed）只存 `td_runtime_task_status` 一份；业务审计表（如 `*_extract_audit`）只记"谁/何时/结果"事件，不与 runtime 表互为备份字段。
4. 监控告警（runtime-monitor）：指标采集、健康检查、告警统一走 `runtime-monitor`；禁止引擎自建监控埋点体系或自行推送告警通道。
5. 事件通知（runtime-event）：跨模块事件统一走 `runtime-event` 的 `EventBusService`（Kafka 不可用时自动降级内存 SpringEventBus，业务侧无感）；禁止引擎/服务自建 `KafkaTemplate`、producer、consumer 或 `@KafkaListener` 直连业务 topic。Topic 常量只允许引用 `runtime/common-api` 的 `KafkaTopics`，禁止字符串字面量散落。审计事件仍按 ST06 写 `ecos.audit`，与业务事件不重复投递。
6. 基础工具：日志、国际化、告警、分页等基础工具统一走 runtime 工具类与 `common-api` 契约（如 `ApiResponse`、`PipelineEvent`、`ICopilotService`），禁止各引擎重复实现。

十、 系统配置与数据字典规范（单表分组 · sysman 为唯一事实源）
1. 单一事实源：全局配置表 `sys_config`、全局字典表 `sys_dict` 由 sysman 统一持有。引擎/工作台**不新建自有配置表或字典表**，作用域靠分组列二分：
   - `sys_config.config_group`：`general` = 平台全局；`{engine}`（`data-engine` / `ontology-engine` / `cognitive` / `kb-engine` …）= 引擎/工作台独立配置。
   - `sys_dict.subsystem`：与所属引擎的 `config_group` **同名对齐**，空值 = 全局字典。
   - 引擎独立字典与其独立配置同属一个作用域标识，设置页中并列展示，一个工作台一套分组名。
2. 命名规范：`config_group` 取模块标识，全小写短横线；`config_key` 必须 `{group}.{子模块}.{名}` 三段前缀，跨组不得重名；`dict_type` 同理带组前缀，全局类型不带前缀。
3. 访问唯一入口：配置与字典的读写一律经 sysman 的 **api 接口**（`SysConfigService` / `IDictService` 及其 api 层暴露的门面）获取，具体要求：
   - 禁止用 `JdbcTemplate` 直接 `SELECT/INSERT/UPDATE sys_config` 或 `sys_dict`（无论跨模块还是本模块）。
   - 禁止 import 其他模块的 `*Impl` 类；依赖只走 api 模块接口，由 Spring 注入实现。
   - 门面方法不够用时，向 sysman api 增补方法（只增不改既有签名），不得在引擎内绕行直连表。
4. 作用域隔离：引擎只允许读写自身 `config_group` / `subsystem` 的数据；`general` 组仅 sysman 与 gateway 可写。跨组读必须有明确理由并在代码注释中说明，写则绝对禁止。隔离手段为查询条件强制带分组：`WHERE config_group = ?` / `config_key LIKE '{group}.%'`。
5. 三档与消费契约：新增配置行必须显式填 `edition`（standard/enterprise/ultimate，对应 Maven profile）；必填 `default_value`，前端 reset 依赖它。消费方生效后回填 `is_consumed / consumed_by / consumed_at`；未标记已消费的配置项不得视为生效配置，不得仅凭"表里有值"判定行为。
6. 缓存一致性：配置/字典读取走服务级缓存；任何写操作（单条、批量、reset）后必须调用 `refreshCache()`，禁止只改库不刷缓存。批量写沿用事务规范。
7. 接口契约：配置/字典对外的 Controller 出入参必须是强类型 DTO/VO（`XxxConfigVO` / `XxxConfigSaveDTO` / `XxxDictVO`），禁止 `Map<String, Object>`（承接第二、四节红线）。
8. 已知偏差与待整改（存量登记，新增代码不得照抄；整改由 PMO 拆原子任务，验收标准=本节对应条款）：

十一、 设计态/运行态版本与 Git 归档（runtime 出 Driver，引擎做编排）
1. 版本存储二分（🔴）：**数据库只存在用版本**（`version_no` + 全量内容列，供运行态读取）；**历史版本一律进 Git**（一次发布 = 一次 commit + 一个 tag）。业务表禁止继续膨胀式追加历史快照行。
   - 载体二分：Git 仓库存**设计资产版本**（元数据/pipeline/血缘/规则/本体/知识树/认知模型/Agent 协同/场景定义），MinIO 与 PG 数据湖层存**数据对象**。禁止把设计资产历史快照写入 MinIO 分层，本条与《数据湖存储分层规范》§七A（三档×分层承载口径）互不替代。
2. 双态定义与流转：
   - 设计态：草稿资产，DB 在用行可原地修改，无 git 记录。
   - 发布：序列化资产为文件 → `GitService.commit` + `createTag`（tag 规范 `{assetType}/{assetId}/{versionNo}`）→ DB `version_no` 前滚 + 写版本索引行 → 发 runtime-event 资产发布事件。
   - 运行态：按 `version_no` 读 DB 在用行；历史回溯与差异对比只从 git 取（`diff` / `getCurrentCommitId`），不查 DB 历史行。
   - 回滚：从 git ref 检出内容覆写 DB 在用行并递增 `version_no`；禁止删表重建，禁止把历史快照行"翻"回在用状态。
3. Git 唯一出口：一切 git 操作只允许 `runtime-access` 的 `GitService` / `GitRepositoryService`（接口注释已声明全系统共用）。禁止 `import org.eclipse.jgit.*`、禁止 `ProcessBuilder` 调 git 命令、禁止在 sysman 或引擎内定义第二套 Git 接口/实体/异常类。
4. 编排层职责：引擎可保留"资产 ↔ 文件序列化 + 提交时机"的编排服务（合规范例：data-engine `PipelineGitService` 注入 runtime `GitService`）。编排层只做序列化与流程编排，不得自行实现 clone/push/diff 等传输能力。
   - 「合规范例」限定范围（2026-09-28 PMO-74 Q11 反向更正）：**仅指"注入 runtime `GitService`、不自建传输能力"这一职责**，不构成对其全部入参的合规背书。`PipelineGitService` 历史上的 `localPath` 入参属 VG-3 违规项，现以 `repositoryId` 为准，仅传已废弃 `localPath` 的请求由 `PipelineGitService` 拒绝并返回 `not_available`（`GitRepoRootResolver.requireInsideRoot` 负责把解析出的路径限制在 `ecos_git_repo_root` 内）；新增代码照抄时必须取 `repositoryId` 分支。
5. 仓库注册与寻址：每类资产对应一条 `GitRepository` 注册记录，`repositoryId` 语义化命名（`dw-metadata` / `dw-pipeline` / `dw-lineage` / `dw-classification` / `ontology-model` / `ontology-function` / `kb-asset-tree` / `cognitive-model` / `agent-collab` / `scenario-def`）。`localPath` 一律由服务端从注册表解析，**任何接口不得接收客户端传入的 `localPath`**（避免路径穿越，客户端只传 `repositoryId`）。仓库根路径单一事实源 = sys_config `ecos_git_repo_root`（`general` 组），禁止第二套缺省根路径并存。
6. 凭据：git username/password/token 走 security-engine 加密存储 + runtime-access 注入；禁止请求体携带明文凭据、禁止写入 `sys_config` 明文列、禁止打印到日志。
7. 六类资产接入要求：① 数据工作台（元数据 / pipeline / 血缘 / 分级分类规则）② 本体工作台（本体模型含自定义函数）③ 知识库（知识资产树）④ 认知模型 ⑤ Agent 协同模型 ⑥ 场景定义，一律按本节 1~6 接入 Git 归档。尚未接入的资产，版本历史接口必须显式返回 `not_available` / 空态，**禁止返回伪成功**（回 `status: committed` 却无 git commitId = 验收失败）。
8. 异步与事件：序列化 + commit 可能耗时，必须走 `runtime-task`（回真实 `taskId`）；完成后经 `runtime-event` 发资产发布事件，Topic 只用 `common-api` 的 `KafkaTopics` 常量；订阅方（KG 同步、场景装配）自行消费，禁止引擎间同步互调阻塞发布链路。
9. 版本索引表：`{asset}_version` 表只允许存索引字段（`asset_id` / `version_no` / `git_commit_id` / `git_tag` / 发布人 / 发布时间 / 状态），不得存全量内容快照。
   - 存量处置（2026-09-28 用户裁决：不受「Schema 只加不删」约束，直接 DROP）：`ecos_ontology_version` / `ecos_object_version` / `ecos_agent_version` / `sys_rule_version` 自本规范起**停止写入**，前端不再将其作为历史版本数据源，新发布链路一律走 git；4 张表按本节 1~8 改造完成后**直接 DROP**（架构铁律 §3.1 v1.9 已开 DROP 例外）。
