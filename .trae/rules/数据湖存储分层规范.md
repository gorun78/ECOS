## 〇、数据域二分总则（🔴 最高优先，2026-09-28 v2.0）

ECOS 存储对象先判**域**，再判**层**：

| 域 | 定义 | 归属规范 | 载体 |
|:--|:--|:--|:--|
| **控制域**（平台运行/控制数据） | 平台自身运行所需：元数据、IAM、管道 DAG 定义、调度、审计、本体/KB/Agent/认知**定义态** | 《数据库访问规范》v1.1（IR/DR/EN/ST/MC） | PG：五引擎 schema（`ecos_data`/`ecos_ontology`/`ecos_knowledge`/`ecos_ai`/`ecos_cognitive`）+ 主控制 schema（现 `public`，目标 `ecos_control`） |
| **业务域**（外部接入数据及加工产物） | 外部源系统数据 + 下述五层对象 | **本规范** | MinIO / PG 业务 schema（`ecos_dw`）/ Neo4j / 向量库 / Doris∨ClickHouse |

1. **五层模型只描述业务域**。控制数据禁止登记进 `td_data_resource`（`layer` 字段仅业务对象），禁止落 MinIO/OLAP/向量载体。
2. 业务数据禁止写入控制域 schema（DB 规范 ST08）；控制数据禁止混入 `ecos_dw`（知识层定义态例外条款见 §一注）。
3. **跨域引用只存定位符**（对象 key、`schema.table`、datasourceId、图谱节点 ID），禁止复制实体数据或跨域直查（铁律 §3.3）。
> 注：知识层的**定义态元数据**（库/目录/文章结构等 `ecos_knowledge` 表）属控制域，由 DB 规范管辖；其**内容形态**（图谱三元组、chunk、向量）属业务域，由本规范管辖。

## 一、五层模型（业务域）

| 枚举（`DataLayer`） | 中文别名 | 定义 | 物理载体 | 生产者 | 消费者 |
|:--|:--|:--|:--|:--|:--|
| `SOURCE` | 源系统 | 外部业务系统原始库 | 外部 PG/MySQL/Oracle/ClickHouse… | — | 采集型管道 |
| `RAW` | **近源层** | 原样落湖、不做业务加工 | **MinIO 数据湖** | 采集型管道（`SINK_MINIO`） | 数据管道、数据质量 |
| `CURATED` | **DW 层** | 清洗/转换/关联后的主题明细 | DW 库表（PG `ecos_dw` / Doris∨ClickHouse） | 数据管道、数据质量 | 本体、知识、管道 |
| `SEMANTIC` | 语义层 / **知识层（双形态）** | 本体/实体/关系（图谱形态）+ 非结构化 chunk 向量（向量形态） | Neo4j 或 PG 表（图谱）；pgvector/专用引擎（向量）；载体分档见 §七A | 本体引擎 + 抽取管道（I→K）；kb ingest（非结构化） | 知识检索 RAG、认知、场景 |
| `APPLICATION` | 应用层 | 面向场景的聚合宽表 / 指标 | DW 库表（PG / Doris∨ClickHouse） | 聚合管道 | 场景工作台 |

**分层铁律**：`DataLayer` 枚举为 Java 侧唯一权威定义（`data-engine-api` 的 `com.chinacreator.gzcm.engine.data.model.DataLayer`），
其他工作台**不得新增层名**（如 `ODS`/`DWD`/`DWS` 一律不使用）。

**知识层双形态（v2.0）**：
| 形态 | 数据 | 写入责任 | 约束 |
|:--|:--|:--|:--|
| 语义图谱 | 结构数据经知识抽取（I→K）的实体/关系 | 抽取管道 / `POST :18086/api/v1/kb/graph/sync` | 图谱与向量**分库分承载**，禁止混存一张表 |
| 向量库 | 非结构化解析 chunk 的 embedding | kb-engine ingest / embedding 管道（模型调用经 `llm-gateway`） | 基线载体 = pgvector `vector` 列（dev 实测已装 0.6.2）；仅在探测到扩展缺失时按 MC03 降级存 TEXT/JSON 并**显式标记**（现存降级点＝DQ MD5 伪向量与 cognitive 关键词回退，见 §七） |

**五行对齐**：`CURATED→SEMANTIC` 即 **ge 格物（D→I）**；`SEMANTIC→K` 即 **zhi 致知（I→K）**。

## 二、近源层（RAW）两个 zone

近源层内部必须区分结构化与非结构化——两者格式要求、分区策略、消费方式、生命周期完全正交。

| 维度 | `STRUCTURED`（结构化近源区） | `UNSTRUCTURED`（非结构化近源区） |
|:--|:--|:--|
| 内容 | 表数据快照 | 原始文档（PDF / Word / Excel / 图片…） |
| 格式要求 | 需 schema / 列序稳定，可按列裁剪 | 二进制原样，保留原文件名 |
| 分区策略 | `dt=YYYY-MM-DD` 日期分区 | 按 `docId` 寻址，无日期分区 |
| 消费方 | 数据管道（SQL 可读） | 解析器 → 抽取文本 |
| 生命周期 | 按 `dw.lake.retention_days`（默认 90 天）滚动清理 | 长期保留（原文不可再生） |

**物理隔离方式**：同一 bucket 内**前缀分区**，不新增 bucket、不新增 Docker 容器。

## 三、MinIO 对象 key 规范

```
结构化：raw/structured/{source}/{table}/dt=YYYY-MM-DD/{table}_{yyyyMMddHHmmss}.csv
非结构化：raw/unstructured/{source}/{docId}/{originalFileName}
```

- `{source}`：上游数据源标识（采集型管道取 `datasourceId`；无 SOURCE_JDBC 的管道取 `default`）
- `dt=` 分区段：字段名固定 `dt`（与 `dw.lake.partition_by` 默认值一致）
- 管道节点配置显式指定 `objectName` 时**以其为准**（既有行为保留）
- **旧前缀 `datalake/{datasourceId}/{table}_{ts}.csv` 保留可读，不再新写**

**新增对象必须走 `raw/{zone}/...` 前缀**——禁止新增 `lake/`、`ods/`、`datalake/` 等其他前缀。

## 四、各工作台读写边界

| 工作台 / 引擎 | 近源层（MinIO RAW） | DW 层（CURATED） | 语义层（SEMANTIC） |
|:--|:--|:--|:--|
| 数据工作台（data-engine） | **读写** | 读写 | — |
| 本体工作台（ontology-engine） | **禁止直读** | **只读** | 读写 |
| 知识工作台（kb-engine） | **禁止直读** | **只读** | 只读 |
| 认知引擎（cognitive-engine） | 禁止 | 只读 | 只读 |
| 场景工作台（workspace） | 禁止 | 通过服务层 REST 读 | 通过服务层 REST 读 |
| **平台自身（sysman/security/runtime/service，v2.0）** | **禁止**（只准存定位符） | **禁止直读**（经数据/知识引擎 REST） | **禁止直读**（经 kb-engine REST） |

**铁律**：本体与知识**从 DW 层取数**，不得绕过 DW 层直读 MinIO 近源层或外部源系统。
非结构化链路的「文档元数据 + 抽取文本」需先落 DW 层表，知识引擎再从此表取数（原文留在 `raw/unstructured/`）。
**平台自身（控制域）只碰自家 PG schema**：调度、审计、监控等只记录业务对象的**定位符与状态**，不得直查/复制五层数据（§〇.3）。

## 五、`td_data_resource` 分层字段口径

| 字段 | 取值 | 说明 |
|:--|:--|:--|
| `layer` | `SOURCE` / `RAW` / `CURATED` / `SEMANTIC` / `APPLICATION` | DB 默认 `RAW`（见 `V54__ecos_data_layer.sql`） |
| `zone` | `STRUCTURED` / `UNSTRUCTURED` / `NULL` | 近源区标识（见 `V133__data_lake_zone.sql`） |
| `resource_type` | `TABLE` / `VIEW` / `API` / `FILE` / `LAKE_OBJECT` | `LAKE_OBJECT` = 数据湖对象（不参与 PG 元数据采集，需显式登记） |
| `source_path` | 库表用 `schema.table`；湖对象用完整对象 key | 分层标记的定位键 |

**合法性矩阵（强制）**

| layer | zone 允许值 |
|:--|:--|
| `RAW` | `STRUCTURED` / `UNSTRUCTURED` |
| 其他层 | `NULL` |

## 六、写入与标记责任

| 动作 | 责任方 | 行为 |
|:--|:--|:--|
| 外部表 → 近源层 | 采集型管道（`SOURCE_JDBC → SINK_MINIO`） | 上传后登记 `td_data_resource`（`layer=RAW`、`zone=STRUCTURED`、`resource_type=LAKE_OBJECT`） |
| 非结构化原文 → 近源层非结构化区 | 知识工作台上传登记（经数据工作台登记端点） | 原文落 `raw/unstructured/{source}/{docId}/{fileName}`，登记 `td_data_resource`（`layer=RAW`、`zone=UNSTRUCTURED`、`resource_type=LAKE_OBJECT`） |
| 文档解析文本 → DW 层表 | 数据工作台解析管道（`TRANSFORM_DOC_PARSE`） | `doc` / `doc_chunk` 落 DW 层（`ecos_dw`），写入后标记 `layer=CURATED`（`zone` 保持 NULL） |
| 近源层 / DW 层 → DW 层表 | 数据管道（`SINK` / `OUTPUT_OBJECT`） | 写入后标记目标表 `layer=CURATED`（`zone` 保持 NULL） |
| DW 层 → 语义层 | 本体引擎 | 本体实体/关系落本体存储，`layer=SEMANTIC` |
| 语义层 → 知识 | 知识引擎 | 经 `POST :18086/api/v1/kb/graph/sync` 同步 |
| 结构数据 → 知识·语义图谱（v2.0） | kb-engine（I→K 抽取 / graph sync） | 图谱形态写 Neo4j（enterprise/ultimate）或 PG 承载表（standard），定义态元数据留 `ecos_knowledge`（控制域） |
| 非结构化 chunk → 知识·向量库（v2.0） | kb-engine ingest / embedding 管道 | 模型调用一律经 `llm-gateway`（引擎禁直连）；pgvector 未启用档位按 DB 规范 MC03 降级存并显式标记 `_json`；载体分档见 §七A |
| DW/应用层 → OLAP 物化（Doris∨ClickHouse，v2.0） | 聚合管道 / 物化任务 | 仅 ultimate 档；Driver 收口 `runtime-access`（IR06/MC04）；`dw.olap.engine` 部署级二选一 |

**标记容错**：分层标记失败**不得使管道执行失败**，仅记录 `warn` 日志（标记为尽力而为的元数据动作）。

## 七A、版本×分层存储矩阵（🔴 分档承载唯一口径，2026-09-28 v2.0）

产品三档（Maven profile：standard/enterprise/ultimate）对外部数据存储能力逐级叠加；**控制域三档同构**（恒为 PG，五引擎 schema + 主控制 schema，见《数据库访问规范》v1.1 §二附）。

| 业务域层 | standard | enterprise | ultimate |
|:--|:--|:--|:--|
| 近源 RAW | MinIO（三档同构基线） | MinIO | MinIO |
| DW CURATED（明细） | PG `ecos_dw` | PG `ecos_dw` | **Doris ∨ ClickHouse** 物化（单表 > 100 万行）+ PG 保留加工链路 |
| 知识·语义图谱 | PG 关系表承载（KG 表） | Neo4j | Neo4j |
| 知识·向量 | pgvector（同库扩展，零新容器，基线首选）；未启用时 MC03 降级存并标记 | pgvector ∨ 专用向量引擎（ADR 选型定） | 同 enterprise，可加大容量引擎 |
| 应用 APPLICATION（聚合/指标） | PG `ecos_dw` | PG `ecos_dw` | **Doris ∨ ClickHouse** |

**Doris ∨ ClickHouse 平替规则**：
1. 同一部署**二选一**（`dw.olap.engine=doris|clickhouse`），禁止双 OLAP 并存造成同层双写；
2. 选择即部署配置，代码经 `@Profile` / 配置守卫（DB 规范 ST02/MC04）；
3. 访问统一收口 `runtime-access`（IR06）：数据源侧 `ClickHouseAdapter`（`StorageType.CLICKHOUSE`）已具备，**内部 DW 物化侧 ClickHouse sink 待补**（工程清单 #12）；
4. 二者均为多库兼容目标（MySQL/Oracle/MSSQL/达梦/金仓）之外的**受控例外**，只准承载业务域 DW/应用层，控制域禁入（MC04）。

**向量载体档位说明（2026-09-28 实查更正）**：dev 库 `sys_man` 扩展列表实测已含 **pgvector 0.6.2**（`pg_extension` 查得，与 pg_trgm/pgcrypto 并存），**未新增容器**，故"是否启用 pgvector"不再是待评估项；剩余动作是把该事实与三档落点写成 ADR（工程清单 #10）。已就绪未启用数据（`ecos_knowledge.knowledge_embedding` 0 行），向量形态的实测验收随 #11 收。
