## 一、五层模型

| 枚举（`DataLayer`） | 中文别名 | 定义 | 物理载体 | 生产者 | 消费者 |
|:--|:--|:--|:--|:--|:--|
| `SOURCE` | 源系统 | 外部业务系统原始库 | 外部 PG/MySQL/Oracle/ClickHouse… | — | 采集型管道 |
| `RAW` | **近源层** | 原样落湖、不做业务加工 | **MinIO 数据湖** | 采集型管道（`SINK_MINIO`） | 数据管道、数据质量 |
| `CURATED` | **DW 层** | 清洗/转换/关联后的主题明细 | DW 库表（PG / Doris） | 数据管道、数据质量 | 本体、知识、管道 |
| `SEMANTIC` | 语义层 | 本体 / 实体 / 关系 | 本体引擎存储 | 本体引擎（ge 格物 D→I） | 知识引擎（zhi 致知 I→K） |
| `APPLICATION` | 应用层 | 面向场景的聚合宽表 / 指标 | DW 库表 | 聚合管道 | 场景工作台 |

**分层铁律**：`DataLayer` 枚举为 Java 侧唯一权威定义（`data-engine-api` 的 `com.chinacreator.gzcm.engine.data.model.DataLayer`），
其他工作台**不得新增层名**（如 `ODS`/`DWD`/`DWS` 一律不使用）。

**五行对齐**：`CURATED→SEMANTIC` 即 **ge 格物（D→I）**；`SEMANTIC→K` 即 **zhi 致知（I→K）**。

## 二、近源层（RAW）两个 zone

近源层内部必须区分结构化与非结构化——两者格式要求、分区策略、消费方式、生命周期完全正交。

| 维度 | `STRUCTURED`（结构化近源区） | `UNSTRUCTURED`（非结构化近源区） |
|:--|:--|:--|
| 内容 | 表数据快照 | 原始文档（PDF / Word / Excel / 图片…） |
| 格式要求 | 需 schema / 列序稳定，可按列裁剪 | 二进制原样，保留原文件名 |
| 分区策略 | `dt=YYYY-MM-DD` 日期分区 | 按 `docId` 寻址，无日期分区 |
| 消费方 | 数据管道（SQL 可读） | 解析器 → 抽取文本 |
| 生命周期 | 按 `dw.lake.retention_days`（默认 90 天）滚动清理 | 长期保留（原文不可再生） |

**物理隔离方式**：同一 bucket 内**前缀分区**，不新增 bucket、不新增 Docker 容器。

## 三、MinIO 对象 key 规范

```
结构化：raw/structured/{source}/{table}/dt=YYYY-MM-DD/{table}_{yyyyMMddHHmmss}.csv
非结构化：raw/unstructured/{source}/{docId}/{originalFileName}
```

- `{source}`：上游数据源标识（采集型管道取 `datasourceId`；无 SOURCE_JDBC 的管道取 `default`）
- `dt=` 分区段：字段名固定 `dt`（与 `dw.lake.partition_by` 默认值一致）
- 管道节点配置显式指定 `objectName` 时**以其为准**（既有行为保留）
- **旧前缀 `datalake/{datasourceId}/{table}_{ts}.csv` 保留可读，不再新写**

**新增对象必须走 `raw/{zone}/...` 前缀**——禁止新增 `lake/`、`ods/`、`datalake/` 等其他前缀。

## 四、各工作台读写边界

| 工作台 / 引擎 | 近源层（MinIO RAW） | DW 层（CURATED） | 语义层（SEMANTIC） |
|:--|:--|:--|:--|
| 数据工作台（data-engine） | **读写** | 读写 | — |
| 本体工作台（ontology-engine） | **禁止直读** | **只读** | 读写 |
| 知识工作台（kb-engine） | **禁止直读** | **只读** | 只读 |
| 认知引擎（cognitive-engine） | 禁止 | 只读 | 只读 |
| 场景工作台（workspace） | 禁止 | 通过服务层 REST 读 | 通过服务层 REST 读 |

**铁律**：本体与知识**从 DW 层取数**，不得绕过 DW 层直读 MinIO 近源层或外部源系统。
非结构化链路的「文档元数据 + 抽取文本」需先落 DW 层表，知识引擎再从此表取数（原文留在 `raw/unstructured/`）。

## 五、`td_data_resource` 分层字段口径

| 字段 | 取值 | 说明 |
|:--|:--|:--|
| `layer` | `SOURCE` / `RAW` / `CURATED` / `SEMANTIC` / `APPLICATION` | DB 默认 `RAW`（见 `V54__ecos_data_layer.sql`） |
| `zone` | `STRUCTURED` / `UNSTRUCTURED` / `NULL` | 近源区标识（见 `V133__data_lake_zone.sql`） |
| `resource_type` | `TABLE` / `VIEW` / `API` / `FILE` / `LAKE_OBJECT` | `LAKE_OBJECT` = 数据湖对象（不参与 PG 元数据采集，需显式登记） |
| `source_path` | 库表用 `schema.table`；湖对象用完整对象 key | 分层标记的定位键 |

**合法性矩阵（强制）**

| layer | zone 允许值 |
|:--|:--|
| `RAW` | `STRUCTURED` / `UNSTRUCTURED` |
| 其他层 | `NULL` |

## 六、写入与标记责任

| 动作 | 责任方 | 行为 |
|:--|:--|:--|
| 外部表 → 近源层 | 采集型管道（`SOURCE_JDBC → SINK_MINIO`） | 上传后登记 `td_data_resource`（`layer=RAW`、`zone=STRUCTURED`、`resource_type=LAKE_OBJECT`） |
| 非结构化原文 → 近源层非结构化区 | 知识工作台上传登记（经数据工作台登记端点） | 原文落 `raw/unstructured/{source}/{docId}/{fileName}`，登记 `td_data_resource`（`layer=RAW`、`zone=UNSTRUCTURED`、`resource_type=LAKE_OBJECT`） |
| 文档解析文本 → DW 层表 | 数据工作台解析管道（`TRANSFORM_DOC_PARSE`） | `doc` / `doc_chunk` 落 DW 层（`ecos_dw`），写入后标记 `layer=CURATED`（`zone` 保持 NULL） |
| 近源层 / DW 层 → DW 层表 | 数据管道（`SINK` / `OUTPUT_OBJECT`） | 写入后标记目标表 `layer=CURATED`（`zone` 保持 NULL） |
| DW 层 → 语义层 | 本体引擎 | 本体实体/关系落本体存储，`layer=SEMANTIC` |
| 语义层 → 知识 | 知识引擎 | 经 `POST :18086/api/v1/kb/graph/sync` 同步 |

**标记容错**：分层标记失败**不得使管道执行失败**，仅记录 `warn` 日志（标记为尽力而为的元数据动作）。
