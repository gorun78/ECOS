# 常见陷阱与优化策略

## 常见陷阱

1. **模块无 PRD 来源**：创建了无法指向 PRD 功能的任务。每个模块必须能说出它覆盖了产品的什么功能
2. **跳过第一门**：模块划分还没确认就继续写详细设计
3. **技术选型跟风**：不要因为"流行"而选某个技术，要看团队能力和业务匹配度
4. **忽视非功能需求**：性能、安全、可维护性要在架构阶段考虑
5. **模块边界模糊**：如果一个模块的职责无法用一句话描述，说明边界不清
6. **薄模块格式缩水**：即使模块无数据库表（如工作空间、Git 管理、看板等），7 节结构必须保留。库表设计节标注数据源类型而非直接删除，字典设计节写"无业务字典"。禁止跳过章节——否则 Wave D4 汇总时格式不一致
7. **薄模块可合并读取**：当连续多个模块为薄模块（0-1 个 Controller、无 DB 表、无 Entity），可在 D3 开始时一次性读取所有薄模块的 Controller 源码，然后逐个输出文档。厚模块（有 DB 表 + 多个 Service）仍严格逐个读取→输出
8. **旧工程反向分析优先**：代码是权威来源，PRD 和已有架构文档做参考。当代码与文档冲突时以代码为准，在追踪表中标注差异
9. **D2→D3 不中断**：D2 输出 00-模块划分计划后直接进入 D3，不要在此时问用户"要不要继续"

## 薄模块识别规则

当模块满足以下所有条件时，视为薄模块：
- Controller 只有 1 个
- 无 JPA Entity 和数据表
- 无独立的 Service 实现（或仅 1 个轻量 Service）
- 无前端独立页面（嵌入 workspace 标签页）

薄模块示例：工作空间（仅有文件系统操作）、Git 管理（JGit 代理）、看板与功能（外部 DB 代理）

## 厚模块 vs 薄模块处理对比

| 场景 | 厚模块 | 薄模块 |
|------|--------|--------|
| 读取策略 | 逐个读取本模块源码 | 可批量读取所有薄模块 Controller |
| 库表设计节 | 完整字段、索引、ER 图 | 标注数据源类型 |
| 流程设计节 | Mermaid flowchart 含事务 | Mermaid flowchart 或时序图 |
| 状态设计节 | stateDiagram-v2 + 转换表 | stateDiagram 或省略为状态表 |
| 字典设计节 | 完整字典项 | "无业务字典" |

## AI-Native Factory 案例（2026-07-30）

8 个模块中：
- 厚模块（4 个）：D001 认证与用户管理、D002 角色与菜单管理、D003 项目管理、D004 角色模板
- 薄模块（4 个）：D005 工作空间、D006 AI 对话（有 chat_history 表但 1 个 Entity）、D007 Git 管理、D008 看板与功能

优化执行：D001→D002→D003 逐个读取+输出 → D004-D008 一次性读全部 Controller → 并行输出文档
