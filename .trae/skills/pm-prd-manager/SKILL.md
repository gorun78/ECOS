# PM PRD Manager Skill (v2 — 3 阶段门禁版)

## 核心原则

与 vue3-frontend-builder 一脉相承，PRD 产出的每个阶段有明确停止条件，用户不确认不跨阶段。三个硬性确认门：

| 门禁 | 阶段 | 停止条件 |
|------|------|---------|
| **第一门** | 需求分析完成 | 用户确认"需求理解正确、范围和优先级已定" |
| **第二门** | PRD 初稿完成 | 用户确认"功能详述、验收标准、非功能需求正确" |
| **第三门** | PRD 评审通过 | 技术负责人/产品负责人批准，进入 Arch |

**硬门槛**：未经每道门禁确认，不得进入下一阶段。

## 触发条件

- 用户说"写 PRD"、"出需求文档"、"帮我写需求"、"需求评审"
- PM 分发任务时指定 `role: pm`，工作流为 L3（完整 PRD）
- 需求模糊、不完整，需要结构化时

## 输入

- **必需**：业务需求描述、项目目标、验收标准
- **可选**：竞品分析、用户调研、历史 PRD、技术约束

## 输出制品

- **PRD**：产品需求文档（artifact_type: PRD）
- **PRD_APPROVAL_RECORD**：各阶段批准记录（artifact_type: APPROVAL_RECORD）

## 执行步骤

### Step 1: 需求采集与澄清 → 第一门禁

#### 1.1 整理原始需求

将用户描述的结构化为：

```
背景：{业务背景}
目标：{要解决什么问题}
期望：{用户期望的行为}
```

#### 1.2 追问缺失信息

- 目标用户是谁？
- 核心场景是什么？
- 验收标准是什么？
- 优先级是什么？

#### 1.3 生成需求分析摘要

```markdown
# 需求分析摘要 — {产品名称}

## 背景与目标

**背景**：{描述业务背景，为什么要做这个功能}

**业务目标**（需量化）：
- {量化的业务指标，如 DAU +10%}

**用户目标**：
- {用户能完成什么任务}

## 需求范围

**包含**：
- {明确范围}

**不包含**（明确排除）：
- {明确排除范围}

## 初步功能清单

| ID | 功能名称 | 优先级 | 说明 |
|----|---------|--------|------|
| F1 | {功能名} | P0/P1/P2 | {一句话说明} |
| F2 | ... | ... | ... |

## 需求缺口（需用户补充）

- {有哪些信息目前缺失，需要用户提供}

## 目标用户与场景

| 用户角色 | 描述 | 主要场景 |
|---------|------|---------|
| {角色名} | {描述} | {场景} |

---

**【第一门禁 — 需求理解确认】**

请确认以下内容：
1. 需求背景和目标描述是否准确？
2. 功能范围（包含/不包含）是否正确？
3. 功能优先级划分（F1/F2/F3）是否合理？
4. 目标用户和主要场景是否完整？
5. 需求缺口是否已补充？

**确认后输出**：需求分析摘要已冻结，进入 PRD 初稿编写。
**未确认**：请补充或修正上述问题，直到确认后再继续。
```

#### 第一门禁规则

- 必须用户逐条确认才能解锁下一阶段
- 有任何一条未确认，需修订后重新确认
- 确认结果写入 `PRD_APPROVAL_RECORD`，标注 `Gate-1: CONFIRMED`

#### 2.3 第二门禁确认

```markdown
---

**【第二门禁 — PRD 初稿确认】**

请确认以下内容：
1. 功能详述是否准确描述了第一门确定的需求？
2. 每个功能的验收标准是否可测试、可验证？
3. 非功能需求（性能/安全/兼容性）是否符合预期？
4. 风险分析和缓解措施是否完整？
5. 功能优先级划分是否正确？

**确认后输出**：PRD 初稿已冻结，进入正式评审流程。
**未确认**：请指出需修改的具体内容，修订后重新确认。
```

#### 第二门禁规则

- 必须用户确认"功能详述 + 验收标准 + 非功能需求"才能解锁
- 确认结果写入 `PRD_APPROVAL_RECORD`，标注 `Gate-2: CONFIRMED`

---

### Step 3: PRD 评审与定稿 → 第三门禁

#### 3.1 组织评审会

邀请：研发（Arch/Fullstack）、测试（QA）、设计、產品負責人

评审议程：
```
1. PRD 背景和目标（5min）
2. 功能详述逐条过（20min）
3. 验收标准可测试性检查（10min）
4. 非功能需求确认（5min）
5. 风险和依赖讨论（5min）
6. 结论：批准/修改后批准/拒绝
```

#### 3.2 评审问题处理

如果评审中发现问题，在 PRD 中记录修改：

```markdown
## 评审修改记录

| 日期 | 修改内容 | 修改人 |
|------|---------|--------|
| {date} | {修改内容} | {修改人} |
```

#### 3.3 第三门禁 — 正式批准

```markdown
**【第三门禁 — PRD 正式批准】**

评审结论：
- [ ] 产品负责人批准
- [ ] 技术负责人/架构师批准
- [ ] QA 代表确认测试可行性

批准结果：
- APPROVED → PRD 状态改为 `APPROVED`，生成 version hash，进入 Arch 阶段
- REJECTED → 打回修改，修订后重新评审
- CONDITIONAL_APPROVED → 附带条件批准，列出条件清单

**批准记录格式**（写入 `PRD_APPROVAL_RECORD`）：
```json
{
  "artifact": "PRD",
  "name": "{产品名称}",
  "version": "v{version}",
  "hash": "{内容哈希}",
  "gates": {
    "Gate-1": { "name": "需求理解确认", "status": "CONFIRMED", "timestamp": "...", "confirmed_by": "用户" },
    "Gate-2": { "name": "PRD初稿确认", "status": "CONFIRMED", "timestamp": "...", "confirmed_by": "用户" },
    "Gate-3": { "name": "正式批准", "status": "APPROVED", "timestamp": "...", "confirmed_by": "产品负责人" }
  },
  "deliverable_allowed": true,
  "conditions": []
}
```
```

#### 第三门禁规则

- 必须产品负责人 + 技术负责人双方 APPROVED 才能解锁
- APPROVED 后 `deliverable_allowed = true`，PM 可触发 Arch 分发
- REJECTED 后打回修改，从第二门重新走

---

### Step 4: 评审后定稿

评审通过后，更新 PRD 状态：

```markdown
> **版本**: v1.0.0
> **状态**: APPROVED
> **Hash**: {内容哈希}
> **批准人**: {产品负责人}、{技术负责人}
> **批准时间**: {timestamp}
```

保存路径：
- `docs/prd/{project}-prd-v{version}.md`（最终版）
- `docs/prd/{project}-prd-v{version}-approval-record.json`（批准记录）

## 需求追溯机制

每个功能点必须可追溯到需求来源：

```markdown
### 功能 → 需求追溯表

| 功能ID | 功能名称 | 优先级 | 需求来源 | 验收标准数 |
|--------|---------|--------|---------|-----------|
| F1 | 商品搜索 | P0 | R-001 用户想快速找到商品 | 3 条 |
| F2 | 购物车 | P0 | R-002 用户想批量结算 | 4 条 |
```

追溯链路：
```
用户原始需求
    ↓
需求分析摘要（第一门）
    ↓
PRD 功能详述（第二门）
    ↓
ARCH_SPEC / SOURCE_PATCH（追溯链终点）
```

## 验证步骤

1. [ ] 第一门确认前，需求分析摘要包含：背景/目标/范围/功能清单/用户/场景
2. [ ] 第一门用户逐条确认后才能进入第二门
3. [ ] PRD 每个功能有用户故事、功能详情、业务流程、验收标准
4. [ ] 第二门用户确认后才能进入评审
5. [ ] PRD 功能可追溯到需求分析条目（需求来源列）
6. [ ] 第三门产品负责人+技术负责人双方 APPROVED
7. [ ] 批准记录写入 `PRD_APPROVAL_RECORD`，含三门状态和 deliverable_allowed
8. [ ] PRD 状态只有 APPROVED 才能作为 Arch 的输入

## 常见陷阱

1. **跳过第一门**：需求还没澄清就写 PRD，功能范围不准确
2. **验收标准模糊**："体验流畅"不可测试，应为"页面加载 < 2s"
3. **跳过用户确认**：觉得用户会直接认可，直接进入下一阶段
4. **追溯断裂**：PRD 功能没有指向需求来源，无法验证完整性
5. **第三门放行过松**：产品或技术任一方有异议就应打回，不是走过场
