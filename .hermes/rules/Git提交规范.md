# Git 提交核心规范

## 一、 核心红线与分支管理

| 规范项 | 核心要求 | 详细说明 / 示例 |
| :--- | :--- | :--- |
| **单一提交** | 一次提交只做一件事 | 单功能/单Bug，严禁多业务混杂提交。 |
| **干净安全** | 提交前强制过滤 | 严禁提交调试代码、敏感密钥、本地配置及打包产物。 |
| **分支隔离** | 严格区分分支用途 | `main/master`：严禁直接提交，仅通过 MR/PR 合入。<br>`dev`：开发主干，所有新功能/修复必须基于此拉取。<br>`test`：测试专用，仅合入自测通过的代码。 |
| **命名规范** | 语义化英文命名 | 从 `dev` 拉取，格式：`类型/模块-描述`。<br>示例：`feature/user-list`、`bugfix/login-error`。<br>严禁拼音、中文或无意义命名。 |

## 二、 Commit Message 规范

| 规范项 | 核心要求 | 详细说明 / 示例 |
| :--- | :--- | :--- |
| **标准格式** | `type(模块): 动宾结构精准描述` | 示例：`feat(用户模块): 新增用户分页查询接口`<br>严禁使用“修改代码”、“update”等模糊文案。 |
| **Type 枚举** | 严格使用以下 8 种类型 | `feat`(新功能) \| `fix`(修复) \| `refactor`(重构) \| `perf`(性能)<br>`style`(格式) \| `docs`(文档) \| `test`(测试) \| `chore`(构建/配置) |
| **拆分规则** | 无关业务必须拆分 | 多业务禁止混杂提交；功能变更与格式优化必须分两次提交。 |

## 三、 合并与推送规则

| 规范项 | 核心要求 | 详细说明 |
| :--- | :--- | :--- |
| **禁止强推** | 严禁对主干 `push -f` | 避免代码覆盖丢失，保护主干安全。 |
| **规范合并** | 走 MR/PR 流程 | 功能完成后通过 MR/PR 合入 `dev`；热修复需先在 `test` 验证。 |
| **防冲突** | 合并前同步代码 | 必须拉取远端最新代码，确保无严重冲突且代码可正常运行。 |

## 四、 提交前强制自检（Checklist）

| 检查维度 | 自检项 | 状态 |
| :--- | :--- | :--- |
| **分支检查** | 是否在合规业务分支？是否误操作主干？ | ☐ |
| **内容检查** | 是否已清除调试代码、敏感信息、冗余文件？是否属于单一变更？ | ☐ |
| **信息检查** | Type 是否准确？描述是否清晰无废话？ | ☐ |
| **状态检查** | 是否已同步最新代码？无强制推送？代码无语法报错？ | ☐ |
