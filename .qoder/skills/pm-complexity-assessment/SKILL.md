# 项目复杂度评估 Skill

## 功能说明

本 Skill 用于评估软件项目的复杂度等级（L1/L2/L3），并推荐适合的工作流模板。PM 在接收到需求后，必须首先调用此 Skill 进行复杂度评估。

## 评估维度

### 6 维度评分（每项 1-10 分）

| 维度 | 低分 (1-3) | 中等 (4-6) | 高分 (7-10) |
|------|-----------|-----------|-----------|
| 功能数量 | 1-2 个功能点 | 3-7 个功能点 | 8+ 功能点 |
| 模块数量 | 单模块 | 2-3 模块 | 4+ 模块 |
| 数据复杂度 | 单表 CRUD | 多表简单关联 | 多表关联 + 事务 |
| 外部依赖 | 无 / 单一 API | 2-3 个外部服务 | 多服务集成 |
| 并发/性能要求 | 单用户 | 中等并发 | 高并发 + 缓存 |
| 用户界面 | CLI / 单页 | 2-4 页面 | 多页面 + 状态管理 |

### 等级映射规则

| 总分范围 | 复杂度等级 | 推荐工作流 |
|---------|-----------|-----------|
| 6-18 | L1 极简 | 需求理解 → 直接编码 → 交付 |
| 19-36 | L2 标准 | 需求理解 → 架构轻量设计 → 前后端并行 → 交付 |
| 37-60 | L3 复杂 | PM → Arch → Backend+Frontend → QA → Reviewer → 交付 |

### 边界情况处理

| 情况 | 处理规则 |
|------|----------|
| 总分恰好等于阈值 | 向下取整（如 18 分归为 L1，36 分归为 L2） |
| 用户不同意评估结果 | 允许用户手动选择工作流模板 |
| 需求不完整 | 先追问用户补充信息，再进行评估 |
| 跨等级特征混合 | 取最高等级（如功能数量低但并发要求高，按高等级处理） |

## 输出格式

### 首层输出（默认展示）

```
【复杂度评估结果】
- 评估等级: L2 标准
- 推荐工作流: 需求理解 → 架构轻量设计 → 前后端并行 → 交付

确认开始吗？(或说「跳过评估直接干」)
```

### 次层输出（用户追问时展示）

```
【复杂度评估详情】
- 功能数量: 4/10 → 中等（CRUD + 用户管理）
- 模块数量: 2/10 → 低（后端 + 前端）
- 数据复杂度: 3/10 → 低（单表为主，简单关联）
- 外部依赖: 2/10 → 低（无外部API）
- 并发要求: 1/10 → 低（单用户）
- 用户界面: 4/10 → 中等（多页面管理后台）
总分: 16/60 → L2 标准模式

【裁剪理由】
- 跳过完整PRD编写（仅生成需求摘要）
- 保留架构轻量设计（快速出API规范）
- 跳过Reviewer正式审查（仅快速检查）
```

### 输出制品

- **COMPLEXITY_ASSESSMENT**：复杂度评估结果（artifact_type: COMPLEXITY_ASSESSMENT）
- **WORKFLOW_SUGGESTION**：建议工作流模板（artifact_type: WORKFLOW_SUGGESTION）

## 工作流模板（跳过清单模式）

### L1 极简工作流

```
适用: 脚本、CLI小工具、单页面工具、数据迁移
耗时: 5-30 分钟
```

| 阶段 | 状态 | 说明 |
|------|------|------|
| PM 需求分析 | ✅ 保留 | 快速理解需求 |
| PM 写完整 PRD | ❌ 跳过 | 仅生成需求摘要 |
| Arch 架构设计 | ❌ 跳过 | 不输出架构图和API规范 |
| Backend 开发 | ✅ 保留 | 直接编码实现 |
| Frontend 开发 | ✅ 保留 | 直接编码实现 |
| QA 全量测试 | ❌ 跳过 | 不执行完整测试套件 |
| Reviewer 审查 | ✅ 保留 | 必须执行代码审查，报告必须产出，禁止跳过 |
| 交付 | ✅ 保留 | 交付可运行产物 |

### L2 标准工作流

```
适用: CRUD应用、管理后台、REST API服务
耗时: 1-4 小时
```

| 阶段 | 状态 | 说明 |
|------|------|------|
| PM 需求分析 | ✅ 保留 | 完整需求分析 |
| PM 写完整 PRD | ❌ 跳过 | 仅生成需求摘要 |
| Arch 架构轻量设计 | ✅ 保留 | 输出API规范和数据模型 |
| Backend 开发 | ✅ 保留 | 完整后端实现 |
| Frontend 开发 | ✅ 保留 | 完整前端实现 |
| QA 测试 | ⚠️ 简化 | 执行核心功能测试 |
| Reviewer 审查 | ✅ 保留 | 必须执行代码审查，报告必须产出，禁止跳过 |
| 交付 | ✅ 保留 | 交付可运行产物 |

### L3 复杂工作流

```
适用: 多模块系统、高并发服务、支付/安全敏感系统
耗时: 4小时 - 数天
```

| 阶段 | 状态 | 说明 |
|------|------|------|
| PM 需求分析 | ✅ 保留 | 完整需求分析 |
| PM 写完整 PRD | ✅ 保留 | 完整PRD文档 |
| Arch 架构设计 | ✅ 保留 | 完整架构设计、API规范、DB Schema |
| Backend 开发 | ✅ 保留 | 完整后端实现 |
| Frontend 开发 | ✅ 保留 | 完整前端实现 |
| QA 测试 | ✅ 保留 | 全量测试套件 + 性能测试 |
| Reviewer 审查 | ✅ 保留 | 正式代码审查 + 可信度评分 |
| 交付 | ✅ 保留 | 完整交付流程 |

## 调用原则

1. **强制触发**：PM 接收到需求后，第一步必须调用此 Skill 进行复杂度评估
2. **逐步披露**：默认只输出首层结果，用户追问时再展示详细信息
3. **用户确认**：评估完成后输出结果供用户确认，支持用户跳过确认直接执行
4. **禁止跳过 Reviewer**：L1/L2/L3 模式均必须触发 Reviewer 审查，报告必须产出，禁止跳过

## 全自动模式（auto_pipeline）

当 PM `config.yaml` 的 `auto_pipeline.enabled: true` 且触发词命中（零干预 / 全自动执行 / 自动编排）时，本 Skill 进入全自动模式：

| 阶段 | 标准模式 | 全自动模式 |
|------|---------|-----------|
| 首层输出 | 输出结果 + `确认开始吗？` 等待用户 | 输出结果 + `[auto_pipeline] 已自动继续` |
| 用户确认 | 必须等待用户「需要/确认」 | 跳过确认，直接进入下一步派发 |
| 评估等级 | 供用户确认，可手动覆盖 | 评估结果直接作为工作流依据 |

**全自动模式规则**：

1. 评估完成后**不输出确认提问**，直接按等级派发（L1 直接开发 / L2 自动架构→开发→审查→部署 / L3 自动 PRD→架构→开发→审查→部署）
2. 用户仍可随时插入指令干预（out-of-band），命中中断标志位时暂停自动流程
3. 部署验证与 Git 提交推送是否全自动，由 `auto_pipeline.phase` 分级控制（见 `kanban-dispatch-json-format/references/auto-pipeline-contract.md`）
