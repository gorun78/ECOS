## 三、缺陷定性与分层

### ISSUE-D — `POST /api/v1/datanet/metadata/collect-async/{id}` 任务执行失败（P1）

- **现象**: HTTP 200, body.code 缺省但 `submit=false`, `status=FAILED`
- **根因 (日志实证)**: 任务到达 `TaskManagementServiceImpl.executeTask` →
  `MetadataCollectTaskExecutor.execute` →
  `ConnectorFactory.getConnector("POSTGRESQL")` →
  `IllegalArgumentException: Unsupported connector type: POSTGRESQL`
- **职责层定位**: `runtime-access`（连接器工厂）缺少对 `POSTGRESQL` 类型的支持；
  `MetadataCollectTaskExecutor` 未做数据源类型→连接器类型的映射/降级
- **可举证**:
  - JAR 反编译 `jar tf` 确认 `gate-impl,jar` 内含 `MetadataCollectTaskExecutor.class`
  - Gateway 运行时 stderr 中 trace 调用栈（上面 1.1 段）
  - runtime-access 源码（上面 1.3 段）
- **影响面**: 所有 source_type=POSTGRESQL 的数据源无法异步采集元数据；
  已验证的 other 3 数据源（含 `ds_qa_3j_test`）全部受影响。
- **建议修正动作（PMO 下发 → BE）**:
  1. **runtime-access**: 在 `ConnectorFactory.SOURCE_TYPES` 增补
     `POSTGRESQL`、`MYSQL`、`ORACLE`、`SQLSERVER`、`DORIS` 等关系型别名，
     或提供 `mapToKnownType(String)` 归一化方法并在 `getConnector` 前调用；
     对应增加 `JdbcConnector` 实例的 `supportedType()` 多注册或别名表。
  2. **data-engine-impl**: `MetadataCollectTaskExecutor.execute` 在
     `getConnector` 前先将 `DataSourceEntity.getDatasourceType()` 归一化。
- **注意**: 禁止硬编码绕过 `getConnector`，禁止在 data-engine 复制
  `runtime-access` 的 connector 逻辑（架构铁律 #4 "基础设施 Driver 一律收敛 runtime"）。

### ISSUE-F — 数据源列表 `items[].metadataConfig` 未回显（P1）

- **现象**: `GET /api/v1/datanet/datasource` 返回 3 条，items[0]
  `metadataConfig=null, metadataStrategy=null`；
  `GET /metadata/config` 未注册（404 在日志片段中未单独体现，但 B 的盘点与 DB G4 对照
  即可证明 ignored=null）。
- **根因 (代码实证)**: `DataSourceController#list` 返回 `ApiResponse<List<DataSourceEntity>>`
  —— 返回的是 **Entity** 而不是 **DTO**。`DataSourceEntity` 的
  `metadataConfig` 字段不被 controller 序列化或 entity 返回路径未填充
  MyBatis 映射列；而 FE 用的 `api/v1/datanet/datasource` 期望
  `DataSourceDTO` 的 JSON 形状（`metadataConfig` 作为 JSONB 对象），不被满足。
- **可举证**:
  - G4 `SELECT datasource_id, metadata_config::text FROM td_datasource LIMIT 2`
    → `ds_qa_3j_test | {}` + `b6431abd… | {}`（DB 端有值，entity 读取无）
  - `DataSourceController.java` `@GetMapping` 声明 `List<DataSourceEntity>`
  - items[0] 同时 `metadataStrategy=null, countMethod=null` —— 三个策略字段
    全 null，指向 Entity 路径不读这三列（而非"DB 没值"）
- **影响面**: FE `ConnectionsTab.tsx` 无法展示当前数据源的 metadata 策略；
  用户在 UI 看到空策略，无法确认生效。
- **建议修正动作（PMO 下发 → BE）**:
  1. `DataSourceController#list` / `#getById`：将返回类型从
     `List<DataSourceEntity>` / `DataSourceEntity` 迁移为
     `List<DataSourceDTO>` / `DataSourceDTO`；
     或保持 Entity 但在 `DataSourceRepository` 的 `mapRow` 中同步写
     `metadataConfig`、`metadataStrategy`、`countMethod`（补齐实体→DTO 同形投影）。
  2. 按架构铁律"API 只增不改"，响应 JSON 形状必须保持既有键不变 ——
     因此推荐方案 2（Entity 读路径补列），保持 API 签名不变，不破坏既有 FE 连接。
