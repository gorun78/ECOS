## 缺陷 (待 PMO 下一批次)

### BUG-D1 ⚠ P1 — collect-async 返回的 "taskId" 不是引擎真实任务 ID

```
POST /collect-async/{dsId}
  → {"submitted":true, "taskId":"{\"datasourceId\":\"...\",\"elapsedMs\":142}", ...}
                                                          ^^^^^^^^
                这个是执行结果 JSON 串, 不是 ITaskManagementService 生成的 UUID

实际 ITaskManagementService.submitTask 生成的 taskId 是 UUID,
存进 td_metadata_collect_log.task_id (例: bcce027c-52d3-4af6-ae40-b6af33f64012)

后果: 前端按 API 文档拿 r.taskId 轮询 /collect-status/{r.taskId} → 404
      (我已用真实 UUID 验证 E' 可拿到 SUCCEEDED)
```

**根因分析** (推断):
- MetadataTaskService.submitCollect(sync=false) 在 taskManagementService.executeTask
  后立即 return null (line 70-72)
- 但 MetadataAsyncTrigger.submitAsync (推断) 可能就用 sync=false 路径,
  它拿到 null 就拼 result JSON 当 taskId 返回 (推断 location 在 MetadataAsyncTrigger)

**建议修正** (单文件 + 单 curl, 批次 1):
- 文件: engine/data-engine/data-engine-impl/.../metadata/MetadataAsyncTrigger.java
- 修法: submitAsync 里把 taskManagementService.submitTask(desc) 返回的 UUID
  作为 taskId 透传给响应; result JSON 放到 TaskStatus 的 result 字段,
  通过 /collect-status/{uuid} 查回 (已验证可得)
- 验证: curl collect-async → 200, 解析 r.taskId = 36-char UUID
  + sleep 2s + curl collect-status/{UUID} → {"available":true,"status":"SUCCEEDED"}
