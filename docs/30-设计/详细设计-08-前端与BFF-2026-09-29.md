### 1.2 「无入口路由根」三套口径（**本册为唯一定义处**）

上一窗曾在 6 处文档写下"19 个无入口路由根"，**该数为算错的中间值**（把 `TAB_LABEL_KEY` 当入口面且漏项）。本册以可复现口径重建，并回填更正各处：

| 口径 | 入口面定义 | 计数基数 | 无入口路由根 | 用途 |
|:--|:--|:--|:--|:--|
| **A** | 仅 `Sidebar.tsx` 12 项主导航（用户可见的唯一常驻入口；12 项全部命中内容根） | 内容路由根 **49** | **37** | 本册权威口径；用于"导航覆盖率"分母 |
| **B** | A ∪ `TAB_LABEL_KEY` 43 键（**标签注册表，非入口面** —— 键只决定"页签已打开时显示什么"，不产生入口） | 49 | **13** | "页签可呈现但无从打开"的次级集合 |
| **C** | B 且**全仓零代码引用**（硬孤岛：既无入口也无任何跳转） | 13 | **8** | **整改优先级最高** |

**基数与排除项（必须按此复现，不得自创基数）**：`<Route path=` 共 **52** 条，去重首段得 **52** 个路由根；其中通配兜底根 `/*` **1** 个、认证/守卫根 `/login`、`/no-access` **2** 个 ⇒ **内容路由根 = 49**。

> 口径 B 的 13 项 = `alerts`、`case_library`、`chatbot_studio`、`domain_designer`、`domains`、`engine-ai`、`engine-cognitive`、`engine-data`、`engine-knowledge`、`engine-ontology`、`engine-security`、`scenario-sandbox`、`tenants`。
> 口径 C 的 8 项 = `case_library`、`domain_designer`、`engine-ai`、`engine-cognitive`、`engine-data`、`engine-knowledge`、`engine-ontology`、`engine-security`（= **6 个 `engine-*`** + 案例库 + 域设计器。全仓 `engine-*` 内容根共 **7** 个，第 7 个 `engine-tasks` 有页签标签注册项故不入 B/C，但仍无 Sidebar 入口 ⇒ 属口径 A）。
> **与历史记载的关系**：PRD-08 原载「38 个路由根无入口」= 把通配兜底根 `/*` 也计入分母（50 − 12）所得，差 1；本册严格内容根 49 ⇒ **37**。上一窗曾把该数改成「19」，**错因是把 `TAB_LABEL_KEY` 当入口面且键集正则只匹配带引号的键（漏 35 个裸标识符键），属算错的中间值**。本册以口径 A=37 / B=13 / C=8 为准，并同窗回填全部引用处。
> **结论口径统一写作**：「52 条 `<Route path=` / 52 路由根 / **49 内容路由根** / **37 无 Sidebar 入口（口径 A）** / 13 无 Sidebar∪页签注册表入口（口径 B）/ **8 全仓零引用硬孤岛（口径 C）**」。凡引用该数据必须带口径字母。

### 4.1 单源路由清单 `route-manifest.ts`（W194/C176 整改）

```
config/route-manifest.ts   // 唯一事实源，被 vite.config.ts 与 server.ts 共同读取

校验（构建期，禁运行期静默）：
  ① dev:  directInDev=true 的项必须能在 vite 表中生成，否则 build 失败
  ② prod: 仅当 ECOS_LOCAL_DIRECT_SERVICE_PROXY=true 才允许 directWhenFlag=true 生效
  ③ streaming=true 的项必须落到"不缓冲分支"（§4.3），否则报错
```

### 4.2 数据流（单向）

```
引擎(service:18081~18090) → gateway(:8080 facade) → BFF(:3000) → httpClient(拦截器：注入 token / 归一 ApiResponse / traceId 记录)
   → react-query cache → 组件渲染
   ← 用户动作 → mutation POST/PUT → 同一通道下行 → 审计事件由后端经 Kafka ecos.audit 落库（前端不参与审计写入）
```

- **BFF 不做业务聚合**：`/api/audit-logs`（`server.ts:120-143`）的聚合逻辑必须迁回 gateway/security-engine；BFF 只做转发 + 鉴权透传 + 承流（W207/C189）。
- **traceId 贯通**：响应头 `X-ECOS-Trace-Id` → `httpClient` 记录 → 错误面板展示，便于与卷 00 `ApiResponse.traceId` 对齐。

### 4.3 `server.ts` 承流改造（P-4 的前端侧落点，W192/C174，M0）

```ts
// 现状 :82-:86
if (contentType.includes("application/json")) { res.status(...).json(await upstream.json()); }
else { res.status(...).send(await upstream.text()); }        // ← 全缓冲，SSE 死亡

// 目标（新增第一分支，其余保持）
if (contentType.includes("text/event-stream")) {
  res.writeHead(upstream.status, { "Content-Type": "text/event-stream",
                                   "Cache-Control": "no-cache, no-transform",
                                   "X-Accel-Buffering": "no", "Connection": "keep-alive" });
  const reader = upstream.body.getReader();                   // 逐块下发，禁止 join/text()
  for (;;) { const { done, value } = await reader.read(); if (done) break; res.write(value); }
  res.end();
} else if (contentType.includes("application/json")) { ... } else { ... }
```

同批处理：`app.use(vite.middlewares)`（`:155`）需**前移到** catch-all（`:146`）之前，或把 catch-all 收窄为"非 vite 资产请求"，以消除 dev 双轨失效（W193/C175）。

### 4.4 Last-Event-ID 续传

`EventSource` 自动带 `Last-Event-ID`；BFF 透传该请求头；gateway 不 strip（与 ADR-7 三段责任一致，卷 00 属主）。断线 3 次后自动切轮询并显示降级条（§2.3）。

## §六 数据设计（前端）

1. **前端不建表、不拥有 schema**（ST07/ST08）。所有持久化属主在后端各册；本册仅声明消费对象。
2. **受控 JSON**：前端接收的受控结构由后端以 `TEXT` 承载（MC02），前端解析失败必须显示"数据契约异常"而非静默兜默认值。
3. **版本与 Git**：只走 `src/services/gitService.ts` 单通道且**只传 `repositoryId`**（铁律 #6 / ADR-12）。现 4 文件引用 ⇒ 其余页面的"版本号/hash"来源必须逐一收口（W199/C181）。
4. **凭据与敏感值**：任何表单/展示**永不回显数据源凭据与密钥**，只显示"已配置 / 未配置"；掩码态不得渲染为空串。开发凭据 `admin/admin123` 仅限本机，**E2E 用例内凭据必须走 env，禁写入用例明文**。
5. **配置与字典**：只经 sysman api 门面（`config_group`/`subsystem` 单表分组），禁止前端硬编码枚举值；W-Agent 降级枚举走配置单源 seed（卷 10 §6.4）。
6. **金额展示**：按后端 `NUMERIC(p,s)` 原样格式化显示；**前端不得自行四舍五入或加解密**，也不得在任何文档/注释中声称"金额明文即可"（ST03-A 逐列登记属后端义务）。
