## 四、C 章 技术设计

### C.1 控制流 1：请求进入安全域到出数据（端到端时序）

```
[0] 浏览器/BFF → gateway（分册 00 C.1 链序）
[1] EcosTrustHeaderFilter: strip X-ECOS-* → JWT 校验 → 注入 X-ECOS-USER/ROLE/TENANT/DOMAIN + X-Request-Id
[2] service: HeaderAuthInterceptor → ServiceContext{userId,tenantId,orgId(server-side),roles,clearance}
       ※ orgId 只从 TD_USER 服务端解析，客户端 X-Org-Id 在 [1] 被剥离（W40）
[3] Controller → SecurityDecisionService#decide(AssetRef{schema.table}, Purpose{page|export|ai}, ctx)
       返回 DecisionBundle{
         rls: {predicateTemplate, bindings:[{name,value}], denyIfEmpty:boolean},
         columns: {mode: allow|deny, names:[...]},
         masks:   [{column, strategy}],
         opa:     {allow:boolean, obligations:[...], policyRef},
         auditSeed: {decisionId, traceId}
       }
[4] 数据访问层（02 册 QueryExecutor）：
       以 predicateTemplate + bindings 生成 **PreparedStatement**（? 绑定），禁字符串拼接
       CLS 在投影列上裁剪；mask 在结果映射阶段应用
[5] 出口：ApiResponse（带 traceId）
[6] 审计：AuditEvent → EventBusService.publish(ecos.audit)（失败进重试表，C.5）
```

**为什么把 decide 做成一次调用**：现状三通道各自零散调 RLS/CLS（S-6 只有 1/3 通道），漏一个就是旁路。合并成单入口后，"绕过"在结构上不可表达 —— 这是 PRD-07 §1.5-3"导出旁路 grep = 0"的**结构性实现**，而不是靠人工审查。

### C.2 裁决子系统设计

#### C.2.1 资产引用与命名（IR02/ST07 对齐）

```
AssetRef = {schema, table, columns[]}     ← 受保护对象最小单元
受保护清单来源: docs/40-实现/列级加密豁免登记表 + ecos_security_asset（新表 E.6.2）
引擎侧不得写裸表名：一律经 data-engine 的 td_data_resource 定位符（ST09 跨域只存定位符）
```

#### C.2.2 RLS：从"条件字符串"改为"参数化谓词"

```jsonc
// 存储形态（ecos_rls_policy.filter_expr 列内容迁移为 JSON 文本；MC02：TEXT，不参与索引）
{
  "template": "department_id = :userDeptId",
  "bindings": [ {"name": "userDeptId", "source": "CONTEXT_ORG"} ],
  "combine": "AND",
  "priority": 10,
  "denyIfEmpty": true
}
```

```
允许的 source 枚举（白名单，越界即 400）:
  CONTEXT_USER_ID | CONTEXT_TENANT_ID | CONTEXT_ORG | CONTEXT_CLEARANCE_LEVEL |
  STATIC_LIST(≤50 项，存库并逐项绑定) | PROJECT_ATTRIBUTION_SUBQUERY(预置模板，见 E.6.2)
禁止: 任何拼接语义（||、CONCAT）、任何 SQL 关键字出现在 template（校验器 regex 黑名单：
      union|drop|insert|update|delete|exec|--|;|/*）
落地: RlsPredicateValidator（security-engine）+ QueryExecutor 消费（02 册 D 章接口）
兼容: 存量 filter_expr 裸文本（如 `clearance_level >= 4`）由迁移脚本一次性改写为
      template+bindings（STATIC 数值改为绑定变量），改写前 lint 阻断新增裸文本
```

#### C.2.3 CLS

```
优先级: 用户级 > 角色级 > 全局（与 PRD §1.2 一致，实现同 ClearanceInterceptor 的级联查询范式，
        但查询权下移到 security-engine，禁拦截器裸 JdbcTemplate —— 关闭分册 00 W04）
输出: {mode: allow|deny, names: [...]}；allow 为空集 = 该角色不可读该资产任何列 → DENY（非全放开）
消费: QueryExecutor 投影裁剪 + 导出列白名单 + AI 工具结果字段裁剪（三处同源）
```

#### C.2.4 脱敏

```
策略集（沿用 DataMaskingService 现有 6 类，补 2 类）:
  ID_CARD | PHONE | NAME | EMAIL | BANK_CARD | AMOUNT | + STAFF_REF(工号哈希) | + FREE_TEXT(截断)
强制点（Q2 双层口径）:
  明细查看: 明文，受 RLS+CLS+审计三重保护
  导出: 必须经 mask 裁决（无策略列 = 拒绝导出该列）
  AI 工具通道: 必须经 mask；且 OPA obligations 若含 mask 指令则优先级高于 CLS 允许集
ST03-A 联动: 未登记豁免的金额列若在导出中出现明文 → FAIL（SecuritySeedConsistencyTest）
```

#### C.2.5 OPA

```
端点沿用: POST /api/security/policy-engine/evaluate {policy, input}
改造: ① 删除 opa.fail-close 配置项，代码常量 true（S-8 → W35）
      ② policy-dir 默认值改为 classpath:opa/policies 解包到 ${java.io.tmpdir}/ecos-opa
         或 ECOS_OPA_POLICY_DIR 环境变量（Windows 可运行，W36）
      ③ 返回值增加 obligations（deniedReason, maskHints, watermark, rateLimitKey）
      ④ 裁决必须落审计（每次 evaluate 一条，含 input 摘要 sha256，不落原文避免敏感外泄）
```

#### C.2.6 加密与密钥治理（W37）

```
算法: AES-256-GCM，IV 12B 随机（每行独立），密文存储格式 base64(version(1B)|IV(12B)|ciphertext|tag)
密钥: 主密钥仅从 ECOS_MASTER_KEY(env) / KMS 读取；KeyManagementService 去掉"不存在即自动创建"分支
      → 缺钥时抛 KeyNotFoundException（写操作失败，不静默生成）

范围: 控制域敏感列（如 staff_ref）；业务域金额列**默认明文**，仅在 ST03-A 登记后强制加密
```

### C.6 降级矩阵（"security 不可用时"的唯一口径）
