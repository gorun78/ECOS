## 〇、复核结论（先看这一页）

方向不变：**不重写引擎，只重排信息架构、收编旧入口、统一换词**。但 v0.1 有 14 处与工程现状不吻合，若不补，会出现「UI 简化了但点不通」或「门禁直接红」。必须一起纳入方案：

| # | v0.1 的假设 | 源码实测 | 本版补法 |
|---|---|---|---|
| 1 | 「发布 vN」一个按钮即可 | 蓝图主链 `DRAFT→DISCOVERING→GAP_ANALYSIS→BLUEPRINT_READY→VALIDATING→READY_FOR_APPROVAL→APPROVED→RELEASED`；发布还要过 4 道校验 + 审批链；**没有草稿更新接口**，每次保存都会生成新版本 | 新增「定义保存/发布」门面，内部串联状态机；新增草稿更新能力（放新 Controller，见 §7） |
| 2 | 定义 = 场景 + 绑定 + 蓝图 | 绑定存 `ecos_scenario_binding`，发布校验读蓝图的 `dependencies_text`，两者互不同步 | 保存时把数据/知识/能力绑定同步成蓝图依赖；否则发布必被门槛拦 |
| 3 | 「激活」是运行前置 | 场景 `ACTIVE` 需要「无孤岛 + 非空 + COGNITION 边契约通过」；**运行接口只校验场景存在，不要求 ACTIVE** | 解耦：**发布版本即可运行**；`ACTIVE` 降为高级治理态，不在主流程暴露 |

### 1.1 复杂度来源

| # | 来源 | 实测证据 |

| 5 | **绑定与依赖双轨** | 六类绑定在 `ecos_scenario_binding`；蓝图发布校验读 `dependencies_text`；两者无同步 |

### 1.2 结论

问题不在能力缺失，而在**没有一层业务语义把技术对象包起来**。本方案优先「重排 + 收编 + 换词」，并把上表的硬约束显式化。

## 三、场景定义（主功能一）

### 3.1 页面结构（单页四段，首次创建走向导）

1. **基本信息**：名称、归属部门、业务目标、成功标准、范围、负责人。
2. **数据（从本体出发）**：
   - 选择本体域 / 实体（`GET /workspace/scenarios/available/objects`）；
   - 依据实体-表映射带出候选数据表（`GET /api/v1/ontology/entity-mappings`）；
   - 选择数据资源 / 数据集绑定（`DATASET`）；
   - 展示「本体实体 → 数据表 → 数据资源」链路。
3. **知识**：
   - **知识库（向量检索）**：从知识资产中选（`GET /workspace/scenarios/available/knowledge`，底层 `knowledge_article` + pgvector 检索）；
   - **规则库**：从规则中心选（`GET /api/v1/ecos/rules`；新增 `RULE_SET` 绑定位）；
   - **图谱**：标注「由本体自动生成，只读」，只给数量与跳转。
4. **校验与版本**：
   - 校验清单只露业务语言；动作：**发布为 vN**、查看历史、版本对比、基于旧版修订；
   - 发布后的版本是运行唯一可引用的版本；发布后可继续编辑，但需再发布才会被正式运行使用。

### 3.2 数据 / 知识 / 规则的真实边界（必须按这个写）

| 用户面 | 后端真实载体 | 约束 |
|---|---|---|
| 场景数据 | `DATASET` 绑定 → datanet 数据源/资源；`OBJECT_TYPE` → 本体实体；映射走 `ecos_entity_table_mapping` | 选实体后要能查到映射；MAPPING 边创建时**必带 `sourceContract`**（映射记录 id） |
| 知识库（向量检索） | `KNOWLEDGE_BASE` 绑定 → `knowledge_article` 资产（`/api/v1/knowledge/assets`）；检索由 kb-engine/pgvector 承担 | 没有「向量集合」实体；不要把「向量库」做成可选库；资产为空时如实空态 |
| 规则库 | 规则中心 `ecos_ontology.ecos_ontology_rule`（`/api/v1/ecos/rules`） | `expert_rule`（`ecos_knowledge.expert_rule`）是另一张表，本期不混入；如要纳入，单独立项 |
| 图谱 | 本体 + 实例派生（PG / Neo4j） | 只读展示，不做第二套配置；不计入绑定 |

**`RULE_SET` 新增改动点（同一批，缺一即半成品）**：

1. `BindingType` 增 `RULE_SET`（tier 归 `SUBGRAPH`）；`BindingCatalog` 图标与 `linkableTo`（可为空）。
2. `ScenarioService.BINDING_ENDPOINTS` 增 `RULE_SET → ruleSets`。
3. `ScenarioVO.emptyBindings()` 增 `ruleSets` 空数组。
4. `ScenarioSaveDTO.ScenarioBindingItem` 注释与校验；`RuleSet` 目标 id 指向 `rule_id`。
5. `ScenarioOptionsController` 增 `GET /available/rules`（走 buszhiRest `/ecos/rules`，沿用 `CallerCredentialSource`）。
6. 前端定义页「知识」分组增规则库；`binding-catalog` 展示；i18n 增键。
7. 测试：`BindingCatalogContractTest`、`ScenarioService` 绑定测试、完整度/预校验不变（`RULE_SET` 不进固定 3 条必需边）。

### 3.3 必需关联与契约（这是「点不通」的最大来源）

现状完整度不是「选了下拉就算」：

| 必需边 | 由什么证明 present | 上游依赖 |
|---|---|---|
| `MAPPING` 数据集→本体 | 连边存在 + `GET /ontology/entity-mappings` 计数 > 0 | 本体实体-表映射已建 |
| `EXTRACTION` 本体→知识 | 连边存在 + `GET /knowledge/sync/status` 的 `syncedCount > 0` | 知识同步已跑过 |
| `COGNITION` 知识→智能体 | 连边存在 + `GET /agent-mesh/agents` 中 `metadata.knowledgeBases` 引用数 > 0 | Agent 元数据已引用知识库 |

而场景 `ACTIVE` 的前置是：无孤岛 + 非空 + **COGNITION 边 present（含契约）**。

**方案口径**：

- 定义页把这三条叫「上游就绪检查」，每条给「去修复」的真实跳转（映射页 / 知识同步 / Agent 配置）；
- **运行不要求 `ACTIVE`**（`ScenarioRunService` 只校验场景存在），所以「发布版本即可运行」成立；
- `ACTIVE` 收进「高级治理」，不作为主流程按钮；不在主流程展示「完整度 100%」承诺；
- 每次定义保存后调用完整度 `invalidate(scenarioId)`，避免 30s 缓存读到旧值。

> 若用户坚持「必须激活才能运行」，则必须同时改造状态机或补齐上游契约，不能只靠前端按钮。

### 3.4 版本维护（Git 承载，业务面不露 Git 术语）

**版本语义（本版冻结）**：

- 一个「定义版本」= 场景基本信息 + 数据/知识/能力绑定 + 蓝图内容（目标/成功标准/范围/依赖）的一次发布快照；
- 发布后不可原地修改；再改生成 vN+1；
- 正式运行记录必须回带「定义版本 + 摘要」；定义有未发布修改时，正式运行给「请先发布」提示（沙箱试算可放行）。

**现状与补法**：

| 能力 | 现状 | 本方案 |
|---|---|---|
| 草稿内容更新 | 蓝图只有 create/revise，**没有 update-draft**；每次保存都新增版本 | 在**新 Controller** `ScenarioDefinitionController` 里提供 `PUT /definition`，内部调用蓝图服务新增的 `updateDraft`（仅 DRAFT 可改） |
| 发布 | 必须按 6 段主链推进 + `enter-approval` + `approve` + `release`；`release` 还要过 4 道校验 | 新增 `POST /definition/publish` 门面，按状态机逐段推进；高风险时停在 `READY_FOR_APPROVAL`，走审批抽屉；低风险（`approvalRequired=false`）可自动审批 |
| 蓝图的 4 道发布门槛 | ① 无 OPEN BLOCKER Gap；② required dependencies 已发布；③ required capabilities 可用；④ P0 tests 通过 | 定义页「校验」逐条用业务语言展示；**数据/知识绑定要同步成 dependencies**，否则门槛 2 必失败 |
| 审批 | `approval_required=1` 时 `approval_ref` 必填；`APPROVED` 才能 RELEASED | 发布抽屉：低风险直接发布；高风险生成待审批记录，不伪造审批人 |
| Git 归档 | 现状只在场景状态迁移后写 `scenarios/<id>/latest.json`；蓝图发布不归档 | 发布成功后用 `DesignAssetArchiver` 写 `scenarios/<id>/<ver>.json`（repo `scenario-def`，复用现有路径契约）；归档失败如实 `FAILED/not_available`，不阻塞业务但登记 |
| 版本历史读面 | `GitController /commits` 无路径过滤；无按资产查版本接口；GitPanel 还在传错 repoId | A 批先用蓝图版本列表（DB 真数据）；B 批新增按资产查 Git 历史读面；GitPanel 撤出主流程 |
| 场景当前版本 | 场景表无 definition_version/digest | 新增列 `definition_version`、`definition_digest`（只存当前版本；历史走 Git） |

> 归档路径以现有 `DesignAssetArchiver` 的 `<repo>/<assetType>/<assetId>/<version>.json` 为准：`scenario-def/scenarios/<id>/<ver>.json`。ADR-22 的 `ecos-design/scenario/definitions/...` 属独立治理线，不在本方案内切换。

### 3.4-b 蓝图与状态机的必要性裁决（建议）

**结论：蓝图作为「版本快照载体」有必要；作为「16 态工作流引擎」没必要。**

保留蓝图的理由（源码实测）：

- 它是当前唯一**带版本号、不可变内容、artifactDigest、发布/审批留痕**的定义载体；场景表只有可变字段，没有版本历史。
- `revise` 能生成 version+1 的 DRAFT，`diff` 能对比两版，`validate` 能出四道门槛明细；这些正是「定义版本」需要的底座。
- 现有 10+ 条 sc001 蓝图版本、E2E 与前端面板都依赖它；直接推翻等于重做版本治理。

不保留 16 态的理由：

| 现状状态 | 实际语义 | 问题 |
|---|---|---|
| `DISCOVERING` / `GAP_ANALYSIS` / `BLUEPRINT_READY` / `VALIDATING` / `READY_FOR_APPROVAL` | 发布动作内部的「盘点/补缺/校验/送审」步骤 | 对用户不是稳定状态，是**一次发布里的中间步骤**；做成状态后，保存、校验、审批都被拆成多次迁移 |
| `APPROVED` | 审批通过 | 即使 `approvalRequired=false`，`release` 也只接受 `APPROVED → RELEASED`，**低风险也必须走审批态**，是隐藏步骤 |
| `ACTIVE` / `RUNNING` / `COMPLETED` | 场景运行态 | 与「发布版本不可变」冲突：同一行版本会被每次运行改状态，**运行可复现性被破坏**；这些应属于场景/运行记录，不属于版本 |
| `NEEDS_CLARIFICATION` / `BLOCKED` / `VALIDATION_FAILED` | 阻塞原因 | 是**标记/原因**，不是生命周期；做成状态后要维护回退边，复杂且容易死锁 |
| `PAUSED` / `DEPRECATED` | 暂停/废弃 | 暂停属运行；废弃可保留为版本终态 |

**建议目标态（3 个生命周期 + 2 个标记）**：

```
status:            DRAFT（草稿/修订中） → RELEASED（已发布） → DEPRECATED（已废弃）
approval_status:   NONE | PENDING | APPROVED | REJECTED   （可选，高风险才用）
validation_status: NOT_RUN | PASSED | FAILED              （发布时计算，不手填）
```

- 用户面只露 4 档：**草稿 / 待审批 / 已发布 / 已废弃**；「修订中」= 基于已发布版本 `revise` 出的新草稿。
- 发布 = `保存 → 校验 → （需要时）审批 → RELEASED → 归档`；中间的发现/补缺/校验步骤只进审计/transitionHistory，不落成状态。
- 运行只引用 `RELEASED` 版本并记录版本号；**运行不改变版本状态**。`ACTIVE/RUNNING/COMPLETED` 归场景/运行记录。
- 阻塞项用 `validation_status=FAILED` + reasons/flags 表达，不再需要 `BLOCKED/NEEDS_CLARIFICATION/VALIDATION_FAILED` 状态。

**迁移口径（只增不改）**：

| 旧状态 | 新口径 |
|---|---|
| DRAFT / DISCOVERING / GAP_ANALYSIS / BLUEPRINT_READY / VALIDATING / READY_FOR_APPROVAL | `DRAFT`；`approval_status=PENDING`（若已送审） |
| APPROVED | `DRAFT` + `approval_status=APPROVED`（等待发布） |
| RELEASED / ACTIVE / RUNNING / COMPLETED | `RELEASED`（历史运行态不再回写版本） |
| DEPRECATED | `DEPRECATED` |
| NEEDS_CLARIFICATION / BLOCKED / VALIDATION_FAILED | `DRAFT` + 对应 flag/reason |

- 新增 `approval_status`、`validation_status` 两列；**保留旧 `status` 列与旧 API** 供兼容读取，新 API 返回计算后的 3 态视图。
- 新状态机 `DefinitionStatusMachine` 只管 3 态；旧 `BlueprintStatus` 保留为只读兼容词表，不再作为新写入口。
- 迁移脚本只 UPDATE 新列/新视图，不改旧值；旧行按映射表回读，不做破坏性改写。
- 测试：新增 3 态迁移矩阵；旧 16 态映射表单测；E2E 状态文案更新；审批/发布门槛不得绕过。

**三个选项**：

| 选项 | 内容 | 评价 |
|---|---|---|
| **A（推荐）** | 保留蓝图表；生命周期收口 3 态 + 审批/校验标记；发布由门面内部串联；旧状态兼容读取 | 改动可控，真正消掉 13 个状态，运行可复现性修复 |
| B | 只在前端把 16 态映射成 4 档，后端状态机不动 | 最快，但 API/测试/发布门面仍要处理 8 段链，复杂度没消 |
| C | 彻底弃用蓝图表，改用场景表 + Git 快照 + 发布指针 | 理念最简，但要迁移 10+ 版本、重写发布/审批/校验/前端/测试，风险最高，不建议本轮做 |

> 建议选 A：**保留“版本载体”，去掉“工作流引擎”**。如果后续两个季度蓝图表仍只承担快照职责，再评估是否退化为 `definition_version` 表 + Git。

### 3.5 保存 / 发布链路（门面职责）

```
保存草稿:
  校验基本信息 → 更新场景字段 → 全量替换绑定 → 同步蓝图 dependencies →
  更新当前 DRAFT 蓝图内容（仅 DRAFT）→ 完整度缓存失效 → 返回定义聚合

发布:
  保存草稿（可选）→ GET validate（4 道门槛）→ 逐段 transition 到 READY_FOR_APPROVAL
  → 低风险: 自动 approve + release；高风险: 停待审批
  → release 成功后: 计算 definitionDigest → 更新场景 definition_version/digest
  → 归档 Git（scenarios/<id>/<ver>.json）→ 审计留痕
```

**硬约束**：不走 `PATCH /scenarios/{id}/status`；场景状态与定义发布是两套状态机，不得混用。

## 四、场景运行（主功能二）

### 4.1 运行发起器（输入必须真实、可缺即报）

| 分析类型 | 正式通道 | 必填输入（用户/服务端） |
|---|---|---|
| 因果 | `POST /workspace/scenarios/{id}/runs`（`runTypes=[DIAGNOSE]`） | 关注指标 `metric`、偏差 `deviation`；可选 Mind |
| 预测 | `POST /workspace/forecast-runs` | `asOfTime`（用户）；`caliberId/caliberVersion`（定义/口径库）；`snapshotId`（数据快照解析）；`formulaVersion`（算法库）；`idempotencyKey/contentHash`（服务端生成） |
| 仿真 | `POST /workspace/scenarios/{id}/runs`（`SIMULATE`；反事实用 `SAFEGUARD`） | 变量/扰动；正式运行或沙箱试算 |
| 比较 | `GET /workspace/forecast-runs/compare` | 两条 **forecast run** 的 runId |
| 复盘 | 只读聚合 | 场景时间线（运行 + 评估 + 动作） |

**预测 run 的 9 个必填要素**（`ForecastRunRequestValidator` 源码）：`scenarioId, runType, caliberId, caliberVersion, asOfTime, snapshotId, formulaVersion, idempotencyKey, contentHash`。

- `idempotencyKey/contentHash` 由门面按规范化载荷（场景 + 定义版本 + 口径 + 时点 + 快照 + 算法）**服务端生成**，不让用户填；
- `caliberId/version` 取定义/口径库的真实值；`snapshotId` 由数据快照解析；`formulaVersion` 取算法库；
- 任一项拿不到 → **400 点名缺项**，不静默使用默认值；
- `projectCount/rowEstimate` 可选，命中阈值才走异步真实 taskId。

### 4.2 正式 / 探索的边界（避免假留痕）

| 能力 | 处置 |
|---|---|
| 正式仿真 | 走 `ScenarioRunService`，落 `ecos_scenario_run`，计运行历史，绑定定义版本 |
| What-If 试算 | 保留现有 `/api/v1/cognitive/scenario/simulate` 探索通道；显式标「试算，不进正式运行历史」，不参与比较/复盘 |
| 认知 POST（diagnose/forecast/simulate/policy） | 保留为高级调试面；不作为主流程正式运行入口 |
| 预测 run | 以 `/forecast-runs` 为正式预测；旧 `runTypes=[FORECAST]` 标记「快速预测（不落六要素）」，高级可见 |

### 4.3 统一运行记录（锚点表，不迁移旧表）

不合并 `ecos_scenario_run` 与 `ecos_dw.ecos_application_forecast_run`，而是给 `ecos_scenario_run` **加锚点列**：

| 新列 | 用途 |
|---|---|
| `definition_version` | 本次运行引用的定义版本 |
| `definition_digest` | 定义快照摘要（防运行后定义漂移不可复现） |
| `analysis_type` | 因果/预测/仿真 |
| `source_type` / `source_id` | 结果在哪：`SCENARIO_RUN` / `FORECAST_RUN` + 源 id |

- 预测分析：门面先创建 forecast run，再在 `ecos_scenario_run` 插一条锚点行（`source_type=FORECAST_RUN`），状态随结果更新；
- 因果/仿真：既有 `ScenarioRunService` 直接写同一张表，补齐新列；
- 读面只读这一张锚点表，结果按 `source_type` 回源；
- 旧 `ecos_scenario_execution` 仍停写；**不迁移**，登记技术债（其 status 约束不含 `SUCCEEDED_DEGRADED`，贸然切换会丢状态）。

### 4.4 比较与复盘的精确定义

**比较分析（按用户口径：运行结果对比）**：

- 只允许两条 **forecast run**；其它类型明确回「该类型暂不支持比较」；
- 现有 compare 返回两侧快照 + `diff` 布尔标记（口径/版本/时点/快照/公式是否不同），**没有逐指标 delta**；
- UI 展示两侧原值 + 差异标记；如需数值差，标注「前端基于两侧真值计算」，或后续加后端 delta。

**复盘（本轮默认口径）**：

- 场景时间线：运行记录 + 运营评估 + 结果评价 + 关联动作；
- `operation-eval` 依赖 Mind；无 Mind 时显示「未绑定认知」而非空表；
- 回放（ReplayTab）按信念变量/版本，不按 run；不宣称「单 run 回放」；
- 动作/决策接口在 `DecisionGateway` 未装配时恒 503，UI 如实展示「动作闭环未接入」；
- 预测/决策页有 `DemoBadge`（`FORECAST_REAL_SOURCES_CONNECTED=false`），运行页复用时**必须保留**，不得摘掉。
