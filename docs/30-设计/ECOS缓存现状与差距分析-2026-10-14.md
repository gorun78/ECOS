## 一、结论摘要（TL;DR）

1. **Redis 属「部分引入 / 半接入」**：全仓无运行期可用的 Redis。`spring-boot-starter-data-redis` 仅在根 pom 的 `dependencyManagement` 声明（`ecos_backend/pom.xml:352-356`），实依赖只在 `sysman-impl` 的 `redis-enabled` Maven profile（属性 `ecos.redis=true`，enterprise/ultimate 档激活）下引入（`sysman-impl/pom.xml:190-218`）；唯一消费代码 `RedisBlacklistStore` 在 standard 档被编译期排除（`sysman-impl/pom.xml:181-185`）。**全仓无 `spring.data.redis.*` / `spring.redis.*` 配置、无 Redis 容器、前端无 Redis 依赖**——即便 enterprise/ultimate 档，`RedisBlacklistStore` 因 `@Autowired(required=false) StringRedisTemplate` 且无连接配置，运行期实际降级为纯 Caffeine。**结论：Redis 未真正接入运行链路。**

2. **缓存能力现状：全部为「单机本地内存缓存」，无分布式缓存、无 Spring Cache 抽象、无统一缓存底座。** 未采用任何 Spring Cache 注解（`@Cacheable/@CacheEvict/@EnableCaching/@CacheManager` 全仓 0 命中）；现有缓存实现散落在各业务模块，形态为 Caffeine 或自建 `ConcurrentHashMap/LinkedHashMap`，且均为**进程内本地缓存**（多实例不共享、跨节点不失效）。

3. **无缓存一致性基础设施**：全仓**未找到** Outbox/事务消息机制（`outbox`/`@TransactionalEventListener`/`TransactionSynchronization`/`AFTER_COMMIT` 0 命中）。事件总线 `runtime-event` 具备 Kafka ↔ 内存降级能力，可作为失效广播的候选载体，但当前**未接线到任何缓存失效逻辑**。

4. **关键缺口**：`架构铁律 §2.5` 运行时底座清单为「PG/Neo4j/MinIO/Doris/Git + 任务/监控/事件/LLM」，**不含 Redis/缓存**——Redis 若作为新的横切基础构件，须先纳入 runtime 底座（否则业务侧自建违宪）。

5. **可复用能力**：`runtime-event` 的 `EventBusService`（Kafka 主 + 内存降级，`ecos.event.kafka.enabled` 开关）可作为缓存失效事件通道底座；既有 Caffeine 缓存点（Token 黑名单/权限/决策/配置/字典/元数据）可作为迁移与一致性治理的对象清单；`sys_config` 配置缓存（`SysConfigService`）与监控底座（`runtime-monitor`）可与缓存治理对接。

### 2.1 Redis 是否已引入

**现状**
- **依赖声明面（BOM）**：根 pom `dependencyManagement` 声明 `spring-boot-starter-data-redis`（无版本，由 Spring Boot BOM 管），注释「Sprint 2: Redis for distributed cache and session」。但**仅版本管理**，非实际依赖。

- **配置面**：全仓 `application*.yml`（gateway + 5 service + 各 engine-boot，共 40+ 个）**未找到** `spring.redis` / `spring.data.redis` / `redis` 配置项（`ecos_backend/**/application*.yml` grep `redis` = 0 命中）。

- **前端面**：全仓 `package.json` grep `redis` = 0 命中。
- **旁证（文档自述）**：`docs/40-实现/ecos-工程现状分析-2026-09-28.md:58` 称「Maven 三档 profile 名存实亡…仅设 `ecos.edition`/`ecos.redis` 属性且全库无代码消费」。

### 2.5 权限模型（缓存不得绕过鉴权）

**现状**（事实直接复用既有基线，仅补与缓存读取路径相关结论）
- 既有基线已查明：密级 L0~L4（`SecurityConfigService.LEVEL_NAMES`）+ `audit_mode` 字典；`ClearanceInterceptor`（超管旁路 + `X-Org-Id` 客户端可控，存量安全偏差 S-14）；RLS/CLS（`RlsController`/`ClsController`，DDL 脚本 `V164` 未实跑）；ABAC/OPA（`AbacController`/`PolicyEngineController`）；`AuditAspect`（AOP）；审计哈希链（`AuditHashChainService`，`ecos_audit_log` SHA-256）。
- **缓存读取路径相关结论**（本次补充）：
  - 权限/策略/决策**存在本地缓存**（`PermissionCacheService` / `AbacPolicyCacheService` / `DecisionCacheService`，见 2.2）。
  - PRD **明确要求**：`PRD-06-ai-engine…md:209`「本地缓存判定必须有 TTL 并在超时后默认 DENY（fail-closed）」；`PRD-07-security-engine…md:233`「不…在引擎侧本地判权限（含『缓存判定』作为唯一依据）」。
  - → **结论：缓存只可作为鉴权的加速层，不得成为鉴权权威；判定权归 security-engine（PEP/PDP）；缓存失效/不可用时必须 fail-closed（DENY），且缓存键须能隔离租户/机构维度。** 现有缓存实现**未见**按 `tenant_id`/`org`/密级维度做键隔离的证据。

**证据**
- 复用《ECOS控制域版本治理现状与差距分析-2026-10-14.md》§2.3（`SecurityConfigService.java:20`、`AuditHashChainService.java`、`SecurityAuditService.java`、`V164__security_rls_cls_policy_ddl_backfill.sql:4` 未实跑声明、`V24`/`V40`/`V12`、详细设计-01 S-2/S-3/S-14）。
- `docs/20-需求/PRD-06-ai-engine需求规格-2026-09-28.md:209`；`docs/20-需求/PRD-07-security-engine需求规格-2026-09-28.md:233`。
- 缓存实现类见 §2.2。

**标签**
- 密级/RLS/CLS/ABAC/审计链：**B**（RLS/CLS 为脚本落地未实跑 → B/C 之间，见既有基线）。
- 「缓存不得作为鉴权唯一依据 + fail-closed」：**A（现行明确要求）**。
- 缓存键租户/机构/密级维度隔离：**D（缺口）** + **E（需安全负责人确认隔离维度）**。
