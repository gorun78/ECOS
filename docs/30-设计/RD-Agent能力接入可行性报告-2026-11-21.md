## 〇、结论摘要（先看这段）

| # | 结论 | 判断 |
|---|---|---|
| 1 | RD-Agent 的可复用价值不在「整仓嵌入」，而在**假设驱动的研究循环 + 可恢复的实验轨迹 DAG + 代码化实验**三件套 | 成立 |
| 2 | 把 RD-Agent 作为 ECOS 生产运行时直接接入 | **不建议**（Linux-only、Docker 强依赖、任意代码执行、单租户文件态、无 RLS/多租户/审计） |
| 3 | 用 RD-Agent(Q) 直接承载经营预测/经营分析结论 | **不建议**（口径、证据等级、金额纪律均不匹配；上游免责声明明确非投资建议） |
| 4 | 推荐路线：**模式移植为主 + 离线研究侧车为辅**（本报告方案 C） | 可行，需用户裁决后进入设计 |
| 5 | 首期落点：AI 工作台新增「研究实验」编排模板；场景工作台新增「实验型运行」异步步骤；定义权仍归场景蓝图 | 可行，只增不改 |
| 6 | 最大阻碍不是技术，而是**可信反馈闭环**：ECOS 当前行动结果→实际指标的聚合口径缺失（P1-18），RD-Agent 的「自评→改进」在业务面上暂时无真值可评 | 必须先解 |

**一句话结论**：RD-Agent 值得借鉴的是「R（提出假设）—D（实现并执行）—F（反馈）—R（记录/选优）」的工程化循环；但它是一套**研究级、Linux 容器内、单租户、代码执行型**的 Python 框架，不能直接住进 ECOS 的 Java/安全/多租户主链。建议先把循环**移植为 AI 工作台的一种受控编排模板**，RD-Agent 本体只作为离线研究沙盒产出候选，经人工审批后才进入场景定义与运行。

## 一、可行性评级（决策版）

| 维度 | 评级 | 依据 |
|---|---|---|
| 能力匹配度 | **中** | 研究循环、实验轨迹、知识沉淀与场景定义/运行有结构同构；但 RD-Agent 的「Scenario」是开发者写死的描述类，不是业务场景定义器 |
| 技术契合度 | **低—中** | Python 3.10/3.11 + Linux + Docker vs ECOS Java 17 + Spring Boot + Windows 开发态；需侧车或移植二选一 |
| 安全可控性 | **低（直接接入）/ 中（隔离后）** | RD-Agent 会生成并执行代码、读写本地文件、直连 LLM；默认无 RLS/OPA/多租户/审计概念 |
| 数据治理 | **低** | 文件式工作区、pickle 会话，无血缘/版本/证据等级；与 ECOS「数字不来自 LLM」「产物落业务数仓」冲突 |
| 运维成熟度 | **低—中** | 研究级项目、接口快速演进、会话靠 pickle 恢复；无生产 SLA |
| 交付成本 | **中—高** | P0 离线验证 2~3 周；P1 只读侧车 1~1.5 月；P2 产品化闭环 2~3 月（不含安全加固与数据治理） |
| 合规/许可 | **可接受** | MIT；但含「as is」免责声明与金融场景风险提示，不能对外承诺结论准确性 |

> 评级含义：**不是「能做/不能做」的二元判断，而是「以什么形态做」**。直接嵌入不可行，受控借鉴可行。

## 二、RD-Agent 工程解剖

### 2.1 项目定位与官方场景

RD-Agent（R&D-Agent）是微软开源的「数据驱动研发自动化」Agent 框架，核心方法论是 **R（Research，提出新想法）+ D（Development，实现并执行）** 的持续循环。官方入口（`rdagent` CLI，`rdagent/app/cli.py`）包括：

| 命令 | 场景 | 本质 |
|---|---|---|
| `rdagent fin_factor` | Qlib 因子挖掘 | 假设→因子代码→回测→反馈 |
| `rdagent fin_model` | Qlib 模型结构演化 | 假设→模型代码→训练评估→反馈 |
| `rdagent fin_quant` | 因子+模型联合优化 | 双循环交替 |
| `rdagent fin_factor_report` | 从研报抽取因子并实现 | 文档理解→代码→回测 |
| `rdagent general_model <paper>` | 从论文复现模型 | 论文理解→代码→评估 |
| `rdagent data_science --competition` | Kaggle/MLE-bench | 方案生成→提交→榜单反馈 |
| `rdagent llm_finetune` | LLM 微调 | 数据处理→训练→基准评估 |

它的「场景」是**每个用例一个 Python 类 + 一套 prompt/评估器**，不是用户可配置的业务场景模型。这一点对 ECOS 的场景定义很关键：RD-Agent 不能替代场景蓝图，只能辅助生成草案或实验计划。

### 2.2 七个核心抽象（源码级）

| 抽象 | 文件 | 职责 | 关键点 |
|---|---|---|---|
| `Scenario` | `core/scenario.py` | 只提供背景、源数据描述、运行环境描述、实验设置 | **纯描述**，无状态机、无审批、无绑定 |
| `Task` / `Experiment` | `core/experiment.py` | 实验规格与子任务；`Workspace` 承载代码与产物 | `FBWorkspace` 是文件式工作区，`execute()` 由子类实现 |
| `Hypothesis` | `core/proposal.py` | 一条假设 + 理由 + 简洁观察/论证/知识 | 与 ECOS 认知域 `Hypothesis` 概念同构 |
| `HypothesisGen` → `Hypothesis2Experiment` | `core/proposal.py` | 依据 `Trace` 历史与 RAG 知识生成假设，再转成实验 | 两个 LLM 环节，输入都是「轨迹历史」 |
| `Coder`（CoSTEER） | `components/coder/CoSTEER/` | 把实验规格进化成可运行代码 | RAG + 多轮演化 + 评估器反馈 + 知识自生成 |
| `Runner` | `utils/env.py` | 在 Docker 环境执行代码、取指标 | 强依赖 Docker；环境即依赖清单 |
| `Feedback`（Summarizer） | `core/proposal.py` | 把执行结果转成「是否接受 + 原因 + 新假设」 | 自评式反馈，非业务真值 |

### 2.3 R/D 循环的实际执行序列

`RDLoop`（`components/workflow/rd_loop.py`）是一个 5 步循环，步骤函数由元类自动发现：

```
direct_exp_gen  →  coding  →  running  →  feedback  →  record
（假设+实验生成）  （CoSTEER 写码） （Docker 执行） （LLM 总结） （写 Trace DAG）
```

- 每步的输入是上一步输出的字典（`prev_out`），框架负责注入；
- `coding` 内部是一个**嵌套进化循环**（CoSTEER 的 `RAGEvoAgent`）：写码→评估→再写，直到可接受或达 `max_loop`；
- `feedback` 在异常时直接给 `decision=false`，正常时由 LLM 对比历史 SOTA 给出结论；
- `record` 只做一件事：把 `(Experiment, Feedback)` 挂到 `Trace` 的 DAG 上。

### 2.4 Trace：实验谱系与 SOTA 选择

`core/proposal.py` 的 `Trace` 是 RD-Agent 最有借鉴价值的工程设计：

- `hist` 保存按时间排序的 `(Experiment, Feedback)`；
- `dag_parent` 保存每个节点的父节点（`()` 新树根、`(i,)` 单父、多父暂未实现）；
- `current_selection` 决定下一轮从哪个节点展开（默认 `SEL_LATEST_SOTA = (-1,)`）；
- `get_sota_experiment()` 沿祖先链回溯，取最近一次 `decision=true` 的实验；
- 支持从任意检查点开新树（`CheckpointSelector`），为「换方向重试」留出结构。

这套「实验谱系 + SOTA 回溯 + 多起点」正好补上 ECOS 当前「一次运行一个结果、无实验历史、无选优」的空缺。

### 2.5 LoopBase：把「循环」工程化

`utils/workflow/loop.py` 是框架的承重墙：

| 能力 | 实现 | 对 ECOS 的启发 |
|---|---|---|
| 步骤自动发现 | `LoopMeta` 扫描方法生成 `steps` | 编排模板可声明式注册 |
| 依赖注入 | `loop_prev_out[li][step]` | 与 WAgent `input_slots` 思路一致 |
| 并行循环 | `asyncio.Queue` + 每步信号量 | 可与 runtime-task 的并发配额对齐 |
| 断点恢复 | 每步成功后 pickle 落 `__session__/{loop}/{step}` | 思路可借，**载体绝不能是 pickle** |
| 失败跳过 | `skip_loop_error` / `withdraw_loop_error` | 对应 ECOS 的降级与重规划 |
| 预算 | `step_n` / `loop_n` / `all_duration` | 与 WAgent 四轴预算同构 |

默认配置 `step_semaphore = 1`（串行），并行度由部署配置决定；`subproc_step` 可强制子进程隔离。这说明它默认是**单机、单任务、串行**的研究工具，不是多租户平台。

### 2.6 技术栈与运行约束（硬约束）

| 项 | 事实 | 影响 |
|---|---|---|
| 语言/版本 | Python 3.10 / 3.11（CI 实测） | ECOS 主链是 Java 17，必须侧车或移植 |
| 操作系统 | README 明写 **currently only supports Linux** | Windows 开发态不能原生跑；POC 需 WSL2/Docker |
| 容器 | 多数场景要求 Docker，且要求当前用户免 sudo 执行 | 与 ECOS「不新增容器需授权」冲突，需专门裁决 |
| LLM 接入 | 默认 LiteLLM；支持 DeepSeek chat，但 embedding 需另配（示例为 SiliconFlow） | ECOS 有 `llm-gateway` 的 chat/embedding，可做兼容适配层 |
| 会话持久化 | pickle 文件（`__session__`）+ 文件工作区 | 无 DB 事务、无审计、无租户隔离 |
| 许可 | MIT | 商用可行，但「as is」免责，金融场景需自担风险 |
| UI | Streamlit / Flask Web UI | 仅研究观测，不可作为产品前端 |

### 2.7 可借鉴 / 不可照搬

| 可借鉴 | 不可照搬 |
|---|---|
| 假设→实验→执行→反馈→记录的闭环 | 直接执行 LLM 生成代码（ECOS 安全红线） |
| Trace 实验谱系 + SOTA 回溯 + 多起点 | pickle 会话与本地文件态（违背审计/多租户） |
| 逐步评估与「可接受即停」 | Docker 直通 + 宿主凭据 |
| 实验知识库自生成 | 单租户、无 RLS/OPA 的默认形态 |
| 预算/步数/时长/并行控制 | Qlib/Kaggle 的领域结论直接搬进经营口径 |

## 三、ECOS 现状：场景定义与运行

### 3.1 产品面

- **AI 工作台**（`#/ai-workbench`）：智能体构建、编排与治理统一平台。现有 Tab 包括 overview / agent / playground / orchestration / evals / models，并已新增 `wagentStudio`「智能体编排」；目标形态是「AI 工作台编排 → 产出 WAgent 候选 → 审批发布 → 场景工作台绑定使用」。
- **场景工作台**（`#/workbench`、`#/decision`）：L1 我的场景 → L2 场景详情 → L3 预测/决策；含沙箱画布、蓝图、运行历史。
- **认知能力**：独立认知工作台已按裁决下沉——治理面入知识工作台，诊断/假设/信念/推演运行面入场景工作台（`useCognition` → `cognitiveClient`），AI 工作台保留模型/能力目录。

### 3.2 场景定义链路（已落地）

| 环节 | 载体 | 关键规则 |
|---|---|---|
| 场景主体 | `ecos_business_scenario` + `ScenarioStatusMachine` | 四态 `DRAFT/ACTIVE/SUSPENDED/COMPLETED`；`ACTIVE→COMPLETED` 需存在 FORMAL 运行 |
| 绑定 | 六类 binding：DATASET / OBJECT_TYPE / KNOWLEDGE_BASE / AI_AGENT / SECURITY_POLICY / INTERFACE | `binding-catalog` 提供目录；实例须在对应域可解析 |
| 连边 | 五类 link：MAPPING / EXTRACTION / COGNITION / GOVERN / EXPOSE | MAPPING 必须带 `sourceContract`；禁孤儿边 |
| 完整度 | `GET .../completeness` | 分母固定 3 条边；返回 coverage/verdict/islands/missingEdges |
| 预校验 | `POST .../pre-validate` | 三项：`mind`（认知 E1 detect）、`sandbox_coverage`（沙箱 6 类资源节点）、`bindings_reachability`（无孤岛） |
| 蓝图 | `ScenarioBlueprint` + 16 态状态机 | `DRAFT→…→APPROVED→RELEASED`；RELEASED 不可原地改，修订 = version+1；发布带 artifactDigest；结构化 goal/scope/dependencies/capabilities/gaps/risks/tests |
| 缺口 | `gaps`（BLOCKER/WARNING/SUGGESTION × OPEN/RESOLVED） | 仅未关闭 BLOCKER 阻断发布 |

**结论**：ECOS 的「场景定义」是一个**带审批与不可变发布的状态机**，权威对象是蓝图，不是一段描述文本。RD-Agent 的 `Scenario` 无法承担这个职责。

### 3.3 场景运行链路（已落地，但是同步短链）

`POST /api/v1/workspace/scenarios/{id}/runs` → `ScenarioRunService.run()`：

- `runMode`：`FORMAL` / `SANDBOX`（FORMAL 不得引用 SANDBOX 基线）；
- `runTypes`：`DIAGNOSE` / `FORECAST` / `SIMULATE` / `STRATEGY` / `SAFEGUARD`；
- 逐类调用 dccheng 的认知端点，**每步独立 try/catch 降级**，全量结果落 `ecos_scenario_run`，诊断置信度回写场景指标；
- 控制器是**同步阻塞**调用（`@Transactional` 内完成全部下游调用），不是异步作业；
- 失败语义：单步失败记 `SUCCEEDED_DEGRADED`，不阻断整体。

**结论**：现有运行是「固定几类分析端点的一次组合调用」，不是「多轮实验 + 反馈改进」。RD-Agent 补的正是后者。

### 3.4 智能体与执行底座（比预期更完整）

| 底座 | 现状 | 对研究循环的意义 |
|---|---|---|
| WAgent 编排 | `Question→Plan(DAG)→Run→Step`；6 类 step：`tool/llm/human_gate/wait_task/sub_run/aggregate`；四轴预算；幂等；崩溃后按最大 succeeded step 恢复；Candidate→审批→发布；Kill Switch | **天然宿主**：研究循环可作为新 Plan 模板，`wait_task`/`sub_run` 可承载长实验与子实验 |
| LLM 网关 | `LLMGateway` 提供 chat / stream / embedding / token 计量 / 模型目录 / 上下文上限 | 可替代 LiteLLM；需加 OpenAI 兼容适配层给 RD-Agent 用 |
| 任务/事件 | runtime-task（调度/重试）、runtime-event（Kafka，可降级内存） | 异步实验与事件唤醒的底座 |
| 代码执行 | `workbook` 的 `PythonRuntime` / `RRuntime`：`ProcessBuilder` 调 `python3`/`Rscript`，30s 超时、512MB（`prlimit`）、10MB stdout、会话目录隔离 | 有「代码执行」影子，但**无容器隔离、无包环境、Linux 命令依赖** |
| 存储/版本 | MinIO、Git 设计资产归档、`ecos_scenario_run` | 实验产物可走 MinIO + Git 引用，避免本地文件态 |

**关键发现**：`PythonRuntime` 用 `prlimit`（Linux 工具）包裹 `python3`；本机 Git Bash 实测 `python3` 与 `prlimit` 均不存在，Windows 开发态该能力不可用。这与 RD-Agent 的 Linux 约束叠加，意味着**任何执行型方案都必须先有 Linux 容器环境**。

### 3.5 与 RD-Agent 的结构差异

| 维度 | RD-Agent | ECOS 现状 |
|---|---|---|
| 循环形态 | 开放式多轮实验，直到可接受/预算耗尽 | 一次同步运行，固定 5 类分析 |
| 反馈来源 | LLM 自评 + 指标比较 | 业务口径 + 认知置信度；实际值聚合缺失（P1-18） |
| 状态持久化 | pickle 会话 + 本地文件 | DB 行 + Git + 审计 |
| 计划结构 | Python 类 + prompt | 蓝图状态机 + WAgent Plan DAG（受控结构） |
| 执行隔离 | Docker 容器（研究级） | JVM 内同步调用；workbook 无容器隔离 |
| 多租户/安全 | 无 | RLS/OPA/信任头/审计/Kill Switch，默认 DENY |
| 定义权 | 开发者写死 Scenario | 蓝图 + 审批 + 不可变发布 |

## 四、能力映射矩阵（RD-Agent → ECOS）

| RD-Agent 抽象 | ECOS 最近落点 | 复用方式 | 复用度 | 主要差距 |
|---|---|---|---|---|
| `Scenario`（描述） | 场景 + 蓝图 + Context Pack | 借其「背景/源数据/运行环境」三段描述结构 | 中 | 蓝图是状态机与审批对象，不能被 Python 类替代 |
| `Task` / `Experiment` | WAgent Run/Step；`ecos_scenario_run` | 新增「实验」实体或扩展运行类型 | 中 | 无实验规格/指标契约 |
| `Workspace` | workbook 会话目录 / MinIO / Git | 借文件式产物 + 版本引用 | 中 | 无包环境、无隔离、无血缘 |
| `Hypothesis` | 认知域 Hypothesis/Belief | 直接把实验假设写成候选 | **高** | 必须走候选—复核—写入闸门 |
| `HypothesisGen` | LLM + 知识库/RAG | 借其「轨迹历史 + 知识检索」提示组织 | 中 | 需证据等级与禁用 LLM 造数 |
| `Hypothesis2Experiment` | `PlanBuilder`/`PlanValidator` | 借「受控结构 + 执行前校验」 | 中 | ECOS Plan 是工具 DAG，非实验规格 |
| `Coder`（CoSTEER） | 无等价 | 借「迭代实现 + 评估器反馈」思想 | 低 | 无代码进化器；需从零建 |
| `Runner`（DockerEnv） | workbook（弱）/ 新沙箱（缺） | 新建立隔离执行服务 | 低 | **最大工程缺口** |
| `Feedback` | 认知 outcome evaluate；运行结果 | 借「决策 + 原因 + 新假设」结构 | 中 | 实际值缺口（P1-18）；LLM 自评不可作权威 |
| `Trace`（DAG/SOTA） | WAgent run steps/events + 运行历史 | 新增实验谱系与 SOTA 选择 | **高** | 无父选择/多起点/SOTA 回溯 |
| `LoopBase` | `WAgentOrchestrator` | 借恢复/预算/信号量设计 | **高** | WAgent 无开放式循环语义 |
| Knowledge Base | 知识库 + 认知资产 | 新增「实验记忆」候选资产 | 中 | 无实验知识形态 |

**总体判断**：结构同构度约 **60%**，但**执行与反馈两端**（Runner、Feedback 真值）是硬缺口；这两端决定 RD-Agent 的价值能否真正落地。

## 五、接入方案对比与推荐

### 5.1 四个候选方案

| 方案 | 形态 | 能力上限 | 与 ECOS 架构契合 | 安全风险 | 交付周期 |
|---|---|---|---|---|---|
| **A 整仓侧车** | 把 RD-Agent 打包成独立 Linux 容器，暴露 REST 适配层，ECOS 调用 | 高（接近原生） | 低（新运行时、新容器、Python 依赖） | **高**（代码执行、数据出域） | 短（2~4 周可跑通 POC） |
| **B 模式移植** | 在 WAgent/场景运行内实现「研究循环」模板与实验实体，不引入 Python | 中（无 CoSTEER、无 Qlib） | **高**（复用现有编排/安全/存储） | 低—中（受控） | 长（2~3 月） |
| **C 混合（推荐）** | B 做产品主干；A 仅作离线研究沙盒，产出候选，人工审批入 ECOS | 中—高 | 高（边界清晰） | 中（隔离后可控） | 中—长（分三段） |
| **D 仅方法借鉴** | 只借文档/流程，不接代码 | 低 | 高 | 低 | 短 |

### 5.2 为什么推荐 C

1. **风险与收益分离**：研究的不确定性留在沙盒，生产主链只接收「候选」，不接收「执行」。
2. **符合 ECOS 既有咽喉**：WAgent 的 Candidate→Approval→Publish、场景蓝图的 APPROVED→RELEASED、认知域的候选—复核—写入，三套闸门现成可用。
3. **不破坏架构铁律**：不新增 Maven 模块、不把 Python 塞进 JVM、不让 Agent 直连 DB；新增研究容器属「需授权」事项，单独裁决。
4. **可退出**：沙盒可随时停用；产品主干不依赖 RD-Agent 上游演进，避免被研究级项目节奏绑架。
5. **可分阶段验证价值**：P0 不写 ECOS 代码即可验证「这套循环对场景定义/运行是否有用」，失败成本低。

## 六、推荐方案（C）的目标形态与设计要点

### 6.1 四段闭环（与 WAgent 现状对齐）

```
AI 工作台「研究实验」模板
  ① 研究循环（沙盒）：假设 → 实验计划 → 代码/配置 → 执行 → 反馈 → 轨迹
        │ 产出候选（假设 / 实验记录 / 蓝图建议 / 缺口建议）
        ▼
  ② 候选评审（WAgent Candidate + 人工 Gate）
        │ 审批通过
        ▼
  ③ 发布（蓝图 version+1 / 认知资产候选 / 实验模板）
        │
        ▼
  ④ 场景工作台绑定与运行（既有 FORMAL/SANDBOX 链路）
```

### 6.2 组件与边界

| 组件 | 归属 | 职责 | 禁止 |
|---|---|---|---|
| 研究模板（`research_loop`） | AI 工作台 / WAgent | 声明阶段、预算、人工闸门、产物槽位 | 自动发布、自动写正式口径 |
| 研究沙盒（RD-Agent 侧车，可选） | 独立容器 | 跑多轮实验、生成候选产物 | 持 DB 凭据、持宿主凭据、挂 docker socket |
| 实验记录服务 | ai-engine 或 workspace | 存实验谱系、指标、产物引用 | 复制认知权威副本 |
| 数据快照出口 | datanet / data-engine | 按场景/口径导出只读快照到 MinIO/只读卷 | 放开生产库直连 |
| 反馈评估 | 认知域 / 业务域 | 用真实指标评估实验 | LLM 自评替代业务真值 |

### 6.3 数据与安全（不可妥协）

1. **不直连数据库**：沙盒只读 ECOS 导出的快照（Parquet/CSV + 只读卷）；快照带租户/场景/口径标记，出域留审计。
2. **代码执行隔离**：独立容器、非 root、只读根文件系统、无宿主凭据、无 Docker socket、网络出口白名单、CPU/内存/时长/磁盘配额、进程数限制。
3. **凭据最小化**：沙盒调用 ECOS 只走「研究专用」短期令牌，作用域限定为提交任务/读取自身快照/上传产物。
4. **产物只进候选**：实验结论、蓝图建议、指标改进一律先落 Candidate；`candidate:publish`/`action:commit` 仍由 OPA 角色级规则把关。
5. **审计全链**：任务号、场景号、快照摘要、模型、提示摘要、代码摘要、执行日志、产物摘要全部留痕；可回放。
6. **失败闭合**：沙盒不可用、LLM 不可用、快照缺失时，研究任务显式失败/降级，不得返回「看起来成功」的空结论。

### 6.4 场景定义接线（只产出草案，不夺定义权）

研究循环可输出以下**草案**，全部落 `DRAFT`，不自动流转：

| 产物 | 对应蓝图字段 | 人工校验点 |
|---|---|---|
| 目标陈述草案 | `goal.statement` | 业务负责人确认口径 |
| 成功标准草案 | `goal.successCriteria` | 必须可度量、可复算 |
| 范围草案 | `scope`（租户/周期/项目/口径） | 与正式口径一致 |
| 依赖草案 | `dependencies`（数据集/本体/知识库/Agent/策略/接口） | 逐项在对应域可解析 |
| 能力需求草案 | `capabilities` | 与模型/能力目录对齐 |
| 缺口草案 | `gaps`（BLOCKER/WARNING/SUGGESTION） | 不得把「未验证」写成「已满足」 |
| 风险/测试草案 | `risks` / `tests` | P0 用例必须可执行 |

> 边界：AI 可「起草」，不能「批准」。蓝图的 `APPROVED/RELEASED` 仍由既有审批链产生。

### 6.5 场景运行接线（新增实验型运行，不替代正式运行）

建议两种落地粒度，二选一或并存：

- **粒度 1（轻）**：在 AI 工作台发起「研究实验」WAgent Run，结果只落实验记录与候选，不写 `ecos_scenario_run`；
- **粒度 2（重）**：在场景运行新增 `runType=EXPERIMENT`（异步，走 `wait_task`/runtime-task），实验完成后生成「建议运行配置」，仍需人以 FORMAL 重跑才产生正式结果。

约束：
- `FORMAL`/`SANDBOX` 语义不变；实验型运行不得计入 `isFormalRunExists`；
- 指标回写仍走既有 `ScenarioRunService` 的 FORMAL 路径，不得由研究任务直接改场景指标；
- 实验产物引用（快照/代码/日志/图表）落 MinIO + Git 引用，DB 只存引用与摘要。

### 6.6 认知闭环接线

- 实验产生的假设 → 认知域 Hypothesis/Belief **候选**（`GENERATED→…→APPROVED→APPLIED`），不得直接改状态；
- 实验反馈 → 认知 `operation-eval`/`outcome-evaluate` 的输入之一，但**业务真值优先**；
- 实验知识 → 知识库/认知资产候选，遵守 C/K 互斥（认知资产不得静默落成 K 类知识）。

### 6.7 分期计划与验收

| 阶段 | 周期（估） | 范围 | 代码面 | 验收（必须真实跑通） | 退出条件 |
|---|---|---|---|---|---|

## 八、红线与不做清单

1. **不直连生产库**：研究沙盒不得持有 PG/Neo4j/MinIO 生产凭据。
2. **不在 JVM 内执行生成代码**：不得在 gateway/workspace 进程内跑 LLM 生成的 Python。
3. **不自动发布**：研究结论不得自动流转蓝图 `APPROVED/RELEASED`，不得自动写场景正式指标。
4. **不让 LLM 造数**：金额、概率、贡献度、指标实际值只能来自确定性计算；LLM 只写解释与建议。
5. **不新增未授权容器/模块**：compose 基线 9 容器、Maven 模块基线 49；新增需单独裁决。
6. **不引入 Linux-only 运行时到 Windows 主链**：POC 用容器，开发态不装 Python 依赖。
7. **不把 RD-Agent(Q) 结论当经营预测**：量化因子研究仅作参考，不进入正式口径。
8. **不牺牲失败语义**：沙盒/LLM/快照不可用时显式失败或降级，禁止 200 空结论。
