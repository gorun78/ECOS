### 1.2 六个域里，四个域的关键端点今天根本读不出来（不是数据缺失）

带 admin `accessToken` 真跑（2026-10-16T03:07 本机）：

| `GET /api/v1/interfaces` | `200` + `bad SQL grammar … FROM ecos_interface_ref` | 缺表 |

| `POST /api/v1/data/pipelines/{id}/execute` | 一期实测 500「Pipeline 执行被 ABAC 策略拒绝」 | OPA fail-closed（见 §4 甲） |

IAM 四条的根因已在 psql 复现，非推定：

```
SELECT "ORG_ID","ORG_NAME" FROM TD_ORGANIZATION;  → ERROR: column "ORG_ID" does not exist
SELECT count(*) FROM TD_ORGANIZATION;             → 3
```

`ecos_control.td_organization` 实列是 `org_id/org_name/…`（`information_schema` 实测），而 `services/sysman/impl/sysman-impl/.../iam/dao/impl/Organization-sql.xml:5,16,20…` 与同目录 `User-sql.xml`/`Role-sql.xml`/`Permission-sql.xml` 用带引号大写标识符 ⇒ PG 大小写敏感必然报错。**数据灌进去也显示不出来**，这与用户「各部分对接正确」直接冲突，属域 0 的前置阻塞。

**补记（2026-10-16 实测，另一项 HEAD 级阻塞，与数据无关）**：上表四条的 live 复验需要 gateway，而 gateway 用当前 HEAD 全新构建后**启不来**——
`APPLICATION FAILED TO START … Error creating bean 'WAgentRunEventStreamController': constructor parameter 3: No qualifying bean of type 'org.springframework.core.task.TaskExecutor' available: expected single matching bean but found 5: clientInboundChannelExecutor, clientOutboundChannelExecutor, brokerChannelExecutor, workspaceTaskExecutor, workspaceProcessIoExecutor`。
根因 = 详设-10 复盘批（commit `105006a6`）的 SSE 泵按**类型**注入 `TaskExecutor`，其 javadoc 自称拿的是 `applicationTaskExecutor`，但 Boot 的 `TaskExecutionAutoConfiguration` 带 `@ConditionalOnMissingBean(Executor.class)`，聚合面已有其它线程池 Bean ⇒ 该自动配置退避、该名字在 gateway 态不存在，而按类型的 5 个候选无 `@Primary`、参数名未被保留 ⇒ 必歧义。ai-engine-boot 切片只有 1 个候选，所以该批次的单模块测试从未暴露（此前的"gateway 能跑"是旧 jar stale）。这也是 pending #180「全量重建 fat-JAR」一直做不完的真实阻塞。
修法（只动 ai-engine 侧，不改 API 签名、不动表结构、不引 workspace Bean）：模块级 config 新增命名池 `runEventStreamTaskExecutor`，控制器改 `@Qualifier` 按名注入。**落地时被本仓两道门禁夹住的事实需登记**：`WAgentForbiddenDependencyArchTest` 红线 3 禁 `engine.ai.wagent..` 包内持 `org.springframework.scheduling.` 类型，而 `TerminologyArchTest.wAgentClassesResideInWagentPackageOnly` 又要求一切 `WAgent*` 命名的类住在该包内 ⇒ 池只能以非 `WAgent` 前缀名住在 `engine.ai.wagent` 之外的模块级 config（真跑证据：首轮命名 `WAgentSseExecutorConfig` 被 TerminologyArchTest 判红，`Tests run: 374, Failures: 1`）。

**同步补记（本窗口 W3 收口）——内联 SQL 同款缺陷**：§1.2 表列 4 端点的 live 复验走的是 `e63771fa` 修完的 5 份 `*-sql.xml`，但 **同一批 Controller 的 6 段内联 SQL 未在 e63771fa 波及面**（HEAD 残留）：`UserController.list`（列表 + count）、`.getRoles`、`.assignRoles` 各一份；`UserLookupDao.findTenantByUsername` / `.deleteUserOrg` / `.insertUserOrg`（登录与用户-组织维护都在这链上）；`ClearanceLookupDao.findOrgById`（机构上下文解析）。本窗口 2026-10-16 全部按 `information_schema` 实测列名订正为不带引号小写（表名 `TD_*` 保持，与 e63771fa 口径一致），`assignRoles` 的 INSERT 顺带补 `created_by='admin'`（`td_user_role.created_by NOT NULL` 无默认，原 SQL 即便标识符写对也必挂；同法在文件既有约定里也能找到 `createUser` 那样传 operator 的先例）。**独立登记不夹带**：`AuditLogDaoImpl.query(condition, int, int)` 走 `databaseAccess.executeQuery` 那份内联 SQL 引用了 `td_audit_log` 实表不存在的 4 列 `resource_type / operation_result / request_data / created_time`（实表列面：`log_id/user_id/action/result/ip_address/…/timestamp`），映射端 `.get("LOG_ID")` 等也是幻影键 ⇒ 属于「审计呈现面」而非域0 IAM 读端点五面所在端点，且行映射与实表对齐需要重写一整遍 setter 面，W3 收口不夹修，登记为独立缺陷。


### 1.3 「Excel 数据源」在当前代码里没有落点

- `data-engine` 的 `StorageType` 枚举实测 9 类（MYSQL/POSTGRESQL/ORACLE/SQLSERVER/CLICKHOUSE/DORIS/STARROCKS/ELASTICSEARCH/MONGODB），**无 FILE/EXCEL/CSV 成员**；
- 全仓 `pom.xml` 零 `poi` / `easyexcel` / `commons-csv` 依赖；
- 唯一结构化文件通道是 `runtime-access` 的 `CsvConnector`（`:47` 起只按 `filePath`+分隔符逐行读，**不解析 xlsx**）。

⇒ 二期口径（明示，不藏着）：**造 N 个 `.csv` 文件（Excel 可直接另存为/打开）作为原始台账数据源**，经 pipeline `SOURCE_CSV` 节点真实装载；`.xlsx` 二进制解析属平台能力缺口，登记为缺陷而非以 seed 伪冒。

## 二、六域依赖图（执行顺序即依赖顺序）

```
域0 安全中心（集团结构：组织/人员/角色/权限/策略）
  └─ 给全部域提供 org 维度、人员身份、策略载体
     ↓
域1 数据工作台（源文件 → 数据源 → 近源层 → DQ 管道 → 数据资产入 ecos_dw）
  └─ 给域2 提供「可映射的物理列」；给域3 提供「可抽取的数据层知识」
     ↓
域2 本体工作台（4 个业务域：对象/属性/关系 + 术语/指标/函数/action/规则/接口 + 数据映射）
  └─ 给域3 提供「本体驱动的知识模型」；给域5 提供 OBJECT_TYPE 绑定对象
     ↓
域3 知识工作台（知识体系树 + 文档 + 图谱 + 术语 + 认知知识体系接入）
  └─ 给域4 提供 KNOWLEDGE_BASE 绑定对象；给域5 提供证据源
     ↓
域4 AI 工作台（六类系统默认智能体 + 编排协同定义 + WAgent 载体）
  └─ 给域5 提供 AI_AGENT 绑定对象
     ↓
域5 场景工作台（sc_entmgmt 装配：六类绑定 + 必需三边 + 蓝图 + 心智模型）
```

域 5 必须最后做：`FixedDenominatorEdgePolicy:24-26` 要求的三条必需边（DATASET→OBJECT_TYPE `MAPPING`、OBJECT_TYPE→KNOWLEDGE_BASE `EXTRACTION`、KNOWLEDGE_BASE→AI_AGENT `COGNITION`）的四个终点分别在域 1/2/3/4 新建，缺一即触 `LINK-400` 孤岛闸。一期只建了 4 条 binding、无必需三边闭环 ⇒ 这就是「只多了一个场景」的直接机制。

### 2.1 句柄（沿用 G3=甲零 DDL 约定，批次号升 V2）

| 句柄 | 值 |
|---|---|
| 批次 / 来源引用 | `batch_id='SEED-ENTMGMT-V2'`、`source_ref='seed:entmgmt-v2'` |
| 场景 / 域 | `scenario_id='sc_entmgmt'`、`domain='entmgmt'` |
| 主键 | `md5('seed:entmgmt-v2:' ‖ 逻辑键)`（确定性 ⇒ 重跑幂等，MC01 应用侧生成） |
| 创建人 | `create_by='seed-entmgmt'` |
| 幂等 | `ON CONFLICT (id) DO NOTHING`（MC03 的 seed 豁免，同法写在脚本头注释） |

### 2.2 seed 边界（红线，不因「演示效果」让步）

- **可 seed**：主数据、定义面、口径、映射、规则、结构（组织/人员/角色/权限/策略、数据源与管道**定义**、本体对象与术语、知识模型与文档、智能体**注册与编排定义**、场景装配）。
- **禁 seed**：一切执行结果——近源层装载行、DQ 问题单与评分快照、管道执行记录、agent 执行步、预测/回测/演练/动作结果（`ecos_cognitive_outcome_evaluation`、`ecos_application_forecast_run`、`agent_execution*`、`ecos_pipeline_execution*` 等）。这些只能由真实执行产生；执行被安全基线拒绝时，**把拒绝码作为实况登记**，不得用 seed 数字冒充。
