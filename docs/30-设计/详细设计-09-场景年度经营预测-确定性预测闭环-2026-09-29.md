## §三 技术设计 · 控制流

### 3.1 预测运行状态机（编排与生产分离，落 R-59 推荐档）

```
workspace :18090（场景层 · 只编排）                cognitive-engine :18089（认知域 · 确定性生产）
        │                                                   │
 POST /forecast-runs ──① 参数与权限(OPA, 默认 DENY)──────────┤
        │  ② DATA_CHECK ──RPC──▶ data-engine DQ 门禁 ────────┤  缺失格清单 → FAILED(DQ_BLOCK)
        │  ③ SNAPSHOT_FROZEN ──▶ runtime-access 写快照+checksum┘ 冻结失败 → FAILED（禁半冻结）
        │  ④ RUNNING ──▶ cognitive.calculateRun(scope, caliberId@version, asOfTime, overrides)
        │                   │  逐格四源取值 → BigDecimal 环节额 → 严格自下而上聚合
        │                   │  三级平衡断言（精确相等）→ 区间合成（CM-02/03）
        │                   └─▶ 产物经 data-engine 写通道落业务域 APPLICATION/ecos_dw（ADR-14）
        │  ⑤ 六要素完备自检 → SUCCEEDED（自检失败 ⇒ FAILED，宁可失败不缺要素）
 ──▶ ITaskManagementService.submitTask（>50 项目 或 >10 万行 ⇒ 异步，真实 taskId，禁自造 jobId）
     前端 AsyncTaskCenter + run 进度页消费 td_runtime_task_status
```

**编排/生产边界的三条硬约束**：
1. workspace **不写金额计算代码**、**不建 `ecos_fc_*` 计算明细表**（§0.6 + AGENTS #5"cognitive 不新增 DB 表"⇒ 明细属业务域产物，经 data-engine 写通道，不由 cognitive 建表）；
2. cognitive-engine **不直接访问事实库**以外的基础设施（Driver/LLM/调度/监控/事件一律 runtime 收口，§2.5）；
3. 任何 `POST` 计算入口必须过 security-engine PEP（§2.4），安全不可用即 DENY。

### 3.2 幂等与复现控制流

```
scopeHash    = SHA-256(排序后 projectId 集 | departmentId 集 | periodRange | stageSet)
overridesHash= SHA-256(规范化 JSON(overrides))     // 键排序 + BigDecimal 字符串化
runKey       = (caliberId@formulaVersion, asOfTime, scopeHash, scenarioSetHash, overridesHash)

POST /forecast-runs:
  1) 命中既有 SUCCEEDED run（runKey 相等）且未带 force ⇒ 返回该 runId + reused=true
  2) force=true ⇒ 新建 run，参数与冻结输入完全复用（快照按 runKey 引用同一份）
  3) 新 run 明细与旧 run 逐行 diff=0 由断言测试强制（§2.3 演练 2b）
```

`as_of_time` 的语义 = **快照可见性时刻**：事实行按 `create_time ≤ asOfTime AND (is_deleted=0 OR deleted_at > asOfTime)` 视图裁剪；合同按 `change_version` 取 asOfTime 有效版本（FC-06）。

### 3.3 口径与审批控制流（FC-01）

```
DRAFT --validate(4 关)--> 通过 --submit--> PENDING_APPROVAL --OPA allow + 财务角色批准--> APPROVED
                                                     │ 拒绝
                                                     ▼
                                            REJECTED（回 DRAFT）
APPROVED --supersede(newVersionId + change_reason)--> 新版 APPROVED，旧版 SUPERSEDED（禁 UPDATE formula、禁物理删）
```

- 批准/升版/拒绝三事件 **经 Kafka `ecos.audit`**（ST06），不走同步自写；
- run 创建时冻结 `caliber_snapshot_json`（TEXT，MC02），历史 run 不受升版影响；
- 版本历史遵循铁律 v2.0 §3.1 + 后端开发规范 §十一：**存在即用版本落库、历史版本走 Git 归档通道**（口径属设计资产，非业务事实）。

### 3.4 关账 / 回灌 / 复审控制流（FC-05）

```
财务关账(period) → period_status=CLOSED（审计事件）
   ├─ ACTUAL 事实经 data-engine 导入管道（唯一回灌通道，禁独立回灌）+ DQ 门禁
   ├─ 展示层：该期"预测 vs 实际"并排（视图层，绝不回写 run 明细）
   └─ 回测：对每个 CLOSED 期间 × 粒度{项目|部门|环节} 计算五指标 → ecos_dw 回测结果
          MAPE > 阈值(默认 15%) 或 区间覆盖率 < 阈值(默认 80%) 或 n<5→LOW_SAMPLE 不告警
             → ITaskManagementService 生成复审任务（画像偏差→知识管理员；假设偏差→财务+经营负责人，原审批人回避）
```

### 4.2 证据链数据流（六要素可点击的落点）

```
result_detail.source_ref_json(TEXT) ─┬─ ACTUAL/PLAN     → 事实行 ID + 合同 change_version
                                     ├─ PROFILE_IMPUTED → profile_key + profile_version + 置信档
                                     ├─ MANUAL_OVERRIDE → assumption_key + 审批人 + 生效期
```
