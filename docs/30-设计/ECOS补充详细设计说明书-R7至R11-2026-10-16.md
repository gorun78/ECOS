## §2.9.6 发布 / 双写状态机、失败恢复与对账（补充）

> 本节为原册 §2.9.6（[L1125-L1148](file:///d:/workspace/javaprojects/ECOS/docs/30-%E8%AE%BE%E8%AE%A1/ECOS%E8%AF%A6%E7%BB%86%E8%AE%BE%E8%AE%A1%E8%AF%B4%E6%98%8E%E4%B9%A6-%E4%BB%8E%E9%9B%B6%E5%AE%9E%E6%96%BD%E7%89%88-2026-10-12.md#L1125-L1148)）的 R7 增量补充。

**① 发布状态机（16 态）**：

```
主链: DRAFT → VALIDATING → PENDING_APPROVAL → APPROVED → READY_TO_APPLY
      → APPLYING → APPLIED → VERIFYING → SUCCEEDED
旁支: REJECTED / PARTIAL_FAILURE / FAILED / ROLLBACK_PENDING / ROLLING_BACK
      / ROLLED_BACK / DRIFTED
```

**红线**：Git 与 DB 属不同持久化系统，**不构成天然单一原子事务**；`Git 提交成功 ≠ DB 应用成功 ≠ 安全审计通过`，三者分别记录；**禁把部分成功报完全成功**。

**② 失败恢复**：Git 写入失败/审批过期/依赖冲突→保留上下文待重试或人工；DB 部分成功→标 `PARTIAL_FAILURE` + 幂等应用 + 补偿/重试；领域 API 超时→持久化发布任务（runtime-task 真实 `taskId`）+ 安全重试 + 对账；回滚→**优先发布已知历史版本（git ref 检出重应用），非任意反向 SQL**；不可逆变更→专门恢复流程；审计不可用→**关键安全变更 fail-closed**。
**③ 对账 8 类判定**：一致 / 缺失对象 / 多余对象 / 内容漂移 / 版本引用不匹配 / 部分发布 / 依赖不一致 / 无法验证。自动修复不得绕过审批。

**四、Outbox 生产半接通（#147AN）——先记账：这里既有本册的存量缺口，也有我本批写出的一句不实断言（#147AO 订正）。** #147AF/D 那批落了表（`V310`）、中继、订阅端，并把生产端接在 `PermissionCacheServiceImpl.evictAll` 上——**这条腿当时确实存在**（`91bbdc50`），所以「生产端已接」在那一句的范围内并不假。真正的缺口是**覆盖面**：`evictAll` 只在 `RoleServiceImpl` 改角色时走，其余 9 个已接缓存的域的写路径**一条都不递料**，中继因此在绝大多数轮次 poll 到 0 行、频道活着却收不到消息——「跨节点失效」这项能力只在单点触发下存在，却在本册里被当成整条链路已通。**#147AO 订正**：上一版本节写「全仓零个 `enqueueDomainInvalidation` 调用方」「中继每轮 poll 到 0 行」，把「多数写路径不递料」误写成「一条都没有」，是我 #147AN 回写时未复核调用点就下判断（复核方式见下条最后一项）。结论方向不变——底座收口才是覆盖面解法。本批接线与钉法：
- **接缝**：`RuntimeCacheManager` 新增 `ObjectProvider<CacheInvalidationNotifier>`（接口在 `cache` 包，实现 `CacheInvalidationRelay` 在 `cache.outbox` 包）——依赖方向单向 `cache.outbox → cache`，**没有包级环**。
- **环在结构层断开**：底座把「执行失效」与「宣告失效」分成两个入口——写路径调 `evictObject` / `invalidateDomain`（清本节点 + 直删共享 Redis 键 + 入队宣告），广播处理端只调 `invalidateDomainLocal`（执行、不宣告）。不靠运行时标志位，所以后来者无法「顺手」把订阅端改回 `invalidateDomain` 而复现成环而不必同时改接口。
- **粒度=域**：粗粒度只会**多清**（多回源），不会少清（返回陈旧值）；换来的是不必为每种对象形态另设事件。代价要点名一处：`evictUser` 走两次 `evictObject`（`permission-set` + `permission-decision`），因此**一次撤权落两行**广播意图，他节点据此整域清一次即可，第二行只是冗余投递。缓存关闭 / 未装配投递口 / 投递异常都只 `warn`，绝不影响本节点已完成的直删（最坏是他节点副本留到 TTL 上限）。
- **宣告口唯一（#147AO 补）**：底座 `invalidateDomain` 自己开始宣告之后，`evictAll` 里那条直连 `relay.enqueueDomainInvalidation` 就变成**同一意图落两行**——这是本批接通生产端与存量接线**重叠**造出来的缺陷，不是存量单独的错误。修法：删掉调用方直连，`RuntimeCacheManager` 成为唯一宣告口（`PermissionCacheServiceImpl` 里那段 `ObjectProvider<CacheInvalidationRelay>` 字段随之清退，不留死代码）。
- **保留期清退（#147AO 补，接通生产端的必然配套）**：生产端一接通，**每一次写路径失效都会落一行**，而此前这张表只在 `evictAll` 触发下长过几行——没有清退就是把「跨节点失效」的代价转成一张无界增长的表。补 `CacheInvalidationOutboxDao.purgePublished(cutoff, limit)` + `CacheInvalidationRelay.purge()`（默认 10 分钟一轮、保留 1440 分钟、单轮 500 行上限）。**只删过期 PUBLISHED；PENDING 是待投递、FAILED 是「广播没成功」的唯一线索，一律不清**——清了就等于把失败重放窗口抹平，重新造出假绿。SQL 侧一条方言纪律同时落进去：截止时刻由 Java 算好作 `timestamp` 参数传入，**不写 `? * INTERVAL '1 minute'`**（PG 的 `INTERVAL` 乘法在扩展协议下同样是占位符类型推断雷区，见 §五那族缺陷）。
- **门禁**：`CacheInvalidationNotifyGateTest` 7 例（`evictObject` 恰好宣告一次 / `invalidateDomain` 宣告 / `invalidateDomainLocal` **零宣告** / 关闭缓存零投递 / 投递异常不影响失效 / 投递口缺席容忍 / 中继实现该接口且底座字段按接口装配）；`PermissionCacheIsolationGateTest.evictAllAnnouncesExactlyOnce` 钉「一次 `evictAll` 恰好一条 Outbox 意图 + `evictUser` 两条按 objectType 各一条」，并做**变异自证**——临时把 `evictAll` 改成连调两次 `invalidateDomain`，该门实跑变红（`expected: <[unit-test|sysman|domain]> but was: <[unit-test|sysman|domain, unit-test|sysman|domain]>`）后还原；这正是「零调用方」那句本该做的复核：查调用点，而不是查记忆。清退半边：`CacheInvalidationRelayTest` 6 例（新增两例＝cutoff 落在 now 之前且等于保留期、单轮上限与异常不冒泡）+ `CacheInvalidationOutboxLiveTest` **5 例**（真 PG + 真 Redis，第 5 例同表造 4 行不同寿命——PENDING / 新鲜 PUBLISHED / 过期 PUBLISHED / FAILED——点名验证只有过期 PUBLISHED 被带走，`purgePublished` 的 `<` 方向与状态过滤都只能在真库上照出来）。
