## 〇、一句话结论

ECOS 的 Git 底座（`runtime-access` 的 `GitService` / `GitRepositoryService` / `GitRepoRegistry` / `DesignAssetArchiver` / 发布状态机 / 备份冻结）**已经具备承流能力**，真正的缺口有两个：**覆盖面**（用户点名的多数设计态资产零 Git 覆盖）与**仓库形态**（6 枚仓无法表达跨域一致性，且与规范 §十一.5 的 10 枚清单永久漂移）。本规范按 ADR-22 冻结「单仓 `ecos-design` + 8 命名空间 + 路径即契约」的目标态，并逐条登记现状。

## 一、适用范围与边界

### 1.1 纳入（设计态 = 人编辑、版本有意义、需要历史与 diff）

七类：① 数据域（元数据 / pipeline / 质量规则 / 分级分类 / 血缘定义）② 本体域（本体模型 / 术语 / 指标与口径 / 自定义函数 / 本体规则）③ 知识域（知识资产树 / 文档元数据 / 合规与专家规则 / 评估种子集）④ 认知域（认知模型 / Mind / 框架 / 认知管线定义）⑤ 智能域（智能体定义 / 工具契约 / Prompt / 逻辑编排 / 模型目录 / 护栏）⑥ 场景域（场景定义 / 蓝图 / 场景-Mind 绑定）⑦ 安全域（OPA 策略 / RBAC / RLS / CLS / 脱敏 / ABAC / 密级 / 数据权限 / 场景安全策略）+ 平台配置字典。

### 1.2 排除（明确不版本化）

| 排除项 | 理由 | 现有承载 |
|---|---|---|
| 图谱节点与关系 | 运行态派生物，可从本体 + 实例重建 | Neo4j / PG 图形态（ST02） |
| 向量与嵌入 | 模型产物，随模型版本变化 | pgvector（ADR-11） |
| 运行记录（`ecos_scenario_execution`、`*_pipeline_execution`、`kg_sync_log`、`dq_alert_record` 等） | 运行态事实，不是设计 | PG |
| 审计与操作日志（`ecos_audit_log`、`td_audit_log`、`sys_user_operation_log`） | 审计证据不得与被审计对象同库（§2.9.9 五原则） | PG + 哈希链 |
| 认知运行时状态（`ecos_cognitive_hypothesis` / `_belief` / `_evidence`） | ADR-9 落盘但属推理过程，非设计态 | `ecos_cognitive` |
| 业务实例与计量（`ecos_biz_metric`、`ecos_biz_target`、DW 层数据） | 业务域数据资产，走五层模型 | `ecos_dw` |
| 会话与消息（`sys_agent_session`、`sys_agent_message`） | 运行时 | PG |
| 用户个人档案与凭据明文 | 凭据治理面；Git 只存**引用** | security-engine 加密存储 |
| 文档原文二进制 | 体积与许可 | MinIO（Git 只存元数据与定位符） |
| 配置的**环境生效值** | 环境差异不入版本库 | `sys_config.config_value`（库内）；Git 只存 schema / `default_value` / `edition` |

> **红线**：`secrets` / `credential` / `private-key` / `.env` / `session` 五类前缀已在注册表 `exclude_paths` 播种（V307），单仓沿用同一份清单。

### 2.3 叶子路径契约（唯一形态）

```
<namespace>/<assetType>/<assetId>/<version>.json     # 版本内容（原文 JSON，不套信封）
<namespace>/<assetType>/<assetId>/latest.json        # 仅限「无版本号语义」的资产（如实时状态类快照）
<namespace>/<assetType>/<assetId>/draft.json         # 可选：草稿，不进 tag、不进历史读面
```

- `version` 取资产真实版本标识（`1.0.0` / `v3` / `2`），**不做补零或重编号**。
- `assetId` 使用稳定的业务键（UUID 或语义 code），禁使用会变化的名字。
- 每段都过 path-traversal 守卫（现有 `requireSafeSegment`：拒绝 `..`、`/`、`\`、`:`）。
- **例外形态（仅两处，须在 manifest 显式声明）**：
  - `security/opa/*.rego` —— 策略文件本身即制品，不套 `<id>/<ver>` 目录；版本由 commit + tag `security/opa/<policyName>/<ver>` 表达。
  - `platform/config/<group>/<key>.json`、`platform/dict/<subsystem>/<type>.json` —— 按分组聚合，单文件承载一组，避免几千个小文件。

### 2.4 单源不重复（强制）

| 资产 | 唯一落点 | 禁止 |
|---|---|---|
| 规则（全平台单一事实源） | `ontology/rules/` | **禁止**在 `knowledge/`、`data/quality/` 再存一份；规则中心前端页面读 `ecos_ontology.ecos_ontology_rule`，与本体规则同源（R10/R11 裁决，补充详设 §6.2.6） |
| 口径（含公式与版本） | `ontology/calibers/` | 禁止在 `data/` 复制；`ecos_biz_metric`（业务实例）不版本化 |
| 术语 | `ontology/terms/` | `ecos_knowledge.ecos_kb_term`（V184 建、**代码零引用**）不另立目录 |
| 认知模型 vs AI 模型目录 | `cognitive/models/` vs `ai/model-catalog/` | 二者语义不同：前者是认知资产（ADR-8），后者是 LLM 厂商/路由目录；禁止互相复制 |
| 场景 Mind 绑定 | `scenario/minds/` | Mind 本体定义在 `cognitive/minds/`；此处只存绑定声明与引用 |
| OPA 策略 | `security/opa/` | 禁止把 rego 内容复制进 `platform/config/` |

### 2.5 聚合粒度（避免 commit 爆炸）

| 场景 | 粒度 | 理由 |
|---|---|---|
| 单资产发布 | 单文件 `<id>/<ver>.json` | 支持按资产 diff 与回滚 |
| 本体模型发布 | `models/<ontologyId>/<ver>.json` 聚合快照 **+** 逐实体增量 | 快照供整体回滚；增量供逐实体历史 |
| 字段级元数据 | 按资源聚合 `fields/<resourceId>/<ver>.json` | 单表数百字段会灌爆仓库 |
| 字典与配置 | 按 group/type 聚合单文件 | `sys_dict` / `sys_config` 行数上千 |
| 基线回填 | 按命名空间一批 `archiveBatch` | 见实施路线 §B3 |

### 2.6 OPA 策略的特殊性

**现状（必须如实登记）**：`OpaPolicyService.updatePolicy` 用 `Files.writeString` 直接改写 OPA 策略文件（`ecos-docker/opa-policies/*.rego`，compose 挂载 `/policies:ro`），**无版本、无审计、无审批**（安全治理缺口，补充详设 §2.9.9 现状审计同族）。

**目标态**：rego 走 `security/opa/` 纳入版本控制（裁决 R-2026-11-20⑦「按建议」：Git 只作**变更记录源**，生效须经独立 apply 腿）。必须守住两条：

1. **commit ≠ 生效**（§2.9.9 五原则之一）：Git 提交只是记录变更；生效必须经过独立的 apply 腿（同步到挂载目录 + OPA bundle 重载 + 健康校验）。
2. **fail-close**：apply 失败时不得保留半生效状态；`opa check` 语法校验前置（历史教训：语法错会让整个 bundle 被拒、容器崩溃循环）。

apply 腿本轮**不实现**，登记为后续独立设计批次（实施路线 §六）——裁决 R-2026-11-20⑦ 已定策略，但执行器、触发方式与 fail-close 实现尚未设计，禁据此宣称 OPA 已受版本控制。在此之前 OPA 策略仍走现有直改文件路径，本规范只保证「一旦纳入就有位置」。

## 四、命名与提交契约

### 4.1 提交消息（强制格式）

```
<type>(<ns>): <action> <assetId> <version>

Asset: <ns>/<type>/<assetId>
Version: <version>
Content-Hash: sha256:<hex>
Status: DRAFT|PUBLISHED|DEPRECATED|RELEASED|ACTIVE
Actor: <user>
Trace: <traceId>
```

- `<type>` 用约定动词：`publish` / `draft` / `deprecate` / `rollback` / `baseline` / `archive` / `apply`。
- 第一行**必须**保持在 72 字符内，便于 `git log --oneline` 阅读。
- trailer 键集**只增不改**（沿用键集只增惯例），读取端按需取用。
- **兼容要求**：现有读取端解析的旧消息形态（`Publish ontology <id> <ver>`、`Draft ontology …`、`Snapshot compliance rule <id> v<ver>`、`Scenario transition to <STATUS> (<id>)`）在旧仓只读期必须继续可解析——因此新增 `ns` 前缀只用于新仓，**旧仓消息格式不重写**。

### 4.2 pipeline 的格式例外

现有 pipeline 归档文件为 `pipelines/<id>/pipeline.yaml`（内容是 JSON DAG，历史原因保留 `.yaml` 扩展名）。目标态统一为 `data/pipelines/<id>/<ver>.json`：

- 旧路径 `pipelines/<id>/pipeline.yaml` 在旧仓保号；
- 新仓写 `.json`，读取端按「新路径优先、旧路径回退」；
- `PipelineGitService` 里 `List.of("pipelines/" + id + "/pipeline.yaml")` 这类硬编码必须收敛到 `DesignAssetLayout`（新增门禁钉住）。

### 4.3 tag 规范

| 场景 | tag 形态 | 示例 |
|---|---|---|
| 单资产发布 | `<ns>/<type>/<assetId>/<ver>` | `ontology/rules/rule-001/1.2` |
| 基线 | `baseline/<ns>/<YYYYMMDD>` | `baseline/data/20261119` |
| 整体发布（跨域） | `release/<YYYYMMDD-HHmm>` | `release/20261119-1530` |

- 旧仓现有 tag `type/id/ver`（无 ns）**只读保留，不重打**、不改名（改写 tag 等同改写历史）。
- 真实签名（GPG/SSH）未接入；现有 `ecos.git.signing.enabled` 产出的是 `simulated:<sha256>`，**禁当成真签**（G2 口径）。

### 4.4 禁止事项（红线）

1. 禁在业务域拼路径字符串（必须经 `DesignAssetLayout`）。
2. 禁 `commitAllChanges` 整树提交用于发布（单仓下会串域）；发布一律 `commitPaths`。
3. 禁接收客户端 `localPath` / 远端 URL / 明文凭据（VG-3/VG-7 同族）。
4. 禁把 `latest.json` 当作「已发布版本」— `latest` 只表示「无版本号语义的当前快照」，不进历史读面。
5. 禁伪成功：未接入 / 归档失败必须 `not_available` / `FAILED`，不得回 `committed` 而无 commitId。
6. 禁把 `config_value`（环境值）、凭据、个人敏感信息写入任何命名空间。

`PublishReconciler` 8 类判定（一致 / 缺失对象 / 多余对象 / 内容漂移 / 版本引用不匹配 / 部分发布 / 依赖不一致 / 无法验证）在单仓内跨命名空间工作，输入从「仓 × 资产」变为「命名空间 × 资产 × 版本」。**自动修复不得绕过审批**（§2.9.6③ 原文约束）。
