**真阳**：#2/#4/#5/#6 共 4 个 Service / Controller 在 4 张 `ecos_knowledge.*` 表上把 `long`（epoch ms, 13 位整数）写进 PG `TIMESTAMP` 列。

### 2.3 PG JDBC + MyBatis 实际行为解析

MyBatis 默认 TypeHandler for `long` 字段会调 `PreparedStatement.setLong(pos, value)`。
PG `setLong` 到 `TIMESTAMP` 列：
- **JDBC 不拦截**：`PreparedStatement.setLong` 只对 BIGINT/INT/INT8 校验；写 TIMESTAMP 列 PG driver 会把它当 epoch seconds（不是 ms！）做 `substring` 拼进 SQL — 取决于 PG JDBC 的 `timestamp` type handler 实现
- **大多数情况**：PG 端会报 `invalid input syntax for type timestamp: "<long digits>"` 或写入错误的 epoch seconds

实际 cart 的 wall-clock，Wave-4.2 06-cheng 用 JUnit 起 H2 或直连 PG 跑 `KGWriterService.writeEntity(new ExtractedEntity("X"))` → `nodeMapper.insert(new KnowledgeNode{createdAt=1750000000000L})` → **MyBatis `PreparedStatement.setLong(7, 1750000000000L)`** → PG 接收 → **`PSQLException: invalid input syntax for type timestamp: "1750000000000"`**（经典）。

Wave-2C 子代理 mock JdbcTemplate 没暴露的问题不是 KB 的问题，是 mock 它本就不存在的对象；QA 子代理不知道 KB 走完的"KB approve → KGWriter 落 graph_node/edge/article/embedding"才触发这次 P0。

## §4 修复路线：3 选项对比（PM 拍）

### 路线 A — ALIGN-TO-MODEL（✅ T-01b 采用）

DDL 跟 model，把 5 张 `ecos_knowledge.*` 表的 `created_at/updated_at` 全部从 `TIMESTAMP` ALTER 成 `BIGINT`，保留 DDL 老 TIMESTAMP 列名但加新列 `created_at_b` 走 BIGINT。

**改动点**：
| # | 文件 | 改动 | 估 |
|---|------|------|----|
| A1 | `gateway/src/main/resources/db/migration/V101__ecos_kb_engintengimealign.sql` | 5 表 × (ALTER 加 `created_at_b BIGINT` / `updated_at_b BIGINT`) + INSERT 回填 + 注释 SQL（不动原 TIMESTAMP 列，铁律"schema 只加不删"） | 1 m |
| A2 | `kb-engine/.../ExpertRuleMapper.java` | 改 SQL：读 `created_at_b as createdAt, updated_at_b as updatedAt`；INSERT 改 `created_at_b=#{createdAt}, updated_at_b=#{updatedAt}` | 1 m |
| A3 | `kb-engine/.../KnowledgeNodeMapper.java` | 同上 | 1 m |
| A4 | `kb-engine/.../KnowledgeEdgeMapper.java` | 同上 | 1 m |
| A5 | `kb-engine/.../KnowledgeArticleMapper.java` | 同上 | 1 m |
| A6 | `kb-engine/.../KnowledgeEmbeddingMapper.java` | 改 `created_at_b as createdAt`，INSERT 改 `created_at_b=#{createdAt}` | 1 m |
| A7 | (no Service/impl change needed — 7 个 Service/Controller 的 `setXxx(long)` 已对齐 model long) | — | 0 m |

**优点**：保持 model 不动；不动 ai-engine（不同 module）；前端无影响。
**缺点**：每个表多 2 列（V101 幂等无副作用）。

### 路线 B — ALIGN-TO-DB

model 全改 `LocalDateTime created_at`，服务层 7 个 `setXxx(System.currentTimeMillis())` → `LocalDateTime.now()`。

- 改 7 个 model 类（含 GraphSubgraph）
- 改 7 个 Service/Controller `setXxx(now→LocalDateTime.now())`
- ai-engine 同名 entity 已经是 LocalDateTime（不改）
- **缺点**：ai-engine 已经按"A-10"对齐 DB TIMESTAMP ↔ LocalDateTime，路线 B 会破坏 cross-module 对称性，且 wave3 前端期望 long timestamp（前端 T-01 任务 2 任务单把 wave3fetch KB extra1/2/3/8 时间字段按 ISO 字符串） — 改 model 后序列化格式一变前端 i18n.toLocaleString 行为要重新审视

### 路线 C — 不修，用 PG 兼容 epoch-millis 写入 TIMESTAMP（手写 TypeHandler）

- 写个 `LongToTimestampTypeHandler` 注册到 MyBatis `type-handlers-package`
- **缺点**：绕开 ECOS 铁律"项目一致性"（架构铁律 4.1 以上无先例）、后续维护看不懂

**T-01b 选择路线 A**：原因 (1) 改动面最小 (2) 不动 model 与序列化 (3) 不动 ai-engine (4) 前端 wave3 期望 unchanged (5) 严格对齐 ECOS 作者 Wave-2C 时设的 model = long 意图。

详细 V101 SQL 与 diff 见 §5。
