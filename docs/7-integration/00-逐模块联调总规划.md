## 一、联调闭环（每模块 6 步，缺一不可）

```
① 归档上一轮      → 把上一轮指令/文档移入 archive/
② 需求文档        → 从差距分析 + 完善计划 + 历史交互提炼，功能点级别，含验收标准
③ 测试方案        → 怎么测：策略 / 环境 / 范围 / 方法（前后端一起）
④ 测试用例        → 测什么：每个功能点的步骤 + 预期结果 + 优先级
⑤ 测试执行        → dogfood(browser_exec) 前端 + curl 后端 + 前后端数据一致性
⑥ 修复            → 发现即修，每 bug 一个 commit，复验后回填测试报告
```

## 二、文件结构（每模块一个子目录，5 份文档）

```
docs/7-integration/{NN}-{module}/
├── 01-需求文档.md      # 模块定位 + 端点/页面清单 + 功能需求 + 遗留项 + stub核实
├── 02-测试方案.md      # 策略/环境/范围/方法/风险
├── 03-测试用例.md      # 用例表（编号/前置/步骤/预期/优先级）
├── 04-测试报告.md      # 执行结果（通过/失败/阻塞）+ 缺陷清单
└── 05-修复记录.md      # 每个 bug 的根因 + 修复 + commit hash + 复验
```

## 四、测试技能（前后端一起）

| 层 | 技能/工具 | 用途 |
|----|----------|------|
| 前端 | `dogfood`（browser_exec 驱动） | 导航/交互/控制台错误/截图取证，5 阶段系统 QA |
| 前端 | `ecos-frontend-debug` | HashRouter `/#/` 路径、TS 编译验证、className/import 修复经验 |
| 后端 | curl + JWT | 端点 200/响应结构/参数校验 |
| 联调 | 前端操作 → 后端响应 → DB 落库 | 数据一致性（前端显示 vs 后端返回 vs DB 实际） |

**测试执行原则**：前端用 dogfood 走完整用户流（登录→导航→CRUD→异常输入），每个交互后查控制台错误 + 后端日志 + DB；后端 curl 覆盖 dogfood 没点到的端点。前后端结果交叉验证，不一致 = bug。

## 六、归档机制

- 每轮开始前，把上一轮目录 `git mv` 到 `archive/7-integration/{NN}-{module}/`（保留历史）
