## 一、测试策略

**前后端一起联调**，三层交叉验证：前端操作 → 后端裁决 → DB/缓存落库。

security-engine 是横切能力，测试核心是**权限裁决正确性**：
- RLS apply 返回的 WHERE 子句是否正确拼出用户可见范围
- CLS columns 返回的可见列是否正确过滤敏感列
- ABAC evaluate 的 OPA 裁决是否正确
- 脱敏的 5 种策略输出是否符合预期

## 二·五、测试数据准备与清理

### 测试数据准备（测试前，ECOS-QA）

| 数据 | 准备内容 | 用途 |
|------|---------|------|
| 测试用户 | test_sec_user（普通角色，用于 RLS/CLS apply 的 userId） | TC-RLS/CLS |
| 测试角色 | test_sec_role（绑定 RLS/CLS 策略） | TC-RLS/CLS 策略绑定 |
| RLS 策略 | test_rls_policy（tenant_id 过滤规则） | TC-RLS-01~03 |
| CLS 策略 | test_cls_policy（隐藏某敏感列） | TC-CLS-01~03 |
| ABAC 策略 | test_abac_policy（OPA rego） | TC-ABAC |
| 审计基线 | 记录 ecos_audit_log 当前行数 | TC-AUDIT 写入验证 |

**命名铁律**：所有测试数据 `test_` 前缀。

### 测试数据清理（测试后）

| 清理项 | 操作 |
|--------|------|
| 策略数据 | 删除 test_rls_policy/test_cls_policy/test_abac_policy |
| 测试角色/用户 | 删除 test_sec_role/test_sec_user |
| 审计日志 | 删除测试期间产生的 audit 记录（如 test_ 标记） |

## 四、测试方法

### 4.1 后端接口（curl + JWT）

```bash
# RLS apply 验证
curl -s -X POST http://localhost:8080/api/security/rls/apply \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"tableName":"ecos_order","userId":"test_sec_user"}'
# 期望: 返回 rlsCondition（如 "tenant_id = 'xxx'"）+ params

# CLS columns 验证
curl -s -X POST http://localhost:8080/api/security/cls/columns \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"tableName":"ecos_order","userId":"test_sec_user"}'
# 期望: 返回 visibleColumns（敏感列被过滤）

# ABAC evaluate 验证
curl -s -X POST http://localhost:8080/api/v1/security/policy-engine/evaluate \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"policy":"test_abac_policy","input":{...}}'
```

### 4.2 前端 UI（dogfood / browser_exec）

SecurityCenter 3 Tab 逐个：PreventTab（策略 CRUD）→ DetectTab（策略配置）→ AuditTab（审计时间线）。每个策略 CRUD 操作后查控制台 + 后端日志。

### 4.3 裁决正确性测试（security 特有）

RLS/CLS/ABAC 不是"端点 200 就行"，是**裁决结果正确**：
- RLS：两个不同 tenant 的用户 apply 同一表，返回不同的 WHERE 条件
- CLS：普通用户 vs admin 的 visibleColumns 不同（admin 全列，普通用户敏感列被过滤）
- 脱敏：同一数据不同角色脱敏结果不同

## 五、测试优先级

| 优先级 | 范围 | 理由 |
|:---:|------|------|
| P0 | 审计写入补实现 + RLS/CLS/ABAC 裁决正确性 | 安全核心，裁决错误 = 数据泄露 |
| P1 | 脱敏 5 策略 + token 踢出 + 端点全覆盖 | 核心能力 |
| P2 | 前端 3 Tab 体验 + GuardrailsView | UI 验证 |
| P3 | 死代码清理 + stub 核实 | 收尾 |

## 六、风险与约束

- **OPA 依赖**：PolicyEngine 依赖 localhost:8181 OPA，不可达则 evaluate 500，先确认 OPA 在线
- **裁决正确性难自动验证**：RLS/CLS 需要构造多租户/多角色数据对比，比 CRUD 测试复杂
- **审计写入是新补端点**：补实现时注意异步写不阻塞调用方 + 不破坏已有 GET 端点
- **死代码清理**：git rm 前 grep 确认零引用（datapermission 旧 impl 实现的是 sysman 接口，可能 sysman 侧还有引用）
