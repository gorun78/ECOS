## 一、测试策略

**前后端一起联调**，不是分开测。核心原则：前端操作 → 后端响应 → DB 落库，三层交叉验证，任何一层不一致 = bug。

测试分三层：
1. **后端接口层**：curl + JWT，验证端点 200 + 响应结构 + 参数校验（覆盖 dogfood 点不到的端点）
2. **前端 UI 层**：dogfood（browser_exec 驱动）走完整用户流，每个交互后查控制台错误 + 后端日志
3. **数据一致性层**：前端显示值 vs 后端返回 vs DB 实际值，三者比对

## 二·五、测试数据准备与清理（本轮新增）

### 测试数据准备（测试前，ECOS-QA 负责）

| 数据 | 准备内容 | 用途 |
|------|---------|------|
| 测试用户 | test_user_01（普通角色）/ test_user_02（预置锁定）/ test_user_03（强制改密=true）/ test_user_04（密码过期） | TC-USER-02~12、TC-AUTH-04/06 |
| 测试角色 | 确认 5 内置角色存在；创建 test_role | TC-ROLE-01/02 |
| 测试配置 | 记录 session_timeout/password_min_length 等关键配置当前值（测试后恢复） | TC-CONFIG-03/05 |
| 测试租户 | 创建 test_tenant（配额已知值） | TC-TENANT-01 |
| 测试字典 | 创建 test_dict_type + test_dict_item | TC-DICT-01 |

**命名铁律**：所有测试数据统一 `test_` 前缀，便于清理时精准删除，不误删真实数据。

### 测试数据清理（测试后，必须执行）

| 清理项 | 操作 |
|--------|------|
| 测试数据 | 删除所有 `test_` 前缀的用户/角色/租户/字典 |
| 被改配置 | 恢复 session_timeout 等配置为测试前记录值 |
| admin 解锁 | 若 TC-AUTH-03 锁定了 admin，清 locked_until/failed_attempts |
| CSV 导入数据 | 删除 CSV 导入产生的用户 |

**清理验收**：`SELECT COUNT(*) FROM users WHERE username LIKE 'test_%'` = 0；关键配置恢复原值；admin 可正常登录。

## 四、测试方法

### 4.1 后端接口测试（curl）

```bash
# 登录拿 token
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}' \
  | python3 -c "import sys,json;d=json.load(sys.stdin);print(d.get('data',{}).get('token','') or d.get('token',''))")

# 每 Controller 关键端点验证
curl -s -H "Authorization: Bearer $TOKEN" "http://localhost:8080/api/v1/system/users?page=1&size=20"
```

每个端点记录：200/500/404/401 → 响应摘要 → 与预期比对。

### 4.2 前端 UI 测试（dogfood / browser_exec）

按 dogfood 5 阶段：Plan（建测试范围）→ Explore（导航+快照+控制台）→ Collect（截图取证）→ Categorize（分级）→ Report（报告）。

重点：每个交互后查 `console` 错误；测正常 + 异常输入（表单验证）；测空状态；测多步流程端到端。

### 4.3 数据一致性测试

前端操作后，用 curl 查后端 + `docker exec ecos-postgres psql` 查 DB，三者比对：
- 前端显示"创建用户成功" → 后端 users 表有记录 → DB 有记录
- 前端显示"删除成功" → DB 记录消失（或软删标记）

## 五、测试优先级

| 优先级 | 范围 | 理由 |
|:---:|------|------|
| P0 | 登录安全 L1-L4 + 认证链路 | 地基中的地基，锁死则全崩 |
| P1 | 用户 U1-U8 + 配置 C1-C6 + 角色 R1-R2 | 核心 CRUD 功能 |
| P2 | 遗留体验项（i18n/样式/响应式/骨架屏/toast/确认弹窗） | 打磨项，不阻塞 |
| P3 | stub 核实 + 边缘情况 | 收尾 |

## 六、风险与约束

- **前端服务未启动**：测试前必须先 `npm run dev`，否则 dogfood 无目标
- **E2 下沉回归风险**：8 个下沉 Controller 的 SQL 语义可能漂移，重点复验 EntityTableMapping（动态 SQL）
- **DB 直查需 docker**：WSL 无 docker CLI，DB 比对需在 Windows 侧执行或通过后端端点间接验证
- **登录锁定副作用**：测 L1 会锁 admin 账户，测完需解锁（DB 改 locked_until 或等 15 分钟），避免影响后续用例
- **测试数据污染**：CSV 导入/批量操作会造测试数据，测完清理
