# 本体提案系统需求细化（ontology_proposals）

> 来源：肖国荣 | 日期：2026-08-26
> 关联：[01-需求文档.md](./01-需求文档.md) §三 F1「提案系统持久化 + 提案-版本打通」的深化
> 用途：下一轮 PMO（PMO-33）的需求输入；本文发现的 H1-H6 硬伤超出 PMO-32（仅测提案表缺失 + 端到端验收）范围
> 定位：本体（Ontology）治理的唯一变更入口——本体结构的每一次改动必须走提案，不允许裸改。
> 现状基线：PMO-28 已交付（表 + 状态机 + 版本联动雏形），Controller 已从内存下沉 PG。
> 本文把"能存能转状态"细化为"真正能做本体治理"的需求，作为后续 PMO 指令的依据。

## 一、现状盘点：已实现 vs 名义上有但实际是空壳

| 能力 | 现状 | 判定 |
|------|------|:---:|
| 提案 CRUD + 状态机 | DRAFT→PENDING→APPROVED/REJECTED→EXECUTED | ✅ 真 |
| 6 种 proposal_type 声明 | CREATE_ENTITY / ADD_PROPERTY / MODIFY_PROPERTY / DELETE_ENTITY / ADD_RELATIONSHIP / CREATE_FUNCTION | ⚠️ 名存实亡（见下） |
| 执行器 executePayload | 只实现 3 种半，其余 no-op | 🔴 硬伤 |
| verify 校验 | 只查字段存在性，不改状态机语义 | 🔴 太弱 |
| 回滚 snapshot | 字段存在，但无人写入、无回滚端点 | 🔴 空壳 |
| approve-and-publish 版本联动 | 顺序颠倒、回填字段错位 | 🔴 数据正确性 bug |

### 硬伤逐条（已核实源码）

**H1 — 执行器只有 3 种半，2 种是 no-op，1 种是错的**

`executePayload` 的 switch：
- `CREATE_ENTITY` → `createEntity` ✅
- `ADD_PROPERTY` → `createProperty` ✅
- `MODIFY_PROPERTY` → `createProperty` ❌ **语义错误**——修改属性走了创建，应走 `updateProperty`，且 updateProperty 需要的是 `propertyId` 不是 `entityId`
- `ADD_RELATIONSHIP` → `createRelationship` ✅
- `DELETE_ENTITY` → default 分支 no-op ❌ 什么都没做，`OntologyService.deleteEntity`（含级联删）根本没人调
- `CREATE_FUNCTION` → default 分支 no-op ❌ Function 沙箱引擎已落地（FunctionSandboxEngine/FunctionValidator/FunctionController 均在，PMO-29 交付），但 executePayload 没接它，此类型在提案执行里是死路

**H2 — 状态机被 verify/execute 塞进了非规范状态**

表注释状态集是 `DRAFT/PENDING/APPROVED/REJECTED/EXECUTED`，但：
- `verify` 把状态改成小写 `verified`
- `execute` 把状态改成小写 `executed`
- 结果状态字段出现 `verified`/`executed` 这种状态机里不存在的值，`TERMINAL_STATUSES` 集合（APPROVED/REJECTED/EXECUTED）既不含 `verified`，也无法解释 `executed` 的合法性。状态机已经乱了。

**H3 — approve-and-publish 版本快照拍在变更前**

当前顺序：`createVersion`（先生成 snapshot）→ `executePayload`（改本体）→ `publishVersion`。
`createVersion` 的 `generateSnapshot` 拍的是**变更前**的本体状态，然后这个"旧快照"被 publish。结果：发布出去的版本 snapshot 不代表本体实际当前状态——顺序反了。正确顺序应是：先执行 payload 改本体 → 再拍快照 → 再发布。

**H4 — version_id 回填的是版本号不是版本 ID**

`approve-and-publish` 里 `version.get("versionNo")`（如 `1.0.1`）被强转成 Long 回填到 `version_id` 字段。但 `version_id` 的语义是"关联版本记录"，应是 version 的 `id`（`ver5001`）。版本号和版本 ID 混淆，导致提案无法反查版本记录。

**H5 — snapshot 回滚是空壳**

`snapshot` 字段在 `createProposal` 时靠调用方手动传，`executePayload` 执行时**不自动记录变更前快照**。没有 rollback 端点，没有任何逻辑消费 snapshot。PMO-28 写的"回滚支持"实际没落地。

**H6 — proposal_type 集合不对称**

只有 `DELETE_ENTITY`，没有 `DELETE_PROPERTY` / `DELETE_RELATIONSHIP`；没有 `MODIFY_ENTITY`。本体治理要覆盖完整 CRUD，类型集不对称导致"删属性/删关系/改实体"这些高频操作无法走提案，被迫绕开提案裸改——正好违背"唯一变更入口"的初衷。

## 二、需求细化（按优先级）

### P0 — 让提案系统"真能用起来"

#### R1. 状态机规范化

- 状态集严格收敛为 5 态：`DRAFT / PENDING / APPROVED / REJECTED / EXECUTED`，大写，DB 加 CHECK 约束。
- `verify` **不再是状态，改为动作**：校验并返回 `{valid, issues[]}`，不写 status。
- `approve` 内部强制先跑 verify，不过则 400 拒绝（verify 降级为 approve 的前置守卫，而非独立环节）。
- `execute` 语义统一为"执行 payload + 状态 → EXECUTED"（真正的执行入口），不再只改状态。
- 新增独立审计时间戳：`submitted_at / approved_at / rejected_at / executed_at`（V4.x migration 加列）。

**验收**：任意合法流转后，`status` 值只可能是 5 态之一；`SELECT DISTINCT status` 无 `verified`/`executed` 小写值。

#### R2. 执行器补全（9 种类型全覆盖）

| proposal_type | 执行器 | 现状 |
|---------------|--------|:---:|
| CREATE_ENTITY | `ontologyService.createEntity` | ✅ |
| MODIFY_ENTITY | `ontologyService.updateEntity` | 🔴 新增 |
| DELETE_ENTITY | `ontologyService.deleteEntity`（级联）+ 影响检查 | 🔴 补 |
| ADD_PROPERTY | `ontologyService.createProperty` | ✅ |
| MODIFY_PROPERTY | `ontologyService.updateProperty`（传 propertyId） | 🔴 修 |
| DELETE_PROPERTY | `ontologyService.deleteProperty` | 🔴 新增 |
| ADD_RELATIONSHIP | `ontologyService.createRelationship` + 环检测 | 🟡 补环检测 |
| DELETE_RELATIONSHIP | `ontologyService.deleteRelationship` | 🔴 新增 |
| CREATE_FUNCTION | `createProperty`（functionType=EXPRESSION）+ FunctionValidator 校验表达式 | 🔴 补 |

**验收**：9 种类型各跑一条 curl，断言本体表（entity/property/relationship）真实变化，不再出现 no-op。

#### R3. 版本联动修正（数据正确性）

- 顺序修正：`executePayload` → `createVersion`（拍变更后快照）→ `publishVersion`。
- `version_id` 回填 version 的 `id`，不是 `versionNo`；version 的 `changeLog` 带上 `proposalId` 便于反查。
- 全程 `@Transactional`：执行/建版本/发布任一失败，提案与本体一起回滚，不留半执行态。

**验收**：approve-and-publish 后，该版本 `snapshot` 与本体当前状态一致；`version_id` 指向 `ver*` 记录且 `SELECT * FROM ecos_ontology_versions WHERE id=<version_id>` 能查到。

### P1 — 治理闭环

#### R4. 自动快照 + 回滚

- `executePayload` 执行前，按 target 自动抓取变更前状态写入 `snapshot`（不再依赖调用方手动传）。
- 新增 `POST /api/v1/ontology/proposals/{id}/rollback`：基于 snapshot 恢复，回滚本身直接执行 + 写审计（紧急操作，不再走提案）。

**验收**：执行 CREATE_ENTITY 后 rollback，实体消失且恢复原状；snapshot 字段非空。

#### R5. verify 语义升级（从"字段存在性"到"本体语义校验"）

verify 校验项（全过才 valid）：
1. **引用完整性**：`entityId`/`propertyId`/`relationshipId` 必须存在；`ADD_PROPERTY` 的目标实体存在。
2. **唯一性冲突**：`CREATE_ENTITY` 的 code 在 domain 内不重复；`ADD_PROPERTY` 的 code 在该实体下不重复。
3. **关系环检测**：`ADD_RELATIONSHIP` 调用 `OntologyService.validateRelationship` 的 DFS，成环则 issue。
4. **属性类型合法性**：`propertyType` 在 `STRING/NUMBER/BOOLEAN/DATE/DATETIME/REFERENCE/EXPRESSION` 白名单内。
5. **级联影响**：`DELETE_ENTITY` 返回将级联删除的属性/关系/action 数量 + 引用它的对象实例数。

**验收**：构造一个"引用不存在实体的 ADD_PROPERTY"，verify 返回 `valid=false` + issue 明确。

#### R6. 事务 + 审批时重新校验

- 提案从 PENDING 进入 approve 时，基于**当前**本体状态重新跑 verify（防止审批期间本体又被别的提案改了）。
- 执行走 `@Transactional`，失败整体回滚。

---

### P2 — 进阶（可延后，避免过度设计）

#### R7. 影响分析 / 变更传播

- DELETE/MODIFY 执行前返回影响范围（下游引用、Function 依赖）。
- 本体变更后触发：kb-engine KG 同步（`graph/sync`）、Function 缓存失效（P0-2 引擎就绪后）。

#### R8. 并发冲突检测

- 同一 domain 内，两个 PENDING/APPROVED 提案若 target 重叠，approve 时告警或阻塞。

#### R9. 审计时间戳独立字段

- 与 R1 合并：`submitted_at / approved_at / rejected_at / executed_at` 独立列，审批/执行轨迹可查。

## 三、payload 契约（细化交付物）

每种 proposal_type 的 payload 必填/可选字段，作为前端表单 + 后端校验的唯一依据：

| proposal_type | 必填 | 可选 |
|---------------|------|------|
| CREATE_ENTITY | code, name | description, entityType(默认 MASTER) |
| MODIFY_ENTITY | entityId | code, name, description, entityType |
| DELETE_ENTITY | entityId | cascade(默认 true) |
| ADD_PROPERTY | entityId, code, name, propertyType | requiredFlag, uniqueFlag, searchableFlag, enumValues, defaultValue, validationRule, refEntityCode, maxLength, minValue, maxValue, functionType, functionExpression |
| MODIFY_PROPERTY | propertyId | 同 ADD_PROPERTY 全部可选 |
| DELETE_PROPERTY | propertyId | — |
| ADD_RELATIONSHIP | sourceEntityId, targetEntityId, code | relationshipType(默认 ONE_TO_MANY), name |
| DELETE_RELATIONSHIP | relationshipId | — |
| CREATE_FUNCTION | entityId, code, name, functionType=EXPRESSION, functionExpression | description |

> 注：`target_entity` 列降级为冗余快照（兼容旧数据），真正的定位字段以 payload 内的 `entityId`/`propertyId`/`relationshipId` 为准。

## 四、优先级推荐（老炮判断）

1. **先做 R1 + R2 + R3**（约 2 天）——这三项是"提案系统能不能真用"的地基，且 R3 是数据正确性 bug，不修就是错的。
2. **再做 R4 + R5 + R6**（约 1.5 天）——治理闭环，提案才从"记录器"变成"守门人"。
3. **R7/R8/R9 挂起**——等 Function 沙箱端到端验证通过（PMO-32 T2）、多版本分支模型（P2）就绪后再做，避免空依赖。

**一句话**：现在的提案系统是个"能存状态的状态机"，还不是"唯一变更入口"。缺的不是表，是**执行器的完整性 + 校验的语义性 + 版本联动的正确性**。先把这三块补齐，提案才配得上"本体治理核心"这个定位。
