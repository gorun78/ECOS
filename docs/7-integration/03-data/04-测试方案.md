# Phase 3 测试方案：data-engine 数据引擎联调

> 配套 `01-需求文档.md` | 2026-08-24

---

## 一、测试策略

**前后端一起联调，不以"后端端点 200"为通过标准。**

三层交叉验证：
1. **前端 dogfood**（browser_exec）走完整用户流，每个交互后查控制台错误 + 后端日志 + DB 落库
2. **后端 curl + JWT** 覆盖 dogfood 没点到的端点
3. **数据一致性**：前端显示 vs 后端返回 vs DB 实际，三者一致才算过

**验收铁律**：DQ 巡检要看到 `ecos_quality_evaluation` 真实落库；Pipeline 要看到 run 状态 QUEUED→RUNNING→COMPLETED 流转；血缘要看到 JSqlParser 解析出的真实 nodes/edges（非空）。

## 四、测试方法

### 4.1 前端 dogfood 流程

```
登录 → 数据工作台 → 数据源接入（填 PG 连接 → 测试）→ 元数据采集
→ 数据目录（看表/字段）→ 血缘（选表看 DAG）→ DQ（建规则 → 评估）
→ Pipeline（建 2 节点 → run → 看状态）→ 控制台查错
```

### 4.2 后端 curl 覆盖

dogfood 没点到的端点（如 SchemaChange、DataLayer、UDF convert、Copilot）用 curl 逐个验证。

### 4.3 前后端数据一致性

- 数据源：前端列表 == curl /datanet/datasource == td_datasource 表
- DQ 规则：前端建的规则 == curl /quality == ecos_quality_rule 表
- Pipeline：前端 run 后 == curl /runs/{runId} == ecos_pipeline_run 表

## 五、风险清单

| 风险 | 影响 | 缓解 |
|------|------|------|
| B3 路径不一致 | 前端 datasource/metadata/catalog 全 404 | 先确认 Gateway 重写规则，再决定改后端还是网关 |
| B1 DQ 表名 | 定时巡检空转 | 修复后造数据验证落库 |
| B4 血缘端点 | 前端血缘页 404 | 补根路径端点 |
| Pipeline 异步线程 | 状态不回流 | 验证 ecos_pipeline_run 状态更新 |
| 两套 Pipeline 表 | 混淆 | 明确前端对接 task/run/step 那套 |
| Neo4j 依赖（企业版） | 血缘/KG 功能 | 标准版不测 Neo4j 相关 |

---

## 六、测试数据准备与清理

- **准备**：造 1 个 PG 数据源（连 sys_man 库）、2 条 DQ 规则（NOT_NULL + UNIQUE）、1 个 2 节点 Pipeline
- **清理**：测试后删除测试数据源/规则/Pipeline，不留脏数据
- **注意**：SchemaChangeDetector 每小时跑，会对比 information_schema 写 schema_changes——测试期间注意别污染
