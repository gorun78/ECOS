## 二、P0 差距详解（本轮必实现）

### P0-1 B3 路径不一致

- **现状**：5 个 Controller `@RequestMapping("/datanet/xxx")`（无 `/api/v1`），前端调 `/api/v1/datanet/xxx`，VersionPrefixRewriteFilter 无 datanet 映射 → 必 404。
- **目标**：后端 5 个 Controller 前缀加 `/api/v1`，对齐前端已定路径。
- **实现动作**：改 5 个 Controller 的 `@RequestMapping`：
  - DataSourceController `/datanet/datasource` → `/api/v1/datanet/datasource`
  - CatalogController `/datanet/catalog` → `/api/v1/datanet/catalog`
  - MetadataController `/datanet/metadata` → `/api/v1/datanet/metadata`
  - CategoryController `/datanet/category` → `/api/v1/datanet/category`
  - DatanetHealthController `/datanet` → `/api/v1/datanet`

### P0-2 B4 血缘根路径端点缺失

- **现状**：DataLineageController 只有 `/pipeline/{taskId}` `/nodes` `/edges` `/build`，前端调 `GET /lineage?datasourceId&tableName` 无映射。`DataLineageService.getLineage(datasourceId, tableName)` 方法已存在（380 行文件核心方法），只是没暴露。
- **目标**：补根路径 `@GetMapping`，透传参数调 getLineage()。
- **实现动作**：DataLineageController 加 `@GetMapping`（根路径）+ `@RequestParam datasourceId/tableName` → `dataLineageService.getLineage(...)`。

### P0-3 B1+B2 DQ 定时巡检表名 + 逻辑

- **B1 现状**：DqScheduledTask 查 `SELECT id,name,rule_type,config_json FROM dq_rules WHERE status='ENABLED'`，真实表 `ecos_quality_rule`（rule_id/rule_name/rule_type/parameters/enabled）→ 永远查 0 条，巡检空转。
- **B2 现状**：遍历 rules，每条都调 `qualityService.evaluateAll()`（内部已遍历全部 enabled 规则）→ N 条规则执行 N 次全量。
- **目标**：查 `ecos_quality_rule` 字段对齐，改成一次 evaluateAll()。
- **实现动作**：改 DqScheduledTask 的 SQL + 删 per-rule 循环。

### P0-4 B9a Pipeline 执行入任务中心

- **现状**：`PipelineTaskServiceImpl.triggerRun` 用 `new Thread(() -> executionEngine.execute(runId), ...).start()`。
- **目标**：走 runtime-task `submitAndExecute`（异步执行），删裸线程。
- **实现动作**：triggerRun 构造 TaskDescription（taskType=PIPELINE_EXECUTION, async=true）→ `taskManagementService.submitAndExecute(...)`。注意 runtime-task 的 executor 类型要能识别 PIPELINE_EXECUTION。

## 三、P1 差距详解（本轮实现）

### P1-1 B6 分类管理真缺口

- **现状**：StubCategoryService 48 行全 no-op（create/update/getById/getTree/getChildren/remove/getCategoryStats 全 return null/empty），无 `td_data_category` 表。
- **目标**：建表 + 真实 CRUD。
- **实现动作**：① 迁移 SQL 建 `td_data_category` 表 ② 重写 StubCategoryService 为真实 JdbcTemplate 实现（或改名 CategoryServiceImpl）。

### P1-2 B7 DQ 规则类型

- **现状**：QualityServiceImpl.evaluateValue 里 `case "UNIQUE": return true;` `case "CUSTOM": return true;` 硬编码放行。
- **目标**：UNIQUE 用 GROUP BY+HAVING 检测重复；CUSTOM 支持自定义表达式。
- **实现动作**：改 evaluateValue 的两个 case。

### P1-3 B8 Pipeline 节点真实化

- **现状**：executeSourceJdbc 用系统 JdbcTemplate 执行（未连外部数据源）；executeTransformSql 返回 `jdbc.update("SELECT 1")` 占位。
- **目标**：executeSourceJdbc 走 ConnectorFactory 拿外部源；executeTransformSql 返回真实影响行数。
- **实现动作**：改 PipelineExecutionService 两个方法。

### P1-4 B5 双系统梳理

- **现状**：PipelineController `/api/v1/pipeline`（def/exec 表）+ PipelineTaskController `/api/v1/engine/data/pipeline`（task/run/step 表）。
- **目标**：确认 `/api/v1/pipeline` 是否有前端消费。
- **实现动作**：grep 前端 + 后端引用，输出结论（死代码 or 保留）。

## 四、P2 差距（本轮出方案/规范，不实现）

| 项 | 现状 | 本轮产出 |
|----|------|---------|
| Pipeline YAML Schema | 无规范，节点类型散落各 Service | `docs/7-integration/03-data/P2-01-Pipeline-Schema规范.md` |
| CDC | 无 FlinkCdcConnector | `docs/7-integration/03-data/P2-02-CDC接入设计.md` |
| 安全对接 | 凭据/访问/脱敏/审计未接线 | 对接点清单（补进需求文档 6.4） |
| B9b cron 统一 | runtime-task `parseCronToDelay` 占位返回 60000 | 修复方案（换 Quartz CronExpression + DQ/Schema 定时统一走 runtime-task） |

**关键发现（B9b）**：runtime-task 的 `TaskSchedulerServiceImpl.parseCronToDelay()` 是占位实现——所有 cron 表达式都返回固定 60000ms（1 分钟），所以 DqScheduledTask/SchemaChangeDetector 才用"双重调度"（runtime-task 注册可见性 + Spring @Scheduled 真触发）。要让定时任务真正统一走 runtime-task，必须先修 runtime 层的 cron 解析，这是跨模块改动，本轮出方案、下轮实现。
