## 一、模块定位与目标场景

**data-engine = 数据引擎，DIKW 的 D 层（Data）。是企业经营管控平台的数据底座。**

**目标场景**：企业环境（老板 + 数据工程师），接入企业 ERP / CRM / 财务 / 业务系统的数据，为上层 DIKW（本体建模、知识图谱、认知推理）供数。

**边界**：只做"数据接入 → 清洗转换 → 入湖 → 目录/血缘/质量"，不碰本体建模（ontology）和推理（cognitive）。

---

## 二、数据接入类型（功能完整性）

企业环境数据源，四类接入，按需分层：

| 接入类型 | 具体来源 | 实现载体 | 版本 |
|---------|---------|---------|:--:|
| **关系型数据库** | MySQL / PG / Oracle / SQLServer / 达梦 / 金仓（6 种，决策已定保留） | runtime-access `JdbcConnector`（已有） | 全版本 |
| **文件** | CSV / Excel（业务导出、手工台账） | runtime-access `CsvConnector`（已有） | 全版本 |
| **API** | 第三方 SaaS / 内部系统 REST（钉钉、用友、泛微等） | runtime-access `RestApiConnector`（已有） | 全版本 |
| **实时 CDC** | ERP/业务库 binlog 变更流（订单、库存、流水） | **新增 Flink CDC**（javaprojects 已有 flink-cdc 资产） | 仅 flagship |

**决策**：数据接入类型 = JDBC + 文件 + REST + CDC 四类，前三种已落地，CDC 是 flagship 增量能力。

---

## 三、数据接入及时性（批流双轨）

| 时效 | 机制 | 场景 | 版本 |
|------|------|------|:--:|
| **批处理（全量）** | JDBC 分页全量抽取，定时调度 | 初始化、日更 | 全版本 |
| **批处理（增量）** | 时间戳 / 主键增量抽取（`WHERE updated_at > last_sync`） | 日更、小时更 | 全版本 |
| **实时（CDC）** | Flink CDC 订阅 binlog，实时入湖 | 订单/库存/流水秒级同步 | 仅 flagship |

**决策**：及时性分三级——全量 / 增量 / 实时。standard/enterprise 走「全量 + 增量」，flagship 加「CDC 实时」。CDC 不进 standard，避免把 Flink 集群的运维成本摊给所有客户（第 8 点版本差异）。

## 六、ETL 架构需求（12 维度，新增）

### 6.1 数据接入（类型 + 及时性）

- 类型四类见第二节；及时性三级见第三节。
- **CDC 落地方案**：flagship 引入 Flink CDC，作为 `FlinkCdcConnector` 注册进 runtime-access 的 ConnectorFactory（动态类型扩展），不另起炉灶。

### 6.2 Pipeline 定义规范（可调试/可监控/可版本管理的地基）

**制定 Pipeline YAML Schema 规范**，参考 Kettle 的 step 模型 + Foundry Pipeline Builder：

```yaml
pipeline:
  id: pipeline-001
  name: 订单入湖
  version: "1.0.0"            # git 版本管理（第 6.12 点）
  schedule: { cron: "0 2 * * ?" }   # 统一走 runtime-task
  nodes:
    - id: source_order
      type: SOURCE_JDBC       # SOURCE_JDBC/SOURCE_CSV/SOURCE_REST/SOURCE_CDC/TRANSFORM_SQL/OUTPUT_OBJECT
      config: { datasourceId, sql, fetchSize }
    - id: transform_clean
      type: TRANSFORM_SQL
      config: { sql }
      dependsOn: [source_order]
    - id: sink_doris
      type: OUTPUT_OBJECT
      config: { targetTable, mode: append|overwrite }
      dependsOn: [transform_clean]
```

- 节点类型枚举 = 四类 SOURCE + TRANSFORM + OUTPUT，可扩展。
- **可调试**：节点级试运行（单节点 preview）+ 逐步执行（execute step by step）。
- **可监控**：每个节点执行状态/耗时/行数接入 runtime-monitor。

### 6.3 高效性（大数据量抽取转换）

- **参考 Kettle**：流式 row-by-row 处理，不把全量数据加载进内存。
- JDBC 分页抽取（fetchSize）+ 批量写入（batch insert）。
- 转换层用 runtime-access 的 `DuckDBQueryService` 做内存 OLAP 加速（中小数据量）。
- 大表 LIMIT + 30s 超时 + 并行度配置（引擎配置参数）。

### 6.4 安全性（与 security-engine 对接）

| 环节 | 对接方式 |
|------|---------|
| 数据源凭据 | runtime-crypto 加密存储，明码不入库 |
| 访问控制 | 数据源/管道的访问走 security-engine 准入等级 + ABAC |
| 查询脱敏 | QueryController 结果脱敏走 security-engine 脱敏能力（email/phone/idCard） |
| 操作审计 | Pipeline 执行/DQ 操作/DQ 巡检走 security-engine 审计 |

**禁止**：data-engine 自建一套权限/脱敏/审计，全部调 security-engine。

### 6.5 充分依赖 runtime（架构铁律 2.2 落地）

| data-engine 能力 | 依赖 runtime 模块 |
|-----------------|------------------|
| 数据接入 | runtime-access `ConnectorFactory`（JDBC/CSV/REST/CDC） |
| git 版本管理 | runtime-access `GitService`（JGit） |
| OLAP 加速 | runtime-access `DuckDBQueryService` |
| 对象存储 | runtime-access `MinioStorageService`（大文件/中间结果） |
| 任务调度 | runtime-task `TaskSchedulerService`（统一） |
| 监控告警 | runtime-monitor |
| 凭据加密 | runtime-crypto |

**铁律**：PG/Neo4j/MinIO/Doris/Git 的 Driver/Client 封装只准走 runtime-access，data-engine 不直接 new 连接。

### 6.6 参考现有方案（不重复造轮子）

| 组件 | 借鉴点 | 不借鉴 |
|------|--------|--------|
| **Kettle**（pentaho-kettle，javaprojects 资产） | step/transform 模型、流式处理、作业调度、transformation 元数据 | 直接嵌入 Kettle 引擎（太重） |
| **Foundry**（文档已镜像 /mnt/d/workspace/foundry/） | Data Connection、Pipeline Builder 的 YAML 定义、Incremental 语义 | Ontology（那是 ontology-engine） |
| **Semantica** | 全链路溯源（血缘的 provenance 升级）、双时态 | 决策管理（那是 cognitive-engine） |

### 6.7 版本差异（基础设施裁剪）

| 能力 | standard | enterprise | flagship |
|------|:--:|:--:|:--:|
| JDBC(6种)/CSV/REST | ✅ | ✅ | ✅ |
| 全量+增量批处理 | ✅ | ✅ | ✅ |
| 血缘（内存解析） | ✅ | ✅ | ✅ |
| 血缘图谱落 Neo4j | — | ✅ | ✅ |
| Doris 大数据 OLAP | — | — | ✅ |
| Flink CDC 实时 | — | — | ✅ |

**铁律**：业务代码不写 `if (edition)`，用 Maven profile + `@ConditionalOnProperty` 裁剪（三版本发布体系）。

### 6.8 可配置性（引擎配置参数）

配置三层（对齐 AI 引擎配置分层）：
- **L1** `application.yml`：默认连接池、fetchSize、超时、并行度
- **L2** 引擎配置表（DataEngineConfigController 已有）：运行时可改
- **L3** Pipeline 任务级覆盖：单个 Pipeline 覆盖全局默认

### 6.9 异步任务中心统一（第 10 点核心）

**废除各自为政的 new Thread + @Scheduled，全部走 runtime-task：**

| 任务 | 现状 | 目标 |
|------|------|------|
| DQ 巡检 | DqScheduledTask 自建 @Scheduled + ExecutorService | 注册 runtime-task，`TaskSchedulerService.scheduleTask` |
| Schema 检测 | SchemaChangeDetector @Scheduled | 同上 |
| Pipeline 执行 | triggerRun 里 `new Thread(...)` | 提交 runtime-task 执行队列，状态回调 |
| Pipeline 定时 | PipelineScheduler 自建 cron 解析 | 走 runtime-task 的 cron |
| CDC 同步 | 无 | flagsight 的 CDC job 注册 runtime-task |

runtime-task 已有完整能力（调度/执行/解析/持久化/监控/统计/日志/回调），data-engine 直接消费，不重复实现。

### 6.10 Pipeline 版本管理（第 12 点）

- PipelineGitService 已有 commit/pull/load/branches（基于 runtime-access GitService）。
- 强化：Pipeline 定义 = YAML 文件存 git 仓库 `pipelines/{id}/pipeline.yaml`，git 管理版本 + 回滚 + 分支。
- 前端 GitCommitDialog 已有，补「版本历史/回滚」展示。
