## 1. 规划目标

| # | 目标 | 落点 |
|:--|------|------|
| G1 | 多源异构数据源同步到数据湖，形成**近源层** | 数据源同步 → 采集型管道 → MinIO 近源区 |
| G2 | 数据管道与数据质量**基于近源层**处理，形成 **DW 层** | 管道读近源区，产出落 DW 层表 |
| G3 | 本体与知识**从 DW 层**取数 | 本体自动发现 / 知识抽取面向 DW 层表 |
| G4 | 引擎配置项按分层**重组** | 引擎配置面板由 7 组重构为 4 段，后端提供分段端点 |

> 分层口径（层名 / zone / 对象 key）以 `.trae/rules/数据湖存储分层规范.md` 为准，本文件不重复定义。

### 2.1 分层：有骨架、无闭环

### 2.2 数据湖：原本只有「写」没有「读」

| 事实 | 状态 |

### 2.3 数据质量：空转评分壳

`DqScheduleServiceImpl.buildContext()` 中 `connectionConfig = 空 Map`、`totalRows = 0`、`failedRows = 0` —— **不实际取数**，只产出评分壳。（P3）

### 2.4 `dw.lake.*` 是死配置

`dw.lake.enabled` / `storage_format` / `partition_by` / `retention_days` / `datasource_id` 在后端仅有 3 处**定义**（`SysConfigService` 种子、`DataEngineConfigController.DEFAULTS`、`V41` 迁移），**无任何业务代码读取**。

## 3. 数据流设计

```
① 采集链（G1）
   外部数据源(SOURCE) ──SOURCE_JDBC→SINK_MINIO──▶ MinIO raw/structured/{source}/{table}/dt=… (RAW)
   状态：✅ 已打通（key 带 zone+分区；登记 td_data_resource: layer=RAW / zone=STRUCTURED）

② 加工链（G2）
   MinIO raw/structured (RAW) ──数据管道──▶ DW 层表 (CURATED)
   状态：❌ 缺 SOURCE_MINIO → 管道无法读湖（P2 关键缺口）；本次仅保证 SINK/OUTPUT_OBJECT 产出标记 layer=CURATED

③ 质量链（G2）
   DW 层表 (CURATED) ──数据质量规则──▶ 评分/告警
   状态：⚠️ 规则/状态机/告警已具备，但 buildContext 空转不取数（P3）

④ 语义链（G3）
   DW 层表 (CURATED) ──本体自动发现/建模──▶ 本体(SEMANTIC) ──KbEngineGraphSyncClient──▶ 知识(K)
   状态：⚠️ 通道已通（POST :18086/api/v1/kb/graph/sync），但自动发现源是「数据源元数据」而非 DW 表（P3）
```

## 4. 引擎配置项 4 段重组

### 4.1 结构：4 段 × 16 子分区 × 68 项

| 段 id | 段名 | 子分区（项数） | 合计 |
|:--|:--|:--|:--:|
| `near-source` | 近源层 | `lake`(5) `storage`(7) `sync`(2) `datasource`(2) | **16** |
| `dw` | DW 层 | `execution`(9) `pipeline`(7) `pipeline-advanced`(12) `quality`(6) `lineage`(5) `query`(2) `cache`(1) `catalog`(1) `metadata`(2) | **45** |
| `semantic` | 语义层 | —（占位空态，配置归本体工作台） | **0** |
| `global` | 全局 | `engine`(1) `notify`(1) `copilot`(5) | **7** |
| | | | **68** |

### 4.2 实现方式（零配置迁移）

- **不改任何 `config_key`**：仅改分组归属与 UI 呈现，无 `sys_config` 数据迁移。
- 后端 `GET /api/v1/engine/data/settings/groups` 为**分层归属唯一真相源**，返回
  `{ segments: [{ id, subgroups: [{ id, configs: {完整 key: 值} }] }] }`；
  旧 `GET /settings`（子组视图）与前端旧拼键逻辑保持原样，互不影响。
- 前端 `buildItemMeta()` 只保留 68 项的**类型元数据**（控件类型 / 默认值 / 枚举 / Doris 灰显），
  分组结构完全由后端决定，消除双真相源。
- 补齐原先 UI 不可见的 **22 项**（pipeline-advanced 12 + notify 1 + copilot 5 + datasource 2 + catalog 1 + metadata 1），
  68 项全可见、可编辑。
- 顺带修复：`GET /settings/defaults` 返回扁平 Map 但旧解析按两层嵌套遍历 → 结果恒 `{}`，
  默认值实际全来自前端字面量。现已改为扁平解析。
