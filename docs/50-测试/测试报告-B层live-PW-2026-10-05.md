## 3. 红色根因分诊（保留红色，不改断言）

### 3.1 共同前端症状
gateway :8080 对上述 24 例统一回 `HTTP 404` + `{"code":404,"message":"端点暂未开放或服务未就绪，请稍后重试或联系管理员"}`。
实测对照（同 token，16:34）：`GET /api/v1/pipeline/definitions`→200、`POST /api/v1/knowledge/rag/rag`→200，而 `/api/v1/workspace/backtests/preview`、`/api/v1/wagent/runs`、`/api/v1/datanet/datalake/unstructured/upload`→404。
即：故障随"归属独立服务是否可达"分布，**非断言错误、非数据内容错误**。

### 3.2 独立服务启动崩溃（日志实测，均为 PSQLException / 装配异常）

### 3.3 上游阻塞归属（登记，不越权改代码/DB）
1. **schema 归属 / 数据迁移**（数据任务面）：控制域表 `sys_config`/`sys_dict`/`ecos_cognitive_evidence` 等现落 `ecos_control`（及 legacy `ecos_sysman` 双联），但独立服务 Datasource 的 `search_path` 未切换 → 独立服务首启查不到表。归数据层 P4 重置脚本（执行待 G4 授权）+ P5 数据访问收口批次。
2. **aiming 控制器双映射**（业务代码面）：`Ambiguous mapping` 需在 `services/aiming/impl/aiming-boot` 主类加等价的 `@ComponentScan.Filter` 排除 `EcosCognitiveEngineOpenHealthController` 老副本（gateway 已如此处理）。**业务代码改动，待逐项授权**，本轮仅登记不改。

> 结论：24 红的解除依赖上述两项上游修复；在独立服务全线起前，B 层 live 契约对这 4 个前缀**结构性不可达**，属阻塞态而非产品缺陷。

## 4. app/e2e（--project=app）——**结构性阻塞，浏览器 E2E 无法闭合**

**阻塞根因（2026-10-05 16:47~17:07 实测四证链）**：BFF :3000 转发 `POST /api/v1/auth/login` **不返回**——直接 curl、Playwright `APIRequestContext`（e2e 套件实际用的登录通道，`ecos-tests/tests/helpers/ecos.ts:loginAsAdmin`）在 25s 内均 HTTP 000 / 未收到响应。对照：

| 探测 | 结果 | 时长 |
| --- | --- | --- |
| 直连 gateway :8080 login（curl，同 token POST 3×）| 200 | 每次 < 400 ms |
| 直接 node → :8080 login（无 BFF，同一进程内 fetch）| 200 | 657 ms |
| node 进程内 顺序 health→login×2（无 BFF）| 403 → 200 → 200 | 全部 < 300 ms |
| BFF :3000 → gateway login（curl）| **HTTP 000 / 未回** | > 30 s（用户超时）|
| BFF :3000 → gateway 其它 POST（如 `/api/v1/x/no-such` 或 `/api/v1/health`）| 403 | 每次 ~250 ms（**无 hang**，可回到 gateway）|
| Playwright `request.newContext({baseURL: 'http://localhost:3000'})` `.post('/api/v1/auth/login')` | **Timeout 25000 ms exceeded** | 25.02 s |

**判定**：① gateway :8080 无故障（直连反复 < 400 ms，网关 JWT 会话连续签发）；② BFF 其它前缀的转发链正常（health-403、404-fallback 均秒回）；③ **仅 BFF 内 `POST /api/v1/auth/login` 这一转发路径 hang 住**（同一物理进程内 undici 上游 fetch → :8080 login 不 return，而同样 fetch 打 gateway 其它 POST 快速返回）。**根本不是测试断言问题，也不是 gateway 问题**——是 BFF 端 `server.ts` 内 `forwardProxy(GATEWAY, …)` 处理 login 端点时的 in-process undici / keep-alive 状态（该 bug 在**首次冷启**的 BFF（00:50:11 本窗新启）即复现，非"长期运行"池污染假设）。

**对 --project=app 的实际影响**：24 例浏览器 E2E 的第一动作 `loginAsAdmin(request)` 一律 60 s 超时（`playwright.config.ts` `timeout:60000`），随后 `injectAuth` 也未执行，用例失败/超时。因此 **无法出现"expected>0"数字**——若强行收口，只能登记"0 绿 / 24 红（均为前置 login 阻塞，非断言失败）"；本报告选择**不 mask 成绿**，也不伪造 "expected" 数字。

**归属与建议**（本轮不越权修复）：
1. **业务代码**：BFF `ecos_frontend/server.ts` `forwardProxy` 的 login 转发路径需专项排查（undici fetch Agent 配置 / body 转发 / keep-alive 生命周期）。**属 ECOS frontend 业务代码**，本 goal 范围（=测试用例+报告）不越权，仅登记。
2. **变通路径**（供后续）：e2e spec 可把 `loginAsAdmin` 改为**直接打 gateway :8080**（`ECOS_API`，`playwright.config.ts` 已有该变量），绕过 BFF 转发——但会同时**改变前端登录链路的端到端可观测性**（原本 e2e 想验 BFF→gateway 链路），属设计取舍，需专项 gate-2 授权。

**§4 结论**：`--project=app` 本轮**无法产出真实绿色契约契约数字**——24 例"因前置 BFF login hang 而结构性阻塞"，**非断言缺陷、非 gateway 缺陷**。不 mask、不回填假数字。
