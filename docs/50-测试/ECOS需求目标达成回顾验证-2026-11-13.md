> 与主方案的关系: 主方案 V3「功能逻辑」验证的是**实现是否按设计工作**；本册验证的是**实现是否达成了需求承诺的目标**——两者不等价。

## 一、为什么需要这一层（两个层面的区别）

### 1.1 一个反例说明差异

| 层级 | 问题 | 实例 |
|---|---|---|
| V3 功能逻辑 | 「这个接口按设计工作吗？」 | `POST /cognitive/outcomes/evaluate` 返回 200 → 功能**按设计**工作 ✅ |
| **RT 需求达成** | 「这个功能达成它承诺的目标了吗？」 | 该接口 200 但 `applicable=false / value seam absent`，**预测-实际-偏差闭环未达成** ❌（P1-18） |

同类实例（本项目实测）：

| 功能 | V3 判定 | RT 判定 | 差距根因 |
|---|---|---|---|
| 场景预校验 | 三项返回结构正确 → PASS | **未达成**：sc001 三项全 fail，预校验「帮用户发现问题并引导修复」的目标未验证闭环 | 缺「发现问题→修复→转绿」的完整链验证 |
| Mind 治理 | 列表/详情/终态写都正常 → PASS | **未达成**：`ContextSecurityTrimmer` 无生产实现 ⇒ required 源恒 403，认知上下文安全裁剪目标未达成 | 组件缺位（P1-9） |
| 决策网关 | 缺位时正确 503 → PASS | **未达成**：`DecisionGateway` 无实现 Bean ⇒ 场景动作闭环断链 | 组件缺位（P1-14） |
| 意向权重感知 | `memoryIntent` 死 API 移除、主循环 5 处零消费（#82 已修） | **需复核**：修复后权重是否真的影响路由决策 | 修复后未验证效果 |

### 1.2 核心原则

1. **「跑通」≠「有用」**：端点 200、页面能开，只证明没坏，不证明达成目标
2. **「达成」须有可观测证据**：不能说「应该能」，要给「改前/改后差异」或「业务结果正确」
3. **需求原文是唯一判据**：以 PRD 的验收标准为尺，不以实现的自述为尺
4. **未达成要分清三态**：功能缺位 / 功能在位但效果未达 / 效果无法度量（最后一种本身是缺陷）

## 二、RT 验证方法（五步法）

每一轮 RT 验证按下列五步走，缺任一步判 `PARTIAL`：

| 步 | 动作 | 产出 |
|---|---|---|
| **R1 取需求原文** | 从 PRD-00/分册取该需求的「描述 + 验收标准 + 现状」原文 | 需求锚（禁转述） |
| **R2 定位实现** | 找到承载该需求的代码/配置/表，确认在位 | 代码锚（文件:行） |
| **R3 设计效果断言** | 定义「怎么算达成」——必须可观测（数值/状态/前后差异），不能是「看起来对」 | 断言式 |
| **R4 实测取证** | 活体执行，采证据三元组（命令/原始输出/断言比对） | 证据 |
| **R5 判达成度** | 判 `达成 / 部分达成 / 未达成 / 无法度量`，并写差距与建议 | 结论 |

### 2.1 达成度判定词（RT 专用，与主方案六值判定并行使用）

| 判定 | 定义 | 必须写 |
|---|---|---|
| `达成` | 需求原文的验收标准全部有实测证据命中 | 证据三元组 |
| `部分达成` | 主目标达成，但有分支/边界未覆盖或降级 | 列出未达成分支 |
| `未达成` | 实现缺位，或实测结果与验收标准不符 | 差距 + 根因 |
| `无法度量` | 需求本身没有可观测标准，或缺少度量数据源 | **这本身要提升为需求缺陷** |

### 2.2 与主方案判定词的组合

```
功能验证（V1~V7，六值）  ×  需求达成（RT，四值）  =  综合结论
```

**综合结论规则**：

| 组合 | 综合结论 | 准出 |
|---|---|---|
| 功能 PASS + RT 达成 | **落地完成** | 可准出 |
| 功能 PASS + RT 部分达成 | **可用但有缺口** | 补缺口后准出 |
| 功能 PASS + RT 未达成 | **假落地（高危）** | **禁止准出**——功能能跑但没达成目标 |
| 功能 PASS + RT 无法度量 | 需先补验收标准 | 暂停准出 |
| 功能 FAIL | 无论 RT 如何 | 禁止准出 |

> **「功能 PASS + RT 未达成」是本册要抓的核心问题**——它正是「假绿」的最高形态：测试全绿、功能可用、目标没达成。

|---|---|
| **功能验证段** | 主方案六值判定（PASS/FAIL/PARTIAL/BLOCKED/NOT_EXECUTED/N/A）+ 证据三元组 |
| **需求达成段** | RT 四值判定（达成/部分达成/未达成/无法度量）+ 需求锚 + 效果断言实测 |

### 7.2 每批必给出的五个数

```
功能层：总数 = PASS + FAIL + PARTIAL + BLOCKED + NOT_EXECUTED + N/A
需求层：需求总数 = 达成 + 部分达成 + 未达成 + 无法度量
假落地数 = 「功能 PASS 且 RT 未达成」的条数        ← 核心健康指标
红线违反数 = 违反架构铁律/数据库规范的条数
无法度量数 = 需求缺可观测标准的条数                ← 应上升为需求缺陷
```

### 7.3 准出加严

| 结论 | 条件（在原有基础上加严） |
|---|---|
| 批通过 | 原条件 + **假落地数 = 0** |
| 有条件通过 | 原条件 + 假落地数 ≤ 2 且均登记修复窗口 |
| 不通过 | 存在假落地数 ≥ 3，或任一 P0 需求未达成 |
