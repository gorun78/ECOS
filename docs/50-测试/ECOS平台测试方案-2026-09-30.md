## 一、测试策略与原则

### 1.1 测试目标

1. **全功能覆盖**：系统已实现的全部功能模块（12 功能域、186 Controller、48 前端路由）均有对应测试用例
2. **PRD 需求追溯**：138 项 PRD 需求 100% 可追溯到测试用例（正向 + 反向）
3. **红线守卫**：8 条平台红线（PRD-00 §9.2）任一项 FAIL = 整体 FAIL，必须独立守卫用例
4. **里程碑准入**：M0/M1/M2/M3 四阶段各有独立准入测试集，不跨阶段放行
5. **风险驱动**：核心功能全量测试，重要功能抽样测试，辅助功能冒烟测试
6. **验收闭环**：PRD-09 §8 六演练作为最终验收基准，全部脚本化可重复执行

### 1.2 测试原则

1. **铁律优先**：架构铁律 v2.0 为最高约束，任何测试不得违反铁律
2. **单源原则**：测试数据、配置、脚本均走单源目录
3. **可重复性**：相同输入必须产出相同结果
4. **故障关闭**：安全不可用 = 默认 DENY，测试必须验证 fail-closed 行为
5. **证据完整**：六要素（forecastRunId/caliberId@version/asOfTime/快照/公式/证据）必须全部可验证
6. **不造假**：未执行的测试记"未执行"，不记"通过"

### 1.3 测试范围

| 维度 | 范围 |
|------|------|
| 功能域 | 12 个（见 §3 详细划分） |
| 后端 | 186 Controller，覆盖全部 API 端点 |
| 前端 | 48 路由、35 页面组件、10 大工作台、60+ 内部 Tab |
| 数据库 | 342 张表，12+ schema |
| PRD | PRD-00~PRD-10（10 卷，138 REQ）作为子集追溯 |
| 场景 | 年度经营预测（首期）+ 全功能回归 |
| 优先级 | P0（全量）+ P1（≥80%）+ P2（冒烟） |

### 1.4 不在范围

- v1 legacy 应用容器（`docker-compose.app-v1-legacy.yml` 默认不跑）
- 第三方可选组件（Doris/ClickHouse ultimate 档，本期不测）
- 性能压测（独立性能测试方案，本方案只含性能基线验证）

## 二、测试层级与类型

### 2.1 测试金字塔

```
                    ┌─────────────────┐
                    │   验收测试       │  六演练（PRD-09 §8）
                    │  (Acceptance)   │  Playwright E2E + curl
                    ├─────────────────┤
                    │   端到端测试     │  跨引擎链路（DIKCW 全链）
                    │    (E2E)        │  Playwright + API 组合
                    ├─────────────────┤
                    │   集成测试       │  引擎内多模块协作
                    │ (Integration)   │  Spring Boot @SpringBootTest
                    ├─────────────────┤
                    │   契约测试       │  API Schema 兼容性
                    │  (Contract)     │  OpenAPI diff + 响应 Schema 校验
                    ├─────────────────┤
                    │   单元测试       │  类/方法级逻辑
                    │    (Unit)       │  JUnit 5 + Mockito
                    └─────────────────┘
```

### 2.2 测试类型矩阵

| 测试类型 | 目的 | 工具 | 执行时机 | 责任方 |
|---------|------|------|---------|--------|
| 单元测试 | 验证类/方法级逻辑正确性 | JUnit 5 + Mockito | 每次 commit | 开发 |
| 集成测试 | 验证模块内多组件协作 | Spring Boot Test | 每次 MR | 开发 + QA |
| 契约测试 | 验证 API Schema 兼容性 | OpenAPI diff + JSON Schema | 每次 MR | 开发 + QA |
| E2E 测试 | 验证跨引擎端到端链路 | Playwright + curl | 每日构建 | QA |
| 验收测试 | 验证业务场景验收标准 | Playwright + curl + 手工 | 里程碑节点 | QA + PMO |
| 红线守卫测试 | 验证 8 条平台红线不可违反 | 专项集成测试 | 每次 MR + 每日 | QA |
| 安全测试 | 验证 RLS/CLS/OPA/审计 | 集成测试 + 渗透测试 | 里程碑节点 | QA + 安全 |
| 性能测试 | 验证性能基线与瓶颈 | JMeter + 监控 | 里程碑节点 | QA + 运维 |
| 回归测试 | 验证既有功能不退化 | 全量自动化测试 | 每次发布 | QA |
| UI/UX 测试 | 验证前端页面功能完整性 | Playwright + 手工 | 每次构建 | QA |

## 十、测试风险与应对

| # | 风险 | 影响 | 应对 |
|:-:|------|------|------|
| 1 | 功能范围大，用例量多 | 测试周期长 | 按优先级分批；自动化优先覆盖 P0 |
| 2 | 跨引擎联调复杂 | 集成测试慢 | 契约测试先行；Mock 兜底 |
| 3 | 测试环境不稳定 | 测试阻塞 | preflight.ps1 体检；容器化 |
| 4 | 遗留代码与新代码并存 | 回归风险 | knownLegacy 停写区域重点监控 |
| 5 | 安全测试专业性 | 漏洞遗漏 | 安全专家审查；自动化扫描 |
