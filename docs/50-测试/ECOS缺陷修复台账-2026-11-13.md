## 二、D1 — gateway PATCH 转发 503（P0，已修复）

### 2.1 真根因（与首份报告的初判不同，此处订正）

首份报告初判「RestTemplate 默认工厂 HttpURLConnection 不支持 PATCH」。**方向对，但定位错**：真正生效的不是 gateway 自己的 `RestTemplateConfig`，而是 **kb-engine 的 `KbEngineRestConfig.restTemplate()`**——它标了 `@Primary`，是 gateway 聚合宿主下全仓唯一的默认 `RestTemplate`（供 13+ 候选 Bean 里的裸注入使用），而它用的是 Spring 默认 `SimpleClientHttpRequestFactory`。

**证据链**：
1. 改 gateway `RestTemplateConfig` 为 `JdkClientHttpRequestFactory` 后重启，PATCH 仍 503
2. 日志里**没有**该 Bean 的创建日志 ⇒ 它根本没被实例化
3. 全仓搜 `@Bean RestTemplate` 发现 `KbEngineRestConfig:35-37` 同名 + `@Primary`
4. 加日志后打印真因：`ResourceAccessException: I/O error on PATCH ... Invalid HTTP method: PATCH`（正是 HttpURLConnection 的 `ProtocolException` 文案）
5. 独立 Java 程序验证 `JdkClientHttpRequestFactory` + PATCH **可用**（返回 403 鉴权错，非方法错）

### 2.2 修复内容

| 文件 | 改动 |
|---|---|
| `ecos_backend/engine/kb-engine/kb-engine-impl/.../config/KbEngineRestConfig.java` | 默认 RestTemplate 改用 `JdkClientHttpRequestFactory`（JDK HttpClient，支持 PATCH），保留 `@Primary` 与凭据中继拦截器 |
| `ecos_backend/gateway/.../config/RestTemplateConfig.java` | Bean 改名 `gatewayForwardRestTemplate`（定向 Bean），**不再**与 kb 的 `@Primary` 同名竞争；同样用 JDK 工厂 |
| `ecos_backend/gateway/.../controller/WorkspaceForwardController.java` | 日志占位符 `"{} {}"` → `"{} {} -> {}: {}"` 并把异常对象作为末参输出堆栈（原写法三参对两占位符，异常信息被吞，导致真因排查多耗数轮） |

### 2.3 回归证据

```
修复前：PATCH /api/v1/workspace/scenarios/sc001/status via 8080
        → HTTP 503 {"errorCode":"ECOS-WS-503-UPSTREAM"}
修复后：PATCH /api/v1/workspace/scenarios/sc001/status via 8080
        → HTTP 409 {"errorCode":"ILLEGAL_TRANSITION","message":"非法状态迁移: ACTIVE -> DRAFT"}
Playwright：V-WS-019g 由 FAIL 转 PASS
```

## 七、D6 — 方法不匹配报 500（P1，已修复）

### 7.1 现象

`GET /api/v1/cognitive/executions`（该端点为 POST-only）→ **HTTP 500 `ECOS-SYS-500`**。
正确语义应为 **405 Method Not Allowed**。

### 7.2 根因

`gateway/GlobalExceptionHandler` **没有 405 分支**，`HttpRequestMethodNotSupportedException`
落入 `handleGeneric` 兜底被报成 500。违反 HTTP 状态行保真：405（调用方用错方法）与
500（服务端故障）的语义天差地别，混报会把排障方向带偏。

### 7.3 修复内容

| 文件 | 改动 |
|---|---|
| `runtime/common-api/.../error/SystemErrorCode.java` | 新增 `ECOS_SYS_405` |
| `gateway/handler/GlobalExceptionHandler.java` | 新增 `handleMethodNotSupported`：返回 405 + `ECOS-SYS-405` + **`Allow` 头**（RFC 9110 要求 405 应列支持方法） |

### 7.4 回归证据

```
GET /api/v1/cognitive/executions
→ HTTP 405
→ {"code":405,"errorCode":"ECOS-SYS-405","message":"请求方法不被支持",...}
→ Allow: POST      ← RFC 9110 要求的响应头
```

## 八、D7 — 畸形 JSON 报 500（P1，已修复）

### 8.1 现象

`POST /api/v1/cognitive/executions` 传 `{bad json` → **HTTP 500 `ECOS-COG-504 cognitive internal error`**。
正确语义应为 **400**（调用方传了坏数据，不是服务端故障）。

### 8.2 根因

`CognitiveErrorAdvice` 有 `@ExceptionHandler(Exception.class)` 兜底，
`HttpMessageNotReadableException` 被它吞掉。这与该文件里既有的
`MissingServletRequestParameterException` 分支是**同一缺陷形态**（catch-all 吞掉本可精确归类的异常，
该文件注释里已记录过一次同类修复 2026-11-10）。

### 8.3 修复内容

`cognitive-engine-impl/.../CognitiveErrorAdvice.java`：新增
`onUnreadableBody(HttpMessageNotReadableException)` → **400 `ECOS-COG-400P`**。

### 8.4 回归证据

```
POST /api/v1/cognitive/executions  body="{bad json"
修复前 → HTTP 500 {"errorCode":"ECOS-COG-504"}
修复后 → HTTP 400 {"errorCode":"ECOS-COG-400P","message":"invalid parameter"}
```

### 8.5 施工踩坑（重要）

改 `cognitive-engine-impl` 后，`mvn -pl gateway package` **不会**更新 gateway fat jar 内嵌的
`BOOT-INF/lib/cognitive-engine-impl-*.jar`——即使 `.m2` 里已是新包。实测 fat jar 内嵌的仍是
早上 09:54 的旧 class，而 `.m2` 已是 12:20 的新包。**必须先 `rm -rf gateway/target` 再 package**。

按 HTTP 状态判成功，于是「资源不存在」被当成成功响应。

**抽样 6 个详情端点，5 个中招**：

| 端点 | body.code | HTTP（修复前） |
|---|---|---|
| `/api/v1/cognitive/hypotheses/NOT_EXIST_999` | 404 | **200** |
| `/api/v1/cognitive/beliefs/NOT_EXIST_999` | 404 | **200** |
| `/api/v1/cognitive/models/NOT_EXIST_999` | 404 | **200** |
| `/api/v1/aip/models/NOT_EXIST_999` | 404 | **200** |
| `/api/v1/aip/agents/NOT_EXIST_999` | 404 | **200** |
| `/api/v1/cognitive/frameworks/NOT_EXIST_999` | 404 | 404（唯一正确的，因其走 ResponseEntity） |

### 9.2 根因

`ApiResponse` 是纯 POJO，Controller 直接 `return ApiResponse.error(404, ...)`，
Spring 默认按 HTTP 200 返回，状态信息只存在于 body。

### 9.3 修复内容（用户裁决：全局 Advice）

新增 `gateway/handler/HttpStatusFidelityAdvice.java`（`@RestControllerAdvice` +
`ResponseBodyAdvice`）：响应体写出前，若 body 是 `ApiResponse` 且 `code` 落在合法 HTTP 码
区间（100~599）且非 0，则把状态行同步为该码。

**两类不映射**：
- `code == 0`（成功）→ 保持 200
- `code < 0`（`CODE_INTERNAL_ERROR = -1` 的信封 v1 系统错误约定）→ 非法 HTTP 码，保持原状态，
  由既有棘轮门「只减不增」追缴

**不覆盖已有显式状态**：若调用方已用 `ResponseEntity` 指定非 200（如 handler 的 405/404 分支），
不改写，只补 200 的缺口。

### 9.4 回归证据

```
修复后 4 个端点全部 200 → 404：
  404  /api/v1/cognitive/hypotheses/NOT_EXIST_999
  404  /api/v1/aip/models/NOT_EXIST_999
  404  /api/v1/cognitive/beliefs/NOT_EXIST_999
  404  /api/v1/cognitive/models/NOT_EXIST_999

全量回归：B0+B1+B2 = 42 passed / 0 failed（未打坏任何既有用例）
```

### 9.5 已知边界（登记）

| 项 | 说明 |
|---|---|
| `code < 0` 出口 | 仍保持 HTTP 200，属信封 v1 遗留约定，由既有棘轮门追缴，不在本批范围 |
| 前端依赖 | 若某前端代码依赖「HTTP 200 + 读 body.code」的旧行为，切换后需同步调整；本轮全量回归未发现回归 |

## 十、D9 — 管道函数列表恒失败（P1，已修复）

### 10.1 现象

`GET /api/v1/engine/data/functions?page=1&pageSize=3` 无论带不带 `category`，恒返回 `{"code":-1,"message":"列出函数失败"}`。

### 10.2 真根因

`PipelineFunctionServiceImpl.listFunctions` 先 `sql.append(" ORDER BY category, name")` 再 `replace("SELECT *", "SELECT COUNT(*)")` 生成计数 SQL，实际拼出：

```sql
SELECT COUNT(*) FROM ecos_pipeline_function WHERE 1=1 AND category = ? ORDER BY category, name
```

PostgreSQL 不接受聚合查询里出现未聚合的 ORDER BY 表达式 → `BadSqlGrammarException`。日志原文：

```
org.springframework.jdbc.BadSqlGrammarException: PreparedStatementCallback; bad SQL grammar
[SELECT COUNT(*) FROM ecos_pipeline_function WHERE 1=1 AND category = ? ORDER BY category, name]
  at ...PipelineFunctionDao.queryCount(PipelineFunctionDao.java:35)
  at ...PipelineFunctionServiceImpl.listFunctions(PipelineFunctionServiceImpl.java:77)
```

**排查弯路（记下来避免重犯）**：先怀疑 datanet 进程，改完重启 datanet 仍失败；实际异常来自 **gateway** 日志——该 Controller 由 gateway monolith 宿主承载，datanet 只是同源副本。**定位必须先 grep 全部日志目录，而不是只 grep 被改模块的日志。**

### 10.3 修复内容

`PipelineFunctionServiceImpl.listFunctions`：把 COUNT 语句的生成**提前到 ORDER BY 拼接之前**，并补回被误删的 `offset` 计算。

```java
String countSql = sql.toString().replace("SELECT *", "SELECT COUNT(*)");
int total = functionDao.queryCount(countSql, params.toArray());

sql.append(" ORDER BY category, name");

sql.append(" LIMIT ? OFFSET ?");
int offset = Math.max(0, page - 1) * pageSize;
params.add(pageSize);
params.add(offset);
```

### 10.4 回归证据

```
# 正向
GET /engine/data/functions?page=1&pageSize=3  → code=0 total=120 list=[fn-array, fn-array_append, fn-array_contains]
GET /engine/data/functions?page=2&pageSize=3  → code=0 total=120 list=[fn-array_join, ...]   ← offset 生效

# 反向探针
A  category=array    → code=0 total=15  cats=['array']   （过滤生效，且 < 全量 120）
B  category=__nope__ → code=0 total=0   len=0            （不存在的分类）
C  page=999          → code=0 total=120 len=0            （越界返回空但 total 稳定）
D  grep "bad SQL grammar \[SELECT COUNT" gateway-stdout.log → 0 命中（计数语句已无 ORDER BY）
```

### 10.5 附带发现（构建面）

gateway fat jar 里的 `BOOT-INF/lib/data-engine-impl-*.jar` 是**旧副本**，即使 `.m2` 已更新。修法是 `rm -rf ecos_backend/gateway/target` 后重打包，再用 `unzip -p ... | md5sum` 与 `.m2` 对齐验证内嵌件一致。

用户侧表现：随便敲一个不存在的 Agent 都能得到「看起来像 AI 说完了」的回复，无法分辨真假。

### 19.2 真根因

`CopilotController.chat` 的兜底分支：

```java
if (copilotChatService != null && copilotChatService.supports(agentId)) { ... 真实 agent-loop ... }
Map<String, Object> legacy = copilotAgentService.chat(agentId, message, sessionId);  // ← 伪造源

也不调用 LLM、也不调工具。同样的毛病在 `quick-questions`：目录外 → `presets.getOrDefault(agentId, List.of("你好，有什么可以帮你？"))`
——凭空给一句「你好」让调用方以为 Agent 存在。

### 19.3 修复

1. `chat`：目录外 agentId → **400 明确拒绝**，并指引 `GET /agents` 查可用值；不再回落旧通道。
2. `quick-questions`：同口径，目录外 agentId → 400。
3. 移除已无用的 `ICopilotAgentService` 依赖与构造器（避免保留死代码），补 `Logger`。

目录内 6 个 Agent 的行为**零变化**（仍走 `CopilotChatService` → `AgentLoopService`）。

### 19.4 验证

```

**关键区分**：`agent-data` 是**真调 agent-loop 后被护栏拦下**（`ECOS-AI-403/GUARDRAIL_DENIED` + 真实 traceId + 30 个工具白名单），

## 二十、D19 — 任务中心：状态操作对不存在任务假成功（P1，已修复）

### 20.1 现象

```
POST /api/v1/task/__NOT_EXIST__/cancel   → 200 {"data":{"message":"Task __NOT_EXIST__ cancelled"}}
POST /api/v1/task/__NOT_EXIST__/archive  → 200 {"data":{"message":"Task __NOT_EXIST__ archived"}}
POST /api/v1/task/submit  {}             → 200 {"data":{"taskId":"cdf5d4d4-…","status":"SUBMITTED"}}
```

三条都是**假成功**：前两条什么都没发生，第三条真的创建了一条无名称/无类型的空任务。

### 20.2 真根因

`gateway/.../TaskController` 的四个状态面直接透传 service，而 `TaskManagementServiceImpl`：

```java
public void cancelTask(String taskId) { setStatus(taskId, CANCELLED); }   // 不校验存在性
public void pauseTask(String taskId)  { setStatus(taskId, PAUSED); }
public void resumeTask(String taskId) { setStatus(taskId, RUNNING); }
```

`setStatus` 直接写持久层，不存在的 id 也是一次无副作用的写入 ⇒ 返回成功。
`submit` 则完全不校验 `taskName`/`taskType`，空 body 也生成 UUID 并落库。

同文件里 `getTask`（`/{taskId}`）**本来就有正确的 404 口径**，只是没被其它四个面复用。

### 20.3 修复

1. 抽出 `requireTaskExists(taskId)`（复用 `getTaskDescription`），cancel/pause/resume/archive 四个面统一前置校验，缺失即 `404 任务不存在: xxx`。
2. `submit` 增加必填校验：`taskName` / `taskType` 为空 → 400。
3. 顺带在注释里写明 archive 的语义（termin 态收敛为 CANCELLED，runtime-task 无独立归档态）。

前端 `services/taskCenter.ts:apiTaskSubmit` 本就传 `taskName` + `taskType`，校验不破坏既有调用。

### 20.4 验证

```
修复前 cancel 不存在任务 → 200 "Task __NOT_EXIST__ cancelled"
修复后 cancel 不存在任务 → 404 "任务不存在: __NOT_EXIST__"
修复后 archive/pause/resume 同口径
修复前 submit {} → 200 且落空任务
修复后 submit {} → 400 "taskName 不能为空"
```

V-CTRL-TASK-006/007/008 三条反向探针常驻；V-CTRL-TASK-002 另做「统计 total ↔ 列表 total ↔ 各状态之和」三方对账，防计数编造。

### 43. D42 — 系统参数面 503 的真因不是「缺注解」而是「表从未建」（P2，登记不修）

**现象**：`GET /api/v1/system/config/params/{id}` → 503 `ECOS-SYS-503`
`"系统参数服务 ISystemParamService未装配，配置面不可用"`。

**排查路径与结论**：

1. `SystemParamController` 本身是 fail-closed 设计（`ObjectProvider.getIfAvailable()` 取不到就 503），
   行为正确——缺依赖不谎报 200＋空集。
2. `SystemParamServiceImpl` **没有 `@Service`**，而同包 `ConfigServiceImpl` 有 ⇒ 容器里确实没有这个 Bean。
   补一行注解看似就能修好。
3. **但再查一层**：`SystemParamDaoImpl` 操作的 `TABLE_NAME = "td_system_param"`，而
   `SELECT ... FROM pg_tables WHERE tablename ILIKE '%param%'` 在本库**零命中**；
   `grep -rn "CREATE TABLE.*td_system_param" docs/50-db_script/` 也**零命中**。
   `td_` 前缀属 v1 legacy 命名（与已作废的 `TD_USER` 同批），与 v2 的 `sys_config` 单表分组不是一套。

**为什么最终不修**：补 `@Service` 只会把「显式 503 未装配」换成「装配后每次查询必 SQL 报错」
——前者是诚实的不可用态，后者把**结构缺失伪装成运行时故障**，恰是本台账反复登记的折叠面。

**已做的改动**：在 `SystemParamServiceImpl` 类上写入 Javadoc，钉住「刻意不注册为 Bean」及其实测依据
（代码零行为变更，仅注释），防止后续有人"顺手补个 @Service"把诚实态换掉。

**补充实验（本批真做了，结论比预想更严重）**：为验证「补上 @Service 会怎样」，实际编译了带注解的版本并
重打 gateway 跑活体。结果**不是** SQL 报错，而是：

```
GET /api/v1/system/config/params  →  HTTP 200  {"code":0,"message":"ok",
    "data":{"data":[],"total":0,"page":1,"pageSize":20}}
```

追到 `SystemDatabaseAccessImpl.query()`（runtime-core）才看清：**它根本不查数据库**——
`ConcurrentMap<String,Object> tableData = dataStore.get(tableName); if (tableData == null) return new ArrayList<>();`
即 `ISystemDatabaseAccess` 是**进程内内存 store 的假实现**，表不在 store 里就返回空列表。

所以补 `@Service` 的真实后果是：**把「诚实 503 未装配」变成「200 + 空集」**——
数据结构缺失被谎报成「有这套功能，只是没数据」，正是方案 §8.3 与详设 §4.7.2 明令禁止的折叠形态，
比原来更糟。这不是猜测，是本批实测。

（实验后源码已回退为无注解版本；当前运行的 jar 仍是带注解的实验包，需在下次重打时复位。）

**待裁决（三选一，不再是二选一）**：

1. 并入 `sys_config` 单表分组（推荐，符合后端规范 §十「配置/字典单表分组」）；
2. 新建 `td_system_param` 表并补 V3xx 迁移；
3. 确认该能力整体废弃 → 删除 Controller 族而非留 503。

裁决前保持 503。另需单独评估：`ISystemDatabaseAccess` 的内存假实现对全仓其他调用方是否有同类
「表缺失读成空数据」风险（本批只证到系统参数一处，未全域排查）。

### 45. D44 — `ISystemDatabaseAccess` 两族实现并存：真库与内存假库（P1，登记待裁决）

**发现路径**：查 D42（系统参数面）时顺藤摸到 `SystemDatabaseAccessImpl`，发现同名接口下有两套互不相同的实现路径。

**实测对照**（同一实现类内）：

| 族 | 方法 | 实际行为 | 证据 |
|---|---|---|---|
| 真库 | `executeQueryFromConfig` / `executeUpdateFromConfig` / `executeInsertFromConfig` / `queryListFromConfig` / `queryObjectFromConfig` | 读 SQL 配置文件 → `replaceParams` → `executeQuery` → `dataSource.getConnection()` **真 JDBC** | `SystemDatabaseAccessImpl.java:382-399`（FromConfig 入口）、`:1331`（`dataSource.getConnection()`） |
| 内存假库 | `query` / `query(table,clazz,cond,offset,limit)` / `findById` / `findOne` / `insert` / `update` / `delete`（按表名的那一族） | `ConcurrentMap<String, ConcurrentMap<String,Object>> dataStore` 进程内 Map；表不在 store 里就 `return new ArrayList<>()` | `SystemDatabaseAccessImpl.java:52`（dataStore 字段）、`:217-220`（缺失表返回空列表） |

**为什么这是缺陷**：

1. **类注释与实现不符**——类 Javadoc 写「使用 Spring DataSource 访问数据库」，但按表名那一族完全不碰 DataSource。
2. **缺失被读成空数据**——表不存在/未装载时返回空列表而非报错，调用方无法区分「没有数据」与「这套存储根本不存在」。D42 的实测正好撞上这个形态：补 `@Service` 后系统参数面从 503 变成 `200 + data:[] total:0`。
3. **同接口两族语义不一致**——同一个 `ISystemDatabaseAccess` 注入后，走 `*FromConfig` 的调用方读写真实 PG，走按表名那族的调用方读写进程内存。**进程重启数据即丢**，且多实例部署时彼此不可见。

**影响面**：`grep -rln "ISystemDatabaseAccess"` 命中 35 个文件（含接口/实现/测试）。已知按表名那一族的调用方之一是 `SystemParamDaoImpl`（`td_system_param`）。**未全域排查其余调用方**属于哪一族——本批只证到系统参数一处，不下全局结论。

**待裁决（本批未改代码）**：

1. 按表名那一族改为真 JDBC 实现（改动大，需逐调用方核对表结构与 SQL）；
2. 保留但显式标注为「内存态/仅测试用」，并在生产 profile 下拒绝装配；
3. 下线该族，迁移调用方至 `*FromConfig` 或 MyBatis。

**为什么不在本批直接修**：这不是单点 bug，而是横切存储语义的架构面选择；改错会让 35 个文件的调用方静默换存储。按架构铁律「横切底座归 runtime」与「不可逆+撞成文红线须停下请示」的既有约定，先登记取证，由属主裁决。

### 46. D45 — 系统参数详情 500 被折叠成 HTTP 200 + `code=-1`（P1，本批已修复并回归）

**现象（存储语义探针实测）**：
```
GET /api/v1/system/config/params/VERIFY_NOT_EXIST_999
→ HTTP 200  {"code":-1,"message":"查询失败","timestamp":...,"success":false}
```

**真根因**：`SystemParamController.get()` 的 `catch (Throwable e)` 走
`ApiResponse.internalError("查询失败")`，而 `internalError(...)`（无参机读码版本）返回
`CODE_INTERNAL_ERROR = -1` + 无 `errorCode` 键。**状态行保真（D8 修复）只对 `code ∈ [400,599]` 生效**，
`-1` 不在其内 ⇒ 服务端故障在 HTTP 面表现为 **200**。

**为什么这次不是"不存在 id 返回 404"那么简单**：`p == null` 分支确实会返回 `notFound`，
但实测走到了 `catch (Throwable)`——因为底层是 D44 的内存 `dataStore` 路径，
`findById` 对缺失表的行为与"查到了但没这条记录"不可区分，最终抛异常并被吞成 `-1`。
即 **D44（存储语义）与 D45（状态行不保真）在这条请求上串联发作**。

**影响面**：`ApiResponse.internalError(String)` 单参重载全仓约 317 处调用共用此工厂
（见 D41 §42 的"同源观察"）。本批第二次撞上它的实际后果，说明这不是理论风险。

**为什么不在本批修**：改 `internalError` 工厂会让 317 处调用的对外形态同时变化
（200→500），属于跨域横切变更；且 D8 的状态行保真层是否应把 `-1` 一并纳入，需要与
"§3.2.7 域内业务错误码归各域"的口径一起裁决。

**当时的处置**：先登记为常驻探针 `storage-semantics.spec.ts` 的 `D42-2`，钉住现状
（修好前该用例红，修好后自动转绿）。后在本批末尾直接实施修复，见下。

**修复（本批已实施）**：采用方案 1——在 `HttpStatusFidelityAdvice` 里把
`ApiResponse.CODE_INTERNAL_ERROR`（-1）**显式映射为 500**，其余负数码仍保持原状（不擅自升格无语义约定的负数）。

```java
// 修复前
int code = apiResponse.getCode();
if (code <= 0 || code < 100 || code > 599) return body;   // -1 被这里静默放过 ⇒ 200

// 修复后
int code = apiResponse.getCode();
if (code == ApiResponse.CODE_INTERNAL_ERROR) {
    code = HttpStatus.INTERNAL_SERVER_ERROR.value();       // -1 ⇒ 500
}
if (code <= 0 || code < 100 || code > 599) return body;
```

选单点的理由：`internalError(String)` 单参重载全仓约 317 处调用共用同一工厂，
逐处改写既不可穷尽也易漏；在**唯一的对外出口**统一纠正，覆盖面与可维护性都最好。

1. `EcosTrustHeaderFilter` 在链前**无条件剥离** `X-ECOS-USER/ROLE/TENANT/DOMAIN`（防伪造，行为正确）；
2. `CallerCredentialSource.current()` 读的是**请求头**——剥离后读不到 ⇒ 返回 `EMPTY`；

   `dataBridgeHandlerIsActuallyRegistered`（注解必须在、且注册类型是 `DataBridgeException`）
   与 `notFoundHandlerStaysMoreSpecific`（两条腿并存且 NotFound 是其子类）。
   补完后重跑变异 → **`Tests run: 23, Failures: 2`**（注册腿转红），复原后 `grep -c MUT` = 0。
3. **活体验证**：重建 workspace JAR 并重启后：

        "message":"no_active_mind_for_scenario=sc001","traceId":"31dd83f…"}

**同批顺带纠正的两处判据错误（我自己的测试假设错，不是产品缺陷）**：

1. **`ECOS-SYS-404` 不是「业务 404」**：初版 spec 断言「路由未注册 ⇒ 响应体无 `errorCode`」，

2. **503 是合法降级态，不是 5xx 故障**：初版 `assertNot5xx` 用了 `toBeLessThan(500)`，

## D53 — 经网关调 OAG 全线 403；health 还指向上游不存在的路径（双缺陷叠加）

**发现方式**：核 V-AI-076（OAG 4 映射）时发现 `GET/POST /api/v1/oag/chat/health` 都 404，
而 `POST /api/v1/oag/health` 回 **503**「OAG health check failed: HTTP 403」。

**根因（两条独立缺陷叠加，必须同时修才通）**：

1. **转发不带认证料**。`OagForwardController` 用 JDK `HttpClient` 转发时只设
   `Content-Type`，既不转发客户端 `Authorization`，也不重注入信任头。而网关
   `EcosTrustHeaderFilter` 会在链前**无条件剥离**客户端传来的 `X-ECOS-USER/ROLE/TENANT`，
   所以上游 :18084 收到的是一个彻底的匿名请求 → `HeaderAuthInterceptor` 回
   `403 ECOS-AUTH-010 缺少信任头`。所有四个 OAG 端点（chat / chat/v2 / chat/stream / health）全中。
2. **health 目标路径虚构**。转发器指向 `POST /api/v1/oag/health`，但 `OagController`
   只映射了 `GET /api/v1/oag/chat/health`（它自己返回的 endpoints 清单里就写着）。即使认证修好，
   这条腿仍会 404。

**上游契约实测**（aiming :18084 直连，四种组合）：
```
无任何头                       → 403（Spring Security 层，默认 Deny）
仅 Authorization              → 403 ECOS-AUTH-010 缺少信任头
仅 X-ECOS-USER/TENANT/ROLE    → 403（Security 层仍要求 Authorization）
Authorization + 三个信任头     → 200 {"status":"UP","pipeline":"OAG 8-step DAG",...}
```
即**两者都要**，缺一不可——这解释了为什么"只补信任头"或"只补 Authorization"的单点修法都不成立。

**修复**（`OagForwardController`）：
- 新增 `applyAuthHeaders(HttpRequest.Builder)`：转发客户端 `Authorization` + 从
  `SecurityContextHolder` 重注入 `X-ECOS-USER/ROLE/TENANT`，口径与
  `WorkspaceForwardController.java:92-111` 完全一致（当时就是同一类缺陷，2026-11-08 已修过一遍）。
  缺失即不注入，由下游 fail-closed，**不伪造身份**。
- `forwardJson` / `chatStream` / health 三处统一经 `applyAuthHeaders` 构造请求。
- health 目标改为 `GET /api/v1/oag/chat/health`；同时**保留** `POST /api/v1/oag/health` 兼容腿
  （既有调用方在用），并新增 `GET /api/v1/oag/chat/health` 与上游同名同动词，两条腿共用
  `probeUpstreamHealth()` 单一实现。

1. **活体对照**：

## D56 — 本体域 V200 治理半途：主表 DROP 了，但「同一逻辑表」在 3 个 schema 里各留一份，读源靠 search_path 兜

**发现方式**：为做 V-ONTO-071/073 对账，我先查 `ecos_ontology.ecos_ontology_relationship` 得 **0 行**，

**继续追才看清**（这次没急着记缺陷是对的）：

**建议裁定的三步**：①DAO 全部补显式 schema 前缀（可立即做，零风险）；
②确认权威副本后，把 0 行空壳标为 deprecated 并在文档地图里注明；

## D57 — 场景状态迁移在权限库缺键下全线不可用：代码要 `scenario:write`，库中无此权限（含 admin）

**发现方式**：验 V-WS-019（迁移权限默认 DENY）时，为确认「有权限的账号能通过」，
用 admin 调 `PATCH /api/v1/workspace/scenarios/sc001/status {"status":"ACTIVE"}`：

```
HTTP 403
{"errorCode":"PERMISSION_DENIED","message":"无权限执行该操作: scenario:write",
 "data":{"permission":"scenario:write"}}
```

**连 admin 都被拒**，说明不是「默认 DENY 生效」，而是**权限点根本没人有**。

**三方交叉验证**：
```
① 代码：ScenarioStatusMachine.java:17-18
   PERM_ACTIVATE = "scenario:activate"（DRAFT→ACTIVE 用）
   PERM_WRITE    = "scenario:write"（其余生命周期翻转用）
② 权限库：ecos_control.td_permission 共 79 条，匹配 'scenario:%' 的只有 3 条：
   scenario:*  /  scenario:publish  /  scenario:read       ← 无 write、无 activate
③ 授权关系：`scenario:*` 这条**没有任何角色持有**（查 td_role_permission 得 0 行），
   所以通配也不会兜住；admin 实际持有 scenario:read（GROUP_FIN/SEGMENT_GM/ENT_EXEC）+ scenario:publish（ENT_EXEC）
```

**定性**：**安全数据缺失，不是代码缺陷**。
代码侧的权限点设计是对的（激活与写分开、默认 DENY、禁本地角色字符串比较）；
缺的是 `td_permission` 里的两条定义 + 给对应角色的授权。

**为什么不在本批修**：补权限 = 写 `td_permission` + `td_role_permission`，
属**安全数据变更**，需要授权（与 OPA 策略、RLS 策略同类，前序批次已多次按此纪律停手）。
且「谁该有 write/activate」是业务授权模型问题，不是测试能拍的。

**影响面**（为什么这条重要）：
`PATCH /{id}/status` 是场景生命周期（DRAFT→ACTIVE→SUSPENDED→COMPLETED）的唯一入口。
权限缺失意味着**场景永远停在创建时的状态**，工作台的生命周期闭环在活体上不可用。
前端若能创建场景却不能激活，用户看到的是「按钮点了没反应/报无权限」。

**合法迁移的另两面已实测正常**（与本缺陷无关，是对照组）：
```
PATCH sc001 {"status":"DRAFT"}  → 409 ILLEGAL_TRANSITION "非法状态迁移: ACTIVE -> DRAFT"（终态/回退直接非法）
PATCH VERIFY-NOT-EXIST {"status":"ACTIVE"} → 404 SCEN-404 场景不存在
```

**建议裁定**：①在 `td_permission` 补 `scenario:write` / `scenario:activate`；
②明确哪些角色持有（ENT_EXEC 应至少覆盖 write；activate 可按治理要求收紧）；
③补完后重跑 V-WS-019，并用非 admin 账号验证「无权限者仍被拒」。

## D58 — AI 域局部异常处理器被全局 handler 抢先命中，参数错误被渲染成 500/502

**发现方式**：验 V-AI-075（NLQ）时，一次合法查询返回
**500「服务内部错误，请稍后重试或联系管理员」**。查日志得真因：

```
IllegalArgumentException: Profile [nlq-fallback] not found for subsystem [sysman]
  at ProfileManagerImpl.getProfile:56 → LLMGatewayServiceImpl.execute:62 → NLQController.nlq:86
ERROR c.c.g.g.handler.GlobalExceptionHandler : Unhandled exception (server internal error)
```

**两个独立问题**（分两层）：

**① 处理器优先级错配（本批修）**
`AiErrorAdvice` 的类注释自称：
> 「本 advice 必须先于网关 `GlobalExceptionHandler` 命中（局部优先）」

但实测走的是**全局** handler。原因：
- `AiErrorAdvice` = `@RestControllerAdvice(basePackages="com.chinacreator.gzcm.engine.ai")`，**无 @Order**
- `GlobalExceptionHandler` = 裸 `@RestControllerAdvice`，同样**无 @Order**
- 两者都是 `Ordered.LOWEST_PRECEDENCE`，谁先命中取决于 bean 注册顺序 ⇒ **「局部优先」没有任何保证**

修法：`AiErrorAdvice` 加 `@Order(Ordered.HIGHEST_PRECEDENCE)`。

**② 分类器不认识 Spring 参数异常（修复①后立刻暴露）**
加上 @Order 后 nlq 的 500 变成 **400 ECOS-AI-400 INVALID_ARGUMENT**（正确了），
但全量回归立刻打出 1 条失败：`V-COP-003 缺 agentId 应 400，实得 502`。

```
AiErrorAdvice: AI 域未处理异常 → class=TOOL_BACKEND_ERROR code=ECOS-AI-502
raw=MissingServletRequestParameterException: Required request parameter 'agentId' ... not present
```
`ErrorCodeMapper.classifyOne` 不认识 `MissingServletRequestParameterException`，
落进 `TOOL_BACKEND_ERROR` 兜底 ⇒ 把**客户端漏传参数**说成「数据服务异常，请稍后重试」，
还标了 `retryable:true`（误导客户端重试一个永远不会成功的请求）。

修法：`classifyOne` 前置识别三类 Spring 参数异常 → `INVALID_ARGUMENT`：
`MissingServletRequestParameterException` / `MethodArgumentTypeMismatchException` / `MissingPathVariableException`。

**活体验证**：
```
NLQ 正常问题      : 500 服务内部错误 → 400 ECOS-AI-400 INVALID_ARGUMENT（带诊断码，retryable=false）
copilot 缺 agentId: 502 TOOL_BACKEND_ERROR → 400 ECOS-AI-400 INVALID_ARGUMENT
copilot 有 agentId: 200（未受影响，反向探针）
NLQ 缺 question   : 400「缺少 question 字段」（原有 Controller 内校验，未受影响）
全量             : 509 passed
```

**登记不修（上游配置，属环境面）**：`nlq-fallback` profile 在全仓零定义——
Java/yml/配置表都查过。NLQ 词典无匹配时必然走到这个悬空引用。
现在至少不再伪装成 500，但**功能本身仍是不可用的**：需要有人决定该 profile 指向哪个模型。
建议：①若 NLQ 兜底是必备能力，补 profile 定义；②若非必备，把 `llmGatewayService.execute(...)`
的失败按「能力未配置」显式降级为 200 + 说明文案（当前代码已有一条这样的分支，
只是异常在到达它之前就抛了）。

**这是本批最有价值的一类发现**：全局 handler 会把**任何**领域异常压成「服务内部错误」，
让「我少传了个参数」和「服务器炸了」看起来一模一样。@Order 修好后，
整个 ai-engine 域的 400/404/403/502 语义才真正生效。

## D71 — 本体发布快照：两 JVM 抢写同一行，`schema_hash` 由"谁最后写"决定（已定位，待裁）

**发现方式**：为闭环 V-ONTO-043/072（发布落快照）做端到端实跑时，抓两侧日志对比。

**证据三元组**：
```
① 一次发布 → 两处消费（gateway 与 dccheng 都订阅了同一 topic）：
   gateway  : received publish event ontology=ont_entmgmt version=1.0.4
              TOPOLOGY_EVENT_CONSUMED hash=44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a
   dccheng  : received publish event ontology=ont_entmgmt version=1.0.4
              WARN fetch schema failed (use placeholder hash): ... 403 Forbidden
              TOPOLOGY_EVENT_CONSUMED hash=789a7e83f9ada303c9eb92b586079263f4f57cba92a35c5c7b3e2c5ad6254ae1

② 库内落的是谁：
   SELECT schema_hash FROM ecos_knowledge.ecos_kb_ontology_snapshot
     → 789a7e83…   ← dccheng 的 placeholder，覆盖了 gateway 的真 schema hash

③ 代码机制（EcosOntologyEventConsumer）：
   fetchAndHashSchema() 异常时 return sha256Hex("placeholder-" + ontologyId + "-" + versionId)
   upsertSnapshot() 按 UNIQUE(ontology_id, version) 冲突更新 ⇒ 两个 JVM 写同一行
```

**缺陷本质**：`schema_hash` 的设计语义是「这一版本的本体内容摘要」，是下游用来判断
「本体是否变了、图谱要不要重算」的依据。现在它同时可能是：
- 真内容摘要（拉得到 schema 的那个 JVM 算出）；
- 或是 `sha256("placeholder-<id>-<ver>")`（拉不到时降级）。

而两个 JVM **都会写**，最终值取决于执行顺序与时序。于是**同一版本号可能对应两种 hash**：
一次发布如果 gateway 先写、dccheng 后写，落库是 placeholder；反之是真摘要。
更糟的是，placeholder 与真摘要都不是错误值——下游无法区分，只看到"hash 变了"。

**为什么本轮不修（如实登记）**：
1. 修法有多条互斥路径，需先定架构口径：
   ① dccheng 侧拉 schema 的 403 是信任链配置问题（应带服务凭据），修它则 placeholder 不再出现；
   ② placeholder 本身应**拒绝落库**（拉不到就写 FAILED 到 `kg_sync_log` 而不是伪造 hash）；
   ③ 应指定**唯一写入方**（单消费者），另一侧只做 KG 同步不做快照。
   三条各自成立，但选哪条决定了「谁是快照权威」，属架构裁决；
2. 单点改 `placeholder` 为「不落库」会改变既有 FAILED 兜底语义（`insertSyncLogFailed` 分支），
   且会掩盖 ② 里的 403 配置缺陷 —— 用改代码掩盖配置问题，正是要避免的。

**已做的（不涉及裁决的部分）**：
- 端到端实跑首证「发布 → 事件 → 落库」链路**是通的**（此前 0 行是历史无事件，非断链）；
- 探针数据完整还原：DB 行删除、Git 归档 `git revert` 两枚反向提交（不改历史）、
  `git ls-tree` 复查 1.0.4 已不在树中；
- 遗留：buszhi 内存索引仍持 1.0.4 条目（需重启 JVM 才消失），已报备用户，未擅自重启共享环境。

**同类面**：`EcosOntologyEventConsumer` 同时挂了 `@EventListener`（同 JVM）与
`EventBusService.subscribe`（Kafka）两条消费路径，代码注释自承"内存 fallback 下本路径被包成
`MemoryEnvelopeEvent`、无对应监听者，属预期无害重复"——但实测日志显示**同一条事件在同一 JVM
内被处理了两次**（gateway 日志 41478 与 41553 两段同内容），即"无害重复"实际发生了重复 upsert
与重复 KG 同步（`kg-ont-1.0.4` 触发两次）。这一点与上面的双 JVM 抢写叠加，构成"一次发布最多四次写入"。

### D71 处置进展（2026-11-14，用户裁决 = 修 403 + 禁 placeholder 落库）

## D72 — 本体版本「发布后无法撤销」：只能靠重写 Git 历史（已登记，未修）

在清理探针数据时暴露：`OntologyGitHistoryReader.listAll` 读的是 **Git 提交消息历史**
（`gitService.listCommits` 全量扫描 subject 里的 `Draft/Publish ontology <id> <ver>`），
不是 Git 工作树。因此：
- `git revert` 能删掉 `1.0.4.json` 文件，但**那条 `Publish … 1.0.4` 提交仍被扫出来**，版本照样列在接口里；
- 全仓 `OntologyVersionController` / `OntologyVersionSimpleController` **无 DELETE 映射**，
  设计册亦无「撤销发布」条款 ⇒ **发出去的版本无法撤回，只能靠重写 Git 历史**。

本轮处置（**已获用户明确授权后**执行）：该仓库 `git remote -v` 为空（纯本地、无远端），
且最顶上 4 个提交全由本轮探针产生（2 笔探针 + 2 笔 revert），故
`git reset --hard a084f98` 后接口从 5 条回到 **4 条（1.0.0~1.0.3）**，环境完全复原。

**产品缺口本身未修**（不属本批范围）：缺少「版本撤销/弃用」的正向操作通道，
线上误发布只能动 Git 历史——这在有远端或有他人协作的仓库上不可接受。
建议下一批补 `POST /api/v1/ecos/versions/{id}/revoke`（把版本标 Deprecated 并记录撤销人/原因），
而不是靠历史重写。
