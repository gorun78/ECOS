## 一、目的与判定哲学

### 1.1 这份方案要解决什么问题

平台上已经积累了多轮「测试通过」的记录，但本方案制定前的实测复核发现：**既有"绿"的口径与产品真实可用性之间存在系统性偏差**。三个实例：

| 实例 | 表面结论 | 实测真相 |
|---|---|---|
| 平台测试方案覆盖面 | 「覆盖 186 Controller / 48 路由」 | 当前实存 **282 Controller / 66 路由 / 494 表** —— 覆盖声明基于 2026-09-30 的旧快照，已滞后约 5 周 |
| E2E 通过数 | 「95 条用例」 | 其中 **23 条为 `test.fixme`/`skip`**，真实可执行上限约 72 条；若按 95 报通过率即为虚高 |
| 迁移脚本 lint | `PASS: 0 项 FAIL` | DR04/DR05 正则误用 `Singleline` ⇒ 全文件起点匹配 ⇒ **恒 0 命中恒 PASS**（D-15）；DR02 捕获组缺 `.` ⇒ schema 限定表永真通过（D-16） |

因此本方案的第一原则不是"多测"，而是**让每一条"通过"都能被证伪**。

### 1.2 判定哲学：四个不接受

1. **不接受无证据的通过** —— 每个 PASS 必须挂命令 + 原始输出 + 断言值
2. **不接受降级冒充正常** —— 503 / `NEEDS_RECONCILE` / 「部分实现」只能记 PARTIAL 或 FAIL
3. **不接受 mock 升格** —— 单测绿只证明函数逻辑，不能替代活体功能验证
4. **不接受静默缺失** —— 未执行的项必须写进「未执行清单」，不允许从分母中消失

### 1.2.1 两层验证：功能层 + 需求达成层（本方案的双层结构）

本方案不止验证「功能是否按设计工作」，还验证「功能是否达成了需求承诺的目标」。两层不等价，且**第二层才能抓住最高形态的假绿**：

| 层 | 问的问题 | 判定词 | 产出 |
|---|---|---|---|
| **功能层**（V1~V7） | 这个功能按设计工作吗？ | PASS / FAIL / PARTIAL / BLOCKED / NOT_EXECUTED / N/A（六值） | 功能是否可用 |
| **需求达成层**（RT） | 这个功能达成它承诺的目标了吗？ | 达成 / 部分达成 / 未达成 / 无法度量（四值） | 目标是否真的实现 |

**最危险的组合是「功能 PASS + RT 未达成」= 假落地**：测试全绿、页面能开、接口 200，但业务目标没实现。本项目已识别 14 项此类高危（见需求达成册 §五），典型如：

| 实例 | 功能层 | 需求层 |
|---|---|---|
| 预测-实际-偏差评估 | 接口 200 正常 | `applicable=false / value seam absent`，闭环未达成（P1-18） |
| 认知上下文安全裁剪 | 正确返回 403 | `ContextSecurityTrimmer` 无生产实现，required 源永不可用（P1-9） |
| 审计落库 | 生产侧发事件正常 | 无 `ecos.audit` 消费者，审计表无行（REQ-PLT-22） |
| 金额列读写 | API 正常读写 | `budget` 为 varchar，违反 MC01（D3） |

**结论规则**：`功能 PASS + RT 未达成` ⇒ 综合判定「假落地」，**禁止准出**。完整方法与 197 条需求映射见 `ECOS需求目标达成回顾验证-2026-11-13.md`。

### 1.3 本方案的产出定位

- **是**：可执行的操作手册 + 可复跑的代码 + 可审计的台账
- **不是**：设计评审、代码 Review、性能压测（各自有独立制品，本方案只在 V7 做基础可观测性检查）

## 三、七个验证维度（V1~V7）

每个功能条目按需勾选适用维度；不适用的记 `N/A` 并写理由。

### V1 界面渲染

| 检查项 | 方法 | 判定阈值 |
|---|---|---|
| 四主题 token 生效 | 切 `slate-light`/`deep-space`/`cyber-terminal`/`royal-purple`，比对关键容器背景/文字色 | 四套均渲染且互不相同；截图存证 |
| 禁硬编码颜色 | 静态 grep `bg-white`/`bg-slate-*`/`text-gray-*` 在受治文件 | 命中数 = 0 |
| i18n 键完整 | 切 zh-CN ↔ en，检查无裸 key（如 `workspace.l1.title` 直出） | 裸 key 数 = 0 |
| 禁硬编码中文 | 静态 grep 受治 TSX 的中文字面量（注释除外） | 命中数 = 0 |
| 图标来源 | 静态检查无裸 `<svg>`（登记例外除外） | 未登记 svg = 0 |
| 组件体积 | 单文件行数 | ≤ 800 行 |
| 布局溢出 | 1600×1000 与 390×844 两档截图 | 无横向滚动条异常、关键按钮可点 |

### V2 交互设计（六态矩阵）

每个屏级组件必须覆盖六态，缺一态即 `PARTIAL`：

| 态 | 触发方式 | 期望表现 | 反例（判 FAIL） |
|---|---|---|---|
| 空 | 查询返回 0 行 | 渲染 empty state + 引导动作 | 空白页 / 一直转圈 |
| 加载 | 网络延迟 | 骨架屏或 spinner | 白屏 / 布局跳动 |
| 错误 | 后端 500 | 错误横幅 + 重试入口 + traceId | 静默吞错 / toast 一闪而过 |
| 边界 | 超长文本、0/负数、超大分页 | 截断/换行不破版 | 溢出遮挡 / NaN |
| 权限 | 低权限账号访问 | 无权限提示，不渲染数据 | 渲染了数据但操作失败 |
| 离线/降级 | 引擎停机 | 503 横幅 + traceId，不显示旧数据当新数据 | 用缓存冒充成功 |

附加交互检查：按钮均有 handler（无死按钮）、模态可开可关可 ESC、表单校验有提示、提交有防重。

### V3 功能逻辑

| 子项 | 内容 |
|---|---|
| Happy path | 完整业务链路走通并落库 |
| 状态机合法跃迁 | 按设计枚举走完合法路径 |
| 状态机非法跃迁 | 越级/回退必须返回业务错误码，且 DB 无副作用 |
| 边界值 | 0、负数、超长、特殊字符、空数组 |
| 幂等 | 相同请求重复提交不产生重复数据 |
| 并发 | 同一资源并发写不出现脏数据（关键资源抽样） |
| 分页/筛选/排序 | 结果与参数一致，total 准确 |

**场景状态机关键枚举**（B1 断言依据，来源 `ScenarioStatusMachine.java`）：
`DRAFT → ... → ACTIVE → COMPLETED`；`COMPLETED` 需存在 FORMAL 运行（SANDBOX 不计），否则 `NO_FORMAL_RUN`。

**蓝图状态机**（`ScenarioBlueprintStateMachine.java`）：
`DRAFT → ... → APPROVED → RELEASED`；`RELEASED` 后不可原地改，须 revise 生成 `version+1`。

### V4 数据一致性

| 子项 | 断言方式 | 证据档 |

### V5 权限与安全

| 检查项 | 期望 | 实测基线（本方案采集） |
|---|---|---|
| 无 token 访问受保护端点 | 拒绝且不返回数据 | `GET /api/v1/system/users` → **403** |
| 错误 token | 拒绝 | 同上 → **401** |
| 有效 token | 允许 | 200 |
| 直连 service 端口（ADR-7） | 仅内网；本次实测直连 18090 → 403 | 记录实际（不判 FAIL，属设计边界） |
| 越权访问他人资源 | 拒绝 | 待 B1/B5 用非 admin 账号验 |
| RLS/ABAC 生效 | 未匹配策略即拒绝（fail-closed） | 已知 `caliber` 读面 403（`RLS_NO_POLICY_MATCHED`） |
| OPA 不可用 | 默认 DENY | 停机演练（B6，需授权） |
| 信任头伪造 | 客户端自带 `X-ECOS-USER` 不得被采信 | gateway 应剥离 |

> **注意一个真实不一致**：无 token 返回 403、错 token 返回 401。语义上「未认证」通常应为 401。此项记为观察项而非缺陷，交架构裁定后再定 PASS/FAIL。

### V6 契约与降级

| 检查项 | 期望 |
|---|---|
| 响应信封统一 | `{code, message, data, timestamp, success}`；失败含 `errorCode` |
| 未知属性不静默成功 | 传非法字段应报错或被明确忽略（不得出现「假成功」） |
| 前端不伪造 | 禁 `Math.random()` 造 hash、禁本地合成认知结论、禁硬编码身份 |
| 引擎不可用 | 前端显示 503 横幅 + traceId，不把空结果当正常 |
| 部分实现显式化 | 如 `NEEDS_RECONCILE`、`value seam absent` 必须原样透出 |

### V7 可观测性

| 检查项 | 期望 |
|---|---|
| traceId 贯通 | 失败响应带 `traceId`，前端可展示，后端日志可检索 |
| 审计落库 | 关键写操作在审计表留痕 |
| 错误码规范 | 非裸 500；带域前缀（如 `ECOS-SYS-503`、`ECOS-KB-050`） |
| 日志无敏感信息 | 凭据/Token 不回显、不落日志 |

## 四、判定词表与证据等级

### 4.1 判定词（六值，无「待定」）

| 判定 | 定义 | 计入通过率 |
|---|---|---|
| `PASS` | 有 L2 及以上证据，且断言值命中期望 | 是 |
| `FAIL` | 有 L2 及以上证据，断言未命中；必须附原始输出 | 否（计失败） |
| `PARTIAL` | 主路径通过但存在未验证分支；**必须列出未执行分支** | 否（单列） |
| `BLOCKED` | 前置条件不满足（引擎未起、权限缺失、数据缺失）；必须写阻塞源与责任方 | 否（单列） |
| `NOT_EXECUTED` | 本轮未跑 | **否（绝不进分母）** |
| `N/A` | 该维度对该功能不适用；必须写理由 | 否（单列） |

### 4.2 证据等级（只升不降）

| 级 | 定义 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| `L1` | 单元测试通过，且有 `Tests run: N, Failures: 0` 行 | 函数/类逻辑正确 | 装配正确性、真实集成行为 |
| `L2` | 真实 HTTP 调活体服务（真实 PG） | 服务端功能与契约 | 用户界面可见性 |
| `L3` | 真实浏览器（Playwright）+ 真实后端 | 用户可见功能与交互 | 数据持久化细节 |
| `L4` | 直连 PG 查询对账 | 持久化一致、schema 正确 | 业务语义正确 |

**组合要求**：涉及写操作的条目，`PASS` 至少需要 `L2 + L4`；涉及界面的条目，至少需要 `L3`。

### 4.3 证据三元组（每个 PASS 必填）

```

断言:      <期望值 → 实际值 的比对>
```

## 八、缺陷登记与流转

### 8.1 分级

| 级 | 定义 | 处置 |
|---|---|---|
| **P0** | 数据丢失/越权/核心链路不可用 | 立即上报，阻断准出 |
| **P1** | 功能与设计不符，但有绕行方案 | 进台账，本批修复或明确排期 |
| **P2** | 环境/门禁问题，非产品功能缺陷 | 登记，避免反复误判 |
| **P3** | 技术债、体验瑕疵 | 登记，择机处理 |

### 8.2 缺陷记录必填字段

```
ID / 标题 / 级别 / 发现批次 / 复现步骤 / 期望 / 实际 /
证据（命令+输出+截图）/ 归因（产品·环境·用例）/ 影响面 / 建议 / 状态
```

### 8.3 归因三分法（关键：避免把用例问题算成产品缺陷）

| 归因 | 判据 | 处置 |
|---|---|---|
| **产品缺陷** | 符合设计文档承诺，但实现不符 | 记缺陷 |
| **环境缺陷** | 因服务未起/数据缺失/配置错误导致 | 记 BLOCKED，不算产品 FAIL |
| **用例缺陷** | 断言写错、路径猜错、期望值与设计不符 | 修用例，重跑，原结果作废 |

## 九、覆盖度记账规则（「不漏项」的机器可核口径）

### 9.1 三个必须闭合的账

| 账 | 口径 | 闭合条件 |
|---|---|---|
| **路由账** | `main.tsx` 的 66 条 `<Route>` | 每条在矩阵中有唯一 ID |
| **端点账** | 282 个 Controller 按域归组 | 每组在矩阵中有代表条目覆盖其主路径；未逐一覆盖的必须在「未覆盖清单」列明 |
| **页面账** | 417 个 `.tsx`（含子组件） | 屏级组件必须有 ID；纯展示子组件可合并计入父条目 |

### 9.2 每份报告必须给出的四个数

```
总数 = PASS + FAIL + PARTIAL + BLOCKED + NOT_EXECUTED + N/A
可执行数 = 总数 - NOT_EXECUTED - BLOCKED - N/A
通过率 = PASS / 可执行数     （分母不含未执行与环境阻塞）
```

**禁止**：把 `PARTIAL` 混入 `PASS`；把 `NOT_EXECUTED` 从分母里悄悄删掉；用「覆盖率 90%」这种无法复算的说法。
