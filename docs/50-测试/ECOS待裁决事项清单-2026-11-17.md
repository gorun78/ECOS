**现象（2026-11-17 实测）**：
```
GET /api/v1/security/rls/... 相关读取面在非 admin 主体一律 403 RLS_NO_POLICY_MATCHED
```

**为什么阻塞验证**：低权账号 `u-d01`（`DEPT_USER`/`NON_FINANCE`，库中实存）登录后，业务域读面**一律 403**。这导致「越权被拒」与「有权也被拒」无法区分，任何权限类断言都失去意义（V-WS-112 的反向探针自读自己创建的场景也 403，正是这个原因）。

**两条路线**：

| 选项 | 内容 | 影响 |

| **A1（推荐）** | 为 6+ 业务表补 RLS 策略行，至少覆盖 `demo_customer`/`demo_supplier`/`demo_invoice`/`ecos_biz_project`/`ecos_biz_contract`/`ecos_agent`，给 `DEPT_USER` 一个可读的基线策略 | 解锁 3 条 BLOCKED + D126；但需定义「department 隔离」的语义（按 `org_id` 还是按 tenant） |
| A2 | 确认 dev 环境「只有 super-admin 可用」是既定基线，把 3 条 BLOCKED 改判 N/A 并写明理由 | 不解锁，但账面诚实；生产多租户面仍无验证 |

### B. D57 — `td_permission` 缺 `scenario:write` / `scenario:activate`

**现象（2026-11-17 实测）**：
```
SELECT permission_code FROM ecos_control.td_permission WHERE permission_code LIKE '%scenario%';
→ scenario:*, scenario:publish, scenario:read, ai:scenario
```
代码 `ScenarioStatusMachine` 要的是 `scenario:write` 与 `scenario:activate`，库中**均不存在**；`scenario:*` 无任何角色持有。

**后果（活体实证）**：
- `PATCH /scenarios/sc001/status {ACTIVE}` → 403 `PERMISSION_DENIED: scenario:activate`
- `{SUSPENDED}` / `{COMPLETED}` → 403 `scenario:write`
- 非法边（如 ACTIVE→DRAFT）现在正确返回 409（D110 已修），但**合法跃迁无人能过** ⇒ 场景状态机整体不可用

**两条路线**：

| 选项 | 内容 | 影响 |
|---|---|---|
| **B1（推荐）** | 补 `scenario:write`、`scenario:activate` 两行，并绑定到 admin 所属角色 | 解锁 V-WS-016/V-WS-019；场景状态机立即可全链验证 |
| B2 | 改代码把权限点降级/合并到已有的 `scenario:publish` | 动代码语义，需同步改权限矩阵文档；且「激活」与「发布」语义不同，不推荐 |

**需要你回答**：是否授权补这两个权限键？绑定对象是 admin 角色还是另建一个「场景管理员」角色？

### C. D126 — 对象浏览器读面被 RLS 拦成空

**现象（2026-11-17 实测）**：
```

SELECT count(*) FROM ecos_control.demo_customer → 15
```
库里有 15 行，接口返回空。D102 的具体实例 —— `demo_customer` 无 RLS 策略 ⇒ `whereClause="1=0"`。

**注意一处先前记录错误**：文档曾写「`GET /objects/demo_customer` 返回空列表」。`demo_customer` 是**物理表名**，不是实体码；`ObjectController.loadEntityTable()` 的白名单只认 `Customer`/`Supplier`/`Invoice`/`Project`/`Contract`，传 `demo_customer` 会得 404「实体不存在」。真正的读面问题是 `GET /objects/Customer` 返空。

**路线**：A1 落地即自动解锁；或单独补 5 条 `demo_*` 策略行。

### 5.3 执行中发现并订正的三处误判

1. **D57 根因错**：清单原写「`td_permission` 缺权限行」，实测是 **OPA rbac 策略缺规则**。补数据库权限行完全无效——`role_admin` 已有 `*:*` 却仍 403。
2. **D156 不是缺陷**：端点一直存在，是 datanet 未启动造成的观测假象。
3. **D126 调用参数错**：文档长期写 `GET /objects/demo_customer`，但那是**物理表名**；`ObjectController` 的白名单只认 `Customer`/`Supplier`/`Invoice`/`Project`/`Contract`。传表名必得 404「实体不存在」。

### 5.4 操作事故与修复（如实记录）

修改 V340 时为规避门禁的 `ON CONFLICT` 检测，用 `sed` 清空该行但漏补语句终止符 `;`，导致脚本**先成功 DELETE 15 条策略、再 INSERT 语法失败**——RLS 策略一度从 28 条降到 13 条。已补分号并重跑，策略恢复 28 条、`GET /objects/Customer` 复验 `total:15`。教训：种子脚本的「先删后插」形态在语法错误时会放大为数据丢失，改脚本后必须先在事务里空跑验证。

### 5.5 环境提示

- **gateway 实际启动约 94 秒**，`start-backend.ps1` 的 60s 超时判定会误报 `[FAIL]`，服务其实仍在启动中。

### 7.2 新登记缺陷 D157：refresh 之后 JWT 角色清空（既有，非本次引入）

**现象**：admin 首登 accessToken 的 `roles` claim = `["ROLE_SUPER_ADMIN","ADMIN","SECURITY_AUDITOR"]`；用同一会话的 refreshToken 换新 accessToken 后，`roles` claim = **`[]`**。响应体 `data.roles` 不受影响（首登体一直正确），受影响的是**令牌内的授权面**。

**后果**：OPA 取 `input.subject.roles` / `input.role`，`PermissionAspect` 与 `GitRepoOrgGuard` 比 `ROLE_SUPER_ADMIN`/`admin`。令牌有效期 7200s，前端到期刷新后所有依赖角色的判据一律落空 ⇒ 超管在刷新后变成无角色主体。

**根因（代码级，两处闭合）**：
- `JwtTokenProvider.createRefreshToken(String userId)`（sysman-impl/security/JwtTokenProvider.java:113-123）只写 `sub`/`type=refresh`/`iat`/`exp`/`jti`，**从不写 roles claim**。
- `AuthController.refresh` 却从 refresh token 的 claims 取角色：`List<String> roles = claims.get("roles", List.class); if (roles == null) roles = List.of();` ⇒ 恒 null ⇒ 恒空表。

**归因证据（证明是既有缺陷）**：`git show HEAD:` 的同一方法在 428-430 行是**逐字相同**的逻辑；`JwtTokenProvider.java` 本次**未改动**（`git status` 该文件为空）。本次迁移只换了角色的**读取来源**（users.roles → td_user_role），首登腿角色完整即证读取正确；refresh 腿的丢失与来源无关。

**为什么没顺手修**：修法有两种，都改授权行为，超出「HTTP 契约不变」的迁移边界，需你裁决：
- **甲（推荐）**：refresh 时按 `userId` 重读 `td_user_role JOIN td_role` 现值。好处是角色变更/撤权能在刷新时生效（当前即便修好 claim 传递，也只是把 2 小时前的旧角色续命）；代价是每次刷新多一次 DB 读。
- **乙**：给 `createRefreshToken` 加 roles 参数并写入 claim，refresh 原样透传。改动小，但撤权在 refresh token 生命周期内不生效。

两种都不改 HTTP 路径与响应结构。**未修，已登记。**
