# 非结构化文档解析方案（MinerU + LLM 抽取 + 实体链接 + 入库审核闭环）

> 文档编号：ECOS-DESIGN-COG-05 | 版本 v1.0 | 2026-09-01
> 作用：Wave-3B「OAG 8 步」里 **s4_extract / s5_build** 两个节点的上游契约文档。
> 注意：Tika 解析（PMO-34）已落到 kb-engine，本文档**不重复**那部分，仅补充 **MinerU 接入（OCR + 版面分析）** + **LLM 抽取产物（entity / link / rule 三类）** + **实体链接到本体对象** + **入库审核闭环** 四段。
> 不做：不搬移 kb-engine、不引入新 Maven 模块、不动 `callAiExtraction` 既有签名（只增字段）。

## 一、背景（已核实代码）

kb-engine 现状（`KnowledgeExtractionService` 320 行）：

| 环节 | 现状 | 评估 |
|------|------|------|
| `upload(file)` | 文件落 `~/ecos-extractions/<uuid>_<name>`，写 `extraction_drafts.status=UPLOADED` | ✅ 完整 |
| `parseFile(path)` | 调 `DocumentParserService.parse(...)`（Tika，PMO-34） | ✅ 完整 |
| `callAiExtraction(text)` | 走 `POST /api/v1/agent-loop/chat`（ai-engine Agent Loop），**统一 systemPrompt 要求 entity/relation/rule JSON** | ✅ 已就位 |
| `approve(id)` | 写 `compliance_rules` 表（规则） + Neo4j 实体（**逻辑不完整**：当前只更新 status，没调 kgWriter） | ⚠️ 缺陷 |
| 实体 → 本体 | **无** — `extracted_entities` 没有 `domain_id`/`object_type_id` 反向关联 | ⚠️ 缺口 |
| 失败重试 | 已实现 `MAX_RETRY=1` | ✅ 完整 |

`extraction_drafts` 表缺列（**仅增加**）：`extracted_links_json`、`entity_links_json`、`reviewer`、`review_at`、`mineru_meta`。

> 铁律引用：[架构铁律 0.3/3.1/3.3](../../ARCHITECTURE-RULES.md) — kb-engine 不直接调 LLM（那就 ai-engine），cognitive 不操作 kb 表（实体链接只通过 `ontology-engine` 的 REST 校验 `object_type` 是否匹配，不直接查 `ecos_object_type`）。

## 三、MinerU 接入策略（不抄 Tika，二期方案）

**为什么不直接替换 Tika**：PMO-34 已交付 Tika 通道，**先保留 Tika 走小额/文本类**；MinerU 走字号 / 版面 / OCR 场景，两条路在同 `DocumentParserService.parse()` 内 **按 file_features 路由**：

```java
// DocumentParserService.parse 改造后（kb-engine，仅示意，本期不动 Tika 通道代码）
public ParseResult parse(Path filePath) {
    long size = Files.size(filePath);
    String type = DetectFileType.fromPath(filePath);     // 新建 @TBD
    boolean needsMinerU = size > 5_242_880 || type == "PDF" && hasImageOrScan(filePath); // 启发式
    return needsMinerU
        ? mineruParser.parse(filePath)                    // 新建 @TBD MinerUHttpParser
        : tikaParser.parse(filePath);                     // 既有
}
```

`MinerUHttpParser` 契约（@TBD，新建独立类不替换 Tika）：

```java
public class MinerUHttpParser {
    // 调外部 MinerU 服务 (MinerU 不是 Docker 容器，Notifier 模式)
    // docker: mineru --serve 端口 8002，由 infra 部署，**不在本仓库 compose**
    // POST http://mineru:8002 /v1/parse  body={file: base64, options:{ocr:true,
    //   layout:true, max_pages:500}}  resp={text, blocks[], page_meta[], usage}
}
```

> 限制：单文件 < 50MB；扫描章节 fallback Tika 文本层；失败抛 `BusinessException`（不静默）。

## 五、实体链接（entity linking） — 本期核心增量

每个 entity 必须附 `linking` 元信息（**结构化**，前端可点击查看）：

```java
// 数据契约（新增 @TBD：entityLinking.java 在 kb-engine-api，与 cognitive 无依赖关系）
public class EntityLinking {
    String entityName;
    String ontologyDomainId;       // ontology-engine /api/v1/ontology/domains 返回
    List<OntologyTypeCandidate> candidates;   // 同名/近名本体对象（top-3）
    int autoLinked;                // 自动命中的个数
}
public class OntologyTypeCandidate {
    String objectTypeLabel;        // 本体对象 label
    double confidence;             // 余弦距离 or 名称相似
    String evidence;               // "name_similarity=0.92"
}
```

调用方式（**跨引擎 REST，不 import ontology-impl**）：

```java
// EntityLinker @TBD 新建（kb-engine-impl）
GET  http://ontology-engine:18083/api/v1/ontology/types?keyword={entityName}&top=3
// 返回 candidates
// 策略：name 精确匹配 + confidence>0.7 → 1 个候选 autoLinked
//      否则 candidates 0-2 个，autoLinked=0，留给审核环节手动选
```

## 六、入库审核闭环

> 现有 `approve(id)` 的缺陷：**实体没写 Neo4j**（只 `UPDATE status`），规则写了但没查重。本期补齐：

```java
// approve 改造后契约
public ApprovalOutcome approve(String id, ApproveRequest req) {
    // 1. 校验 status
    // 2. 规则去重：compliance_rules 上 name+domain 唯一
    // 3. 实体：走 KGWriterService.saveSubGraph(...)（已有 API）写入 Neo4j
    // 4. 规则：ruleMapper.insert(...)（已有）
    // 5. 写 ecos_provenance_entry (entity_type="extraction", source_type="KB", activity="approve")
    // 6. 审计 POST /api/v1/security/audit/log (异步)
    // 返回 ApprovalOutcome { counts: {rules, entities, links}, rejectedReasons: [] }
}
```

`ApproveRequest` 含 `entityEdits[]`（审核人可改 entity type） + `ruleEdits[]`（改规则 condition/action）。

**拒绝分支**：`reject(id, reason)` 已存在；本期增 `rejectedReason` 字段（避免空拒绝）。
