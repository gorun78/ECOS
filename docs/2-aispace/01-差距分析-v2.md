## 〇、参照标准：Palantir AIP 核心哲学

Palantir AIP的本质：
> **Ontology = 企业业务的可执行数字孪生**。数据不搬、逻辑不重写——所有现有系统的数据在 Ontology 层被赋予"业务语义身份"，让 LLM 和 Agent 真正理解"这个数据代表什么业务含义、谁能操作它、怎么操作才是对的"。

**五层架构**：Apollo底座(L0) → 数据基础层(L1) → 模型服务层(L2) → ★本体核心层(L3)★ → 应用交互层(L4) → 决策行动层(L5)

**OAG 8步闭环**：提问 → 意图抽取 → 本体检索 → 权限校验 → Prompt构建 → LLM推理 → 验证审计 → 结构化回复/操作

**AIP vs 通用Agent框架的最本质差异**：AIP有Ontology层做语义锚定，Agent不是在碎片化文本里靠RAG硬猜，而是通过Ontology理解"这个数据是啥、谁能碰、怎么操作才是对的"。

## 二、核心差距（按严重度排序）

### 🔴 G0：OAG 8步闭环 — 零实现

**Palantir的做法**：用户提问→意图抽取(实体映射到Ontology ObjectType)→本体知识检索(图遍历+属性校验)→权限校验(RBAC+ABAC+行级)→OAG Prompt构建(结构化Ontology语义注入LLM，非碎片RAG)→LLM推理→结果验证(业务规则+数据一致性)→结构化回复/操作执行

**ECOS现状**：`AgentLoopService` 是通用多轮工具调用，没有Ontology感知。AI工作台里的ChatbotStudio是三栏mock，对话就是"用户发消息→调LLM→返回"。没有任何OAG流水线。

**需要做的**：
1. 构建OAG Pipeline引擎（串联8个节点的DAG执行器）
2. 每个节点对接已有引擎——意图抽取→cognitive-engine，本体检索→ontology-engine，权限校验→security-engine，Prompt构建→kb-engine
3. 让AgentLoop从"通用工具调用"升级为"Ontology驱动的结构化推理"

---

### 🔴 G1：Ontology不是灵魂，只是"一个模块"

**Palantir的做法**：Ontology是L3核心层，ObjectType+LinkType+ActionType+Function+PermissionEngine+AuditLogger全部围绕Ontology构建。Agent访问数据的唯一途径是通过Ontology。

**ECOS现状**：ontology-engine有ObjectType和LinkType，但缺两个致命组件：
- **ActionType完全缺失**：没有"动词"概念，Agent想操作数据只能调通用SQL/REST工具，没有前置条件校验、后置动作、审计约束
- **PermissionEngine弱耦合**：security-engine的RLS/CLS是独立端点，Ontology查询时不自动注入权限过滤

**需要做的**：
1. ontology-engine补充ActionType：前置条件+后置动作+审计约束
2. ontology-engine + security-engine深层集成：每次Ontology查询自动调RLS/CLS
3. AI工作台的"本体工作台"接入AI Agent——让用户为本体对象配置ActionType

---

### 🟡 G2：缺AIP Evals评估框架

**Palantir的做法**：AIP Evals——Agent评估框架，跨模型性能对比、幻觉检测、执行稳定性测试

**ECOS现状**：`AgentStudioController`有`/test`和`/compare`端点但无评估体系（无标准问题集、无评分维度、无雷达图）。

**需要做的**：
1. 内置业务场景问题集（财务分析/供应链/制造执行各20道题）
2. 5维度评分：准确性/安全性/响应时间/幻觉率/工具调用正确率
3. 前端评估面板：选择Agent→选择问题集→跑评估→雷达图+逐题详情

---

### 🟡 G3：ChatbotStudio — 从mock升级为OAG对话面板

**当前**：1612行mock代码，左侧Agent列表+中间对话区+右侧配置面板全是硬编码。

**目标**：真实的OAG对话面板。
1. 对话区展示OAG 8步进度条（当前在第几步）
2. 中间消息区显示"本体解析了什么对象→权限过滤了哪些字段→数据来自哪个数据源"
3. 右侧不是硬编码配置面板，而是动态显示当前对话的Ontology上下文（当前涉及的对象类型、关联关系图谱缩略图）
4. SSE流式打字效果
5. 多线程切换 + 导出

---

### 🟡 G4：Agent工作台 — 从CRUD升级为Agent全生命周期

**当前**：AIPAgentController提供CRUD+templates+instantiate。AgentStudioView是1301行mock。

**Palantir全生命周期**：Build → Orchestrate → Evaluate → Deploy → Monitor

**目标**：
1. **Agent市场**：6内置模板卡片化展示+一键实例化
2. **Agent测试控制台**：调backend test API + 实时SSE输出
3. **Agent部署**：已实例化Agent有"上线/下线"开关+版本回滚
4. **Agent监控**：调用量/平均响应时间/错误率/幻觉率趋势图

---

### 🟡 G5：LogicView — 从列表升级为可视化工作流编排

**当前**：LogicView是列表形式。

**Palantir Logic画布**：可视化工作流编辑器，if-then规则+定时调度+Human-in-the-Loop节点

**目标**：
1. 引入拖拽画布（React Flow）
2. 节点类型：LLM调用/工具调用/Ontology查询/人工审批/条件分支/定时触发
3. 双击节点展开配置面板
4. 一键执行+实时节点状态

---

### 🟢 G6：三网隔离安全 — 远期规划

Palantir针对政务场景设计了"政务内网(涉密数据)→政务外网(AI推理)→政务外网(用户交互)"三层隔离。

ECOS目前是单层安全（security-engine统一管理）。三网隔离属于Phase 4-5的架构演进，不在Phase 2范围。但OAG Pipeline设计时需预留安全代理层接口。

---

### 🟢 G7：Workshop可视化 — 远期

Palantir Workshop是拖拽式应用构建器。当前不做，留Phase 5。

## 四、与旧差距分析的对比

旧版差距分析（01-差距分析.md）关注的是"前端mock对接后端API"——这是一个纯对接任务。新版差距分析从Palantir AIP的高度重新审视后，核心矛盾不再是"有没有对接"，而是：

> **ECOS缺的不是Agent工具，缺的是"Ontology驱动的OAG闭环"。**

后端AgentLoop已经有了工具调用能力，但没有Ontology语义层作为Agent的"业务地图"。Agent不知道它访问的数据代表什么业务含义——它只是在调通用SQL，不是在操作业务对象。

**Phase 2不是做"前端对接"——是补上从Ontology→OAG→Agent评估→可视化编排的全链路AI能力。**
