### 1.2 关键功能逐项检查

#### 1.2.1 Health 端点 — 🟢 已有

- `GET /api/v1/engine/ontology/health` → HealthCheck (db ping + ontology count)
- `GET /api/v1/engine/ontology/config` → 引擎配置
- `GET /api/v1/engine/ontology/status` → 引擎状态
- `POST /api/v1/engine/ontology/start` / `POST .../stop` → 生命周期
- **实现类**: `OntologyEngineImpl` (84行) → 实现 `IEngine` 接口，包含 `healthCheck()`/`pingDb()`/`countOntologies()`/`AtomicReference<EngineStatus>`
- **HealthService**: `OntologyEngineHealthService` (60行) — 5 个 health 指标 (DB/Entity/Property/Relationship counts)

#### 1.2.2 自动发现 (DB 表 → 本体推荐) — 🟡 基础，缺 UI 闭环

- **Controller**: `AutoDiscoverController` (48行)
  - `POST /api/v1/ecos/domains/{domainCode}/auto-discover` — 指定 datasourceId + resourceNames，自动从 `td_data_field` 表读取字段，创建实体+属性+映射
  - `GET /api/v1/ecos/entity-mappings` — 查询已创建的映射
- **Service**: `AutoDiscoverService` (214行)
  - ✅ 查询 `td_data_resource` / `td_data_field` 获取 DB schema
  - ✅ 自动创建 `ecos_ontology_entity` / `ecos_ontology_property` 记录
  - ✅ 创建 `ecos_entity_table_mapping` 映射记录 (ON CONFLICT upsert)
  - ✅ SQL 类型到本体类型的映射 (INT→NUMBER, VARCHAR→STRING, etc.)
  - ✅ 表名→实体名驼峰转换 (snake_case→CamelCase)
- **缺失**: 前端无自动发现触发 UI；无推荐置信度/预览机制

#### 1.2.3 Function 执行引擎 — 🔴 空白

- **前端有**: 属性创建支持 `functionType: "EXPRESSION"` 和 `functionExpression` 字段
- **后端有**: `PreconditionEngine.java` / `PostActionExecutor.java` (规则评估，非沙箱执行)
- **缺失**:
  - 🔴 无 Function 表达式沙箱执行引擎
  - 🔴 无 Function 计算服务 (编译/解析/执行表达式)
  - 🔴 无 Function 调用审计/超时控制/权限隔离
  - 🔴 无 Function 测试端点（有 Action test，无 Function test）

#### 1.2.4 版本管理 — 🟡 基础，缺多版本共存

- ✅ 创建版本 (Draft) → 发布 → 回滚 → 废弃
- ✅ 版本 diff (v1 vs v2)
- ✅ 简化端点版本查询
- 🔴 缺少: 多版本同时共存 (同时有 Published v2 + Draft v3)
- 🔴 缺少: 版本时间线可视化 API (无 timeline 端点)
- 🔴 缺少: 版本间依赖/影响分析

#### 1.2.5 提案/审批工作流 — 🟡 基础，未持久化

- `OntologyProposalController` (349行) — **内存存储 (ConcurrentHashMap)**
  - ✅ DRAFT → PENDING → (APPROVED | REJECTED) 状态机
  - ✅ verify + execute PMO 指令端点
  - 🟡 进程重启数据丢失
  - 🟡 未与 OntologyVersionController 的发布流程集成
- `OntologyWorkflowController` (84行) / `WorkflowController` (221行) — **DB 持久化**
  - ✅ 工作流定义 CRUD + 发布/测试/验证/预览/克隆/导出
  - ✅ 流程实例启动/挂起/恢复/终止
  - 🟡 工作流审批与提案审批是两套独立系统，未打通

#### 1.2.6 跨本体对齐 — 🔴 空白

- `OntologyMappingController` 只处理单个实体到数据源的映射
- 🔴 无跨本体对齐端点 (ontology A entity X ↔ ontology B entity Y)
- 🔴 无对齐推荐/冲突检测
- 🔴 无本体合并/匹配算法

## 7. 架构专家修改意见

> 以下意见基于 DIKW 体系下本体层的定位：**本体 = 数据（D层）与知识（K层）之间的语义桥梁**。
> 核心原则：本体工作台不是画ER图的工具，是让企业数据"可理解、可推理、可治理"的语义基础设施。

### 7.1 定位修正：从"ER图编辑器"到"语义建模工厂"

当前 Phase 4 计划把"可视化ER图编辑器"列为首要前端功能，这是**方向性偏差**。

**问题**：企业数据建模的起点不是空白画布，而是已有数据库。要求用户从零拖拽建实体是反直觉的——数据已经躺在PG里了。Phase 3 已接入真实财务数据，放着不用却让人手动画ER图，本末倒置。

**修正**：将**自动发现**提升为 Phase 4 的核心用户入口，手动建模降为补充手段。

```
用户工作流（修正后）：
  连接数据源 → 自动发现候选实体 → 预览+勾选 → 一键生成本体
                                                    ↓
                                    需要调整？→ 手动编辑（属性/关系/Function）
```

这要求将 §1.2.2 的自动发现从 P1 提升到 **P0**：前端必须有完整的"触发→预览→确认"闭环。后端 AutoDiscoverService (214行) 已就绪，前端缺失是当前最大短板。

### 7.2 Function 类型：本体层的"计算属性"，不是附属功能

DIKW 体系中，**I（信息）层的核心价值是"为数据赋予业务含义"**。Function 类型是实现这一价值的关键机制：

```
D层（数据）:  fin_revenue.amount = 1,200,000  ← 原始数字
I层（本体）:  本月营收 = SUM(amount WHERE period=current_month)  ← Function计算 → 业务含义
K层（知识）:  毛利率下降5% → 因果链追溯 → 根因定位  ← cognitive-engine消费
```

**架构决策**：

1. **Function 沙箱执行引擎设计**（不是通用脚本引擎，是受限表达式计算器）：
   - 表达式语法：仿 SQL 聚合 + 数学运算（`SUM()`, `AVG()`, `COUNT()`, `+`, `-`, `*`, `/`, `CASE WHEN`）
   - 安全边界：白名单函数（禁止 `Runtime.exec`/反射/网络/文件IO），无变量声明，纯表达式
   - 执行模型：表达式编译→JdbcTemplate参数化查询→单值返回，超时5s
   - 缓存策略：Caffeine 本地缓存，TTL 300s，本体变更时主动失效
   - 审计：每次调用记录（Function名/参数/结果/耗时/调用者），写入 `ecos_function_audit_log`

2. **依赖图**：Function A 引用 Property X（这是一个 Function），Property X 引用 Property Y（这是 DB 字段）。形成 `Function→Function→DB字段` 的DAG。发布时校验无环。

3. **前端编辑器**（P1，Function 引擎就绪后再做）：Monaco Editor 嵌入，注册自定义语言（关键字高亮+自动补全本体属性名），执行预览按钮显示实时结果。

**优先级调整**：Function 沙箱引擎从 P0 保持不变，但前端表达式编辑器从 P1 降为 P1（引擎比编辑器优先）。

### 7.3 提案系统：本体治理的核心机制

当前 OntologyProposalController (349行) 用 ConcurrentHashMap 存提案——**进程重启全部丢失**。这是架构债，不是功能缺失。

**设计原则**：本体的每一次变更都应经过提案→审批→执行→归档。不是"可选的工作流"，是**唯一变更入口**。

**架构决策**：

1. **持久化优先**：提案写入 `ecos_ontology_proposals` 表（PG），状态机 `DRAFT→PENDING→APPROVED→EXECUTED/REJECTED`
2. **提案与版本联动**：审批通过→自动创建 Draft 版本→执行变更→版本发布。不是两套独立系统。
3. **变更类型覆盖**：CREATE_ENTITY, ADD_PROPERTY, MODIFY_PROPERTY, DELETE_ENTITY, ADD_RELATIONSHIP, CREATE_FUNCTION —— 每种类型对应不同的执行器
4. **回滚支持**：已执行的提案保留变更前快照（JSON），支持一键回滚

**独立工作流系统（WorkflowController 221行）与本体的关系**：保留工作流系统作为通用的流程引擎（Phase 5 全链路联调用），但本体域的变更审批走提案系统——更轻量、语义明确。

### 7.4 版本管理：从"线性版本号"到"分支模型"

当前模型 `v1→v2→v3` 适合发布记录，不适合并行开发。

**修正方案**（轻量分支，不过度设计）：

```
main（生产）  ← 只有一个 Published 版本
draft（工作区）← 当前正在编辑的版本，可以有多个变更叠加
proposal-{id} ← 每个提案对应一个临时版本快照（提案执行时自动创建）
```

**实现**：
- `ecos_ontology_versions` 表加 `branch` 字段（MAIN/DRAFT/PROPOSAL）
- 任何时候只能有 1 个 MAIN (published) + 1 个 DRAFT
- 提案执行：DRAFT fork → PROPOSAL → 变更写入 → 合并回 DRAFT → DRAFT publish → 旧 MAIN deprecated + 新 MAIN created
- 前端时间线：横轴按时间排列版本卡片，纵轴标识分支

**降级策略**（如果 2 周不够）：先做"单工作区 Draft"——只有 MAIN + DRAFT，不做 proposal 临时分支。前端时间线可以先做列表视图（非可视化时间轴）。

### 7.5 ER 图编辑器：分阶段交付

完整的 ReactFlow 交互式 ER 编辑器需要 2-3 周独立开发，Phase 4 的 2 周窗口内不可行。采用分阶段策略：

| 阶段 | 交付 | 周期 | 归属 |
|------|------|:--:|------|
| **M1（当前）** | SVG 静态画布 + 点击展开详情 + 高亮关系 | 已有 | — |
| **M2（Phase 4）** | 节点拖拽重排 + 框选 + 右键菜单（编辑/删除/添加关系） | 3天 | Phase 4 |
| **M3（Phase 5）** | ReactFlow 交互式画布 + 自动布局 + 缩放 + 小地图 | 2周 | Phase 5 |

**Phase 4 的 M2 交付物**：在当前 `DomainDesignerView` 的 SVG 画布上增加：
- 拖拽节点（记录新位置到 localStorage，不持久化到后端）
- 点击实体 → 右侧属性面板选中该实体
- 右键菜单：编辑实体 / 删除实体 / 添加关系 / 添加属性

这样在不引入新依赖的前提下，本体工作台从"只能看"升级为"可以操作"。
