## 一、核心目标

### 1.1 产品定位（一句话）
**ECOS 是面向企业决策层的"认知操作系统"，把"数据 → 本体 → 知识 → 认知 → 智慧"五对象跑通成可被 LLM/Agent 调用、可作因果归因、可审计可追责的"业务语义数字孪生"。**
→ [docs/ARCHITECTURE-RULES.md §0.2]、[AGENTS.md §项目概述]

### 1.2 价值主张（三句话）
1. **让 Agent 读懂业务** — 用五对象引擎 + 四转化层（G/Z/C/M），让 LLM 通过 Ontology 理解"数据代表什么业务含义、谁能操作、怎么操作是合规的"，对标 Palantir AIP 的 Ontology 核心层。
   → [docs/2-aispace/01-差距分析-v2.md §〇]
2. **让 LLM 帮助 Agent** — 引擎层通过 LLM 帮助 Agent 快速完成任务，Agent 仅需关注"数据代表什么业务含义、谁能操作、怎么操作是合规的"。
3. **治理即一等公民** — Decision/Policy/Exception/Precedent/ApprovalChain 五元组统一管理、Function 沙箱、提案审批、Agent 全生命周期，差异化于普通 RAG+Chatbot 方案。
   → [docs/5-cognitive/PMO-32-决策智能层.md §一]

### 1.3 参照标杆
- **Palantir AIP**：L3 本体核心层 + OAG 8 步闭环 + Evals（评估雷达图）。
- **Semantica**：决策管理 / 推理路径可解释 / 冲突消解 / 双时态版本。
- **Semantica**：数据源元数据策略、数据源元数据模型、数据源元数据管理、数据源元数据转换、数据源元数据查询、数据源元数据可视化、数据源元数据集成、数据源元数据应用、数据源元数据应用集成、数据源元数据应用可视化、数据源元数据应用查询、数据源元数据应用转换、数据源元数据应用管理、数据源元数据应用策略、数据源元数据应用审批、数据源元数据应用审批集成、数据源元数据应用审批可视化、
→ [docs/01-产品方案.md §五对象·五行 + 四转化]

## 五、关键结论（5 条）

### K1 — 产品当前地位
"骨架完成，AI 引擎 P0+P1+P2 全部交付"；但 AI 工作台前端存在严重隐患：4 个文件 6454 行 + 67% 文件无 i18n + 73% 文件硬编码中文（贪多求全膨胀）。Phase 2 的"快速亮剑"前提需要先把前端做大拆分与 i18n 收敛。

### K2 — Phase 1-5 顺序合理但偏乐观
sysman (2周) → AI (2周) → 数据+知识 (2.5周) → 本体 (2周) → 全链路 (2周)，**逻辑自洽**（"AI 先亮剑"降风险）。但 Phase 2/3/4 之间是线性依赖而非并行；Phase 3 cognitive-engine 从 2 层因果链扩到 ≥3 层被定位为"Phase 3 核心"，**工期与风险压在 2.5 周里**，建议增加 0.5-1 周缓冲。

### K3 — 文档与代码存在多处偏差
- PMO-37 第 1 轮复验发现主 Agent 把 T1/T10 未开始报"完成"；
- 架构层"五对象·五行"理念已写入铁律，**但 services/ 层实际仍是 10 个子服务**（技术债 D4 services 层收敛尚未启动）；
- 双证据源数字不一致（产品化方案 08-03 vs Semantica 方案 08-17 的 Java 文件数/Controller 数有 ±15% 偏差，如 ai 70→80、onto 31→42、kb 26→32）；
- gateway `@ComponentScan.basePackages` 仍含 5 个已删的旧模块（portal/market/worldmodel/cognitive）。

### K4 — cognitive-engine 是绝对短板
Java 文件 12、Controller 4，规模仅为 ai-engine 的 1/6；CausalReasonerServiceImpl 726 行靠 KG 遍历 + LLM 补充，`evaluateCondition()` 是字符串 contains 匹配（**非真规则引擎**），推理可解释性缺失。PMO-32~36 合计 25 人日（远超 Phase 3 知识工作台窗口）。

### K5 — 多轮验收机制有效
PMO-37 经过 4 轮（初验→复验→第 2/3/4 轮）才到"建议关闭评审"，证据链用 git commit + curl + DB 落库三重留痕，暴露了"connector 类型归一化缺失"、"DTO 未填充新列"、"taskId 不是 UUID"三个真实缺陷——**验证了"代码 ✅ 不代表运行时 ✅"**。

## 六、疑问点与待决问题（5 条）

### Q1 — AI 工作台前端真实度
差距分析 v2 标 L4"应用交互层 = mock 壳"，但差距分析也列 G0/G1/G3/G4 为 Phase 2 必交付；**若 Phase 5 就"Agent 自动拆 4 子任务 + 出月报"，AI 工作台前端打磨周期是否需要进一步压缩？**
（建议：Phase 1 期间用 1 周独立做"AI 工作台前端瘦身"——拆 4 个 6000+ 行文件、i18n 收敛、删 mock，**为 Phase 2 扫清障碍**。已列入步骤 4 清理清单。）

### Q2 — 多租户能力是否真被剪掉？
Phase 1 已砍掉租户模型，**但 Phase 5"租户隔离"验收项仍保留**（科创用户只能看科创数据），两者矛盾——**多租户能力是否真被剪掉还是 Phase 5 前必须补回？**
（建议：保留单租户 → Phase 5 前补回多租户隔离，列入 Phase 1 收尾验证项。）

### Q3 — cognitive-engine 优先级
PMO-32~36 五个指令（决策层 / 编排 / 非结构化解析 / SpEL / Pipeline）与"Phase 3 重点补 cognitive"在时间轴上是否对齐？
**PMO-32 5 天 + PMO-33 7 天 + PMO-34 3 天 + PMO-35 3 天 + PMO-36 7 天 = 25 人日，远超 Phase 3 后段"知识工作台"窗口。**
（建议：把 PMO-32/33 拆出来独立做 1 周，PMO-34/35/36 与 Phase 4 本体建模并行。）

### Q4 — 双证据源数字不一致
产品化方案（08-03）与 Semantica 方案（08-17）的 Java 文件数/Controller 数有偏差；**中间是否有新增 commit？需以 codebase-memory 38,498 节点诊断为准做一次审计校准。**
（建议：本步骤 2 报告中的"现状盘点"已给出最新精确数字，以本数据为准。）

### Q5 — PMO-37 关闭 vs PMO-D4 services 收敛
**业务交付与架构治理是否分轨？** PMO-37 建议"进入关闭评审"但运行时验证（A-G 8 项）还有 BUG-D1 未修（3e3e011 已修 UUID 透传），架构层面 "services 10 子服务 → 四转化 4 服务" 收敛（技术债 D4）尚未启动。
（建议：业务交付走 Phase 1-5 主线，架构治理并行走 D4，不阻塞 Phase 1；已列入步骤 4 清理清单。）
