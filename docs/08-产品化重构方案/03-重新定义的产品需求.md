# 步骤 3 — 重新定义的产品需求（SMART）

> 文档编号：ECOS-NRD-03 | 版本 v1.0 | 生成时间：2026-09-01
> 原则：所有需求必须符合 **SPEC-C**（具化 Specific / 可衡量 Measurable / 可实现 Achievable / 相关 Relevant / 有时限 Time-bound）
> 文档目的：替代散落各处的 Phase 1-5 描述，作为**单一可信需求源**

---

## 一、产品愿景（SPEC-C·Time-bound 框架）

### 1.1 一句话愿景（具化）
**到 2026-12-15（14 周内），ECOS 完成从"骨架完成"到"产品级企业认知操作系统"的跨越：5 大目标用户角色在真实业务场景中跑通 5 个端到端场景，所有核心链路 ≥3 层因果链、全程 KAG 可解释、72 小时稳定运行。**

### 1.2 三句话价值主张（具化到对象+输出）
1. **业务/管理层**：自然语言提问→AI 30-60s 出《月度经营分析报告》（含数据表格+≥3 层因果链图+改进建议）
2. **本体建模师/数据治理人员**：从 PG 财务数据自动发现本体候选对象（置信度 ≥0.7），一键发布到 KG，RAG 检索返回制度条款+关联本体对象
3. **系统管理员**：所有 Agent 调用、Function 执行、规则判定全程可审计（含 ReasoningPath + Justification 五元组）

## 四、用例场景（主流程 + 异常流程）

### 4.1 UC-01 科创月度经营分析（主场景）

**前置条件**：科创租户已创建 + PG 财务库已接入 + 财务本体已建 + 制度文档已抽取

**主流程**（Happy Path）：
```
1. 用户登录 sysman (admin@c1scientist)
2. 进入 AI 工作台 → 选择 ai-agent (orchestrator)
3. 输入 "分析科创信息上个月的经营情况"
4. Orchestrator 拆解：
   ├→ data-agent: "查 2026.7 营收/成本/利润/订单/交付率"
   ├→ ontology-agent: "获取财务域本体, 理解指标间关系"
   ├→ cognitive-agent: "对毛利率下降 5.3% 做因果链分析"
   └→ ai-agent 汇总
5. 每个子 Agent 调 llm-gateway → 调对应引擎 REST → 返回结果
6. 前端展示 3 个并行卡片 (data/ontology/cognitive) + 汇总 《7月经营分析报告》
7. 报告含：数据表格 + ≥3 层因果链图 + 改进建议
```

**验收**：
- [ ] 总耗时 < 60s
- [ ] 因果链 ≥ 3 层
- [ ] 报告含 3 个明确改进建议
- [ ] 无 console error
- [ ] 审计日志含 5 个 Agent 调用记录

**异常流程**：
| # | 异常 | 期望行为 |
|:--|------|------|
| E1 | data-agent 查 PG 超时 (30s) | 返回 "查询超时, 建议检查 PG 负载" + 跳过 data 子任务 + 汇总中明确标注 "数据查询超时" |
| E2 | cognitive-agent 查不到根因 | 返回 "因果链 ≤2 层, 可能数据不足, 建议查 ontology 补全" (但**至少给出 2 层**) |
| E3 | LLM Provider 500 错误 | 自动重试 3 次 (指数退避 1/2/4s) → 仍失败 → 友好错误提示 + 建议降级 Provider |
| E4 | 用户中途断网 ≤5s | SSE 自动重连, 5s 内恢复输出 |
| E5 | 用户中途切 Tab (≥5s 后) | 卡片提示 "对话仍在后台运行, 查看详情" |

### 4.2 UC-02 供应商准入审查（合规/法务场景）

**前置**：compliance_rules 表已载入 5 条准入规则

**主流程**：
```
1. 提交供应商申请 (含工商数据/财务数据)
2. 调 POST /api/v1/cognitive/evaluate-supplier
3. SpEL 规则评估 → 逐条匹配 → 生成 ReasoningPath:
   - Rule 1 (注册资本 ≥1000 万): [满足]
   - Rule 2 (连续 3 年盈利): [满足]
   - Rule 3 (无失信记录): [不满足] → Justification "工商 records 显示有失信"
4. 输出 Decision = REJECT, 含 Justification 全文
5. 审计日志写入 5 条 (申请/规则评估 3 条/决策)
```

**验收**：
- [ ] 5 条规则 100% 匹配评估 (无遗漏)
- [ ] REJECT 的 Justification 可读 (含具体规则名+数据源)
- [ ] 总耗时 < 10s
- [ ] 审计日志可追溯

**异常流程**：E1 规则配置错误 (SpEL 语法错) → 给出具体行号 + 修复建议 (不崩溃)

### 4.3 UC-03 多租户隔离（安全核心场景）

**前置**：已创建租户 A (c1scientist) + B (c2scientist), 各 1 个 admin 用户

**主流程**：
```
1. user_a 登录 → Schema 自动切到 a
2. user_a SELECT * FROM user → 只看 a.user
3. user_b 登录 → Schema 切到 b
4. user_a 尝试访问 /api/v1/tenant/b/user → 403
5. 跨租户写入 → 403 + 审计日志记录"越权尝试"
```

**验收**：
- [ ] 跨租户 SELECT/UPDATE/DELETE 100% 403
- [ ] 审计日志含 5 次越权尝试
- [ ] 性能开销 < 5% (RLS 注入)

**异常流程**：E1 security-engine 不可用 → 默认 DENY (100% 拒绝, 不降级为放行)

### 4.4 UC-04 DQ 每日巡检

**主流程**：
```
1. 08:00 触发 (runtime-task 全局调度)
2. 拉取所有注册的 DQ 规则 (按表分组)
3. 对每张表跑 3 类规则:
   - 空值率: SELECT COUNT(*) WHERE col IS NULL / COUNT(*)
   - 重复率: SELECT COUNT(*) - COUNT(DISTINCT col) / COUNT(*)
   - 值域:  配置 min/max 或 regex
4. 结果写入 dq_result 表 (含命中数/百分率/严重度)
5. 不达标规则 → 告警 (runtime-monitor → 邮件/Webhook)
```

**验收**：
- [ ] 10 张表跑 < 120s
- [ ] 命中规则可读 (列名 + 实际值示例)
- [ ] 失败告警 < 5min 送达

**异常**：E1 PG 超时 30s → 跳过该表, 记 "执行失败, 原因: 超时, 建议扩大 timeout", 不阻塞其他表

### 4.5 UC-05 本体自动发现

**主流程**：
```
1. 选择一数据源 → 选 5 张表
2. 调 POST /api/v1/ontology/auto-discover
3. 后端 Job:
   - 表名 → 提取关键词 (商品信息/订单明细)
   - 字段名 → 映射已知本体属性 (id/编码/名称...)
   - 类型 → 推断 (string→资产/decimal→金额)
   - 多表 JOIN → 推断关系
4. 返回候选对象+属性+关系 (含 confidence ≥0.7 的)
5. 前端 ER 编辑器高亮 → 用户勾选 → 发布 v1.0
```

**验收**：
- [ ] 5 张表自动推荐 ≤50s
- [ ] confidence ≥0.7 的候选 ≥12 个
- [ ] 发布后 KG 节点同步

**异常**：E1 表字段全部无名/拼音 → 推荐 0 个, 返回"表结构不规范, 建议先优化字段命名"
