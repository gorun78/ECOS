# Phase 1: sysman — 安全体系分析

> 用户的安全规划：事前（权限/隔离/项目授权）→ 事中（MAC/PBAC/RLS/CLS）→ 事后（审计）

---

## 一、当前安全能力分布（混乱）

```
sysman (身份层)                    security-engine (策略执行层)
├── UserController               ├── SecuritySandboxService
├── RoleController               ├── DataMaskingService
├── PermissionController         ├── OpaPolicyService
├── OrganizationController       ├── RowLevelSecurityService
├── AbacController          ←──→ ├── ColumnLevelSecurityService
├── DataPermissionController     ├── SecurityConfigService
├── SecurityConfigController     ├── IDataSecurityPolicyService
├── PolicyEngineController       │
├── CryptoAuditController        │
├── AuditController              │
└── DataMaskingController        │
```

**问题**：
1. 职责模糊：ABAC策略CRUD在sysman，OPA策略执行在security-engine，用户不知道该去哪
2. 前后端不对齐：前端有SecurityAudit.tsx在sysman下，但security-engine也有AuditController
3. 无统一入口：安全管理分散在"用户管理/系统配置/安全审计"等多个菜单

## 二、安全体系三段模型——职责重新划分

### 事前（Prevent）：谁可以做什么

| 能力 | 当前位置 | Phase 1归属 | 说明 |
|------|---------|:--:|------|
| 用户管理 | sysman/UserController | **sysman** | 身份CRUD，不变 |
| 角色管理 | sysman/RoleController | **sysman** | 角色CRUD+用户-角色绑定，不变 |
| 权限定义 | sysman/PermissionController | **sysman** | 资源→操作映射，不变 |
| 组织管理 | sysman/OrganizationController | **sysman** | 组织树CRUD，不变 |
| 项目授权 | 无 | **sysman** | 新增：项目→用户/角色授权关联表（P2随项目工作台一起做） |
| ABAC策略 | sysman/AbacController | **security-engine** 🔄 | CRUD迁入security-engine，sysman调用security-engine的REST |
| 安全配置文件 | sysman/SecurityConfigController | **security-engine** 🔄 | user/role安全profile的绑定逻辑迁入 |

### 事中（Detect & Protect）：访问时实时检查

| 能力 | 当前位置 | Phase 1归属 | 说明 |
|------|---------|:--:|------|
| 安全标记MAC | 无 | **security-engine** | 新增：数据密级标签（公开/内部/机密/绝密），文件/表/字段打标 |
| 合规分析PBAC | 无 | **security-engine** | 新增：访问目的声明+合规规则评估。如"for_audit"目的可以临时提升权限 |
| 行级安全RLS | DataPermissionController + RowLevelSecurityService | **security-engine** | 整合，统一为RLS REST端点 |
| 列级安全CLS | ColumnLevelSecurityService | **security-engine** | 不变 |
| 脱敏规则 | DataMaskingService | **security-engine** | 不变，加变更通知机制 |
| OPA策略执行 | OpaPolicyService | **security-engine** | 不变 |
| 策略评估 | PolicyEngineController | **security-engine** 🔄 | 从sysman迁入，提供 `POST /api/v1/security/policy/evaluate` |

### 事后（Audit）：追溯谁做了什么

| 能力 | 当前位置 | Phase 1归属 | 说明 |
|------|---------|:--:|------|
| 操作审计 | sysman/AuditController | **security-engine** 🔄 | 迁入security-engine，统合一站式审计 |
| 加密审计 | sysman/CryptoAuditController | **security-engine** 🔄 | 同上 |
| 数据访问审计 | 无 | **security-engine** | 新增：记录每次数据查询的SQL/参数/返回行数/耗时 |

### 最终架构

```
sysman（纯身份管理）                  security-engine（安全策略+执行+审计）
├── AuthController                  ├── AbacController         ← 从sysman迁入
├── UserController                  ├── SecurityProfileController ← 从sysman迁入
├── RoleController                  ├── PolicyEngineController ← 从sysman迁入
├── PermissionController            ├── MacLabelController      ← 新增（安全标记）
├── OrganizationController          ├── PbacController          ← 新增（合规分析）
└── ProjectAuthController           ├── RlsController           ← 整合现有
    (P2新增)                        ├── ClsController           ← 不变
                                    ├── DataMaskingService      ← 不变
                                    ├── OpaPolicyService        ← 不变
                                    ├── AuditController         ← 从sysman迁入
                                    ├── CryptoAuditController   ← 从sysman迁入
                                    └── DataAccessAuditController ← 新增
```

## 四、安全接入规则（其他引擎如何调用）

### 4.1 统一REST端点

所有引擎调用安全能力通过security-engine的REST API（端口18081，或走Gateway代理）：

| 调用场景 | 端点 | 调用方 |
|---------|------|--------|
| 检查用户操作权限 | `POST /api/v1/security/policy/evaluate` | 所有引擎 |
| 应用行级安全 | `POST /api/v1/security/rls/apply` | data-engine |
| 应用列级安全 | `POST /api/v1/security/cls/columns` | data-engine |
| 数据脱敏 | `POST /api/v1/security/masking/apply` | data-engine |
| 检查合规规则 | `POST /api/v1/security/pbac/check` | cognitive-engine, ai-engine |
| 记录审计日志 | `POST /api/v1/security/audit/log` | 所有引擎 |

### 4.2 调用规范

```json
// 策略评估请求
POST /api/v1/security/policy/evaluate
{
  "subject": {"userId": "u_001", "role": "analyst", "clearanceLevel": 2},
  "resource": {"type": "ontology", "id": "obj_finance", "classification": "内部"},
  "action": "read",
  "context": {"ip": "192.168.1.1", "time": "2026-08-03T09:00:00"}
}
// 响应
{"allowed": true, "matchedPolicies": ["POL-001"], "obligations": ["mask_salary"]}
```

### 4.3 接入规则（铁律）

1. **所有引擎的安全检查走security-engine REST**，不在本引擎内重复实现
2. **审计日志集中写security-engine**，各引擎不维护自己的审计表
3. **脱敏规则统一在security-engine管理**，data-engine查询后调masking/apply
4. **安全标记MAC由security-engine统一管理**，标记变更通知相关引擎刷缓存

## 六、内置角色（更新）

去掉租户/项目后，5个内置角色：

| 角色 | 可访问子系统 | 权限范围 | 理由 |
|------|------------|------|------|
| **admin** | 全部（安全中心） | 用户/角色/权限CRUD + 系统配置 + 全部安全策略 | 系统管理员，管控全局 |
| **data-manager** | g（数据工作台） | 数据源/血缘/DQ规则/Pipeline管理 | 数据团队，负责数据底座 |
| **ontology-designer** | zhi（本体工作台） | 本体对象/关系/Function/版本管理 | 建模团队，负责信息建模 |
| **knowledge-engineer** | cheng（知识工作台） | KG/规则库/分类/知识抽取管理 | 知识团队，负责知识资产 |
| **analyst** | 全部（只读+AI） | 数据查询/KG检索/RAG/AI对话/诊断/评估 | 业务分析人员，消费所有数据和分析能力 |

理由：
- 5个角色对应5个子系统的管理职责，边界清晰
- analyst作为通用消费者，跨子系统使用AI能力，不需要管理权限
- 不设viewer——analyst配置为只读即等同于viewer
- 不设operator——admin覆盖系统运维
- 如果未来需要更细粒度，在5个基础角色上通过权限组合扩展
