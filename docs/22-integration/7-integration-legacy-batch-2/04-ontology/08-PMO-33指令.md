## §背景

07 需求细化核实了 H1-H6 六处硬伤。PMO-28 交付的提案系统是"能存状态的状态机"，不是"唯一变更入口"——缺的是**执行器的完整性 + 校验的语义性 + 版本联动的正确性**。本轮按 R1-R5 补齐差距。

Function 沙箱引擎已就绪（PMO-29 交付：FunctionSandboxEngine/FunctionValidator/FunctionController 均在），CREATE_FUNCTION 执行器可直接落地，无空依赖。

**前置依赖**：PMO-32 T0 已完成（ecos_ontology_proposals 表已 @PostConstruct 兜底建表，提案 POST 不再 500）。若 PMO-32 尚未收尾，先等表建好再开工。

## §Task

### T1 — 状态机规范化（R1）

**文件**：`engine/ontology-engine/ontology-engine-impl/.../controller/OntologyProposalController.java` + `.../service/OntologyProposalService.java`

**操作**：
1. 状态严格收敛 5 态（大写）：`DRAFT / PENDING / APPROVED / REJECTED / EXECUTED`。删除 verify 里写 `verified`、execute 里写 `executed`（小写）的逻辑。
2. `verify` 降级为动作：`POST /{id}/verify` 只返回 `{valid, issues[]}`，**不写 status**。
3. `approve` 内部强制先跑 verify 逻辑：verify 不过 → 400 拒绝（verify 成为 approve 的前置守卫）。
4. `execute` 语义统一：真正执行 payload（调 executePayload）+ 状态 → `EXECUTED`，不再只改状态。
5. 加审计时间戳列（@PostConstruct 兜底，Flyway 禁用）：`submitted_at / approved_at / rejected_at / executed_at`，submit/approve/reject/execute 时回填对应列。
6. status 值在 Controller 层用 `Set` 强校验（`TERMINAL_STATUSES` 已存在，补非终态合法性检查），不加 DB CHECK（避免已有脏数据 ALTER 失败）。

**验收**：
```bash
# 全链路后 status 只有大写 5 态
curl -s -H "Authorization: Bearer ***" http://localhost:8080/api/v1/ontology/proposals | python3 -c "import sys,json; s=set(p['status'] for p in json.load(sys.stdin)['data']); print('PASS' if s.issubset({'DRAFT','PENDING','APPROVED','REJECTED','EXECUTED'}) else 'FAIL:'+str(s))"
# 期望 PASS
# approve 一个 payload 缺失的提案 → 400（verify 前置拦截）
```

### T2 — 执行器补全 9 类型（R2，核心）

**文件**：`OntologyProposalController.java` 的 `executePayload`（OntologyService 的 updateEntity/updateProperty/deleteEntity/deleteProperty/deleteRelationship 方法已存在，直接调用）

**操作**：按 07 payload 契约，9 种 proposal_type 各对应明确执行器：

| proposal_type | 执行器 | 关键点 |
|---------------|--------|--------|
| CREATE_ENTITY | `ontologyService.createEntity(domainCode, body)` | 已有 |
| MODIFY_ENTITY | `ontologyService.updateEntity(entityId, body)` | **新增** |
| DELETE_ENTITY | `ontologyService.deleteEntity(entityId)` | **补**（原 no-op），级联删 |
| ADD_PROPERTY | `ontologyService.createProperty(entityId, body)` | 已有 |
| MODIFY_PROPERTY | `ontologyService.updateProperty(propertyId, body)` | **修**（原错调 createProperty，需 propertyId） |
| DELETE_PROPERTY | `ontologyService.deleteProperty(propertyId)` | **新增** |
| ADD_RELATIONSHIP | `ontologyService.createRelationship(sourceEntityId, body)` + 环检测 | **补环检测**（调 validateRelationship，成环则拒绝） |
| DELETE_RELATIONSHIP | `ontologyService.deleteRelationship(relationshipId)` | **新增** |
| CREATE_FUNCTION | `ontologyService.createProperty(entityId, {functionType:"EXPRESSION", functionExpression:...})` | **补**（原 no-op），表达式先用 FunctionValidator.validate 校验 |

**验收**（每种类型一条 curl + 落库断言，禁止只断言 200）：
```bash
# MODIFY_PROPERTY：先建属性拿 id，再 MODIFY，断言 code 变化且 property 总数不变
# DELETE_ENTITY：断言 ecos_ontology_entity -1 且级联 property/relationship 删除
# ADD_RELATIONSHIP 成环：断言 400 + issue
# CREATE_FUNCTION：断言 ecos_ontology_property 新增一行 functionType=EXPRESSION
```

### T3 — 版本联动修正（R3，数据正确性）

**文件**：`OntologyProposalController.java` 的 `approveAndPublish`

**操作**：
1. **顺序修正**：`executePayload` → `createVersion`（拍变更后快照）→ `publishVersion`。当前 createVersion 在前，快照拍的是变更前状态，发布的是旧快照——必须颠倒。
2. `version_id` 回填 `version.getId()`（`ver5001`），不是 `version.getVersionNo()`（`1.0.1`）。
3. version 的 `changeLog` 带上 `proposalId`（如 `Proposal {id}: {proposalType}`）。
4. 全程 `@Transactional`：执行/建版本/发布任一失败，提案与本体一起回滚。

**验收**：
```bash
# approve-and-publish 后，该版本 snapshot 与本体当前状态一致（snapshot.entities 含新创建的实体）
# version_id 指向 ver* 记录：SELECT * FROM ecos_ontology_versions WHERE id=<version_id> 能查到
```

### T4 — 自动快照 + 回滚（R4）

**文件**：`OntologyProposalController.java` + `OntologyProposalService.java`

**操作**：
1. `executePayload` 执行前，按 target 自动抓变更前状态写入 `snapshot`（用 ontologyService 查当前 entity/property/relationship），不再依赖调用方手动传。
2. 新增 `POST /api/v1/ontology/proposals/{id}/rollback`：基于 snapshot 恢复，直接执行 + 写审计（紧急操作，不再走提案）。

**验收**：
```bash
# 执行 CREATE_ENTITY 后：snapshot 字段非空
# rollback 后：ecos_ontology_entity 该实体消失（恢复原状）
```

### T5 — verify 语义升级（R5）

**文件**：`OntologyProposalController.java` 的 `verifyProposal`

**操作**：verify 校验项（全过才 valid，返回 issues 列表）：
1. **引用完整性**：`entityId`/`propertyId`/`relationshipId` 必须存在；ADD_PROPERTY 的目标实体存在。
2. **唯一性冲突**：CREATE_ENTITY 的 code 在 domain 内不重复；ADD_PROPERTY 的 code 在该实体下不重复。
3. **环检测**：ADD_RELATIONSHIP 调 `ontologyService.validateRelationship`，成环则 issue。
4. **类型白名单**：propertyType ∈ {STRING/NUMBER/BOOLEAN/DATE/DATETIME/REFERENCE/EXPRESSION}。
5. **级联影响**：DELETE_ENTITY 返回将级联删除的 property/relationship/action 数量 + 引用它的对象实例数。

**验收**：
```bash
# 构造"引用不存在实体的 ADD_PROPERTY" → verify 返回 valid=false + issue 明确
# 构造"重复 code 的 CREATE_ENTITY" → valid=false + issue
```

## §执行顺序

```
T1（状态机）→ T2（执行器）→ T3（版本联动）→ T4（快照回滚）→ T5（校验升级）
```

T1 是基础（状态语义理清，T2-T5 才不会在脏状态上叠加）。T3/T4 依赖 T2 的执行器就绪（快照要能查、payload 要能真执行）。T5 依赖 T2 的 9 类型就绪（才能校验各类型引用）。

## §禁止清单

1. curl 200 就判 PASS（必须看本体表 entity/property/relationship 落库变化）
2. 只写 Flyway 迁移文件不 @PostConstruct 兜底（加审计时间戳列同理，Flyway 已禁用）
3. MODIFY_PROPERTY 再调 createProperty（必须 updateProperty + propertyId）
4. verify 改 status（verify 是动作，只返回 valid/issues，不写状态）
5. 提案执行不留快照（snapshot 必须 executePayload 前自动写入）
6. DELETE_ENTITY 物理删除不做影响检查（执行前 verify 已返回级联影响）
7. 跨 Phase 预创建文件
