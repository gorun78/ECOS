# 推理可解释性规格（SpEL 评估 → 5 类 Contract）

> 文档编号：ECOS-DESIGN-COG-04 | 版本 v1.0 | 2026-09-01
> 作用：Wave-3B「CausalReasoner / Rules 可解释」规格。**PMO-35 已实施 SpEL + ReasoningPath 三件套**，本文档向前补齐 **RuleRef / PrecedentRef** 两个 Contract，向后给出 CausalReasoner 重写后如何把因果层级（CausalChainNode 深度）映射到 ReasoningStep 的展开规则。
> 不做的事：**不引入 Drools/KIE**、**不重写 PMO-35 已落盘的 3 个 Contract**。

---

## 一、背景（已核实代码）

`ecos_backend/engine/cognitive-engine/cognitive-engine-impl` 已存在：

| 文件 | 现状 |
|------|------|
| `service/SpelConditionEvaluator.java` | SpEL + contains 降级双通道，**EvalResult{ satisfied, detail, evaluatedVars }** 已落地 |
| `service/ReasoningPathBuilder.java` | 单步 → `ReasoningStep`；多步 → `ReasoningPath` 已落地，但 **`justification` 是字符串拼接**（`"Evaluated N rules, M matched. Conclusion: ..."`），非结构化 |
| `model/ReasoningStep.java` | stepId/description/ruleApplied/inputFacts/outputFact/confidence |
| `model/ReasoningPath.java` | steps/conclusion/justification（**字符串**） |
| `model/Justification.java` | conclusion/path/evidence |

**核心问题**：
1. **5 类 Contract 缺一**：`RuleRef` / `PrecedentRef` 未建模，前端无法点击"哪条规则 / 哪个先例"。
2. **`justification` 是字符串**，前端只能展示原始文本，无法 highlight 单步。
3. **因果层级（CausalReasoner 726 行）** 输出的 `CausalChainNode`（depth 1..N, confidence, source∈{KG/LLM/RULE}） **没有进入推理路径** — 用户在 `/api/v1/cognitive/diagnose` 看不到"为什么这个根因"。

> 铁律引用：[架构铁律 0.2/0.3](../../ARCHITECTURE-RULES.md)：cognitive 不新增 DB 表，不引入规则引擎。本设计 **零新增 DB 表**（推理路径纯内存，与 `ReasonerResult` 同生命周期）；SpEL 评估继续走 `SpelConditionEvaluator`，不引入新引擎。

## 三、5 类 Contract 字段定义（强类型，全 Lombok 风格）

> 命名约定：class 在 `com.chinacreator.gzcm.engine.cognitive2.model`，DTO 用 `@Data`，计算类用 `@Getter @Setter @NoArgsConstructor`。

```java
// 1. RuleRef：规则引用（新增 @TBD）
public class RuleRef {
    String ruleId;        // sys_compliance_rule.id
    String ruleName;      // 规则名
    String condition;     // 原 condition（SpEL 或自然语言）
    String action;        // 原 action 文本
    String category;      // 命中分类（compliance / business / oag）
    String version;       // 规则版本（kb-engine 提供）
    int sourceRank;       // 在规则命中列表中的排序（0=最优先）
}

// 2. PrecedentRef：先例引用（新增 @TBD）
public class PrecedentRef {
    String precedentId;             // ecos_decision_precedent.id (PMO-32)
    String decisionId;              // 出回决策 id
    String summary;                 // 案例摘要
    String outcome;                 // 历史结果
    JSONObject similarityEvidence;  // 相似度证据：{vector_score, category, scenario_len_diff}
    double similarity;              // 0~1
}
```

> `ReasoningStep` / `ReasoningPath` / `Justification` **不删字段**，只 **新增**：

```java
// 3. ReasoningStep：新增 2 字段（不删除现有 stepId/description/ruleApplied/inputFacts/outputFact/confidence）
public class ReasoningStep {
    // ... 既有字段保持不变 ...
    RuleRef ruleRef;                 // 新增：可空（KG 步骤为 null）
    PrecedentRef precedentRef;       // 新增：可空
    String sourceType;               // 新增：KG / RULE / RAG / LLM / PRECEDENT
    int stepIndex;                   // 新增：层号（diagnose 因果拓扑排序）
}

// 4. ReasoningPath：新增 1 字段
public class ReasoningPath {
    List<ReasoningStep> steps;       // 既有
    String conclusion;               // 既有
    String justification;            // 既有（兼容字符串，包含文本摘要）
    List<JustificationClause> clauses; // 新增 @TBD：结构化解释（多段）
    List<RuleRef> ruleRefs;          // 新增：本路径引用的所有规则
    List<PrecedentRef> precedentRefs;// 新增
}

// 5. JustificationClause：解释子条款（新增 @TBD）
public class JustificationClause {
    String clauseId;
    String clauseType;     // FACT_ACCRUAL（事实累计）/ RULE_TRIGGER（规则命中）/ PRECEDENT_RECALL（先例召回）/ COUNTER_EVIDENCE（反证）
    ReasoningStep stepRef; // 关联的 stepId
    String text;           // 渲染文本（i18n key 或 plain）
    String i18nKey;        // i18n key（前端用 t() 查）
    List<String> factRefs; // 引用的事实 key
    double weight;         // 该条款在结论权重 0~1
}
```

> **向后兼容**：旧的 `ReasoningStep.ruleApplied: String` 与新的 `ruleRef` 并存；渲染层按规则：`ruleRef != null ? ruleRef.ruleName : ruleApplied`。

## 四、CausalReasoner 重写 → ReasoningStep 映射

> **CausalReasonerServiceImpl 当前 726 行待拆**。重写后的 `diagnose()` 输出 `CausalChainResult`，新增 `reasoningPath` 字段，由下层三子组件 + 新增 `ReasoningPathFromCausalBuilder`（@TBD）生成。

### 4.1 因果链 path → step 展开

`CausalChainNode` 已含：`depth / confidence / source∈{KG,LLM,RULE} / metricName / description`。
新 builder 把每个 node 展开为 1 个 `ReasoningStep`：

```java
// ReasoningPathFromCausalBuilder.buildNode(node, ctx) -> ReasoningStep
List<ReasoningStep> steps = causalChain.stream().map(node -> {
    ReasoningStep s = new ReasoningStep();
    s.setStepId("depth-" + node.getDepth());
    s.setStepIndex(node.getDepth());
    s.setDescription(node.getDescription());
    s.setInputFacts(ctx.getFactsFor(node));   // 该层事实快照
    s.setOutputFact(node.getMetricName());
    s.setConfidence(node.getConfidence());
    s.setSourceType(node.getSource());         // KG / LLM / RULE

    // source=RULE 时：必须维护 ruleRef
    if ("RULE".equalsIgnoreCase(node.getSource()) && node.getRuleId() != null) {
        s.setRuleRef(ctx.ruleRefs.get(node.getRuleId()));
    }
    // source=PRECEDENT 时：precedentRef
    if (node.getPrecedentId() != null) {
        s.setPrecedentRef(ctx.precedentRefs.get(node.getPrecedentId()));
    }
    return s;
}).toList();
```

**展开规则**：
- 每层 1 step，**最多** `maxDepth - 1` 步
- 同一 metric 重复出现 → 合并 step，ruleRef 取优先级最高
- 全部 RULE 节点都带 `sourceRank`（来自规则命中 order）

## 五、SpEL 安全加固（增量要求）

`SpelConditionEvaluator` 现状用 `SimpleEvaluationContext.forReadOnlyDataBinding()`，**已安全**，增量三项：

```java
// SpelConditionEvaluator.java 加固
private static final int MAX_FACTS_SIZE = 20;
private static final Set<String> DANGEROUS_PATTERNS = Set.of("T(", "new ", "constructor", ".class");

public EvalResult evaluate(String expression, Map<String, Object> facts) {
    // 1. 大小检查（防 OOM）
    if (facts != null && facts.size() > MAX_FACTS_SIZE) {
        log.warn("SpEL facts too large ({}), truncating to {}", facts.size(), MAX_FACTS_SIZE);
        facts = truncate(facts, MAX_FACTS_SIZE);
    }
    // 2. 危险词拦截
    if (expression != null && DANGEROUS_PATTERNS.stream().anyMatch(expression::contains)) {
        return EvalResult.deny("Expression rejected: contains prohibited token");
    }
    // 3. trySpel / containsMatch（既有）
}
```

## 九、附：为什么 5 类 Contract 而非 3 类

- **3 类**（ReasoningPath/ReasoningStep/Justification）= 用户视角的"读"
- **2 类**（RuleRef/PrecedentRef）= 系统视角的"证"——前者指向"用了什么规则"，后者指向"基于什么先例"
- 分成 5 类有两个好处：① 前端 5 个组件解耦（每类独立 React 子组件）；② 跨引擎 API 调用时可按需携带（KG 推理只需 RuleRef，诊断可两者皆有）。
