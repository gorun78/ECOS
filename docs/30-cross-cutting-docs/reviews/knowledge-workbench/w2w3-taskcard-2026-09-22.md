## W2 批次（本体映射契约 + 抽取执行接入）认领 2 项

### TA-1 🔴 P0 — 即时抽取接入 runtime-task（替代原「WR-1 抽取路径不落库」）

**铁律依据**：[架构铁律.md](../../INDEX.md) §1.6-1（即时任务统一接触） + §2.1（引擎间只调 API）。

**现状**：`StructuredExtractController` `dryRun=false` 路径直接调 `KbImportTaskExecutor.execute` / `KbEntityInstanceExtractionService.extract`，**不经 `ITaskManagementService.submitTask + executeTask`**：
- 响应回了业务自造 `jobId`（`KBK1S-<ts>`）而非 runtime-task `taskId`
- `td_runtime_task*` 5 表**零写入**
- `AsyncTaskCenterView` / taskCenter API **看不到本次抽取**
- 前端 `MonitorPanel` 的 logs / export / 最近任务全部 0 行（KB 自有表无行可查）

**修复**（4 处）：
1. `StructuredExtractController#triggerStructured`：
   - `dryRun=true` → **保持原**（同步短跑、不落 task）
   - `dryRun=false` → 改为：
     ```java
     TaskDescription desc = new TaskDescription();
     desc.setTaskType("KB_IMPORT");
     desc.setTaskName("结构化抽取即时: " + (ontologyId==null?"ALL":ontologyId));
     Map<String,Object> params = new LinkedHashMap<>();
     params.put("ontologyId", ontologyId);
     params.put("mode", mode);
     params.put("dryRun", false);
     params.put("biz_kind", "KB_EXTRACT");
     desc.setParameters(params);
     desc.setAsync(false);       // 同数据工作台：同步等 executeTask 派发
     String taskId = taskManagementService.submitTask(desc);
     taskManagementService.executeTask(taskId);   // 已入 dispatch queue，异步跑
     return KbImportTriggerVO.builder().taskId(taskId).jobId(taskId).status("SUBMITTED").build();
     ```
   - **`jobId = taskId`**（统一标识；前端用 `taskId` 拉 logs/progress）
2. `KbImportTaskExecutor` 在 `onTaskComplete` 后写 **`kb_extract_audit`**（审计层，已实现）；**不再写** runtime 状态
3. `ExtractJobInfo` 接口字段 `jobId` 改名 `taskId: string`（同名同义，**铁律 §5.1-11 前后端契约同源**）
4. `kbscheduledextractcontroller` ——**让位给 TB-1**（见下节）

**验收**：
- `curl -X POST /api/v1/knowledge/extract/structured -d '{"dryRun":false,"mode":"FULL"}'` → 回 `taskId: TASK-...`（非 `KBK1S-` 前缀）
- `curl /api/v1/taskCenter/task-status?taskId=TASK-...` 看 status / progress / logs
- `AsyncTaskCenterView` TopBar 进异步任务中心 → 列表出现该 taskId（KB_EXTRACT 类别）
- 10 万行截断：`GET /api/v1/taskCenter/tasks/{taskId}/logs` 拿到 `rows_capped` 事件

### WR-2 🔴 P0 — `buildNodeId` 跨实体 id 冲突（数据破坏）

**问题**：`KbEntityInstanceExtractionService#L783-790`
```java
private String buildNodeId(String nodeType, String pkValue) {
    String raw = nodeType + ":" + pkValue;
    if (raw.length() <= SHORT_COLUMN_MAX) {
        return raw;
    }
    String prefix = nodeType.length() > 20 ? nodeType.substring(0, 20) : nodeType;
    return prefix + "-" + sha256Hex(raw).substring(0, ID_HASH_LEN);
}
```

**核心 bug** — 实体 code 截断到 **20 字符**：两个不同实体的 code（如 `myOrganizationDetailsA` / `myOrganizationDetailzB`）截到相同 20 字符 → **不同实体的节点共用 prefix**——仅凭 SHA-256 前 40 字符区分——**两个不同 pk 走完整 SHA-256，它们的 hash 前 40 字符可碰撞**（多项式碰撞可能性非零）。`ON CONFLICT (id) DO UPDATE` 会**互相覆盖**，造成实体数据丢失。

**修复**（两选一）：
- **方案 A（推荐）**：`node_id` = `sha256(ontologyId + "::" + nodeType + "::" + pkValue).substring(0, 20)` —— 前 20 字符含本体限定，**杜绝跨本体/跨实体冲突**
- 方案 B：扩列宽 `graph_node.id → VARCHAR(200)`，id 走 `entityCode:hash(200 全量)`
- 同时 `graph_edge.id` 同修订（`buildEdgeId` L793-800 同问题）

**验收**：
- 两个不同实体的 code 长度 ≥ 20，各 10 PK 行触抽 → 检查 `SELECT id, node_type FROM graph_node WHERE node_type IN (X, Y) LIMIT 20`，**两实体 id 完全不重合**

## W3 批次（知识存储 + 萃取后端）认领 4 项

### TB-1 🔴 P0 — 定时抽取迁 `td_runtime_task_plan`（废弃 `kb_scheduled_extract`）

**铁律依据**：架构铁律 §1.6-2（定时任务禁止自建 `*_scheduled_*` 表） + §2.5-3（委托 `runtime-task` 全局调度）

**现状**：`ScheduledExtractController` 写自有的 `ecos_knowledge.kb_scheduled_extract`（V141 建），字段 `schedule_id/name/ontology_ids/mode/period/cron_expression/next_run_at/enabled/last_run_at/last_status`——
- 与 `td_runtime_task_plan` **重复**（`plan_name` / `task_type` / `cron_expression` / `next_run_at` / `task_status` / `last_status`）
- 双源 createdAt → 一处写 GB 任务、`schedule_task` 注册 runtime 计划是一条独立 SQL——**两套时间表，两处调度**
- `AsyncTaskCenterView` 已通过 `taskCenter` API 看到 `td_runtime_task*`——**但 KB 定时不进 scene**，因为 KB 另起一套

**修复**（5 处）：
1. **迁移 DDL**（标 deprecate 不 drop，供读时回退）：
   - 新增 `V<next>__kb_scheduled_extract_deprecate.sql`：
     ```sql
     -- 不作 outer drop；只置只读 + 加 history 标
     UPDATE ecos_knowledge.kb_scheduled_extract SET comment = 'DEPRECATED (V141, 2026-09-22)' WHERE 1=1;
     -- 新建只读视图替代（避免意外 DELETE）
     CREATE VIEW kb_scheduled_extract_readonly AS
       SELECT id, schedule_id, name, cron_expression, last_status, created_at
       FROM ecos_knowledge.kb_scheduled_extract WHERE is_deleted = 0;
     ```
   - 新增/扩展 `td_runtime_task_plan`：
     ```sql
     -- 复用现有 taskType+params；无新列（biz_kind 在 task_type 中嵌：kb_extract）
     ```
2. `ScheduledExtractController` 5 端点（T5-1 ~ T5-5）全部重写——**改为走 `td_runtime_task_plan` + `ITaskManagementService.scheduleTask(desc, cron)`**：
   - `POST /extract/scheduled` → `scheduleTask + INSERT td_runtime_task_plan`（**不再 INSERT kb_scheduled_extract**）
   - `GET /extract/scheduled` → `SELECT FROM td_runtime_task_plan WHERE task_type = 'KB_EXTRACT'`
   - 其它同逻辑改 `plan_id`
3. `AsyncTaskCenterView` 加 `KB_EXTRACT` 类别 filter（`taskClassifier` 按 `taskType=KB_IMPORT` 归类 + `biz_kind=KB_EXTRACT/SCHEDULED` 标注）
4. `taskCenter` 服务层 `categorize()` 加 `KB_EXTRACT` 类别
5. 旧 `kb_scheduled_extract` 数据 → 一次性 `REBIRTH`：从现有表读行 → `scheduleTask` 重注册到 runtime → 旧行置 `comment='MOBILITIZED'`

**验收**：
- `curl -X DELETE /api/v1/knowledge/extract/scheduled/{old_id}` 不再写 `kb_scheduled_extract`，而是 `DELETE FROM td_runtime_task_plan WHERE plan_id=?`
- `AsyncTaskCenterView` → filter「KB 抽取（定时）」→ 定时行可见，状态实时，**与 kb Tab 内嵌视图同源**
- `kb_scheduled_extract` 行数 **不再增长**（DEPRECATED 注释生效，grep `kb_scheduled_extract` 的 INSERT 语句 0 命中）


### WK-1 🔴 P0 — `dry-run` 计数误导（`nodeCreated` 虚高）

**问题**：`extractForMapping#L293-296` vs `#L296-300`：
```java
if (dryRun) {
    report.setNodeCreated(report.getNodeCreated() + 1);
} else if (upsertNode(...)) {
    report.setNodeCreated(...);
} else {
    report.setNodeUpdated(...);
}
```
**Dry-run 永远 `nodeCreated=N / nodeUpdated=0`** —— 因为没查 PG 不知道哪些节点已存在。用户拿 dry-run 估算"新建 1 万节点"，真跑可能 8k 已存在 → 9.9k updated / 0 created，**严重误导**。

**修复**（最小路径）：
- 在 `dryRun==true` 分支**额外**调 `queryExistingNodeIds` 一次（已有方法 L409）
- 命中 → `nodeUpdated++`，未命中 → `nodeCreated++`
- 注：已将 `queryExistingNodeIds` 抽成可复用（它已是 private，dry 路径内调即可）

**验收**：
- 实体 X 抽 100 行 → dry-run → `nodeCreated=100, nodeUpdated=0`
- 真跑 → `nodeCreated=100, nodeUpdated=0`
- 再 dry-run → `nodeCreated=0, nodeUpdated=100`
- 同名 pk 增 1 行 → `nodeCreated=1, nodeUpdated=100`

### WK-3 🔴 P0 — `emitAudit` 假 Kafka（**铁律 §2.4-5 违**）

**问题**：`KbEntityInstanceExtractionService#L865-873`
```java
private void emitAudit(String action, String detail) {
    try {
        String payload = String.format("{\"action\":\"%s\",...}");
        log.info("AUDIT topic={} payload={}", KafkaTopics.AUDIT, payload);
    } catch (Exception e) { log.warn("emitAudit fallback log failed"); }
}
```
注释声明"走 Kafka `ecos.audit`"，**但构造器根本没注入 `KafkaTemplate`，没有 producer.send** —— 纯 log 流，等价于无审计。Reviewer 上一卡片只扫了 Datalake 没扫 kb-engine，漏了这条。

**修复**：
- 构造器加 `KafkaTemplate kafkaTemplate`（由 `runtime-access` 提供 `KafkaTemplate` bean，已在 `runtime-access` 注册）
- `send(KafkaTopics.AUDIT, jobId, payload)`，`.Future.get(timeout)` 失败 → `log.warn + 业务不抛`
- 验收 `KafkaConsumer` 在 `ecos.audit` topic 收到 `kg_instance_extract` 事件

**验收**：
- 抽 1 行 → `kafka-console-consumer --topic ecos.audit` 看到 `{"action":"kg_instance_extract", "detail":"jobId=KBK1S-... mode=FULL dryRun=false nodesCreated=1..."}`
- 同时 `log.info` 留审计 trail（双走）
