# ECOS 场景工作台与认知引擎实施任务书

## 一、任务目标

基于 ECOS 现有代码、系统架构、数据库模型、API 规范及项目文档，落实 `docs` 目录中新增的以下设计文档：

1. `详细设计-场景工作台.md`
2. `详细设计-认知引擎.md`
3. `实施任务与验收清单.md`
4. `README-CodingAgent-执行说明.md`

以上文件的实际路径以 `docs` 目录中的检索结果为准。如果文件位于子目录，必须先找到实际位置，不得因路径不同而跳过。

本次任务的目标是将设计转化为可以运行、测试和验收的实际代码，而不是仅生成代码示例、技术方案或空壳页面。

实施范围包括：

- 场景工作台：场景定义、结构化建模、对象和能力绑定、关系编排、完整性校验、生命周期管理及沙盘隔离。
- 认知引擎：认知框架管理、认知方法管理、Mind/心智模型、认知任务与执行、上下文组装、认知产物、证据与信念管理、结果验证及反馈评估。
- 两者与 ECOS 现有数据层、本体层、知识层、AI 模型管理、Agent Runtime、权限审计及前端框架的集成。

## 二、不可违反的实施原则

### 2.1 先理解现有系统，再修改代码

首先检查：

- 仓库目录、开发规范、构建与测试命令。
- `docs` 中的 ECOS 总体架构、需求文档及本次详细设计。
- 已实现的场景、认知、知识、本体、数据、模型、Agent、权限等模块。
- 现有数据库表、实体、迁移脚本、API、DTO、事件和前端路由。
- 已有测试、未完成任务和当前工作区的未提交变更。

以实际代码和执行结果为准，不得仅根据文档推断功能已经实现或不存在。

### 2.2 保护既有架构与实现

- 不得随意重写已完成的模块。
- 不得为追求设计文档中的类名而机械地新建重复实体、数据库表、服务或 API。
- 优先复用已有基础设施、统一组件、服务接口、权限体系、审计机制和错误处理规范。
- 如果现有实现与新设计存在冲突，先形成差异清单，判断是文档需要适配，还是代码需要改造，再按影响最小的方式实施。
- 不得擅自修改公共接口、数据库结构或核心架构约束；必要变更必须记录原因、兼容性影响、迁移方案和测试要求。
- 不得覆盖、回滚或清理与本任务无关的用户代码和未提交变更。

### 2.3 明确 DIKCW 的职责边界

遵守 ECOS 既定架构：

- **D / 数据层**：提供权威业务数据、数据质量信息和确定性计算结果。
- **I / 本体层**：提供业务对象、关系、属性、语义约束及业务对象映射。
- **K / 知识层**：管理可复用知识、文档、规则、案例和知识检索能力。
- **C / 认知层**：组织认知任务、框架、方法、证据、假设、信念、推理过程、验证及结果评估。
- **W / Agent 工作层**：负责任务分解、计划编排、工具调用和执行协同。

各层通过既有服务接口协作，不得让认知引擎直接绕过数据、本体、知识、权限等模块操作底层资源。

特别注意：

1. 不得把一次任务的临时上下文当作长期知识写入知识库。
2. 不得让 LLM 自行创造正式业务口径、业务事实或未经授权的业务规则。
3. 不得将相关性直接认定为因果关系。
4. 不得将探索性预测或沙盘结果直接写入正式业务数据。
5. 不得允许认知框架或模型评分覆盖权限、安全、审批等硬约束。
6. 不得把认知流程执行成功等同于业务结论正确。

## 三、第一阶段：代码与设计审计

先完成审计，再进入实质开发。

输出文件：`docs/实施记录/ECOS-场景工作台与认知引擎-现状审计.md`

审计报告必须包含：

1. 当前系统架构与相关模块的实际目录、入口和职责。
2. 四份设计文档与现有代码的逐项映射。
3. 已实现、部分实现、未实现、存在冲突的功能清单。
4. 可直接复用的实体、服务、接口、组件和基础设施。
5. 数据库变更需求与兼容性风险。
6. API、前端路由、权限、审计和测试现状。
7. 实施依赖、风险、阻塞项和建议执行顺序。
8. 每项判断对应的代码路径、类名、接口名或测试证据。

禁止用“已支持”“已完成”等没有证据的描述代替代码审计。

审计结束后，继续实施，不要仅输出审计报告便停止。

## 四、第二阶段：形成可执行实施计划

输出文件：`docs/实施记录/ECOS-场景工作台与认知引擎-实施计划.md`

将任务拆分为有明确依赖关系的开发批次，每批次说明：

- 目标和范围。
- 对应设计章节及需求。
- 需要修改或新增的文件、模块。
- 数据模型及 API 变更。
- 前后端任务。
- 测试与验收条件。
- 依赖、风险及回滚方式。

优先顺序如下：

1. 现状审计与差异确认。
2. 场景工作台的核心数据模型、服务和 API。
3. 场景工作台前端及生命周期。
4. 认知引擎的框架注册、版本管理与执行契约。
5. 认知任务、计划、执行状态机、上下文组装与产物引用。
6. 证据、假设、信念、验证和反馈评估。
7. 场景工作台与认知引擎的端到端集成。
8. 权限、安全、审计、性能及回归测试。
9. 文档、部署与交付验收。

若代码审计发现更合理的依赖顺序，可以调整，但必须记录理由。

## 五、第三阶段：实现与集成

### 5.1 场景工作台

按照详细设计实现适用于现有技术栈的完整功能，至少覆盖：

- 场景定义与版本。
- 场景目标、输入、输出、约束及验收标准。
- 业务对象、本体类型、数据资源、知识资源、认知框架、模型和 Agent 能力的绑定。
- 组件之间的关系与执行依赖。
- 场景完整性校验及错误定位。
- 场景生命周期与发布控制。
- 沙盘执行和正式环境隔离。
- 场景配置持久化、查询、编辑和版本管理。
- 前端交互、后端校验和 API 联调。
- 权限检查、操作审计和异常处理。

场景完整性校验必须能区分阻断性错误、警告和可选建议。不能仅用前端校验代替后端校验。

### 5.2 认知引擎

按照详细设计实现：

- 认知框架定义、版本、注册、查询、启停和适用范围管理。
- 认知方法与框架的关联及职责区分。
- Mind/心智模型的结构化表达、引用和版本管理。
- 认知任务、计划、执行记录和产物引用。
- Context Builder：从授权的数据、本体、知识和任务输入中构建任务上下文。
- 认知执行契约：输入输出 Schema、前置条件、验证规则、预算、停止条件及异常处理。
- 证据、事实、假设、信念和结论的结构化管理及来源追溯。
- 执行结果验证、业务结果评估和反馈记录。
- 与现有模型网关、知识检索、Agent Runtime、数据服务及权限服务集成。

认知框架版本必须具备可追溯性；已经被执行记录引用的历史版本，不得因修改新版本而被静默覆盖。

框架选择必须先过滤权限、状态、输入条件、依赖、风险审批等硬约束，再对可用候选进行适配性排序。未经校准的评分不得解释为概率或置信度。

认知执行状态必须遵守设计中的状态机及终态约束。至少保证：

- 非法状态转换被拒绝。
- 重复请求不会造成重复副作用。
- 失败、取消、超预算、等待输入及人工审核状态可追踪。
- 输出通过 Schema 与业务验证后，才能标记为流程执行成功。
- 业务结论正确性与流程执行状态分别记录。

如果已有实现提供等价能力，应适配并复用，不要机械地另建一套。

### 5.3 持久化与数据迁移

- 先确认现有 ORM、数据库和迁移工具，再设计增量迁移。
- 优先复用现有资产目录、执行追踪和业务结果存储。
- 不得仅为了保存临时上下文而新增独立的 `cognitive_context` 持久化表。
- 临时上下文可以在执行期组装；需要审计时保存必要的引用、摘要、版本、哈希或符合安全策略的快照。
- 对新增字段、索引、唯一约束、外键、数据迁移和回滚策略提供说明。
- 迁移不得破坏已有数据，且必须经过相应测试。

### 5.4 前端实现

- 使用 ECOS 现有前端框架、组件库、路由和设计规范。
- 不得以静态演示页、写死的假数据或不可操作的按钮冒充完成。
- 表单、列表、详情、版本切换、校验反馈、执行状态、错误提示和权限控制必须与实际 API 联动。
- 对加载中、空数据、无权限、校验失败、执行失败和网络异常提供明确反馈。
- 确保已有页面和路由不受无关影响。

## 六、第四阶段：测试与验收

每个批次完成后立即执行测试，不得等到全部代码写完再统一测试。

至少完成：

1. 单元测试。
2. 服务层和数据库集成测试。
3. API 契约及权限测试。
4. 前端构建、类型检查及必要的交互测试。
5. 数据迁移与兼容性测试。
6. 场景工作台到认知引擎的端到端测试。
7. 现有相关模块回归测试。

重点覆盖以下异常场景：

- 场景缺少必要对象或输入。
- 引用不存在、已停用或版本不匹配的资源。
- 用户没有目标资源或执行权限。
- 认知框架输入不符合 Schema。
- LLM 输出格式错误或无法通过验证。
- 证据来源缺失或无法追溯。
- 执行超时、预算耗尽、重复提交或执行取消。
- 执行中断后的状态恢复。
- 沙盘结果被错误写入正式环境。
- 历史版本被覆盖。
- 人工审核尚未完成却试图发布或执行。
- 外部服务不可用及部分执行失败。

以 `实施任务与验收清单.md` 为基础维护验收结果。每项标记为“通过”“失败”“阻塞”或“未执行”，并提供测试证据。

不得为了让测试通过而删除已有测试、降低断言标准、跳过失败用例或把未执行标记为通过。

## 七、第五阶段：端到端业务验证

使用 ECOS 的企业年度经营数据预测场景进行端到端验证。优先使用现有测试数据；没有合适数据时，创建明确标记的合成测试数据，不得将其混入正式业务数据。

场景至少验证：

1. 按企业正式口径定义收入、成本和利润。
2. 收入拆分为验收收入、回款收入和分包收入。
3. 成本拆分为薪酬成本、管理成本和市场成本。
4. 使用本体关系绑定项目、合同、部门、收入节点、成本项和相关数据。
5. 由确定性业务规则计算基准值，认知引擎负责组织差异分析、假设生成、证据评估及情景分析。
6. 对每项重要假设记录证据、来源、适用范围及验证状态。
7. 对关键参数执行情景或敏感性分析。
8. 将预测、实际结果、偏差和评估记录关联起来。
9. 验证沙盘分析不会修改正式财务数据、正式规则或生产模型。
10. 验证关键结论可追溯到输入数据、规则、框架版本和执行记录。

不得由 LLM 临时决定正式收入口径，也不得把未经验证的根因假设当作事实。

如果现有环境缺少执行此场景所需的业务数据或服务，明确记录阻塞项并完成其余可测试部分，不得伪造端到端测试通过结果。

## 八、开发纪律

- 直接在现有 ECOS 仓库内实施，不另起无关项目。
- 按现有命名、分层、异常处理、日志和代码格式规范开发。
- 优先使用小步、可审查的增量修改。
- 不得提交密钥、真实凭证或敏感业务数据。
- 不得擅自安装大规模依赖或升级基础框架；确有必要时先记录影响。
- 不得执行破坏性数据库操作或覆盖用户文件。
- 如果存在影响正确性或安全性的重大歧义，先记录并提出明确问题；其余任务继续推进。
- 不得只创建 TODO、接口空壳、假实现或伪造测试结果。
- 每个阶段都要记录实际修改文件、运行命令、测试结果和遗留问题。

## 十、立即开始执行

现在开始：

**先审计现有 ECOS 仓库及 `docs` 中的相关设计文件，然后编写现状审计报告和实施计划，接着按照依赖顺序持续实施、测试和修复。**

不要在输出审计报告或实施计划后停止；在没有重大阻塞的情况下，应继续推进可独立完成的开发任务。

只有在实际实现、运行测试并核实结果后，才能将功能标记为完成。最终向我汇报真实进度、测试证据、未完成事项及下一步建议。
