# 详细设计：ECOS 认知引擎（cognitive-engine / C）

> 文档版本：v1.0  
> 日期：2026-10-29  
> 目标：在既有 cognitive-engine 与 aiming 部署形态内，补齐可被业务场景调用、可验证、可追溯、可受控反馈的认知能力。  
> 核心原则：认知引擎组织和验证认知过程；它不替代 data/ontology/kb/ai/security，也不拥有正式业务事实。

## 1. 术语与对象边界

### 1.1 六个核心概念

| 概念 | 定义 | ECOS 所属/用法 |
|---|---|---|
| Scenario | 业务目标、范围、约束、参与对象、成功标准的场景定义 | workspace 持有 Scenario Blueprint 生命周期 |
| Mind | 认知主体在某领域/任务上的认知能力配置与运行组织机制 | C 层逻辑概念；引用 capabilityMask、边界、资产和策略，不自动等于独立服务 |
| Mental Model（心智模型） | 对领域结构、业务机制、关系与因果解释的可修正表征 | 可引用 I/K 与经治理的 C 资产；不是权威本体的替代品 |
| Cognitive Framework | 某类问题的认知过程组织规范：步骤、依赖、输入输出、验证、停止条件 | Framework Registry 管理版本化定义 |
| Cognitive Method | 框架步骤内使用的分析/推理方法，如溯因、反证、差异分解、贝叶斯更新 | 由框架引用，不必单独作为可部署模型 |
| Cognitive Model | 具备输入输出契约、适用范围、评估与版本的计算/判断能力 | Cognitive Model Registry 管理认知模型资产；LLM/小模型本身仍由 AI Model/Capability Center 管理 |

Mind 不等于 Agent；W Agent 是任务编排与工具执行机制。Mind 也不等于单一数据库实体。优先把 Mind 定义为 C 层的逻辑聚合/能力配置，只有在现有数据模型需要且 ADR 批准时才扩展持久化。

### 1.2 DIKCW 边界

- D：权威业务数据、数据质量、输入快照与确定性计算来源。
- I：权威业务概念、对象、属性、关系、指标口径与语义约束。
- K：可复用知识资产：制度、规则、方法、案例、经验、模式、文档。
- C：当前任务的 Context Pack、Evidence 引用、Hypothesis、Belief、因果解释、预测解释、Decision Basis、认知框架/模型引用和验证结果。
- W：目标分解、计划编排、受控工具调用、预算、暂停、澄清、重规划与用户交互。
- Feedback：运行/真实结果的评估与更新候选；经治理后才可能影响 D/I/K/C。

### 1.3 C 类资产持久化原则

1. 单次推理中间状态默认请求态，不因模型生成就自动落盘。
2. 需要跨任务复用的 Hypothesis/Belief/Evidence/Mind 等对象，必须符合既有 ADR 和生命周期规则。
3. 复用现有已批准的物理载体和迁移体系；先核验 `public.ecos_cognitive_hypothesis`、`public.ecos_cognitive_belief`、`public.ecos_cognitive_evidence` 是否为当前物理真身。
4. 不新增 `cognitive_context` 表、不新增认知业务事实表、不复制 K 类资产。
5. 对外提供引用、状态、来源和版本，不暴露未授权的敏感原文。
6. 确定性计算产物由业务域/data-engine 持有；C 层只保留 `CalculationResultRef` 等稳定引用与校验结果。

## 2. 总体职责与依赖方向

### 2.1 cognitive-engine 负责

- Context Builder：按当前任务、Blueprint、权限范围和预算组装请求态 Context Pack。
- 认知资产目录/只读解析与受控提案接口。
- Cognitive Framework Registry：定义/版本/发布/适用范围/契约。
- Cognitive Model Registry：认知模型的版本、评估与发布门禁；若现有注册中心已有归属，复用并建立映射。
- 任务理解辅助、认知策略选择、计划校验协议（执行计划真正的 W Runtime 归 ai-engine）。
- E1-E4 认知查询端点及其语义。
- 混合推理、因果诊断、预测驱动反事实的认知解释层。
- Evidence/Hypothesis/Belief/Decision Basis 的语义、引用、验证与受控生命周期。
- Outcome Evaluator：对照实际结果评估预测/判断并产生更新候选。

### 2.2 明确不负责

- 不执行独立 Agent loop；不接管 W Agent Runtime。
- 不管理通用 LLM/Embedding/小模型供应商连接；通过 AI Model/Capability Center 和 `llm-gateway`。
- 不代替 security-engine 做权限、密级、自动化等级、审批或 Kill Switch 决策。
- 不写数据域/本体域/知识域的权威业务表。
- 不把 LLM 输出当作权威事实、正式金额或已验证因果结论。
- 不新增规则引擎；规则执行复用现有受控规则/本体/业务能力。
- 不私建异步任务系统；长任务交由 `runtime-task`。

## 3. 认知引擎逻辑组件

| 组件 | 输入 | 输出 | 约束 |
|---|---|---|---|
| Context Builder | task、scenarioId、blueprintVersion、scope、include、budget | Context Pack + digest + gaps/conflicts | 请求态；按权限过滤；不新增上下文表 |
| Framework Registry | 框架定义/版本/发布操作 | 可用框架与版本 | 发布版本不可变；安全审核 |
| Cognitive Model Registry | 模型元数据、评估结果、发布申请 | 可用模型版本与状态 | 不与 AI Model Registry 混淆 |
| Strategy Selector | task + Context Pack + 候选框架 + 策略配置 | 候选、排除原因、计划草案、停止条件 | 硬约束先过滤，评分不能覆盖硬约束 |
| Plan Validator | 计划、契约、能力、权限要求 | 通过/失败问题列表 | 不能只依赖 LLM 自检 |
| Cognitive Executor Adapter | 已验证步骤、受控执行能力 | Step Result、trace refs | 实际工具执行经 ai-engine ToolExecutor |
| Evidence/Hypothesis/Belief Service | 证据引用、候选假设、评价/更新请求 | 结构化认知对象/引用 | 不将未验证输出自动升级为事实 |
| Outcome Evaluator | 预测/决策结果引用、实际结果引用、评价规则 | 指标、偏差诊断、更新候选 | 不自动修改生产模型/规则/知识 |
| Audit/Trace Adapter | traceId、任务/场景/版本、步骤事件 | 可追溯事件引用 | 复用现有审计/事件底座 |

逻辑请求：

    "successCriteria": [
      "金额可追溯",
      "关键风险有证据",
      "所有必需验证通过"
    ]
  },
  "scope": {
    "tenantId": "tenant-1",
    "projectIds": ["p1", "p2"],
    "departmentIds": ["d1"],
    "periods": ["2027"],
    "caliberId": "caliber-01",
    "asOfTime": "2026-10-29T00:00:00Z"
  },
  "requiredCapabilities": [
    "DATA_PROFILE",
    "ONTOLOGY_READ",

  ],

### 4.3 构建规则

1. 先验证任务/Blueprint 版本、调用者身份、权限、范围与预算。
2. 按需调用 data-engine、ontology-engine、kb-engine、cognitive registry、AI Capability Center 的既有接口；不跨域读表。
3. 对每个来源记录类型、稳定 ID、版本/快照、权威级别、时间、权限过滤结果和引用。
4. 识别缺失、过期、口径冲突、实体映射不完整、知识版本冲突、模型能力不可用。
5. 对来源排序可以采用配置化规则；不能把未经校准的 LLM 自评“可信度”当作权威概率。
6. 计算 `contextDigest`：对规范化后的、与本任务相关的来源引用、版本、范围和关键配置做稳定哈希；不得把随机时间字段或无关展示字段加入 digest。
7. 默认返回引用而非复制大型数据正文；敏感字段遵循 RLS/CLS/脱敏。
8. Context Pack 仅在请求态/受控缓存中存在；如果需要审计，记录 digest、来源引用和事件，不新增 `cognitive_context` 表。
9. 缺少关键输入时返回结构化 `gaps[]`，供 workspace 展示；不能用空对象或 LLM 编造值补齐。
10. 下游步骤必须携带 `contextDigest`/source refs，以保证运行链路可追溯。

### 4.4 错误语义

- 400：输入契约错误；
- 401/403：身份/权限失败；
- 404：场景/Blueprint/引用资产不存在；
- 409：Blueprint 版本冲突、引用版本不兼容或状态冲突；
- 422：必需输入缺失/无法满足前置条件（若当前 API 错误规范使用另一状态码则映射，不破坏统一契约）；
- 503：必需依赖不可用；
- 429：配额/速率限制；
- 500：未分类内部错误，必须关联 traceId。

`[]`、404、403、503 语义不得在前端或适配层互相折叠。

## 5. 认知框架注册与契约

### 5.1 Cognitive Framework Definition

框架定义至少有：
- `frameworkId`：稳定 ID；
- `version`：不可变版本；
- `name`、`category`、`purpose`；
- `applicability.problemTypes/domains`；
- `preconditions`；
- `inputSchemaRef`、`outputSchemaRef`；
- `steps`/`executorType`；
- `requiredCapabilities`；
- `validationProfileRef`；
- `budgetPolicyRef`；
- `stopConditions`；
- `governance`：发布审批、可否产生副作用、适用密级、状态；
- `createdBy/createdAt/publishedBy/publishedAt`。

状态建议：`DRAFT → VALIDATING → PUBLISHED → DEPRECATED/DISABLED`。已发布版本不可原地修改；修复必须发布新版本。实际枚举须先与现有注册/状态体系对齐。

### 5.2 首批框架目录

MVP 先注册四个框架，不要求首期实现所有认知理论：

| ID | 框架 | 作用 | 关键限制 |
|---|---|---|---|
| `CF-01-01` | 问题定义与边界识别 | 明确目标、范围、成功标准、未知项 | 不能替用户确认未给出的业务口径 |
| `CF-04-01` | 证据质量与来源评价 | 评价来源、时效、完整性、相关性与冲突 | 不将评分直接等同于事实真伪 |
| `CF-03-03` | 溯因与竞争性假设分析 | 从异常形成候选原因并寻找反证 | 不将相关性直接写成因果结论 |
| `CF-06-02` | 情景规划与敏感性分析 | 对结构化假设进行情景对比 | 正式数值由确定性业务计算产生，LLM 不计算金额 |

后续可扩展概念对齐、演绎推理、因果图、预测误差校准、多准则决策、案例迁移和元认知监控。

### 5.3 框架 YAML 示例

```yaml
framework_id: CF-03-03
version: "1.0.0"
name: 溯因与竞争性假设分析
category: ABDUCTIVE_REASONING
status: DRAFT
purpose: >
  根据异常事实与可核验证据提出竞争性原因假设，
  评估支持与反对证据，并明确未解决的不确定性。
applicability:
  problem_types: [metric_deviation, process_anomaly]
  domains: [enterprise_operations]
preconditions:
  - anomaly_definition_present
  - comparison_baseline_present
inputs:
  schema_ref: ecos://schemas/cognitive/abduction-input/v1
outputs:
  schema_ref: ecos://schemas/cognitive/abduction-output/v1
  required_fields:
    - hypotheses
    - supportingEvidence
    - contradictingEvidence
    - uncertainty
    - unresolvedQuestions
execution:
  executor_type: controlled_reasoning
  max_iterations: 5
  require_trace: true
  allow_unbounded_loop: false
validation:
  require_evidence_refs: true
  require_contradiction_check: true
  prohibit_unsupported_causal_claims: true
governance:
  immutable_after_publish: true
  production_approval_required: true
  allow_direct_side_effects: false
```

YAML 是声明式元数据，不是任意代码容器。`executor_type` 必须映射到白名单中的受控执行器。

## 6. 认知策略选择器

### 6.1 输入输出

输入：
- task goal/problemType/scope/constraints/risk；
- Context Pack 与 gaps/conflicts；
- 已发布且可用的框架版本；
- capability/model/tool 可用性；
- security-engine 授权结果/策略引用；
- budget 与 success criteria。

输出：
- `selectedFrameworks[]`；
- `excludedFrameworks[]`（每个有原因码）；
- `planDraft`（DAG 步骤、依赖、契约、引用版本）；
- `missingInputs[]`；
- `validationRequirements[]`；
- `stopConditions[]`；
- `riskDecision`；
- `selectionTrace`。

### 6.2 选择算法

第一阶段：硬约束过滤，检查状态/适用域/输入/依赖/权限/风险/预算/验证能力。任一强制条件失败就排除，不得被排序分数覆盖。

第二阶段：对通过的候选按问题适配度、输入满足度、可验证性、风险适配、预期收益、成本时延排序。MVP 优先规则化排序；没有评估数据时不设置伪精确概率。

第三阶段：组装计划 DAG，明确每一步输入输出、版本、依赖、预算、验证和失败策略。

第四阶段：计划验证：
- DAG 无环；
- 所有依赖和 Schema 可解析；
- 上游输出可映射到下游输入；
- 必需验证步骤存在；
- 预算总和不超限；
- 所有工具调用都能通过 Tool Contract 与 security-engine；
- 不存在未经授权的副作用。

第五阶段：执行时根据结果决定继续、补输入、切换框架、重规划、暂停或人工升级。所有动态变化记入运行事件，不能无痕改计划。

### 6.3 伪代码

```text
select(task, context):
  validateTaskAndContext(task, context)
  candidates = registry.find(task.problemType, task.domain)
  eligible = []
  excluded = []

  for framework in candidates:
    result = hardConstraintCheck(framework, task, context)
    if result.passed:
      eligible.add(framework)
    else:
      excluded.add({id: framework.id, reasons: result.reasons})

  if eligible.empty:
    return NEEDS_INPUT_OR_HUMAN(gaps=context.gaps, excluded=excluded)

  ranked = deterministicRank(eligible, task, context)
  plan = composePlan(ranked, task, context)
  validation = planValidator.validate(plan)

  if not validation.passed:
    return REPLAN_OR_REJECT(validation.issues)

  return {plan, excluded, selectionTrace, stopConditions}
```

策略选择器提出计划；真正的 W Agent Runtime 负责执行和任务状态。不要在 cognitive-engine 再实现一个 while-loop Agent。

## 7. 计划/执行契约与状态

### 7.1 统一关联键

每条执行事件尽可能关联：
`traceId`、`requestId`、`scenarioId`、`blueprintId`、`blueprintVersion`、`taskId`、`planId`、`executionId`、`contextDigest`、`frameworkId/version`、`capabilityId`、`runId/forecastRunId`。

缺少某些键时允许为空，但不得编造；关联键命名按现有 runtime/trace 契约统一。

### 7.2 执行状态语义

推荐语义（映射既有 Runtime 状态，不新增平行状态机）：
- `CREATED`、`PLANNED`、`VALIDATING`、`RUNNING`、`VERIFYING`；
- 终态：`SUCCEEDED`、`NEEDS_INPUT`、`NEEDS_HUMAN_REVIEW`、`REJECTED`、`INVALID_OUTPUT`、`FAILED`、`BUDGET_EXCEEDED`、`CANCELLED`。

`SUCCEEDED` 仅表示执行流程与声明的验证通过，不代表业务判断真确。状态持久化应复用 runtime-task/既有执行记录，不能新增另一套任务表。

### 7.3 异常策略

- 输入缺失：返回 `NEEDS_INPUT` 与 gap，不编造；
- 权限拒绝/策略服务不可用：停止，fail-closed；
- 依赖 503：标记依赖不可用，不折叠为空结果；
- 工具临时失败：按既有重试策略有限重试；
- 输出 Schema 失败：有限修复后重验，否则 `INVALID_OUTPUT`；
- 证据冲突：保留双方，生成冲突对象或人工复核，不静默删证；
- 超预算：立即停止并保存部分执行引用；
- 版本不可用：不静默切换到最新版本；重新规划须显式记录；
- 运行无进展/循环：达到最大迭代或无进展阈值即停止；
- 业务副作用：只能通过 ToolExecutor 和 security-engine 授权；默认禁止框架直接副作用。

## 8. 认知产物契约

### 8.1 Evidence

建议字段语义：
- `evidenceId` 或稳定引用；
- `sourceType/sourceId/sourceVersion`；
- `sourceAuthority`；
- `observedAt/asOfTime`；
- `scope`；
- `evidenceKind`（数据/规则/案例/模型输出/人工陈述等）；
- `supports[]` / `contradicts[]`；
- `limitations`；
- `provenanceRef`；
- `sandbox/formal lineage`（如适用）。

证据不等于事实：Evidence 是对某项判断提供支持或反对的材料引用；Fact 应由权威数据、已确认事件或经过规定确认流程的来源提供。

### 8.2 Hypothesis

必须区分候选、受证据支持、被相信、被反驳/失效等状态，且不能因 LLM 输出直接升级为已确认事实。状态枚举先复用当前存量定义（已知设计线索含 `PROPOSED/EVIDENCED/BELIEVED/REFUTED`，必须以代码/迁移为准）。

至少保留：
- 陈述与作用范围；
- 支持/反对证据引用；
- 来源与生成方式；
- 不确定性和适用条件；
- 状态、版本、有效期；
- 创建/复核主体与审计引用。

### 8.3 Belief

Belief 是当前认知主体对某命题的非确定性判断，不等于事实。若存在 probability/score：
- 明确其含义、量纲、校准来源和更新时间；
- 未经校准不得把 LLM 自评值展示为概率；
- 保留支持/反证与版本；
- 允许撤销、失效、冲突与人工复核。

### 8.4 Decision Basis 与确定性计算引用

Decision Basis 记录决策依赖的目标、约束、证据、候选方案、风险与取舍，不等同于最终 Decision/Action。金额和正式业务指标使用 `CalculationResultRef`/`forecastRunId` 等引用业务域权威结果，不在 cognitive-engine 再存一份金额事实。

## 9. Cognitive Model Registry 与 Framework Registry

### 9.1 Framework Registry

管理“如何组织认知过程”：类别、版本、适用范围、输入输出契约、步骤、验证、停止、治理。

### 9.2 Cognitive Model Registry

管理认知模型本身：模型 ID/版本、类型、适用域、输入输出契约、评估集/指标、校准、成本/时延、依赖能力、发布门禁、停用状态。

### 9.3 与 AI Model/Capability Center 的关系

- Cognitive Model Registry 管理认知域模型资产语义与业务适用性。
- AI Model Registry/Capability Center 管理可执行模型/能力、提供方、路由、硬件/运行环境、成本和技术指标。
- 一个认知模型可以引用一个或多个 AI 模型/工具能力。
- 不允许两套 Registry 各自维护相互冲突的运行可用状态；通过稳定引用和发布门禁协作。
- 所有 LLM/Embedding 供应商访问经 `llm-gateway`；小模型也通过统一 Capability Contract 和已批准执行路径。

## 10. 既有认知端点 E1-E4 的兼容要求

已知设计基线中的 E1-E4 语义：
- E1 `detect`：返回场景 Mind 集合及 `capabilityMask`、`closedLoopBounds` 等已有字段；
- E2 `operation-eval`：按既有权重规则对 Belief/趋势进行排序；
- E3 `hypotheses`：支持严格 `mind` 过滤；
- E4 `beliefs`：支持严格 `mind` 过滤。

Coding Agent 必须从 OpenAPI、Controller、DTO 和 `features/20260917-scenario-workbench/` 在途契约读取真实路径/参数/响应。不得根据这些短名称猜测 endpoint URL。

兼容规则：
- 不属于场景的 `mind` 不得静默回退为全局查询；按既有契约返回 400/空/404 的语义。
- `[]` 表示查询成功但没有结果；404 表示资源不存在；503 表示认知能力/依赖不可用；403 表示无权限。
- cognitive 未启用时的 503 必须原样传递给 UI，不得包装成空成功。
- `capabilityMask` 枚举集中在现有 `cognitive-engine-api` 包中维护。
- 不改变现有端点路径/签名；若要新增字段，保证向后兼容并更新 OpenAPI/契约测试。

## 11. 因果、预测与反事实

- 因果解释发生在确定性预测/计算之后；不能代替业务金额计算。
- 因果链的每条边应标注依据类型：权威业务规则、统计证据、领域假设或待验证推断。
- 只有假设没有证据时，标为 `UNVERIFIED_HYPOTHESIS`，不能输出确定因果措辞。
- 反事实必须引用具体 `forecastRunId`、输入快照、口径、范围与被修改的结构化假设；情景金额由确定性预测服务计算。
- 情景只允许改变指定项目/部门/期间/环节的假设；必须与基准逐项比较收入、成本、利润及因素贡献。
- `ScenarioSimulatorServiceImpl` 若在现有系统中承担探索式交互，应继续作为探索层，不得充当可审计的财务金额计算器。

## 12. Outcome Evaluator 与受控反馈

输入：原始运行引用、原输入快照、口径/公式版本、真实结果引用、评估规则版本。
输出：
- 误差/准确度指标；
- 偏差方向与分组分析；
- 可能原因与证据引用；
- 待复审假设/模型/规则候选；
- 建议责任人/截止时间（如果由现有工作流承载）；
- 需审批的变更清单。

不得：
- 因单次偏差自动修改生产规则/Belief/模型；
- 用实际值覆盖历史预测快照；
- 把未经审批的更新候选写入正式知识、本体或数据资产；
- 将预测输出与真实结果不一致简单归因于模型错误，必须检查数据口径、时效、覆盖、结构变化和行动干预。

## 13. 安全、日志与观测

- 工具执行前调用 security-engine/PDP，执行后检查 obligations 并审计。
- PDP 不可用时默认拒绝任何受保护写操作；只读降级也必须符合现有策略。
- 每个请求使用既有 `traceId`/`requestId`；记录 `scenarioId`、`blueprintVersion`、`contextDigest`、框架/模型版本与执行状态。
- 记录模型调用次数、Token/成本、工具调用、延迟、重试、预算耗尽和停止原因；使用现有计量/运行监控设施。
- 不把 prompt 原文、凭据或不必要的敏感数据写入日志。
- 对认知产物的来源引用、状态变更、批准和失效操作必须可审计。

## 14. 验收测试

### CE-01 Context Pack 来源追溯
每个来源都有稳定引用、版本/快照、权限过滤结果；digest 对相同规范化输入稳定。

### CE-02 不新增上下文表
数据库迁移检查确认没有新增 `cognitive_context` 或认知业务事实表。

### CE-03 框架版本不可变
发布后修改同版本定义被拒绝；新版本可独立发布；历史执行绑定旧版本。

### CE-04 硬约束优先
无权限/缺关键输入/依赖不可用的框架不会因评分高而被选择执行。

### CE-05 计划校验
循环依赖、缺失 Schema、无效能力引用、超预算计划均被拒绝。

### CE-06 证据冲突
同时存在支持和反对证据时，两者均被保留，输出不确定性和待解决问题。

### CE-07 反因果过度断言
仅相关性/单条案例不能生成已确认因果结论。

### CE-08 正式金额来源
预测数字只能引用确定性业务运行结果；LLM 生成的金额不得通过验证。

### CE-09 运行时停止
预算超限、无进展循环、取消和安全拒绝均能停止并保存部分 trace。

### CE-10 E1-E4 兼容
空数组、404、503、403 的语义区分与既有契约一致，场景 mind 过滤严格生效。

### CE-11 受控反馈
预测偏差只产生 Outcome Evaluation 和更新候选；不会自动改生产规则/知识/模型。

### CE-12 安全 fail-closed
模拟 security-engine/PDP 不可用，任何受保护写入均拒绝；审计记录原因。

## 15. 首期实施范围

MVP 只要求把以下链路跑通：
1. Context Builder 能组装并校验场景请求态上下文；
2. Framework Registry 可读取已发布框架版本；
3. Strategy Selector 能硬过滤并形成可校验计划草案；
4. E1-E4 现有认知接口语义正确；
5. 证据/假设/信念可引用且状态/来源可追溯；
6. 根因分析输出竞争性假设和反证，而不是确定因果；
7. 情景分析调用确定性预测业务能力；
8. Outcome Evaluator 形成受控更新候选；
9. traceId 与场景/蓝图/上下文/框架/运行版本贯通。

不得在首期为追求“完整认知系统”而一次性实现所有框架、重构模型注册、创建新存储层或重写 Agent Runtime。
