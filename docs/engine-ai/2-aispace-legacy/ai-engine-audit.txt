1. Agent Loop 执行引擎 — 评分: 4.0/5
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 优势：
  • AgentLoopService (1032行) 实现了完整的 think→tool_call→observe→think 循环
  • 多轮工具调用循环：支持连续工具调用后 LLM 继续推理，直到输出 final response
  • 最大迭代限制：默认5轮，通过三层配置可动态调整（maxIterations字段）
  • 超时控制：工具调用30s超时(TOOL_TIMEOUT_MS)，单LLM HTTP请求120s超时
  • SSE流式输出：AgentLoopController实现完整SSE streaming，5种事件类型
    (token/tool_call/tool_result/done/error)，异步执行+回调
  • Token预算管理：trimHistory()实现从近到远的token裁剪，保留system消息
  • LLM响应解析策略丰富：5级回退(JSON原生→```json代码块→<tool_call>标签→
    正则function_call→普通文本)，极强兼容性
  • ToolCall Schema校验：parseToolCalls后自动validateToolCalls（必填/类型/默认值）
  • Skill运行时注入：buildSystemPrompt将DB中Skill列表动态注入System Prompt
  • MemoryExtractor注入点预留（T3阶段，已实现接口但暂未接入历史消息）

⚠️ 问题：
  • AgentLoop整体超时控制未实现：虽然AgentLoopConfig有agentTimeoutMs参数
    (默认300s)，但AgentLoopService.run()方法并未使用该值做整体超时中断——
    所有超时仅在单个工具调用层面（30s）和单LLM调用层面（120s HTTP超时）。
    如果Agent连续5轮LLM调用每轮都用满120s，总耗时可能达到600s+
  • SSE流式并非真正token级流式：splitIntoTokens()是按段落/句子切分后逐块发送，
    且每个"token"间有10ms延迟。不是LLM原生streaming（逐token返回），而是
    等待完整AgentLoop执行完成后一次性拆分输出
  • LLM调用失败重试过于简单：仅在turn==1时重试一次，没有指数退避，
    后续轮次的LLM失败直接返回error
  • tool_result消息的tool_call_id传递不完整：DeepSeekProvider.convertMessages()
    中tool角色消息未设置tool_call_id字段，可能导致某些LLM的多工具并行调用混乱

📊 代码证据：
  AgentLoopService.java L106-213: run()方法 — 完整loop但缺整体超时
  AgentLoopController.java L122-201: chatStream — 伪流式(exec loop后拆分)
  AgentLoopService.java L573-612: parseToolCalls — 5级解析回退
  AgentLoopService.java L384-443: trimHistory — token预算裁剪

2. Tool 系统 — 评分: 4.5/5
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 优势：
  • 双层架构：ToolRegistry(注册中心, 609行) + ToolExecutorService(执行器, 536行)
  • ToolRegistry优先级执行：AgentLoopService先查ToolRegistry，未命中的回退到
    ToolExecutorService的DB fallback逻辑
  • 内置8个工具：query_db / invoke_rest / delegate_to_agent / read_file / 
    write_file / search_files / patch (FileToolService) + getCurrentTime / 
    calculateRisk (Builtin)
  • 三种执行模式全覆盖：SQL(JdbcTemplate)、REST(RestTemplate/HttpExchange)、
    BUILTIN(Java函数)
  • 数据库加载：ecos_ai.ecos_tool_definition表动态加载(WHERE status='ACTIVE')
  • Fallback机制：DB无数据时回退到内存fallbackTools(7个预定义工具)
  • ToolSchema完整定义：支持参数类型/必填/默认值/枚举值/描述，自动生成
    OpenAI function-calling兼容的JSON Schema
  • 结果截断保护：TOOL_RESULT_MAX_CHARS=2000，ToolExecutorService和
    AgentLoopService双层截断
  • SQL安全：仅允许SELECT/WITH语句
  • REST URL模板：支持{paramName}占位符替换

⚠️ 问题：
  • 工具注册是硬编码的：initBuiltinTools()在构造函数中调用，不支持运行时
    热注册/热更新。新增工具需改代码重新部署
  • template agent声明的toolWhitelist未在运行时被执行过滤：AgentLoopService
    解析tool_call后直接执行，未根据Agent模板的toolWhitelist做权限校验——
    toolWhitelist只在AgentTemplateService实例化时写入capability，未被
    AgentLoopService消费
  • FileToolService实现了文件操作但类内容未审计(可能缺少路径遍历防护)
  • query_db没有结果行数限制(LIMIT)，恶意SELECT可能拉全表

📊 代码证据：

  ToolExecutorService.java L132-155: loadFromDatabase — ecos_tool_definition表
  ToolSchema.java L69-111: toFunctionCallSchema — OpenAI兼容Schema生成

3. 会话管理 — 评分: 3.5/5
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 优势：
  • PG持久化：sys_agent_session + sys_agent_message 两张表完整CRUD
  • 生命周期状态机：ACTIVE → IDLE(30min无活动) → EXPIRED → ARCHIVED
  • 线程支持：支持thread_id字段，同一会话下多线程对话
  • 消息持久化：chatInSession端点自动持久化user+assistant消息
  • markIdleSessions()批量标记过期
  • 查询支持：按状态/agent/thread多维度查询

⚠️ 问题：
  • 🔴 上下文窗口管理缺失：AgentSessionService仅做持久化存储，不管理上下文窗口。
    Token裁剪在AgentLoopService.trimHistory()中基于estimate估算，且裁剪后
    消息不写回DB——即每次对话重新加载全量消息再做裁剪，对长会话性能差
  • 🔴 历史消息压缩完全缺失：无消息摘要/压缩机制。长会话超过token上限后只能
    简单从近到远丢弃，丢失早期上下文
  • 会话过期定时清理未实现：markIdleSessions()存在但无Spring @Scheduled调用，
    需要外部触发
  • AgentSessionService与AgentLoopService中的AgentSession是两个不同类：
    AgentSessionService.AgentSession (DB持久化POJO, 418行)
    vs runtime AgentSession (AgentLoopService.run的参数, 来自runtime.llm.session包)
    两者不统一，会话内对话持久化时仅记录user+assistant，不记录tool messages
  • chat端点(非会话)不持久化消息——每次调用都是无状态

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  • delegate_to_agent作为内置工具注册到ToolRegistry，LLM可自然调用
  • 超时控制：子Agent 120s超时，通过Future.get(timeout)实现
  • 单层委托约束：子Agent的system prompt不包含delegate_to_agent工具描述

  • 子Agent结果仅截断至3000字符，但未做结构化合并
  • 无并发控制：如果主Agent在一次turn中发出多个delegate_to_agent，是串行执行的
  • 无子Agent间通信机制：子Agent之间完全隔离，无法协作
  • 无委托预算控制：主Agent理论上可以在5轮中每轮都delegate，产生25个子Agent调用

  • Provider选择器：selectProvider()按priority排序，选择第一个可用且支持
    function-calling的Provider
  • 双路径fallback：Provider优先→LLMGateway兜底，配置了deepseekApiKey
  • Provider不可用时自动跳过(isAvailable()检查api-key)
  • AgentLoopConfig的defaultProvider字段支持运行时切换

⚠️ 问题：
  • 🔴 目前只有1个Provider实现(DeepSeekProvider)，无通义千问/OpenAI/Anthropic
    等其他厂商的实现——LLMProvider接口设计了多Provider架构但实际只有deepseek
  • 无故障转移(failover)机制：如果DeepSeekProvider返回失败，代码会fallback到
    LLMGateway，但LLMGateway本质是同一个deepseek。不存在"A厂商挂了自动切B厂商"
  • 无速率限制(rate limiting)：对DeepSeek API无QPS控制，高并发下可能触发
    API限流
  • 无断路器(circuit breaker)：Provider连续失败后无熔断保护
  • 无模型级别的选择和路由——AgentLoopConfig中的model字段直接透传，
    但LLMProvider.selectProvider()只看Provider不看model

📊 代码证据：

✅ 优势：
  • 统一结果模型：AgentLoopResult以success/errorMsg区分成功/失败
  • ToolResult以success标识工具执行成功/失败，error字段含错误详情
  • ChatResponse统一LLM响应模型(success/errorMsg/tokens)
  • LLM调用重试：turn==1时格式错误自动重试一次
  • Controller层统一try-catch返回ApiResponse
  • DeepSeekProvider区分了超时异常(HttpTimeoutException)和通用异常
  • JdbcTemplate不可用时的降级处理（返回fallbackTools或友好错误）

⚠️ 问题：
  • 🔴 无业务异常分类体系：没有ErrorCode枚举或BizException层级。
    错误信息用裸字符串传递，无法按错误类型做分类处理
  • 无指数退避重试：LLM重试仅一次且无延迟，网络波动下可能连续失败
  • 降级策略不完整：工具执行失败后AgentLoop直接continue下一轮，
    不会告知LLM"工具失败了请换一个方案"
  • AgentLoopResult.maxTurnsExceeded硬编码turns=5而非实际maxTurns值
  • Controller层错误文案不一致：ApiResponse.success("Agent 推理未成功完成", data)
    在非成功场景仍返回success外层，语义混淆
  • 工具执行超时(TimeoutException)后ExecutorService shutdownNow未处理
    interrupt信号传播
