## §1 逐轮变更详解

### 1.1 R7 · 控制域版本治理与双写审计（Git × DB 治理闭环）

- **原名册锚点**：§4.6「平台与横切能力」需求卡 **S6**，[L581-L607](file:///d:/workspace/javaprojects/ECOS/docs/20-%E9%9C%80%E6%B1%82/ECOS%E9%9C%80%E6%B1%82%E8%A7%84%E6%A0%BC%E8%AF%B4%E6%98%8E%E4%B9%A6-%E5%85%A8%E6%96%B0%E5%90%88%E5%B9%B6%E7%89%88-2026-10-12.md#L581-L607)
- **变更原因**：控制域对象（机构/权限/Pipeline/本体/知识/认知/Agent/场景）此前**只有 DB 运行态、无统一版本治理**，变更无法形成可审查、可比较、可追溯、可回滚的版本；同时存在「把 Git 提交成功误当审计通过」的认知风险。需确立「Git（声明式版本）/ DB（运行态） / 独立审计（不可抵赖证据）」三机制**互不替代**。
- **新增需求条目**：

  | REQ | 一句话要点 | 优先级 |
  |:--|:--|:--:|
  | REQ-PLT-30 | 控制域对象目录（数据分类单源）+ 五类边界（配置 vs 运行态业务数据 vs 执行状态 vs 审计证据 vs 大数据产物） | P1 |
  | REQ-PLT-31 | 版本契约（稳定 ID / Schema 版本 / 规范化序列化 / 内容指纹 / 差异 / 变更原因与操作者 / commit SHA / 目标环境 / 依赖检查）；**发布引用固定 commit SHA，禁引用可变分支名** | P1 |
  | REQ-PLT-32 | 历史版本查询 + 经授权重发布；回滚优先发布已知历史版本，**禁任意反向 SQL** | P1 |
  | REQ-PLT-33 | 双写发布一致性协议（提案→依赖检查→审批→固定 commit→发布任务→幂等应用→状态持久化→重试→对账→补偿/回滚→发布后验证）；**Git×DB 非单一原子事务，禁止部分成功报完全成功** | P1（目标能力） |
  | REQ-SEC-12 | 敏感数据不入普通 Git（密码/密钥/令牌/会话/个人敏感信息）；审计记录不可被普通控制域编辑权限删改；发布权与编辑权分离；Agent 只能经受控 API 提提案 | P1 |
  | REQ-SEC-13 | 审计分级映射（审计等级—变更风险—审批策略—发布门禁），四级 L1~L4 为**建议基线**，须与 `clearance_level` L0~L4 / `audit_mode` 核对映射后生效 | P1 |
  | REQ-NF-10 | 双写失败必须产生**可识别状态**（PARTIAL_FAILURE/FAILED/DRIFTED），对账区分 一致/缺失/意外/漂移/版本不匹配/部分发布/依赖不一致/无法验证 | P1 |

- **功能调整**：无既有功能被删除；新增**平台横切治理能力**，不新增部署模块、不新增数据库表、不新开 REQ 系列。
- **边界场景变更**：① 三份结果分别记录（Git 提交 ≠ DB 应用 ≠ 审计合规）；② 6 类设计资产（知识资产树/认知模型/心智模型/场景定义/Agent 定义/Agent 协同）**当前均未接入 Git 归档**，接入前版本接口返回 `not_available`，**禁止伪成功**；③ Git 仓库注册表**无建表 DDL、无 repositoryId 注册种子**（缺口）；④ 已知偏差按「缺口登记、待排期」，不假装闭环。
- **非功能指标更新**：新增 REQ-NF-10（双写状态可识别、对账八类判定）。
- **影响范围**：横切全平台控制域（§4.1 组织权限 / §4.2 本体 / §4.3 认知资产 / §4.4 场景 / §4.5 AI 工作台 / 数据引擎）；复用 runtime-access `GitService`、`AuditHashChainService`、Kafka `ecos.audit`。
- **裁决（2026-10-16 · PMO）**：
  - **Git 仓库注册表定名 `ecos_git_repo`**（原 `td_git_repository` 命名作废）；须补建表 DDL + `repositoryId` 注册种子；代码/文档中 `td_git_repository` 残留按改名范围清理。
  - **审计等级维持 L1~L4 四级**（与 REQ-SEC-13 及原设计册 §2.9.4④ 一致）；「可简化为三级」记为**允许的降级选项（非默认）**，避免过度复杂；仍须与既有 `clearance_level` L0~L4 / `audit_mode` 核对映射，**不得替换现有安全等级定义**。
  - 4 张废弃版本表 DROP 前置条件（备份 + 15 处读写切 git）按原处置建议执行。
- **验收标准**：见原名册 L599-L606 七条 + 本册 §6 DoD-R7。

### 1.2 R8 · Redis 缓存架构与一致性治理

- **原名册锚点**：§4.6 需求卡 **S7**，[L609-L639](file:///d:/workspace/javaprojects/ECOS/docs/20-%E9%9C%80%E6%B1%82/ECOS%E9%9C%80%E6%B1%82%E8%A7%84%E6%A0%BC%E8%AF%B4%E6%98%8E%E4%B9%A6-%E5%85%A8%E6%96%B0%E5%90%88%E5%B9%B6%E7%89%88-2026-10-12.md#L609-L639)
- **变更原因**：Phase 0 事实核查确认——Redis **未接入运行链路**（仅 sysman-impl 的 `redis-enabled` profile 单点 `RedisBlacklistStore`）、现有缓存**全为单机本地内存**（Caffeine/ConcurrentHashMap）、**无 Spring Cache 抽象**、**无 Outbox/事务消息**、runtime 底座不含 Redis/缓存（记为**底座缺口**）。需把缓存定义为「可重建的受控加速层」并纳入统一治理，避免缓存成为绕权/伪权威通道。
- **新增需求条目**：

  | REQ | 一句话要点 |
  |:--|:--|
  | REQ-PLT-34 | 缓存纳入 runtime 底座 + **八条实施原则**（权威源唯一/可重建/权限先于缓存/版本可追溯/明确一致性等级/失效可观测/安全审计独立/避免过度缓存） |
  | REQ-PLT-35 | 缓存对象分类与一致性策略矩阵（**14 类**缓存对象 × 策略/一致性/失效触发/隔离维度） |
  | REQ-PLT-36 | 缓存键规范 **`ecos:{env}:{domain}:{objectType}:{scope}:{objectId}:v{version}`**；键禁明文敏感信息、不得成为绕权依据 |
  | REQ-PLT-37 | 一致性机制四类（Cache-Aside / 版本化缓存 / 主动失效与事件驱动 / 先提交权威数据再失效缓存）；Outbox 列为**待建设能力** |
  | REQ-PLT-38 | 双写审计与 Git 衔接：可选审计字段 **8 项**（cache_strategy/cache_namespace/cache_version/cache_invalidation_event_id/cache_invalidation_status/cache_verification_status/cache_failure_reason/cache_verified_at）；发布状态机分别记录 6 步 |
  | REQ-SEC-14 | 权限·安全：受控网络+认证+最小权限+传输加密；环境/租户/机构/用户隔离；权限缓存定义最大陈旧时间并证明撤权生效；**fail-closed（DENY）**；不缓存高敏感数据 |
  | REQ-NF-11 | 性能容量与故障降级：Redis 不可用须 **9 场景降级**；**Redis 故障绝不绕过认证与授权**；性能目标基于实测与 SLA |
  | REQ-NF-12 | 可观测：缓存指标（命中率/失效/降级/键基数）经 `runtime-monitor` 采集 + 日志 + 告警 |
  | REQ-NF-13 | 测试验收：功能一致性 / 安全（含故障不得绕权）/ 稳定性与性能 |

- **边界场景变更**：Redis 不可用时鉴权以权威源+安全引擎裁决（fail-closed）；键含权限范围维度缺失→拒绝返回；缓存丢失可重建；**不得声称已分布式/已接入**；Outbox/Spring Cache/键隔离维度/Redis 底座归属均为**待建设/待架构裁决缺口**。
- **非功能指标更新**：REQ-NF-11（9 场景降级 + 故障不绕权）、REQ-NF-12（可观测指标）、REQ-NF-13（测试验收）。**全部数值/指标名称标注为「建议基线」，未压测前不得作为承诺**。
- **影响范围**：横切全平台读路径；涉及 runtime-event `EventBusService`、runtime-monitor、SysConfigService.refreshCache()、ClearanceInterceptor 与 RLS/CLS/ABAC。
- **裁决（2026-10-16 · PMO）**：
  - **Redis 缓存能力归属 runtime 公共底座，由 Runtime 统一管理配置**（缓存连接、失效策略、缓存粒度等配置由 Runtime 统一供给，各服务不自建缓存配置）。
  - **须同步登记「架构铁律 §2.5 runtime 公共底座清单」修订待办**（现底座清单不含 Redis/缓存），不静默改铁律。
  - 缓存键隔离维度与 `ClearanceInterceptor` 客户端可控 `X-Org-Id` 存量偏差**一并处置**；**Outbox/事务消息与 Spring Cache 抽象列入待建设清单**。
- **验收标准**：见原名册 L631-L638 七条 + 本册 §6 DoD-R8。

### 1.3 R9 · Git 控制域安全与可信发布治理

- **原名册锚点**：§4.6 需求卡 **S8**，[L641-L686](file:///d:/workspace/javaprojects/ECOS/docs/20-%E9%9C%80%E6%B1%82/ECOS%E9%9C%80%E6%B1%82%E8%A7%84%E6%A0%BC%E8%AF%B4%E6%98%8E%E4%B9%A6-%E5%85%A8%E6%96%B0%E5%90%88%E5%B9%B6%E7%89%88-2026-10-12.md#L641-L686)
- **变更原因**：S6 已确立「Git 是控制域版本载体」，但**未回答"该链路上每个环节凭什么可信"**——仓库被越权读/篡改/投毒/删除会直接传导到运行时权限、数据处理与 Agent 执行。需把 Git 安全纳入控制平面安全架构。
- **新增需求条目**：

  | REQ | 一句话要点 |
  |:--|:--|
  | REQ-SEC-15 | 仓库访问与身份权限：企业身份+MFA+最小权限；**五权分离**（读/变更/审批/发布/密钥）；服务用专属身份；Git 平台权限 ≠ ECOS 业务权限 |
  | REQ-SEC-16 | 凭据与密钥安全：秘密禁入 Git；Secret Manager 存秘密、Git 只存引用；Secret Scanning；泄露即轮换，不以删提交掩盖 |
  | REQ-SEC-17 | 变更审批与职责分离：五角色矩阵（发起人/领域负责人/安全审批人/发布服务身份/审计人员）；高风险双人审批可配置 |
  | REQ-SEC-18 | 完整性与可信发布：分支保护禁直推禁强推；关键提交/标签签名；签名发布清单绑定 仓库标识+Commit SHA+内容哈希+目标环境+审批记录+策略版本；**Commit SHA ≠ 发布授权** |
  | REQ-SEC-19 | 防恶意配置与 Agent 投毒：进运行时前 Schema/引用/依赖校验；白名单收敛；**Agent 不得因 Git 写权限获得生产发布权** |
  | REQ-SEC-20 | Redis 与 Git 安全边界：Redis 不监听 Git 自动发布；未审批分支内容不进生产缓存；撤权有失效时限；Redis 被攻破不得获得 Git 写权 |
  | REQ-SEC-21 | 独立审计与防篡改：审计存储权限与 Git 仓库权限分离；发布事件关联 13 类字段；完整性校验+保留策略+独立备份 |
  | REQ-PLT-39 | 备份恢复与事件响应：五类事件预案（仓库删除/篡改、Token/签名密钥泄露、恶意提交、未审批发布、版本分歧）；发布冻结；回滚前重新验证授权 |
  | REQ-NF-14 | 安全测试与验收：越权/秘密扫描/签名验证/审批绕过/投毒注入/Git-Redis 信任边界/审计完整性/备份恢复演练 |
