## 一、部署形态需求细化

### 1.1 REQ-PLT-01 微服务 v2 七 JAR 部署

**细化规则**：

| 部署单元 | 端口 | 启动顺序 | 健康检查 | 依赖 |
|---|:--:|:--:|---|---|
| 基础设施容器（PG/Neo4j/MinIO/OPA/Kafka/ZK） | — | 1 | `docker ps` 全部 healthy | — |
| sysman | 18081 | 2 | `GET /actuator/health` 或既有 health 端点 | PG |
| datanet | 18082 | 2 | 同上 | PG、MinIO |
| buszhi | 18083 | 2 | 同上 | PG |
| dccheng | 18086 | 2 | 同上 | PG、（enterprise）Neo4j |
| aiming | 18084 | 2 | 同上 | PG、llm-gateway 内嵌 |
| workspace | 18090 | 3 | 同上 | 5 service 可达 |
| gateway | 8080 | 4（最后） | `GET :8080/actuator/health` | 全部 service |

**验收用例**：
1. 按序启动 7 进程，各健康检查 200；
2. 乱序杀 sysman 后调 gateway 业务端点 → 5xx/503 明确错误而非挂死；
3. `GatewayRouteIntegrityTest` 绿（既有，守护 5 前缀路由表）。

### 1.2 REQ-PLT-02 gateway 唯一入口 + 头防伪

**细化规则**：
1. gateway 校验 token 后 **strip 全部外部 `X-ECOS-*` 头**，按认证结果重新注入（`X-ECOS-USER-ID` / `X-ECOS-ROLES` / `X-ECOS-TENANT` 等，以 gateway 现有实现清单为准）；
2. 前端 BFF（server.ts）默认全部前缀转 `GATEWAY_URL`；`ECOS_LOCAL_DIRECT_SERVICE_PROXY=true` 时仅本地调试允许 5 类前缀直连 service 端口；
3. service 侧 `HeaderAuthInterceptor`：非 gateway 来源（头缺失/非法）默认 DENY。

**验收用例**：
| # | 用例 | 期望 |
|:--:|---|---|
| 1 | 外部请求伪造 `X-ECOS-USER-ID: u999` 经 gateway | service 收到的是 gateway 重注入值，非 u999 |
| 2 | 直连 :18082 带头无 gateway 签名 | 403/DENY |
| 3 | 关直连开关后前端抓包 | 无 18081~18090 直连请求 |

**裁定**：档位名统一为 `standard / enterprise / ultimate`；`flagship` 全部替换为 `ultimate`。

**验收**：grep flagship 仅存于过渡期并列注解与 DEPRECATED 注释；三档各启动一次冒烟通过。

## 二、DIKCW 贯通需求细化

### 2.1 REQ-PLT-10 主链 E2E 贯通用例（P0）

**定义一条黄金链路用例（集成测试脚本，落 `ecos-tests/` 或 gateway test）**：

| 步 | 操作 | 端点/动作 | 期望结果 |
|:--:|---|---|---|
| 1 | 登记数据源 | datanet `POST /api/v1/datanet/datasource` | 201，datasourceId |
| 2 | 采集入湖 | 管道 `SOURCE_JDBC→SINK_MINIO` runOnce | MinIO `raw/structured/...` 有对象；`td_data_resource` layer=RAW zone=STRUCTURED |
| 3 | 落 DW | 管道 `SOURCE_MINIO→SINK`（或 TRANSFORM） | 目标表 layer=CURATED |
| 4 | 本体映射 | ontology entity-mappings 保存 | 映射校验通过（DW 表/列存在性） |
| 5 | KG 抽取 | kb `POST /api/v1/knowledge/extract/structured`（INCREMENTAL） | graph_node/edge upsert >0；watermark 更新；kg_sync_log 台账 |
| 6 | 认知消费 | cognitive 假设/信念（心智层） | 场景关联 hypothesis/belief 可查 |
| 7 | 场景消费 | workspace E1 detect | 返回 Mind 集合（或 503 穿透，两者均为合法） |

**失败判定**：任一步非期望即链路 FAIL；每步产物 ID 串联记录到测试报告。
**测试数据**：专用 schema/前缀 `e2e_`，用后清理（逻辑删除）。

### 2.2 REQ-PLT-11 W→D 现实反馈链（P1，新实现）

**数据模型（DDL 草案，落 DW 层，遵循 DR 红线）**：

```sql
CREATE TABLE IF NOT EXISTS ecos_biz_action_outcome (
    id              VARCHAR(36) PRIMARY KEY DEFAULT gen_random_uuid(),
    action_id       VARCHAR(36) NOT NULL,           -- 关联经营动作（PRD-09 FC-04）
    scenario_id     VARCHAR(36) NOT NULL,
    forecast_run_id VARCHAR(36),                    -- 产生该动作的预测运行
    period          VARCHAR(7)  NOT NULL,           -- YYYY-MM
    metric_code     VARCHAR(64) NOT NULL,           -- 回流指标编码
    outcome_value   NUMERIC(18,4) NOT NULL,
    outcome_type    VARCHAR(20) NOT NULL,           -- EVENT / METRIC / FACT
    source_ref      VARCHAR(255),                   -- 证据/凭证引用
    create_time     TIMESTAMP NOT NULL DEFAULT NOW(),
    update_time     TIMESTAMP NOT NULL DEFAULT NOW(),
    create_by       VARCHAR(100),
    update_by       VARCHAR(100),
    is_deleted      SMALLINT NOT NULL DEFAULT 0,
    version_no      VARCHAR(20) NOT NULL DEFAULT '1',
    domain          VARCHAR(50) NOT NULL DEFAULT 'default'
);
CREATE INDEX IF NOT EXISTS idx_bao_action ON ecos_biz_action_outcome(action_id);
CREATE INDEX IF NOT EXISTS idx_bao_scenario_period ON ecos_biz_action_outcome(scenario_id, period);
```

**写入路径**：workspace 行动执行完成 → `POST /api/v1/datanet/facts/action-outcomes`（datanet 新增端点，只增不改）→ 落表 → 发 `PipelineEvent("ACTION_OUTCOME_RECORDED")`。
**消费路径**：下一轮预测运行的输入快照（PRD-09 FC-02）把 action_outcome 纳入事实集合。
**边界**：workspace 不直连 PG（IR01），必须经 datanet REST。

**验收**：动作完成→outcome 落表→事件可查→新预测运行快照含该 outcome。

### 2.3 REQ-PLT-12 认知三档落盘守护

**守护断言（测试清单）**：
1. cognitive 域写操作仅涉及 4 表：`ecos_cognitive_model` / `ecos_cognitive_evidence` / `ecos_cognitive_hypothesis` / `ecos_cognitive_belief`（SQL 审计 + ARCH-07）；
2. 推理结果类端点（diagnose/forecast/simulate）响应后 DB 无新增行（集成测试断言 count 不变）；
3. 三表对场景侧只读（E1–E4 仅 SELECT；cognitive 不写 business 表）。

### 2.4 REQ-PLT-13 场景组成模型与完整度（在途 PMO-66 对齐）

**完整度计算公式（规范定义）**：

```
必备边类型 E_req = { DATASET→OBJECT_TYPE(映射), OBJECT_TYPE→KNOWLEDGE_BASE(抽取), KNOWLEDGE_BASE→AI_AGENT(认知) }
coverage = |E_present ∩ E_req| / |E_req|          -- 按真实连边，禁止按绑定数量
场景完整度 = coverage × 100%
```

**孤岛判定**：绑定节点在 `ecos_scenario_binding_link` 中入度+出度=0（SECURITY_POLICY/INTERFACE 除外，二者分别挂"约束覆盖"与"出口暴露"关系）→ 保存拒绝，返回缺失边提示。
**验收**：完整度指标与 binding_link 表一致；孤岛绑定保存返回 4xx + 明确缺边说明；完整度=绑定数量的实现判 FAIL。

## 三、横切能力需求细化

### 3.1 REQ-PLT-20/21/22/23 收敛矩阵

**安全调用点矩阵（REQ-PLT-20 细化，与 PRD-07 联动）**：

| 引擎 | 时机 | security 端点 | 失败行为 |
|---|---|---|---|
| data-engine | 查询前 | `POST /api/security/rls/apply` | DENY |
| data-engine | 结果返回前 | `POST /api/security/cls/columns` | DENY |
| 各引擎 | 敏感字段返回前 | `POST /api/security/mask` | DENY |
| ai-engine | 工具/Function 执行前 | `POST /api/v1/security/policy-engine/evaluate` | DENY（PRD-06 AI-01） |
| 全部 | 写操作后 | Kafka `ecos.audit` | log 兜底不阻断 |

**runtime-access 收敛清单（REQ-PLT-21）**：合法 Driver 持有点仅 `runtime-access`（JdbcConnector/Neo4jClient/MinioStorageService/DuckDB/Git）；违规存量 4 处清偿见 PRD-02 DATA-05。
**审计事件 schema（REQ-PLT-22，Kafka `ecos.audit` 消息体最小字段集）**：

```json
{
  "eventId": "uuid", "eventType": "DATA_WRITE|ACTION_EXEC|GUARDRAIL_DENY|...",
  "service": "datanet", "operator": "u001", "operatorRoles": ["admin"],
  "resource": {"type": "table", "id": "..."}, "result": "SUCCESS|DENIED|FAILED",
  "traceId": "X-Request-Id 值", "occurredAt": "ISO8601", "detail": {}
}
```

**DLQ（REQ-PLT-23）**：消费失败 3 次重试后进 `<topic>.DLT`；DLQ 积压 >100 触发 runtime-monitor 告警。

## 四、非功能需求细化（REQ-NF-01~09）

| 编号 | 细化规格 | 验收方式 |
|---|---|---|
| NF-01 | 安全八条落地点=§3.1 矩阵；强制卡：涉敏 Task 评审记录必须含 security 集成项，verifier `grep -E "encrypt\|decrypt\|SecretService\|IDataEncryptionService\|securityEngine"` 命中 0 判 FAIL | 评审模板增栏 + CI grep |
| NF-02 | 可复现性实现=快照引用（PRD-09 FC-02/03）：运行 SUCCEEDED 前断言每结果行携带六要素；快照表 checksum 校验 | 集成测试：改事实后旧运行结果 diff=0 |
| NF-03 | 限流参数表：元数据缓存 Caffeine TTL=5min；抽取 PAGE_LIMIT=500×MAX_PAGES=200；管道单任务 ≤30min 超时中断；Function 超时 5s；前端批量 status 并发 ≤10（PRD-08 FE-08） | 各限流点单测/压测 |
| NF-04 | trace 规范：入口读 `X-Request-Id`（无则生成）→ MDC `traceId` → 跨引擎 REST 透传 → 日志 pattern 含 `%X{traceId}`；关键事件格式 `EVT={模块} op={动作} agent={} scenario={} mind={} cost={}ms` | 一次跨引擎请求 grep traceId 串起 ≥3 服务日志 |
| NF-05 | 最低测试集矩阵：**每引擎 ≥1 组契约/集成用例**（security=RLS/CLS/mask/OPA 四组；data=pipeline 安全(已有)+采集链路；ontology=映射契约；kb=抽取 C1/C2/C4+dry-run；cognitive=E1–E4(待 PMO-66)；ai=护栏裁决(待 G4)）+ 三滤波器匿名回归自动化 + CI integration 阶段非空 | PMO-73 G3 交付 |
| NF-06 | 契约回归：既有端点清单冻结（以 ecos-kb 扫描产物为基线），CI diff 新增允许、删除/签名变更 FAIL | ecos-kb scan_all.py 产物对比 |
| NF-07 | 隔离验证：standard 档确认 schema 隔离生效（两 service 写同库不同 schema）；enterprise 档每 service 独立 database 连接串核查 | 两档各一次部署验证 |
| NF-08 | 无障碍基线：全部可点击元素 keyboard reachable；正负方向=颜色+文本（▲/▼）双标识；移动端只读总览断点 ≥375px | 前端走查清单 |
| NF-09 | lint 门禁：tsc 0 错误为提交前置；新增代码禁 `console.*` 无 category、禁硬编码中文（i18n key）、禁硬编码 Tailwind 色值；组件 >800 行报警 | ESLint/tsc CI |

## 五、数据需求细化（REQ-DB-01~06）

| 编号 | 细化规格 |
|---|---|
| DB-01 | 全部新表 DDL 走《数据库访问规范》§四模板：`ecos_` 前缀 + UUIDv4 主键 + 审计 5 字段（create_time/update_time/create_by/update_by/is_deleted）+ domain + version_no；JSONB 加 `_json` 后缀；布尔加 `is_` 前缀；V{n} 与 seed.sql 同 commit；DDL 落 `runtime/runtime-access/src/main/resources/db/migration/`（存量治理裁定） |
| DB-02 | 禁止清单：cognitive 域新增任何业务事实表（ARCH-07 守护）；预测/事实/口径/动作类新表一律落数据/业务域（datanet 管辖 schema） |
| DB-03 | 表存在性预检脚本（QA 开测前必跑）：`SELECT to_regclass('public.kb_cognitive_hypothesis'), to_regclass('public.kb_cognitive_belief'), to_regclass('public.kb_mind_registry');` 任一 NULL → 阻塞测试并回溯 V127~V129 迁移是否执行；场景 Mind 绑定表三候选（kb_scenario_mind_binding / ecos_mind_binding / Mind 直挂 scenario_id）以 Pg 实查 DDL 为准，查实前不进任何 DDL 批次 |
