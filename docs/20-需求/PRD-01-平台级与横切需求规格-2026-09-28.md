### 1.1 REQ-PLT-01 微服务 v2 七 JAR 部署

**细化规则**：

| 部署单元 | 端口 | 启动顺序 | 健康检查 | 依赖 |
|---|:--:|:--:|---|---|
| 基础设施容器（PG/Neo4j/MinIO/OPA/Kafka/ZK） | — | 1 | `docker ps` 全部 healthy | — |
| sysman | 18081 | 2 | `GET /actuator/health` 或既有 health 端点 | PG |
| datanet | 18082 | 2 | 同上 | PG、MinIO |
| buszhi | 18083 | 2 | 同上 | PG |

**验收用例**：

### 1.2 REQ-PLT-02 gateway 唯一入口 + 头防伪

**细化规则**：
1. gateway 校验 token 后 **strip 全部外部 `X-ECOS-*` 头**，按认证结果重新注入（`X-ECOS-USER-ID` / `X-ECOS-ROLES` / `X-ECOS-TENANT` 等，以 gateway 现有实现清单为准）；
2. 前端 BFF（server.ts）默认全部前缀转 `GATEWAY_URL`；`ECOS_LOCAL_DIRECT_SERVICE_PROXY=true` 时仅本地调试允许 5 类前缀直连 service 端口；
3. service 侧 `HeaderAuthInterceptor`：非 gateway 来源（头缺失/非法）默认 DENY。

**验收用例**：
| # | 用例 | 期望 |
|:--:|---|---|
| 1 | 外部请求伪造 `X-ECOS-USER-ID: u999` 经 gateway | service 收到的是 gateway 重注入值，非 u999 |
| 2 | 直连 :18082 带头无 gateway 签名 | 403/DENY |
| 3 | 关直连开关后前端抓包 | 无 18081~18090 直连请求 |

## 二、DIKCW 贯通需求细化

### 2.1 REQ-PLT-10 主链 E2E 贯通用例（P0）

**定义一条黄金链路用例（集成测试脚本，落 `ecos-tests/` 或 gateway test）**：

| 步 | 操作 | 端点/动作 | 期望结果 |
|:--:|---|---|---|
| 1 | 登记数据源 | datanet `POST /api/v1/datanet/datasource` | 201，datasourceId |
| 2 | 采集入湖 | 管道 `SOURCE_JDBC→SINK_MINIO` runOnce | MinIO `raw/structured/...` 有对象；`td_data_resource` layer=RAW zone=STRUCTURED |
| 3 | 落 DW | 管道 `SOURCE_MINIO→SINK`（或 TRANSFORM） | 目标表 layer=CURATED |
| 4 | 本体映射 | ontology entity-mappings 保存 | 映射校验通过（DW 表/列存在性） |
| 5 | KG 抽取 | kb `POST /api/v1/knowledge/extract/structured`（INCREMENTAL） | graph_node/edge upsert >0；watermark 更新；kg_sync_log 台账 |
| 6 | 认知消费 | cognitive 假设/信念（心智层） | 场景关联 hypothesis/belief 可查 |
| 7 | 场景消费 | workspace E1 detect | 返回 Mind 集合（或 503 穿透，两者均为合法） |

**失败判定**：任一步非期望即链路 FAIL；每步产物 ID 串联记录到测试报告。
**测试数据**：专用 schema/前缀 `e2e_`，用后清理（逻辑删除）。

### 2.2 REQ-PLT-11 W→D 现实反馈链（P1，新实现）

**数据模型（DDL 草案，落 DW 层，遵循 DR 红线）**：

```sql
CREATE TABLE IF NOT EXISTS ecos_biz_action_outcome (
    id              VARCHAR(36) PRIMARY KEY,           -- MC01（Q1 b 批准，v1.4 更正）：应用侧生成 UUID，DDL 禁 DEFAULT gen_random_uuid()（PG 方言，多库不可用）
    action_id       VARCHAR(36) NOT NULL,           -- 关联经营动作（PRD-09 FC-04）
    scenario_id     VARCHAR(36) NOT NULL,
    forecast_run_id VARCHAR(36),                    -- 产生该动作的预测运行
    period          VARCHAR(7)  NOT NULL,           -- YYYY-MM
    metric_code     VARCHAR(64) NOT NULL,           -- 回流指标编码
    outcome_value   NUMERIC(18,4) NOT NULL,
    outcome_type    VARCHAR(20) NOT NULL,           -- EVENT / METRIC / FACT
    source_ref      VARCHAR(255),                   -- 证据/凭证引用
    create_time     TIMESTAMP NOT NULL DEFAULT NOW(),
    update_time     TIMESTAMP NOT NULL DEFAULT NOW(),
    create_by       VARCHAR(100),
    update_by       VARCHAR(100),
    is_deleted      SMALLINT NOT NULL DEFAULT 0,
    version_no      VARCHAR(20) NOT NULL DEFAULT '1',
    domain          VARCHAR(50) NOT NULL DEFAULT 'default'
);
CREATE INDEX IF NOT EXISTS idx_bao_action ON ecos_biz_action_outcome(action_id);
CREATE INDEX IF NOT EXISTS idx_bao_scenario_period ON ecos_biz_action_outcome(scenario_id, period);
```

**写入路径**：workspace 行动执行完成 → `POST /api/v1/datanet/facts/action-outcomes`（datanet 新增端点，只增不改）→ 落表 → 发 `PipelineEvent("ACTION_OUTCOME_RECORDED")`。
**消费路径**：下一轮预测运行的输入快照（PRD-09 FC-02）把 action_outcome 纳入事实集合。
**边界**：workspace 不直连 PG（IR01），必须经 datanet REST。

**验收**：动作完成→outcome 落表→事件可查→新预测运行快照含该 outcome。

### 2.4 REQ-PLT-13 场景组成模型与完整度（在途 PMO-66 对齐）

**完整度计算公式（规范定义）**：

```
必备边类型 E_req = { DATASET→OBJECT_TYPE(映射), OBJECT_TYPE→KNOWLEDGE_BASE(抽取), KNOWLEDGE_BASE→AI_AGENT(认知) }
coverage = |E_present ∩ E_req| / |E_req|          -- 按真实连边，禁止按绑定数量
场景完整度 = coverage × 100%
```

**孤岛判定**：绑定节点在 `ecos_scenario_binding_link` 中入度+出度=0（SECURITY_POLICY/INTERFACE 除外，二者分别挂"约束覆盖"与"出口暴露"关系）→ 保存拒绝，返回缺失边提示。
**验收**：完整度指标与 binding_link 表一致；孤岛绑定保存返回 4xx + 明确缺边说明；完整度=绑定数量的实现判 FAIL。
