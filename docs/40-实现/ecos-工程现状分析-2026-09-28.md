## 一、架构现状（微服务 v2，代码核实）

### 1.1 部署单元（7 JAR）

| 单元 | 端口 | 入口 | 职责 |
|:--|:--:|:--|:--|
| gateway | :8080 | `GatewayApplication`（monolith fat-JAR） | 唯一对外 facade，扫全部包 + 60 excludeFilters 防同路径 Controller 冲突 |
| services/sysman | :18081 | `SysmanServiceApplication` | IAM/菜单/审计/脱敏 |
| services/datanet | :18082 | `DatanetServiceApplication` | 数据源/管道/DQ/血缘 |
| services/buszhi | :18083 | `BuszhiServiceApplication` | 本体/工作流 |
| services/aiming | :18084 | `AimingServiceApplication` | Agent/LLM + 认知（cognitive run in aiming） |
| services/dccheng | :18086 | `DcchengServiceApplication` | KB/知识图谱/RAG/规则 |
| workspace | :18090 | `WorkspaceServiceApplication` | 场景层，REST 调全部 5 service |

- `services/` = v2 独立部署单元（boot fat-JAR，Maven 依赖 engine-impl library）；`service/{ge,zhi,cheng,ming}` 仅为四转化 API 文档占位目录，**非 Maven 模块**（不删除）。
- 依赖方向由 ArchUnit 守卫：`workspace →(REST)→ services →(Maven)→ engine-impl → engine-api → common-api`。

### 1.2 Engine 层

六引擎统一 api/impl/boot 三模块制；6 个 boot 均带 spring-boot-maven-plugin，可独立运行（端口与 services 刻意重叠 = 双跑遗留）。Controller 规模：data 37 / ai 32 / ontology 34 / kb 21 / security 13 / cognitive 17；impl Service 类：data 55 / security 30 / kb 27 / ai 24 / cognitive 20 / ontology 18。

### 1.3 Runtime 层

依赖链：common-api（契约叶子）← runtime-core ← runtime-access ← runtime-monitor / runtime-task；llm-gateway 依赖 core+common-api（okhttp-sse）。runtime-event 为 PMO-50 新增 Kafka 事件总线，`ecs.event.kafka.enabled` 关闭时降级内存 SpringEventBus。runtime-access 含 opt-in Maven profile `jdbc-drivers`（ojdbc/mssql/达梦/金仓/openGauss/ClickHouse，离线构建可排除）；Neo4j 驱动 `@ConditionalOnProperty("neo4j.uri")` 运行时条件化。

### 1.4 前端

`src/pages/` 305 个 .tsx + `components/` 94 个，约 50 条路由（HashRouter）。工作台落位：data-workbench（含 pipeline-editor）/ ontology / knowledge / aiworkbench / business-workbench / scenario-sandbox / security-center。i18n：`locales/` 10 领域 × zh/en，`t()` 支持插值与内联 fallback 重载，缺译回退 en → fallback → key。主题四套（slate-light/deep-space/cyber-terminal/royal-purple），localStorage `ecos_theme`。Provider 层次：LanguageProvider（最外）> StrictMode > HashRouter > ThemeProvider > ToastProvider。状态：zustand（`stores/useWorkbenchStore.ts`）；Provider 混在 components/ 与 providers/，无独立 contexts/ 目录。

## 三、风险与债务（按优先级）

| # | 问题 | 证据 | 影响 |
|:--:|:--|:--|:--|
| 1 | **零集成测试** | 全库约 81 个测试文件均为纯单测 + 12 个 ArchUnit/守卫类；0 个 `@SpringBootTest`、0 个 Testcontainers（依赖已在 root pom 声明却闲置）；workspace 0 测试；JaCoCo 门禁 `jacoco.check.skip`/`perModuleCheck.skip` 默认 true | 微服务拆分回归全靠人工，service 层与场景层改动高风险 |
| 2 | **两层代理口径不一** | `server.ts` BFF 默认全走 GATEWAY_URL，开 `ECOS_LOCAL_DIRECT_SERVICE_PROXY` 后 5 类前缀直连（/api/dq、/api/v1/ecos/git、/api/datalake→18082；/api/v1/workspace→18090；/api/v1/cognitive→18084）；而 `vite.config.ts` dev 另有一套直连表（18081~18086/18089/18090），绕过 BFF | dev 与生产行为不一致，路由问题难排查 |
| 3 | **Maven 三档 profile 名存实亡** | root pom 三 profile `<modules>` 完全相同，仅设 `ecos.edition`/`ecos.redis` 属性且全库无代码消费；档位实际靠 `application-{standard,enterprise,flagship}.yml` 的 provider 开关实现；profile 名 `ultimate` 与 yml 名 `flagship` 不一致 | "一条代码三套发布"卖点未生效，档位语义分裂 |
| 4 | **工程卫生** | 后端根目录 45 个 mvn-*.log + `_logs/`；`services/` 下 4 个已卸载孤儿骨架（api-gateway/identity-service/ontology-service/agent-service，前三个带端口冲突 yml，agent-service 为有意保留双容器）；前端 npm+pnpm 双锁并存（pnpm-lock 更新，正向 pnpm 迁移中）、reactflow 残于 package-lock（源码 import 已全迁 @xyflow/react）、49KB chromium .deb 已入库、遗留脚本（migrate_i18n.py/fix_remaining.py/transform_ceos.sh 等）、嵌套死目录 `ecos_frontend/ecos_frontend/` | 认知负担 + 依赖解析混乱 + 仓库膨胀 |
| 5 | **元数据口径** | root pom 仍名 `DataBridge-GZCM v2 / databridge-v2`；root pom 中注释掉的 portal/market/worldmodel 等废弃 module 残留；testcontainers/mysql、milo、moquette 等依赖声明后闲置 | 品牌与工件名不一致 |
| 6 | **前端巨石** | `api.ts` 单文件 110KB；前端仅 14 个 test 文件对 305 页面 | 维护与回归成本高 |
