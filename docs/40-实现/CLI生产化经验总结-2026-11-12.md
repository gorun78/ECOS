## 一、技术经验

### 1.1 代码模式与最佳实践（可复用）

1. **「状态单源」台账模式**：一切「已做/未做/门禁跑到什么程度」以登记册为准（[CLI-MVP落地登记](file:///D:/workspace/javaprojects/ECOS/docs/40-实现/CLI-MVP落地登记-2026-11-09.md) 效力条款），与任何"已验收"表述冲突时以台账为准。这避免了多会话/多 Agent 对同一批次的状态分歧。
2. **契约单源 + 门禁自守**：OpenAPI 契约放 `docs/10-架构/api-contracts/`，配 `CliContractParityTest`（4 法：清单一致 / 命令树一致 / planned 语义 / 变异探针）+ `ops.json` 重生成幂等校验（`-Dcli.gen=true` 后 diff 为零）。契约改动必须过门禁，产物手改后门禁仍绿的情况被第二重保险拦住。
3. **planned 命令不装成功**：`model route` 等 planned 命令输出 `status=UNAVAILABLE` + `code=ECOS-CLI-NOT-IMPLEMENTED` + `source_refs[0].operationId`，绝不返回空集合装成功。这是「不假绿」原则在产品语义层的延伸。
4. **测试反向钉死裁决**：用户裁决「cli-e2e 不入 CI」不是删 job 完事——`CiTriggerCoverageTest.ciJobsMatchRuling` 断言 job 齐全**且 `cli-e2e` 反向不存在**。裁决必须写进测试，防止后人不知情加回常红 job。教训来源：第一次移除 job 后 verify 直接 1 红（`allThreeJobsExist`），就是门禁没随裁决同步。
5. **门禁基线数值与脚本数耦合**：`SCRIPT_COUNT_FLOOR=278 / MAX=328 / NEXT=329` 与单源目录实数强绑定，删除/新增迁移必须同批改门禁——否则恒红或恒假绿。
6. **无 Docker 活体测试底座**：embedded PG（`~/env/pg-embedded`）+ JDBC 侧跑迁移 + embedded Redis，可在无 Docker Desktop 时复现真实库行为。本轮全部四组建库实测均出自此底座。
7. **脱敏/幂等/分页先于功能**：CLI 硬化顺序被证明正确——先传输出面（SSE/日志/脱敏/幂等键）再接命令，后接的命令自动继承硬化层，无回补成本。

### 1.2 解决方案（本轮解决的具体问题）

| 问题 | 根因 | 解法 |
|:--|:--|:--|
| 审计表 0 行但接口 200 | iBATIS `extractSqlFromElement` 只收 `TEXT_NODE`，CDATA 段被漏 ⇒ `td_audit_log` 静默失败 | `SystemDatabaseAccessImpl` 双节点类型兼容 + 4 条**断言 SQL 正文**的测试（非仅断 key 存在——空串也能过 key 断言，这正是缺陷长期不被发现的原因） |
| `ecos_audit_log` 写失败 | V295 建锚表时缺 `changes`/`category` 列，三个写路径全用 | V328 `ADD COLUMN IF NOT EXISTS`（纯增量，零风险） |
| trace_id 头空 | `RequestContextFilter` bean 命名冲突，整条过滤器链不执行 | 显式命名 bean + `X-Trace-Id`（新）与 `X-Request-Id`（旧）双写 |
| L3 审批恒 403 | 客户端硬编码 `subject.role="user"` 与 OPA `input.role` 层级不符 | 审批凭证链（V326 `ecos_ai.agent_approval` 四眼校验：approver ≠ requester）+ 无 token → BLOCKED/exit 2 |
| CLI 分页丢 filter | 翻页时 filter 未透传 | 发请求前校验分页参数（`ab3dc6dc`） |

### 1.3 踩坑记录（防复发，按代价排序）

1. **grep 检索路径段拆分陷阱**：`@RequestMapping("/api/v1/cli")` 类级注解 + 方法级映射拼接，grep `cli/preflight` 永不命中 ⇒ 误判「端点缺失」。修法：先 grep 类名再读源码，登记册 v6.23 已留痕自纠。
2. **`-Dtest='A+B'` 假绿**：surefire `+` 拼接静默跑 0 用例且 exit=0。**必须用逗号** `,`。无 `Tests run:` 行的 BUILD SUCCESS 一律视为未执行。
3. **文档台账只准 append**：v6.26 曾被 Edit 插到 v6.25 之前（用上一行行首做锚），台账乱序。修法：新版本行一律 append 到 EOF，改后 `grep '^| v'` 验序列。
4. **Write 工具对已存在大文件反复拒绝**：162KB 台账属"大文件"，走"先取出行 → sed 删行 → cat >> 追加"链。
5. **未提交实验物必须按门禁清理**：V329（541 行建库脚本）从未提交，但留在工作树会撞 `NEXT_FREE_VERSION=329` 断言。实验产物在提交前要过一遍所有计数门禁，否则它就是颗地雷。修法：备份到仓外 `/tmp/v329-backup/` 再删。
6. **共享工作树并发污染**：合并前必须 `git status` 核对暂存区只含本批文件——本轮工作树常驻 15 个并行会话改动（wagent/scenario/entmgmt），`comm -12` 求交集确认零交叉后才 checkout/merge。
7. **GBK 日志 grep 报 binary file**：`iconv -f GBK -t UTF-8` 先转再 grep。
8. **fat jar 变瘦**：残留 JVM 锁住 jar 时 repackage 静默产出 233K 瘦包。查锁要看 `Win32_Process` 命令行，不能只看 netstat。

## 二、流程经验

### 2.1 协作效率（单人 Agent × 用户裁决制）

- **裁决点前移**：三处关键决策（V327 连带提交 / 建库路线 / 先出报告）都在动手前用选项卡问清，事后零返工。对比早期批次「先做再问」模式，返工率明显下降。
- **「先出报告不继续改」是有效止损**：从零建库审计报告先落库（`8031039f`），用户据此做「不建库」终裁，避免了 3~5 轮 V329 迭代的沉没成本投入。
- **并行会话隔离纪律**：主工作树共享，提交前 ① 看暂存区文件清单 ② 与脏文件求交集 ③ 只 add 自己的路径。本轮两次合并零污染。

### 2.2 任务分发问题

- **批字母制（A~G）优于单一巨批**：每批自带验收判据（§七），失败面可控。批 D（审批凭证）一次就验出四眼校验与失败语义，得益于批次边界清晰。
- **「未做清单」与「做了清单」同权重**：登记册 v6.20/v6.26 显式登记未做边界（审计域两项治理、从零建库独立立项），这是下一轮的天然输入，防止范围膨胀。

### 2.3 审查反馈（假绿族谱——本轮最大贡献）

本轮共识别并修复 **8 类假绿/静默失败**，全部有测试钉死：

| # | 假绿形态 | 检测哨兵 |
|:--|:--|:--|
| 1 | 断言 key 存在但正文为空（CDATA 漏取长期潜伏） | 断言 SQL BODY 内容 |
| 2 | `-Dtest` 语法错误跑 0 用例 exit=0 | 数 `Tests run:` 行 |
| 3 | 变异探针未先证「真的改上了」 | 探针前先 diff 确认 |
| 4 | 单测 mock 看不见装配面（bean 名冲突整链不执行） | 活体请求 + 日志取证 |
| 5 | dry-run 实际触网（设不可达 base-url 仍秒回 SUCCESS） | 不可达端口测零触网 |
| 6 | 响应头空值被当 trace_id 输出 | 对账 `ecos_audit_log.trace_id` == CLI 输出 |
| 7 | 「三 job 齐全」断言与用户裁决脱钩 | 裁决写进测试反向断言 |
| 8 | 台账/文档宣称与实跑状态漂移 | 三遍离线核对 + 状态单源台账 |

**方法论沉淀**：「测试绿」必须出自真实命令的 `Tests run: N, Failures: 0` 行 + 报告文件时间戳新；「完成」必须区分单测/真库/活体三档，不混报。

## 三、改进建议（下一轮产品化）

按「收益 × 成本 × 风险」排序：

1. **【建议下轮首做】L3 授权墙独立立项**：OPA `rbac.rego` 仅 4 条 allow 且客户端硬编码角色与 `input.role` 层级不符，`publish/commit` 恒 403。这是 CLI 三条 L3 命令之外唯一全仓级阻塞，属产品化「能不能用」的硬闸门。修法轮廓：策略面补 role 层级映射 + 客户端从凭证链取真实 role（复用 V326 审批凭证通道），配一条「无授权必 403」的 fail-closed 门禁用例。
2. **从零建库若重启，先补 schema 引导而非锚表**：实测 136 失败中 **90 个纯因 schema 不存在**（链内仅 21 枚写过 `CREATE SCHEMA` 且全在 V111+ 与链尾），10 条 `CREATE SCHEMA` 就能 +70 通过数，比补 37 张锚表成本低一个数量级。需先改铁律 §3.1 口径（独立立项，见审计报告 §六）。
3. **审计域两项治理收尾**：`td_audit_log` 端到端（依赖 `AuditLogServiceImpl` 事件装配）与 `audit_mode` 读取的 schema 漂移（`td_user_security_profile` 未限定 schema，靠 search_path 侥幸命中）。均为真缺陷但影响面收敛，适合与 L3 墙同批。
4. **agent run 活体腿补环境**：`startRun` 需真调 LLM+Kafka，本机无 DeepSeek key 且 broker 未起时 CLI 如实报 UNAVAILABLE（行为正确）。产品化若要演示链路，需一份「环境依赖清单 + 一键起」的 ops 手册，放 `40-实现/ops/`。
5. **CLI 契约门禁推广到前端 BFF**：`ops.json` 幂等校验目前只覆盖 gateway↔CLI 两侧。前端 `server.ts`（Express BFF）的 `/api/*` 转发面无同构门禁，契约漂移时前端静默失效。复用 `CliContractParityTest` 模式即可，成本约一天。
