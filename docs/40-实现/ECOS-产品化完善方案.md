## 一、完善顺序

```
Phase 1: sysman（系统管理）          — 地基，2周
Phase 2: ming（AI工作台）            — 快速亮剑，2周
Phase 3: g + cheng（数据轻量版 + 知识引擎重点补）— 2.5周
Phase 4: zhi（本体工作台）           — I层建模，2周
Phase 5: 全链路深度联调               — 真实数据跑通，2周
```

### 为什么是这个顺序

```
Phase 1 地基 ──→ Phase 2 AI先亮剑（展示价值，前端打磨快）
                      │
Phase 3 数据+知识 ────┤  AI深度演示需要的数据底座和诊断引擎
                      │
Phase 4 本体建模 ─────┤  依赖数据就绪后才能建本体
                      │
Phase 5 全链路联调 ───┘  数据→本体→知识→AI全通，产品级交付
```

核心逻辑：

- **Phase 2优先AI**：AI引擎已最强（70文件/P0-P2完成），前端打磨只需2天，2周能出"可摸可看"的AI工作台。其他引擎的Service都薄，先做有风险的——AI没有这个风险。
- **Phase 3合并数据和知识**：两件事同时推——data只做轻量版（接入1个数据源+DQ+血缘），知识重点补cognitive-engine（诊断引擎从2层因果链扩展到≥3层）。这样Phase 4做本体时有数据可用，Phase 5全链路联调时Agent能"查真实数据"。
- **Phase 4本体后置**：本体建模依赖数据就绪，同时也被AI和知识依赖。放在Phase 4是最合理的中间位置。
- **Phase 5收尾**：前面四个Phase积累的数据+本体+知识+AI能力，一次全链路跑通。

| 能力 | 现状 | 目标 |
|------|------|------|
| 诊断引擎 | 偏差>阈值→通知 | **偏差→因果链≥3层→根因定位→建议**（不降级为"数据不足"） |

**因果链≥3层示例**：
```

  → 原因: 营收下降3% + 成本上升2%
    → 营收下降: 大客户A订单减少40%
      → 根因: 大客户A切换供应商
    → 成本上升: 原材料价格上涨8%
      → 根因: 供应商集中度风险暴露
```

## 六、Phase 5: 全链路深度联调（2周）

> 前四个Phase积累的能力：sysman租户隔离 + AI工作台6内置Agent + data真实数据 + knowledge知识图谱 + ontology本体模型。Phase 5做全链路贯穿。

### 目标场景：科创信息月度经营分析

```
用户: "分析科创信息上个月的经营情况"
  ↓
ai-agent(orchestrator) 拆解:
  ├→ data-agent: "查2026年7月的经营数据（营收/成本/利润/订单/交付率）"
  ├→ ontology-agent: "获取财务域本体模型，理解指标间的关系"
  ├→ cognitive-agent: "对毛利率下降5.3%做因果链分析，追溯根因"
  └→ ai-agent 汇总: 生成《7月经营分析报告》含数据表格+因果链图+改进建议
```

### 联调清单

| 链路 | 验证内容 |
|------|------|
| 租户隔离 | 科创信息用户只能看到科创的数据和本体，看不到其他租户 |
| 数据→本体 | 财务数据表→本体对象映射正确，属性类型匹配 |
| 本体→知识 | 本体变更后知识图谱Schema自动更新，实体链接正确 |
| 知识→AI | RAG检索返回相关制度条款，KG推理追溯因果链≥3层 |
| AI→数据 | data-agent准确查询PG返回脱敏数据，来源标注正确 |
| AI→诊断 | cognitive-agent给出根因定位（非泛泛"需进一步分析"） |
| AI→评估 | 对科创场景评估orchestrator Agent，得分≥4.0/5.0 |

### 前端联调

- 从sysman登录→切换到AI工作台→创建Agent实例→对话→查看Pipeline执行→评估报告，全流程无console error
- 多线程对话不影响
- SSE流式输出稳定，无断线

### 性能基准

| Agent对话首字延迟 | <3s |
