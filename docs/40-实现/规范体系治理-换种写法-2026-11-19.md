# 规范体系治理建议 — 换种写法

> 来源: 用户提问「规则太长，除规则外有没有更好的处理方式」 | 日期: 2026-11-19 | 责任人: 架构治理
> 版本: v1.0（建议稿，未执行任何改动）
> 追溯: 架构铁律 v2.4 / 数据库访问规范 v1.6 / 文档目录规范 v3.3

## 〇、一句话结论

**规则内容一条都不用删，问题在于它们几乎全部只写成了文章。**

文章这种载体的三个毛病，在这个仓库里都已经实际发生：

| 毛病 | 本仓实证 |
|---|---|
| 每次干活都得重读，读了也记不住 | 一次后端改动实际读入约 127 KB（AGENTS.md + 索引 + 铁律 + 后端规范），其中大部分条款与当次改动无关 |
| 违反了没人拦，全靠自觉 | 前端 `npm run lint` 实际只做类型检查，没装 ESLint；git hooks 14 个全是 `.sample` 未启用；两个现成校验脚本写好却没人调用 |
| 同一个数字抄多处，改漏一处就自相矛盾 | 端口号出现在 147 个文件；`V350` 在 7 个文件；索引已写「32 条红线」而正文是 30 条，索引写前端规范 v1.1 而实际是 v1.2 |

同样的意思，有更省事的表达方式。就像教人开车，「红灯停」贴在墙上不如红绿灯本身管用。

**本文的作用域**：只做分析给建议，不改任何规则、代码、配置。下文所有数字均可用 §七 的命令复现。

## 二、五个洞（按严重程度排）

### 洞一（最严重）：CI 门禁大半空转，等于没有

这是本次调查最大的发现，比规则太长严重得多。

`.github/workflows/ecos-ci.yml` 里有五处致命问题：

| # | 问题 | 证据 |
|---|---|---|
| 1 | **触发分支对不上** | CI 只在 `main` / `develop` 触发；实际开发在 `master`（比 `main` 多 1114 个 commit），且 `develop` 分支不存在。**日常提交根本不触发 CI。** |
| 2 | 单测步骤指向不存在的模块 | `mvn test -pl common/common-api`，但该路径不存在（实际在 `runtime/common-api`，有 43 个测试）。这步必然失败，却挂着 `continue-on-error: true`，永远绿。 |
| 3 | 后端测试实际只跑 19 个 | 唯一真正执行的测试步骤是 `-Dtest='*Arch*'`，只匹配 gateway 的 19 个 arch 测试；gateway 总共有 102 个测试文件，其余 83 个不在 CI。 |
| 4 | 四个核心门禁完全不在 CI | `DdlComplianceLintTest`、`SecretScanGateTest`、`MigrationVersionUniquenessTest`、`PublicSqlRegressionTest` 在 CI 配置里出现次数均为 0。 |
| 5 | 三道放行开关 | `|| true`（遗留模块检查）、`-DskipTests -Dmaven.test.skip=true`（构建）、`continue-on-error: true` ×2（单测、docker 冒烟）。 |

再叠加一个事实：项目里已有 `check-controller-filter.sh`（三滤波器校验，铁律自标「最高频踩坑」）和 `check-dangling-changes.sh`，**两个脚本全仓无人调用**。

**这意味着：铁律里那 7 处、DB 规范里那 10 处自称「门禁/自动挡」的机制，在真实提交路径上大部分不生效。** 规则写得再细，没有东西执行它，等于零。

### 洞二：前端没有代码检查工具

- `ecos_frontend/package.json` 中 `eslint` 出现次数 = **0**
- `npm run lint` 实际是 `tsc --noEmit`（只查类型，不查风格）
- 已有 `no-hardcoded-colors.test.ts`、`i18n-coverage.test.ts` 等 59 个检测用例，但它们是 **vitest 提交时跑**，写代码时编辑器零提示
- `lint:size`（文件大小检查）不在 CI 里

区别很实际：测试是提交时才红，ESLint 是**打字时编辑器里就标红**。对 AI Agent 也一样——不用读规范，直接就收到反馈。

### 洞三：git hooks 一个都没启用

`.git/hooks/` 下 14 个文件全部带 `.sample` 后缀。所以「提交信息必须是 `type(模块): 动宾结构`」这条规矩，写错了照样能提交、能推送。

这条能 100% 机器判定，却完全靠人记得去读那 63 行规范。

### 洞四：数字到处抄，已经自相矛盾

| 事实 | 散落范围 | 已发生的漂移 |
|---|---|---|
| 端口号（18086/18090 等） | **147 个文件** | — |
| DDL 版本号 `V350` | **7 个文件** | — |
| 「7 个部署 JAR」 | 3 个文件 | — |
| 红线数量 | 索引 vs 正文 | 索引写 **32 条**（**正确**），但规范正文 `.trae/rules/数据库访问规范.md:6` 写「共 **30** 条」，而同一行枚举 6+8+3+9+6 = 32——**正文自相矛盾** |
| 规范版本号 | 索引/触发文件 vs 文件头 | 索引写前端 v1.1（实际 1.2）、DB v1.6 ok 但触发文件写 v1.2；触发文件还写铁律 v2.0（实际 2.4） |

这不是纪律问题，是缺少单源导致的必然结果。改一个数字要改一片，漏一处就矛盾。

### 洞五：已有的检查会假绿

项目里已经登记过两个假绿缺陷（见 `AGENTS.md` 中 D-15/D-16 条目）：

- **D-15**：DR04/DR05 正则用 `Singleline` 而非 `Multiline`，导致「恒 0 命中恒 PASS」
- **D-16**：DR02 捕获组缺 `.`，对 `CREATE TABLE <schema>.<table>` 只吃到 schema 段，判定永真通过

**这个教训最关键：加了检查 ≠ 规矩被兜住了。** 所以下文每一条机器化建议，都强制要求先用一条「能变红的合成违例」证明它真的会红，再转绿。

## 三、八件事：能机器管的，别用文章管

> 原则：**介质阶梯**——越靠上越便宜可靠。
> ① 让错误写不出来（生成器/类型） ② 提交时变红（lint/测试） ③ 启动时拒绝（fail-fast） ④ 单源生成（消灭手抄） ⑤ 文章（仅人判条款） ⑥ 技能（仅流程型）

### 第 1 件：一个数字只写在一个地方（最划算）

建一份机器可读单源（如 `project.meta.yml` 或常量类），承载：端口表、模块基线数、schema 枚举、DDL 版本常量。

- 启动脚本、门禁脚本、AGENTS.md 表格、docker compose 全部**读它**或**由它生成**
- 规范里改写成「以 X 为准」，不再复述数字。`MigrationVersionUniquenessTest` 里的 `SCRIPT_COUNT_FLOOR` / `MAX_BASELINE_VERSION` / `NEXT_FREE_VERSION` 已是正确形态，把铁律里那串 `V350/298/278` 改成引用常量名

**验收**：改一次端口只改一个文件，全链实跑通过；新增门禁检测「规范正文出现已被单源化的数字」即红。

**改动面**：新增 1 个配置 + 1 个一致性门禁；接入 `_win_tasks/*.ps1`（**需获批，该目录「只增不改」**）。

### 第 2 件：加一个检查，专盯文档自相矛盾

写个测试（放 gateway arch 测试目录，先例 `SecretScanGateTest`），校验：

- 索引写的版本号 == 各规范文件头版本号
- 索引写的红线条数 == 正文数出来的条数
- 被引用的规则文件路径确实存在
- 规范头部无「vX.Y 变更」大块（防止历史回流）
- 规范总行数 ratchet：只许减不许增

**验收（关键）**：先让它在**今天已存在的两处矛盾上变红**（正文 30 vs 枚举 32；索引 v1.1 vs 实际 v1.2），证明它能红，再修数据转绿。

**改动面**：新增 1 个测试类；修 `.qoder/rules/00-规范索引.md` 的两处数字与版本。

### 第 3 件：前端装上 ESLint

把已有测试兜底的规则前移到编辑期：

- 禁硬编码中文（`i18n-coverage.test.ts` 已有语义）
- 禁结构性 Tailwind 颜色（`no-hardcoded-colors.test.ts` 已有）
- 图标仅 `lucide-react`
- 文件行数上限（`file-size.test.ts` 已有）

保留原有测试作为防线，两者并存。

**验收**：每条自定义规则配一个能变红的样例文件；`npm run lint` 输出包含 ESLint 结果。

**改动面**：`ecos_frontend/package.json` 加依赖与脚本；新增 `eslint.config.js`；CI 前端 job 改为跑 ESLint。

### 第 4 件：新建走生成器，别靠记

- **三滤波器**：已有 `check-controller-filter.sh` 但无人调用。两条路：写成 `new-controller` 脚手架直接生成已接线骨架；或把该脚本接进提交门禁。「最高频踩坑」变成「用生成器」或「提交即校验」。
- **DDL 新脚本**：生成器自动取下一版本号、写头注、落到活单源目录 `docs/50-db_script/02-flyway-migration/gateway/`。版本号不再手抄。

**验收**：生成器产物跑既有门禁全绿；手工删掉一处接线必须红。

**改动面**：新增 1~2 个脚本；脚本须被至少一处门禁/CI 引用（否则重蹈洞一）。

### 第 5 件：给每条规则标上「谁在管它」

在规范里每条红线/铁律行尾追加标记：`[gate: DdlComplianceLintTest]` 或 `[manual]`。

不改规则内容，但立刻产出一张**覆盖率地图**：标 `manual` 的就是待机器化 backlog，标 gate 的读者可以少读正文。

**前置硬约束：先修 D-15/D-16 假绿，再谈覆盖率标注。** 检查本身不可信时标注就是自欺。

**验收**：统计 `manual` 条数作为北极星指标，只降不升。

### 第 6 件：该在启动时拒的，别写在文档里

如 `dw.olap.engine` 只能 `doris|clickhouse` 二选一。现状是配错了要翻文档才知道；改成启动 fail-fast 退出，报错信息带上规则编号（如 `ST05`）。

**验收**：故意配错，启动即失败且错误信息含规则编号。

**改动面**：配置校验类 + 对应 yml。

### 第 7 件：流程类规范搬进 skill

你已有 41 个 skill。以下内容是**操作步骤**不是**知识**，适合按需加载：

- 铁律 §五 PMO 执行铁律（禁做清单 / 原子任务 / ≤5 Task / 验证四步法）
- 铁律 §七 新 PMO 指令模板
- DB 规范 §七 DDL 审查清单

搬过去后铁律里只留一句指针。skill 按需加载，不占常驻上下文。

**验收**：指令模板移除后，触发匹配测试通过；铁律对应章节只剩指针。

### 第 8 件：把 git hooks 和 CI 真正接通（**最高优先级，见下文**）

- 启用 commitlint 校验提交信息格式
- 启用 pre-commit 跑快检门禁
- **修 CI**：触发分支改成 `master`；修掉指向 `common/common-api` 的错误路径；去掉三个放行开关；补跑四个核心门禁；补跑 `npm run lint:size`

**这条涉及本机环境与仓库流程，需单独批准。**

## 四、建议顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| **第零批（新）** | 第 8 件：修 CI 触发分支 + 空跑步骤 + 接四个核心门禁 | **所有机器化的前提**。CI 不跑，后面做的检查照样没人执行。先止血。 |
| 第一批 | 第 1、2 件：数字单源 + 文档一致性检查 | 最便宜，先把地面扫干净 |
| 第二批 | 第 3、4 件：ESLint + 生成器 | 最高频踩坑，见效最快 |
| 第三批 | 第 5 件：规则标「谁在管」（先修 D-15/D-16） | 依赖第一批单源，且必须先恢复检查可信度 |
| 第四批 | 第 7 件：流程搬进 skill | 独立，随时可做 |
| 第五批 | 第 6 件：启动校验 | 涉运行时行为，单独批准 |

## 五、不做的事 / 边界

- **不删规则内容**。本文不主张「规则太多砍掉一半」，规则本身对这类工程都是必须的。
- **不取消 `.trae`（单源正文）+ `.qoder`（触发路由）双层结构**。这个设计是对的。
- **不动 `开发环境登录凭据.md`**。它被标注为红线文件，任何 Agent 不得修改。
- **不做纯文档瘦身**（压缩头部、拆册、章节路由）。那只是优化「读规则的成本」，没解决「规则有没有被执行」这个真问题。可作为并行的小优化，但不是主线。
- **变更史不回流**。若后续建变更台账，任何触发文件禁止引用它。

## 六、判断标准

治理是否有效，不看规范写得有多整齐，看三个数：

1. **`manual` 标注条数**——只降不升（衡量机器化进度）
2. **CI 实际执行的测试文件数**——当前实际 19 / 全仓 924，目标逐步抬升（衡量执行真实度）
3. **同一事实的文件副本数**——当前端口 147、V350 7，目标收敛（衡量单源程度）
