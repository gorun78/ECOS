## 一、技术经验

### 1.1 代码模式与最佳实践（可复用）

1. **「验收标识三载体」是反假绿的宪法级设计**（主册 §15.3）：只认 `mvn -Dtest=类#方法` / Playwright 用例名 / lint 脚本名；"人工确认""测试通过"式表述不得写入交付说明。这直接催生了后续所有 DoD 判定表的「验证方法」列都是可执行命令。
2. **DoD 判定分两层**（R7~R11 §3.1）：**设计落地**层 = 文档/字段/契约落地核对；**代码实现**层 = 构建与验收载体实测。两者分开记，不许混报。配套纪律：「需求已批准」「设计已完成」不得表述为「实现已完成」「验收已通过」（补充册一附录 B 最后一条）。
3. **禁捷径清单**（补充册一附录 B 10 条）值得逐字沿用：不新建"认知场景引擎"绕开既有 workspace/cognitive/ai；不在控制 schema 复制正式资产；不把 Prompt/上下文/隐藏推理写进长期表（只留引用+摘要哈希）；LLM 不产财务金额；空返回 ≠ 没数据（区分空集合/未启用/无权限/缺表/超时/故障）；Candidate 生成-验证-审批-应用不得是单步；单次偏差不自动改生产资产；不为小模型建第二套管理；不把批准当完成。
4. **不新增部署基线**（R7~R11 核心承诺）：7 服务 / 无新 JAR / 无新 schema / 无新容器——Rule Center 是逻辑域合入知识工作台 Tab，不升格物理模块；不引规则引擎（禁 Drools）。所有设计增量在这个硬边界内解决，值得作为所有后续设计册的模板条款。
5. **契约载体优先于新表**（B35）：COGNITION 边需要「智能体→知识库引用」，没建新表，而是用 `ecos_agent_registry.metadata` JSONB 扩展位 + V316 幂等 `jsonb_set`——"增量数据配置而非新增数据模型"的判断标准可复用。
6. **迁移号段纪律**：V311~V319 顺延占号，`MigrationVersionUniquenessTest` 基线同步升（316/317→319/320）；并发批次占号（V315 被占→顺延 V316）必须实查后改号，不预留不跳号。

### 1.2 解决方案（三册落地解决的具体问题族）

| 问题族 | 根因模式 | 解法模式 |
|:--|:--|:--|
| 服务间信任链断腿（P1-12/P1-15） | gateway 剥信任头 + 各引擎 RestTemplate 裸调 → 按匿名 403 → 整链降级 | `CallerCredentialSource.applyTo` 单源中继 + 各引擎薄拦截器（判据单源、无上下文不加头 fail-closed）；异步腿无请求上下文仍 fail-closed（设计如此，需服务凭证另批） |
| 契约探测假零（B34 腿 3） | 出站缺 `Accept` → gateway 内容协商用 XML → Jackson2Xml 读回数字变 String → `asLong=0` → contractCount 假 0 | 出站钉 `Accept: application/json` + 变异探针。**「协商面」是新型假绿源** |
| pgjdbc int8 计数映射（B39） | `COUNT(*)`（int8）读 `Integer.class` 抛转换异常 → 详情吞成 404、列表成 409 | 一律 `Long` 取再降位 + `AssetRowMapperInt8ContractTest` |
| 本体快照三重叠加（P1-11） | 列名漂移（created_at vs create_time）+ 表不存在 + 溯源列缺 → 同步恒失败 | 逐层定位：账实订正 DAO 列名 → 快照腿切 V179 权威表 → V314 幂等重放补 8 列。**连环根因要一层层剥，修第一层后必须 live 复测再定位下一层** |
| RLS 演示读策略（B36） | fail-closed 行为正确、缺策略**数据** | 幂等 INSERT 策略行（仅 role_admin、1=1、不放宽其它实体）——「补数据不放宽代码」的边界处理 |
| 蓝图发布链（B37/B39） | gaps 自由文本 → validate fail-closed 不可发布 | 以真实 live 证据重建 v2/v3（tests 三条 P0 均带当日实证）→ 状态机 5 步推进 → approve/release → 双摘要落库 |
| XML 化 + `never()` 假绿（§19.6 #6） | `verify(never())` 内裸值与 `anyString()` 混用，null 实参不匹配 → 「0 次写」断言假绿 | `never()` 面统一 `any()` |

### 1.3 踩坑记录（按代价排序，含三册 §19.6 的 10 项历史缺陷沉淀）

1. **`-DskipTests` 提交 = 缺陷永久潜伏**：§19.6 十项缺陷全部"此前从未暴露"，首轮真跑一次全现形（硬编码 base-url 违两态寻址门禁、NPE 拆箱、白名单未登记、`*IT` 类从未执行、路由表 23→25 计数漂移…）。**规则：收口判定必须真跑「门禁所在模块」全量 test，不是只跑本批新增用例**。
2. **`*IT.java` 系统性假绿**：surefire 默认 include 只有 `Test*/*Test/*Tests/*TestCase`，不含 `*IT`——3 类 7 用例长期"绿"但从未执行。本批只修了 ai-engine-impl（pom 补 `<includes>`），其余 5 个 `*IT` 显式登记不做半截子改动。**根治口径「命名规约统一 + surefire 配置上收父 POM」是独立批次**。
3. **缺口必须如实挂账，不许用豁免基线垫**：B34 曾按门禁登记豁免并声明「不代他域还债」，同日实质收口后**豁免基线同步删除**（11→10 条）、门禁回严态。豁免是过渡态，登记后仍要真修，且「只减不增」。
4. **计数基线漂移**：路由重写表 23→25、Controller 计数 33→37——基线数值与实码漂移时必须 `git ls-tree` 两时点独立实测后订正并注归属，不许拍脑袋改。
5. **「类存在」≠「已承流」**：G1 的 `PublishManifest` 六项绑定在位但 main 面零调用、G4 四眼审批判据是死代码——设计册回写时逐条按代码取证核定，禁止把"契约就绪"写成"发布已接"。
6. **数据前置缺陷层层嵌套**：P0-2 五个阻断源（EXTRACTION 假零、COGNITION 无载体、RLS 缺策略、运行记录 0 行、蓝图未发布）互相纠缠，逐个 live 定位 + 逐批收口（B34/B35/B36/B37），最后完整度 1.0。**多阻断源并行时建 P0 台账逐项销号，比串行猜测快**。
7. **`jsonb_set` 幂等写入 + dev 库实跑复核**：V316/V317/V318/V319 全部「幂等 + 仅当缺失时写」+ dev 实跑（`UPDATE 1`/`INSERT 0 1`）+ 门禁同批升级——迁移脚本四件套纪律。
8. **设计文档「写明执行回写」章节**：补充册一 §19（实施落地记录）和 R7~R11 的「执行回写（#147XX · 日期）」行内批注是本轮最有效的实践——**设计册自带回写区，每轮收口直接订正原文并注明批次号**，文档永不与实态漂移。

## 二、流程经验

### 2.1 协作效率

- **裁决摘要进设计册**（R7~R11 §0.3）：每轮设计增量先落 PMO 裁决表（审计等级 / 注册表定名 / Redis 归属 / Rule Center 不升格 / 禁规则引擎），开发按裁决执行零歧义。
- **「三方对照使用说明」**（R7~R11 §0.4）：写给开发人员的两步查询表（增量查落位表 → 基线查原册同编号章节 → 完成判定查 DoD）——设计册自带导航，避免"读 600 页找一句话"。
- **P0~P3 四级遗留分级 + 每项带「需要谁/什么」列**：P0 阻断验收 / P1 功能缺口 / P2 门禁环境 / P3 技术债，外加「需人工决策的问题」独立小节（5 项待裁决）。这使 10+ 并行缺口的推进路径一目了然。
- **B01~B44 批次回写制**：每批一个锚点段（修了什么/根因/live 证据/门禁数字/残余），闭环一项划掉一项（P1 台账中 9 项 `~~删除线~~` 表示已闭环）。

### 2.2 任务分发问题

- **批内只做该批的事**：B38 明确"曾尝试把拦截器下沉 runtime-core，但 runtime-core 无 spring-web 依赖，不为一个适配器改模块依赖"——**边界成本意识**，不为局部优雅改全局结构。
- **不代他域还债 + 例外处理**：§19.6 第 5 条先声明不代还，后同批实质收口——例外要显式声明理由（"该缺陷属他册存量，但命中本批门禁故收口"）。
- **并行会话占用号段**：V315 被并发批次占用 → 实查后顺延 V316。多 Agent 并行时迁移号段必须实查占号再定号。

### 2.3 审查反馈（三册沉淀的假绿族谱——全仓级）

| # | 假绿/静默失败形态 | 首发现场 | 检测哨兵 |
|:--|:--|:--|:--|
| 1 | `-DskipTests` 提交，门禁从未实跑 | §19.6 十项缺陷 | 收口批真跑门禁所在模块全量 |
| 2 | `*IT.java` 不在 surefire 默认 include | §19.6 #10 | pom 显式 `<includes>`；根治=父 POM 上收 |
| 3 | `verify(never())` 混用裸值与 `anyString()` | §19.6 #6 | `never()` 面统一 `any()` |
| 4 | Accept 协商面 XML 化 → 数字变 String → 计数假 0 | B34 | 出站钉 Accept:application/json + 变异探针 |
| 5 | int8 `COUNT(*)` 读 Integer 抛异常 → 404/409 掩盖 | B39 | Long 先取再降位 + 契约测试 |
| 6 | 服务间裸调无凭据中继 → 403 被吞成"业务降级" | P1-12/P1-15 | 中继单源 + 拦截器契约测试 + live 复验 |
| 7 | "类存在"被当"已承流"（死代码判据） | G1/G4 | 逐条代码取证（调用面 grep） |
| 8 | 豁免基线垫平门禁后不回收 | B34 豁免删除 | 只减不增 + 收口即删 |
| 9 | 计数基线与实码漂移（23→25 / 33→37） | §19.6 #8/#9 | 两时点 `git ls-tree` 独立实测 |
| 10 | ObjectProvider<Object> 多候选 → 审计腿静默降级 | P2-8 | 装配面门禁（单测 mock 看不见，需 live + 日志） |

**方法论**：假绿的共性是「证据面与执行面分离」——测试存在≠执行了、类存在≠被调用、门禁绿≠门禁跑过。所有哨兵的共同点是把断言锚定到**执行事实**（Tests run 行 / 调用面 grep / live 请求）。

## 三、改进建议（下一轮产品化，按收益×成本排序）

### 3.1 阻塞「能不能用」的硬项（建议首做）

1. **P1-18 业务聚合口径 + 真实结果数据**：预测-实际-偏差闭环已 fail-loud 到位（`NEEDS_RECONCILE`，零伪造），缺的是「行动结果→指标实际值」聚合契约（落 `ecos_dw`，属业务域卷02）与真实数据（表 0 行）。这是补充册一 §18 第 9/10 项（偏差诊断与版本发布）的唯一余项，**收口它 = 补充册一 DoD 全闭合**。
2. **G1/G2 承流接线 + G3 凭据供给**：发布授权与 Commit SHA 绑定的契约在位但 main 面零调用；GPG/SSH 真实签名需密钥授权；`sys_config` 无任何 `ecos.git.*` 行（凭据面"代码已收口、凭据未供给"）。三项构成「可信发布链」从部分到可用的距离，需用户裁决密钥与凭据供给。
3. **L3 授权墙**（沿用 CLI 复盘结论）：OPA `rbac.rego` 仅 4 条 allow + 客户端硬编码角色与层级不符 → publish/commit 恒 403。与 G1 承流是同一条「发布可信链」，建议同批立项。
4. **`*IT` 执行面根治**：父 POM surefire `<includes>` 上收 + 命名规约统一（§19.6 第 7 条的既有根治口径），一次性消灭全仓 5 个未执行 `*IT` 类的假绿面。成本约半天，收益是全仓测试可信度。

### 3.2 验收完整性

5. **年度经营预测 E2E 的 Playwright 工程实跑**：10 项业务验证阻塞中大部分已由 B34~B44 逐项解锁（完整度 1.0、四类运行、蓝图 RELEASED、Mind 权威源、contextDigest 在位），**E2E 具备起跑条件**——这是主册第 12 篇（确定性计算闭环）与补充册一 DoD「固定的年度经营预测演练端到端通过」的最终验收，跑通后两大 DoD 同时闭合。
6. **P0-4 全栈负向测试矩阵**：PDP 下线、认知 503、E1-E4 live 负向面未跑（仅排除项做了只读实证）。正向绿不等于负向对——fail-closed 语义（OPA/RLS/Clearance）需要专门的负向用例证明"该拒的真的拒了"。

### 3.3 结构性收尾

7. **G8 组织维度种子铺设**：载体（V308 `owner_org_id`）+ 内部头 + 守卫全就绪，但 6 枚注册行 org 全空 ⇒ live 守卫面未受测。需运维按机构填种子（一次数据供给），守卫面即可 live 验证。
8. **P2-5 schema 漂移单源修正**：`ecos_ontology_git_archive_pending`（V170.2 建在 public）/`ecos_runtime_audit_retry`（V244 建在 public）被代码按限定 schema 查询，目前靠 `LIKE ... INCLUDING ALL` 幂等补表垫着。建议以迁移单源修正（新迁移把表建对 schema）+ 加漂移门禁（`information_schema` 对账），替代手工补表。
9. **P1-3 执行记录跨进程恢复**：执行事件映射到 runtime-task 既有记录（不新建执行表），需先确认任务类型与字段映射——这是"须确认再动"型，先裁决再实施。
10. **契约门禁推广**（沿用 CLI 复盘）：`CliContractParityTest` 模式推广到前端 BFF `server.ts` 转发面，约一天成本。
