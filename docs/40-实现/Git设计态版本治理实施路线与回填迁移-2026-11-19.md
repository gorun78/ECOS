## B3 — 基线回填

### 3.1 口径（用户裁决：回填基线快照）

- 每命名空间**一批** commit（`archiveBatch`），消息首行 `baseline(<ns>): import current state <YYYY-MM-DD>`，trailer `Status` 取资产真实状态。
- tag：`baseline/<ns>/<YYYYMMDD>`。
- **基线 ≠ 发布**：不得把基线写成 `publish`，不得据此认为该资产在 Git 上被发布过。
- 导出只读：全程 `SELECT`，禁任何 `UPDATE/INSERT`。

### 3.2 逐命名空间导出清单与预期

| 命名空间 | 导出对象 | 数据源（只读） | 序列化要点 |
|---|---|---|---|
| `data` | 数据源、资源、字段、目录、分类分级、pipeline、质量规则+调度 | `td_datasource`/`td_data_resource`/`td_catalog_item`/`ecos_data_asset*`/`ecos_pipeline_definition`+node+edge/`dq_rule`/`dq_schedule` | **数据源必须剥密码**，只留 `credentialRef`；字段按资源聚合 |
| `ontology` | 本体模型快照、逐实体、映射、术语、指标、口径、规则、自定义函数 | `ecos_ontology_entity`(+property/relationship 在 `ecos_control`)、`ecos_entity_table_mapping`、`ecos_glossary_term`、`ecos_metric_definition`、`ecos_caliber`(+version)、`ecos_ontology_rule`、`ecos_data.ecos_pipeline_function`(120 行) | 快照与增量并存；口径取当前在用版本内容；函数导出走 `PipelineFunctionDao`（裁决 R-2026-11-20②：此表为唯一载体，`FunctionController` 无 CRUD 落库） |
| `knowledge` | 合规规则、专家规则、知识资产、文档元数据、种子集 | `sys_compliance_rule`、`expert_rule`、`knowledge_article`、`kb_doc` | 文档只存元数据 + 哈希 + 存储路径 |
| `cognitive` | 认知模型、Mind、框架、管线 | `ecos_cognitive_model`、`_mind`、`_framework`、`_pipeline` | 模型取 registry 当前版本 |
| `ai` | Agent（两套载体）、工具契约、编排（AIP + workflow）、模型目录、护栏 | `ecos_agent`(5 行)、`ecos_agent_registry`(13 行)、`ecos_wagent_tool_contract`、`ecos_aip_pipeline`、`ecos_workflow`(+node/edge)、`ecos_llm_model_registry` | **两套 Agent 载体分别导出并在登记表标注待收敛**（裁决 R-2026-11-20⑤：目标单源 = `ecos_ai.ecos_agent_registry`，收敛属后续数据迁移）；编排两套不可合并 |
| `scenario` | 场景定义、蓝图（全版本）、Mind 绑定 | `ecos_business_scenario`、`ecos_scenario_blueprint`、`ecos_cognitive_scenario_mind` | 蓝图逐版本一文件（天然版本行） |
| `security` | OPA rego、RBAC、RLS、CLS、脱敏、ABAC、密级、数据权限、场景安全策略 | `ecos-docker/opa-policies/*.rego`、`td_role*`/`td_permission`、`ecos_rls_policy`、`ecos_cls_policy`、`ecos_mask_strategy`、`td_abac_policy`、`td_*_security_profile`、`ecos_security_policy` | **OPA 现状以文件为准**（库内无副本），基线取文件当前内容；密级档案含人员维度，须脱敏或仅导规则 |
| `platform` | 配置 schema 与字典 | `sys_config`（**只取 `config_group`/`config_key`/`config_type`/`default_value`/`edition`/`status`**）、`sys_dict` | **禁导出 `config_value`** |

### 3.3 缺口登记表（必须产出，禁静默跳过）

对每个命名空间记录：

| 列 | 含义 |
|---|---|
| 资产类型 | 如「数据源」 |
| 源表 / 源文件 | 全限定名 |
| 源行数 | `SELECT count(*)` |
| 导出条数 | 实际写入文件数 |
| 差值原因 | 空值/不可序列化/外键悬空/重复键/敏感剔除 |
| 处置 | 已导出 / 剔除（附理由）/ 遗留待裁决 |

**判定**：任一行「差值为空但原因未写明」⇒ 本批不通过。

### 3.4 验收门

- 每命名空间一条基线 commit + 一个 baseline tag，`git log` 可列。
- `DesignAssetHistoryReader` 能按基线 tag 读回任意资产内容，且内容 sha256 与登记表一致。
- 缺口登记表覆盖 8 个命名空间，无空白原因。
- 旧六仓仍零新增 commit（窗口持续）。

### 3.5 回滚

`git reset` 或重建新仓目录（旧仓未动、写面未切），业务零影响。

## B4 — 未接入域接线

### 4.1 接线顺序（低风险 → 高风险）

| 序 | 域 | 接线点 | 特殊约束 |
|---|---|---|---|
| 1 | `data` 元数据/分类 | `MetadataController` / `CatalogController` / `AssetController` 的写方法 | 数据源剥密；血缘**先裁决**是否引入声明载体 |
| 2 | `data` 质量规则 | `DqRuleLifecycleServiceImpl`（approve 发布点） | 与 B5 联动：先切 Git 再停写 `dq_rule_version` |
| 3 | `ontology` 术语/指标/口径 | `GlossaryController` / `CaliberController` 发布点 | 口径与 `ecos_caliber_version` 联动（B5） |
| 4 | `ontology` 本体规则 | `OntologyRuleService` 发布点（已有 `git_ref` 列与「缺 git_ref 拒发布」门） | 规则中心与本体规则**同一份**，禁建第二份 |
| 5 | `ai` 编排 | `AIPPipelineController`、`WorkflowController` | 两套载体分别落 `ai/orchestrations/{aip,workflow}/` |
| 6 | `ai` Agent 收敛 | `AgentConfigController`（`ecos_agent`）+ `AIPAgentController`（registry） | 先裁决 §九.5 收敛方案，再统一落 `ai/agents/`；**禁止**双写两份 |
| 7 | `cognitive` Mind | `MindRegistrationService` | 绑定声明落 `scenario/minds/`，定义落 `cognitive/minds/` |
| 8 | `scenario` 蓝图 | `ScenarioBlueprintService.release` | RELEASED 后不可变 ⇒ 一版本一文件天然契合 |
| 9 | `security` 全部配置 | 各 Controller 写方法 + `OpaPolicyService` | OPA 只做「提交记录」，**apply 腿不在本批**（§六） |
| 10 | `platform` 配置字典 | sysman 写入点 | 只版本化 schema/default/edition |

### 4.2 每个接线点的统一要求

1. 注入 `DesignAssetArchiver`（经 `OptionalArchiver` 门，缺席即 `not_available` + 机读码 + WARN）。
2. 路径一律经 `DesignAssetLayout`，禁字面量。
3. 提交在**业务事务提交之后**（沿用 `ScenarioStatusTransitionService.archiveScenarioAfterCommit` 的 `afterCommit` 形态），避免回滚留下幽灵提交。
4. 归档 `ARCHIVED` 才发治理审计（携 `git_repository` / `git_commit_sha` / `content_hash`），沿用 `GovernanceAuditPublisher`。
5. 归档失败**不回滚业务**，但必须在响应与日志里分态（禁报完全成功）。

### 4.3 验收门（每域独立）

- 发布动作 → 新仓出现对应路径文件 → **真实 commitId** → tag 存在 → `readAtRef` 按 tag 读回内容与响应 sha256 一致。
- 同一域连续两次发布 → 版本列表 2 行且顺序正确、`content_source=GIT`。
- 归档器移除（测试装配）→ 接口返回 `not_available` + 机读码，**非 200 伪成功**。
- 该域模块全量 test 绿（附 `Tests run:` 行，禁 `-DskipTests`）。
- 门禁只跑焦点视为未验：横切门禁须跑「门禁所在模块」全量。

### 4.4 回滚

每域独立特性开关（建议 `ecos.git.archive.<ns>.enabled`，缺省 false 至该域验收通过）；关闭后回退到「无归档 + `not_available`」既有行为，业务不中断。

## B5 — 版本表处置（沿用四表模式）

### 5.1 对象

> 注：`ecos_ontology_version`/`ecos_object_version`/`sys_rule_version` 已 DROP（V323/V324/V325），不在本批范围；本批只订正 `00_init` 中仍残留的 CREATE（G-p）。

### 5.2 步骤（每表一套，缺一不可）

1. **写面切 Git**：approve/升版时归档到 `data/quality/rules/<id>/<ver>.json` 与 `ontology/calibers/<id>/<ver>.json`，**零库写**。
2. **读面切 Git**：版本列表与详情从提交重建，`content_source` 三态（`GIT` / `DB_IN_USE` / `DB_FALLBACK` + 原因），禁把「查不到」折叠成「无历史」。
3. **双跑观察**：同一窗口内验证 Git 重建结果与表内行数与内容一致（对账）。
4. **备份**：`pg_dump` 该表，登记文件大小与 sha256。
5. **DROP**：单独迁移脚本（V361 起），脚本头写明备份路径与前置已完成项。
6. **订正 init 基线**：`docs/50-db_script/00_init/` 中对应 CREATE 加注记或按既定做法处理，避免 init 与活库继续漂移。

### 5.4 验收门

- 停写后表行数恒定（连续多次发布不变）。
- 版本列表/详情全链 200，内容 sha256 与 Git 文件一致。
- 备份文件存在且 sha256 登记。
- DROP 后原接口不回退为 500（Git 重建腿可用）。
- DDL/版本门 35 例全绿（与 DS-4 同口径）。

### 5.5 回滚

DROP 不可逆：只能从备份恢复（须在停写窗口内）。因此**每一步都必须先备份再 DROP**，且备份须存到受控位置并登记哈希（不入仓库）。

### 6.3 旧仓收口：置 DISABLED 后删除（裁决 R-2026-11-20⑧）

> ⚠️ **删除不可逆**。裁决为「删除」，但删除前四项前置缺一不可（见 ADR-22 §2.4）。

1. 六个旧注册行先置 `status='DISABLED'`（**先禁用、后删除，两步不得合并**）。
2. 对账：每仓 `rev-list --count` 与 HEAD sha 与 B2 步骤 1 记录**完全一致**（证明全程零改写）。
3. `historyOverlay` 读面验收通过（旧历史在新仓可读，或已备份留档）。
4. 逐仓备份 + sha256 登记 + 异地留存；备份不入库。
5. **删除动作须单独授权窗口**，执行记录回写 ADR-22 §2.4 与本文。
6. 删除前须留档的真实历史量（2026-11-19 实测）：`ontology` 32 commit/26 tag、`kb-asset-tree` 4/3、`cognitive-model` 2/2、`scenario-def` 5/0、`agent-collab` 0/0、`pipeline` 0/0——前四仓共 **43 条发布历史**。

- 门禁全量跑「门禁所在模块」（`runtime/common-api` + `gateway`），附 `Tests run:` 行；禁 `-Dtest` 焦点冒充。
- 增面后若撞钉值（文件计数/用例计数），按既定做法升锚并如实登记，禁为换绿扩豁免名录。
- 前端 `npx tsc --noEmit` 零错误 + 单通道门禁绿。
- 六仓零改写对账通过；删除前四项前置逐条签核。

## 五、跨批次的硬性纪律

1. **不宣称未验证的完成**：「测试绿」必须出自真实跑通的命令并附 `Tests run:` 行；无该行一律记未执行。
2. **横切门禁跑全量**：只跑焦点用例如同假绿通道。
3. **单源目录与钉值**：迁移脚本只落 `docs/50-db_script/02-flyway-migration/gateway/`（V361+）；历史脚本归档目录只读；门禁扫描面 = 活单源 ∪ 归档。
4. **构建产物保真**：变更模块需 `clean install` 后再验；gateway fat jar 需带 `-Decos.verify.fatjar=true` 才算验过（否则记未验）。
5. **备份先于破坏**：任何 DROP/删除动作前必须有可回溯备份与哈希登记。
6. **诚实三态**：`ARCHIVED` / `NOT_AVAILABLE` / `FAILED` 不得折叠；`not_available` 不是成功。

## 七、风险登记

| # | 风险 | 触发条件 | 缓解 |
|---|---|---|---|
