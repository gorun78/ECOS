| `ecos_control.sys_rule_version` | **0** | kb `ComplianceRuleDao.insertVersion` | `ComplianceRuleVersionService.getVersions`（已优先按 `git_ref` 读回） |

**本轮已执行（授权内、非破坏）**：三表 `pg_dump` 备份（`/tmp/ds4-version-tables-bak-20261108-123453.sql`，44,651 B）＋读写面盘点。

**本轮未执行**：停写、读面切 Git、DROP。原因：三域读面尚未具备 Git 历史枚举能力（见下），此时停写会让版本历史与规则版本查询直接空掉——属功能破坏，不是迁移。

## 三、逐域迁移步骤与验收门

### 3.1 本体版本（`ecos_ontology_version`，2 行，最先做）

1. runtime-access **已有**按路径过滤的提交史读面 `GitService.listCommits`（`GitServiceImpl` 以 `RevWalk#addPath` 实现）与 `readFileAtRef`；**真正缺口是 commit→版本 DTO 的映射**（版本号/状态/发布人/发布时间从提交元数据与归档文件内容推导），不新增 Git 只读 SPI 也能开工。
2. `OntologyVersionService` 历史读面改用该 SPI（`ontology-model` 仓 `ontologies/{ontologyId}@v{version}`）；DB 仅保留**在用版本指针**。
3. 停写 `insert/updateStatus/setGitRef`（发布链已能 Git 归档，`git_ref` 回填使命结束）。
4. 验收门：Git 历史条数 = 改前 DB 2 行（`ont_entmgmt` 1.0.0/1.0.1，refs `9b03ceec…`/`fcfdee94…`）；历史内容逐字等于改前 `snapshot`；`OntologyGitHistoryApiController` 200；旧表读写 0 命中。
5. 备份后 `DROP TABLE ecos_ontology.ecos_ontology_version`（备份已就绪）。

### 3.2 规则版本（`sys_rule_version`，0 行，第二优先）

1. 现有 `ComplianceRuleVersionService` 已按 `git_ref` 优先读回内容；补「按 `rules/{ruleId}/` 枚举历史」的 Git list。
2. `getVersions` 改读 Git 历史；`insertVersion/setGitRef` 停写。
3. 验收门：改前 0 行 ⇒ 迁移后 Git 历史与规则当前版本一致；规则版本端点 200；DB 0 命中。
4. 备份后 DROP。

### 3.3 对象运行时版本（`ecos_object_version`，0 行，最后）

1. 先裁决归档仓（对象路径落 `ontology-model` 或新增注册仓；后者需架构审批）。
2. `ObjectRuntimeDao` 写路径接 `DesignAssetArchiver`，读路径改 Git list。
3. 验收门：对象状态机/时间线回归通过；DB 0 命中。
4. 备份后 DROP。
