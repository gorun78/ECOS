**本轮修掉的两个活体缺陷（都是真缺陷，不是策略数据）**：

1. **出站信任链断腿（护栏把 403 误报成 503）**：gateway `EcosTrustHeaderFilter` 在链首无条件剥离 `X-ECOS-USER/ROLE/TENANT`，而护栏/工具出站腿只中继 `Authorization` ⇒ 属主 `HeaderAuthInterceptor` 恒 403 `ECOS-AUTH-010`，护栏再把它折成 `GUARDRAIL_FAIL_CLOSED`(503「安全服务不可用」)，与真实策略拒绝混态（违反「不可用 ≠ 无权限」）。修法同 gateway `WorkspaceForwardController` 既有先例：新增 `ServicePrincipalTrustHeaders`，从**已验签主体**（`SecurityContextHolder` + `TenantContextHolder`）补回被剥离的头；入口已带则不覆盖，取不到就不写（仍 fail-closed）。**修复前后实测：503 FAIL_CLOSED → 403 GUARDRAIL_DENIED（拿到真实裁决）。**
2. **工具端点漂移**：`ontology_list_metrics` 指向不存在的 `/api/v1/ontology/metrics`（404），改为真实存在的 `/api/v1/ontology/calibers`（200）。

失败判读：401 → 凭据中继失效（`CallerCredentialSource` 空缺）；403 → ABAC/策略拒（先直打 OPA 确认策略，勿动 SecurityConfig）；**503 `GUARDRAIL_FAIL_CLOSED` → 先查信任链与超时（2s 预算，冷启动首调实测 3~6s 会超时）**；404 → 端点漂移（对照 `CopilotToolCatalog`）；`ECOS-AI-AGENT-RUNTIME-ABSENT` → 目录未装配。

**已知策略基线（非本批缺陷）**：dev 的 `ecos-docker/opa-policies/rbac.rego` 仅放行 `read|list|get|pipeline.execute`，护栏动作 `ai:guardrail:input/output` 与工具域动作不在词表 ⇒ 按 fail-closed 判 DENY。要让对话真正跑通需**授权调整/导入 OPA 策略数据**（与 2026-10-11 记录的 ABAC 基线同源）；本批未改 rego、未绕 SecurityConfig。

```bash

curl -s -X POST "http://localhost:8181/v1/data/ecos/rbac" -H "Content-Type: application/json" -d '{"input":{"action":"ai:guardrail:input"}}'   # => {"result":{"allow":false}}  dev 策略基线
```

## 五、风险与边界（如实登记）

1. **T3 确认门是提示层约束**：`confirm=true` 由模型按 SOUL 纪律在用户确认后携带；服务端只强制「无 confirm 不执行」，无法验证"用户真的点了确认"（对话式 UI 的固有边界）。真实写权仍由 ABAC 策略门把守。
2. **属主端点可达性**：T2/T3 写面（管道/治理/预测）依赖 datanet/workspace 服务在线；MONOLITH 族（本体/知识/AI/安全）经 :8080 需 security 放行对应主体。
2.1 **对话可跑通的前置是策略数据**：dev `rbac.rego` 不含 `ai:guardrail:*` / 工具域动作 ⇒ 输入护栏恒 DENY。这是策略缺口不是代码缺陷；补策略属数据授权（须先获批，见 §四「已知策略基线」）。护栏 2s 超时预算对冷启动首调偏紧（实测 3~6s），预热后 <1s。
3. **126 工具的上下文压力**：每智能体白名单 14~30 个（远小于全量 126）；后续可加工具检索层（本期不做）。
4. **RAG docIds 透传**：knowledge 检索端点是否支持 docIds 过滤未验证（属主不支持时仅展示绑定，UI 已如实标注）。
5. **数据迁移**：旧 builtin-* 仅停用（status=INACTIVE），改回 ACTIVE 即复原；Copilot 种子 seedVersion=2，只补缺不覆盖用户改值。
6. **前端建议区/切换器**已在前批落地（路由驱动 + 动态建议默认收起）；本批未改 Copilot 抽屉。
