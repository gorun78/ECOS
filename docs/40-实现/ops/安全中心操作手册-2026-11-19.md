## 〇、本手册覆盖范围与阅读对象

- **覆盖范围**：ECOS 安全中心（前端 `#/security-center` 五个子页）+ 其背后的安全机制（认证 JWT、网关过滤链、security-engine 裁决面、OPA 策略引擎、审计链、脱敏/行列级安全、clearance 密级准入）+ **ecos-cli 命令行客户端安全机制**。
- **阅读对象**：平台管理员（日常操作 §五~§九、§4A OPA 运维）、安全审计员（§八~§九）、后端/前端开发者（机制描述 §二~§四、§4A）、CLI 使用者（§9A）。
- **不覆盖**：基础设施层安全（Docker/PG/Neo4j 自身加固）、网络层防火墙、生产 K8s 部署安全——本手册只讲 ECOS 应用内安全面。

**关键事实先行（三条贯穿全手册的铁律）**：
1. **安全裁决单源**：RLS/列过滤/脱敏/ABAC/审计 一律走 security-engine REST，禁止各引擎内重复实现（架构铁律 §2.4）。
2. **Fail-Closed**：security 引擎不可用 / OPA 不可达 / 审计链查询异常 → **默认 DENY**（拒绝访问），绝不放行。
3. **审计不可物理删除**：审计记录只打 `archived` 标记，不 DELETE。

## 二、认证与会话机制（怎么登录、token 怎么流转）

### 2.1 登录链路

```
浏览器 Login 页 ──POST /api/v1/auth/login──> gateway :8080 ──> sysman AuthController
                                                                    │ 查 TD_USER → 锁定检查 → BCrypt/PBKDF2 比对
                                                                    │ → 工作站 IP 校验 → 强制改密检查
                                                                    ▼
                                                        JwtTokenProvider 签发 RS256 JWT
                                                                    │
浏览器 <──{ code:0, data:{ accessToken, refreshToken } }────────────┘
   │ localStorage 写入: token / username / roles / ecos_user_id
   ▼
后续每个请求：apiFetch 注入 Authorization: Bearer <token>
```

- **登录 API**：`POST /api/v1/auth/login`（无 Authorization 头）— `ecos_backend/services/sysman/impl/sysman-boot/.../controller/AuthController.java:73`
- **登录前置检查**（任一失败即拒）：账户锁定（`locked`/`locked_until`）→ 密码比对（BCrypt 主 / PBKDF2 兼容）→ 工作站绑定 IP 校验 → 是否强制改密 — `AuthController.java:93-163`
- **JWT 算法**：**RS256**（RSA 私钥签 / 公钥验），组件 `JwtTokenProvider` — `services/sysman/impl/sysman-impl/.../security/JwtTokenProvider.java:104,122,151-156`
- **Token 有效期**（硬编码，`JwtTokenProvider.java:48,51,138`）：
  - access token = **15 分钟**
  - refresh token = **30 天**
  - change-password 临时 token = **5 分钟**
- **RSA 密钥对来源**：配置 `jwt.private-key` / `jwt.public-key`（PEM 或 Base64-DER）；未配置时启动生成临时 RSA-2048（**仅开发用，重启后所有已签发 token 全部失效**）— `JwtTokenProvider.java:53-68`。本机 PEM 落点 `~/.config/ecos/jwt-private-key.pem`，由 `_win_tasks/start-backend.ps1` 注入 `JWT_PRIVATE_KEY` 环境变量。
- **前端 token 存储**：登录成功后写 `localStorage.token`（主键）+ `username` + `roles` + `ecos_user_id`（经 `GET /api/v1/auth/me` 二次拉取）— `ecos_frontend/src/pages/Login.tsx:63-79`
- **token 读取兼容**：`localStorage['token'] | ['accessToken'] | ['jwt'] | sessionStorage['jwt']` 四键兼容 — `src/services/auth.ts:13-27`
- **请求携带**：自封装 fetch 通道 `apiFetch/apiFetchData`，每请求注入 `Authorization: Bearer <token>` — `src/services/httpClient.ts:374-376,404-406`

### 2.2 token 过期与登出

- **401 处理**：`handleAuthExpired()` 清会话三 key + 跳 `#/login` — `httpClient.ts:158-179`
- **403 语义分离**：403 = token 有效但权限不足 → 抛 `NoAccessError`，**不清 token**，广播 `ecos-no-access` 事件供页面渲染「权限不足」态 — `httpClient.ts:187-225`
- **登录后 30s 宽限期**：避免新登录瞬时 401 误清 token（`AUTH_GRACE_KEY`）— `Login.tsx:69-72` + `httpClient.ts:128-153`
- **登出单源**：`performLogout()` = `clearAuthSession()`（保留 `ecos_locale`/`ecos_theme`）→ 跳 `#/login`；触发点 = Topbar 用户菜单 + NoAccess 页 — `src/services/auth.ts:48-85`
- **路由守卫**：`<RequireAuth>` 包全部受保护路由：无 token → `/login`；有 token 先探 `GET /auth/me`：401→`/login`，403→`/no-access?reason=forbidden`，5xx/网络错误→**fail-closed** 也跳 `/no-access?reason=unavailable` — `src/components/RequireAuth.tsx:27-117`
- **黑名单（强制下线）**：`JwtAuthenticationFilter` 查 `sys_token_blacklist`，查询异常 **fail-closed → 503 ECOS-AUTH-005** — `JwtAuthenticationFilter.java:104-121`

### 2.3 其他认证端点

| 端点 | 用途 | 证据 |
|:--|:--|:--|
| `POST /api/v1/auth/refresh` | 用 refresh token 换新 access token | `AuthController.java:415` |
| `GET /api/v1/auth/me` | 取当前用户信息（含 userId） | `AuthController.java:234` |

## §4A、OPA 策略引擎（原理 / 规则 / 操作 / 与安全中心的关系）

### 4A.1 OPA 是什么、在 ECOS 里干什么

OPA（Open Policy Agent）是 CNCF 毕业的**通用策略引擎**，把「访问控制决策」从业务代码里剥离成声明式策略（Rego 语言）。ECOS 用 OPA 承载 **ABAC（属性基访问控制）的裁决面**——业务代码不问「这个用户能不能干这件事」，而是把「谁、对什么、做什么」打包发给 OPA，由策略文件回答 ALLOW/DENY。

**部署形态**：OPA 以独立容器 `ecos-opa` 运行（`openpolicyagent/opa:0.63.0`，端口 8181，内存上限 64m），策略目录 `./opa-policies` 只读挂载进容器 `/policies`，启动命令带 `-b /policies`（bundle 模式，策略即数据，热加载）。证据：`ecos-docker/docker-compose.yml:145-162`。

> ⚠ compose 里 `command` 若去掉 `-b /policies`，OPA 将以**零策略**启动，所有裁决恒 `POLICY_UNDEFINED` → 后端 fail-closed 全部 DENY。

### 4A.2 策略文件清单（唯一策略源 = `ecos-docker/opa-policies/`）

| 文件 | OPA 包名 | 裁决域 | 默认决策 |
|:--|:--|:--|:--|
| `rbac.rego` | `ecos.rbac` | 动作级放行（pipeline.execute / 场景状态机 scenario:* / WAgent 特权动作 candidate:publish·action:commit / AI 护栏 ai:guardrail:* / LLM 外发 llm:chat） | `default allow = false` |
| `data_access.rego` | `ecos.data_access` | 数据访问护栏（角色 × 通道 page/export/ai 三维矩阵 + 违规集 + 义务 obligations） | `default allow = false` |

**为什么文件名用下划线不用点号**：`OpaPolicyService.SAFE_NAME = ^[a-zA-Z0-9_-]{1,64}$` 不允许点号；早期裁决入口用 `"data.access"` 调 evaluate 时校验在 try 之外抛出，**OPA 从未被真正咨询**，每次落异常兜底 DENY。文件/包名合规是被咨询的前提。证据：`ecos-docker/opa-policies/data_access.rego:1-12`。

### 4A.3 裁决调用链（谁触发 OPA）

```
业务代码（场景状态机/WAgent 发布/LLM 网关/AI 护栏/数据查询）
    │
    ├─ workspace 侧: WorkspaceSecurityEngineClient.evaluate ──┐
    ├─ ai 侧:       AiSecurityEngineClient.evaluate          │ REST
    ├─ llm 网关:    SecurityEngineBridge.evaluateVerdict     │
    ▼                                                         ▼
SecurityDecisionService / SecurityPolicyController ──> OpaPolicyService.evaluate(policy, input)
                                                              │
                                                              ▼ HTTP POST
                                                  OPA 容器 {opa.url}/v1/data/ecos/{policy}
                                                              │
                                                              ▼
                                                  rego 求值 → { allow, obligations[] }
```

- **后端唯一 OPA 调用类** = `OpaPolicyService`（`java.net.http.HttpClient`，connectTimeout 3s / 单请求 5s）— `engine/security-engine/security-engine-impl/.../service/OpaPolicyService.java:24-26,100-119`
- **默认配置**：`opa.url = http://localhost:8181`、`opa.policy-dir = /opt/ecos/opa-policies` — `OpaPolicyService.java:69-79`、yml 侧 `security-engine-boot/src/main/resources/application.yml:27-29`
- **请求报文**：`{"input": <调用方组装的 Map>}`，input 结构**不是**固定四元组，由各调用方按 rego 契约组装（如 data_access 要 `subject.roles`/`subject.department`/`purpose`/`resource.dataScope`；rbac 场景要 `action`+`subject.role/roles`）。
- **进程内调用方**（谁真实触发 OPA）：`SecurityDecisionService`（数据访问主路，策略名常量 `POLICY_DATA_ACCESS="data_access"`）、`SecurityPolicyController`（`evaluate("abac",...)`）、`PolicyEngineController`（REST 入口）。`PolicyEnforcementPointImpl` 与 `AbacPermissionCheckerImpl` **不调 OPA**（grep 0 命中，它们是 DB 态 ABAC 通道，与 OPA 是两套并行裁决面）。证据：`SecurityDecisionService.java:56,62,382-390`。

### 4A.4 四态裁决（不是二元 ALLOW/DENY）

`OpaPolicyService` 把 OPA 应答解析为**四态**（常量单源 = `runtime/common-api/.../security/guardrail/GuardrailDecisionContract.java`）：

| 态 | 触发条件 | 语义 |
|:--|:--|:--|
| `STATE_ALLOW` | 2xx 且 `result.allow=true` | 放行 |
| `STATE_DENY` | 2xx 且 `result.allow=false` | 策略明确拒绝 |
| `STATE_POLICY_UNDEFINED` | 2xx 但应答无 `result` 或无 `allow` 键（策略不存在/规则未命中） | **fail-closed → 按拒绝处理** |
| `STATE_UNAVAILABLE` | 非 2xx / 超时 / 应答不可解析 / OPA 不可达 | **fail-closed → 按拒绝处理** |

返回还携带：`obligations[]`（deniedReason/maskHints/watermark/rateLimitKey）、`inputDigest`（SHA-256 留痕）、`policyRef=ecos.<policy>`、`source=opa|fallback`。`FAIL_CLOSE = true` 是**硬编码常量**（配置项已移除，无 fail-open 分支）— `OpaPolicyService.java:47-54,69-79,144-218`。

### 4A.5 规则细节：rbac.rego（动作级）

`default allow = false` 之上的白名单规则（证据：`ecos-docker/opa-policies/rbac.rego`）：

| 动作 | 放行条件 | 出处/背景 |
|:--|:--|:--|
| `pipeline.execute` | `input.role == "system"` | 系统内部管道执行 |
| `read` / `list` / `get` | `input.role != ""`（已认证即可） | 通用读面 |
| `scenario:write` / `scenario:activate` / `scenario:publish` | `is_scenario_admin`（role 或 roles 含 `admin`/`ROLE_SUPER_ADMIN`） | 场景状态机写类，2026-11-17 从「已认证即放行」收紧到角色级（D57） |
| `scenario:read` | `input.subject.userId != ""` | 场景读类（读面非越权风险面） |
| `candidate:publish` / `action:commit` | `input.role` 为 admin/ROLE_SUPER_ADMIN | WAgent L3 特权动作（2026-11-11 授权批） |
| `ai:guardrail:*` | 顶层 `role != ""` 或 `count(subject.roles) > 0` | 内容护栏准入（通过与否仍由 security-engine 规则引擎定，非一律放行） |
| `llm:chat` | `subject.role == "llm-gateway-service"` | 只放行 LLM 网关内部服务主体 |

**载荷形态坑**：场景状态机送 `{action, permission, subject:{userId, role, roles}}`（顶层无 role，角色在 subject 里）；护栏调用送 `{action, type, stage, subject:{userId, roles:[...]}}`（顶层也无 role）——写规则时必须同时认「顶层 role」与「subject.roles 数组」两种形态，否则恒 false。

### 4A.6 规则细节：data_access.rego（数据访问护栏，角色×通道矩阵）

实现详设-01 §4.7.2「角色 × 通道验收矩阵」。三通道：`page`（页面）/ `export`（导出）/ `ai`（AI 工具）；purpose 缺失时按 `environment.channel=="AGENT"` 推断为 ai、否则 page。

**角色矩阵**（与 V246 策略种子同源）：`data_roles = {finance_lead, project_owner, dept_user}`（能进数据面的角色）；`finance_roles = {finance_lead}`（唯一可无请求域限定的角色）。

**违规集（任一命中即 DENY，全部理由串成 deniedReason）**：

| 违规码 | 含义 |
|:--|:--|
| `NO_DATA_ACCESS_ROLE` | 主体不在 data_roles |
| `AI_SCOPE_NOT_DECLARED` | AI 通道 + 非财务主体 + 未声明 projectIds（禁全域扫描） |
| `AI_SUBJECT_DEPARTMENT_UNRESOLVED` | 组织域未解析（无横向越权地板，fail-closed） |
| `AI_DEPARTMENT_NOT_DECLARED` | 带 projectIds 但没声明所属 departmentId（载荷缺陷） |
| `AI_SCOPE_OUT_OF_SUBJECT_DEPARTMENT` | 请求域 ≠ 主体部门（**横向越权**） |

**义务（obligations，四类，拒绝态也须带 deniedReason）**：
- `DENIED`：`deniedReason = 违规码用 "+" 连接`
- `mask`：非财务主体对敏感列 `["hourly_rate","amount"]` 打 `strategy=hide`
- `watermark`：`purpose==export` 且放行时，附导出件页眉页脚水印文本
- `rateLimit`：`purpose==ai` 且放行时，附限流键 `ai.tool.<userId>`

证据：`ecos-docker/opa-policies/data_access.rego:29-186`。

### 4A.7 OPA 操作方式（运维/管理员）

**A. 查状态 / 连通性**
```bash
curl http://localhost:8181/v1/policies            # OPA 已加载的策略清单（无 /v1/health，404 正常）
curl http://localhost:8080/api/v1/policy-engine/status   # 后端视角：OPA 连通 + 本地 .rego 数
```
`GET /status` 返回 `{engine:"OPA v0.63.0", status:connected|error|disconnected, policies:<本地.rego数>, timestamp}` — `PolicyEngineController.java:22-25`、`OpaPolicyService.java:81-98`。

**B. 手动评估（绕过前端直接验策略）**
```bash
curl -X POST http://localhost:8080/api/v1/policy-engine/evaluate \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"policy":"rbac","input":{"action":"scenario:write","subject":{"userId":"u-1","role":"dept_user","roles":["dept_user"]}}}'
# 或直连 OPA（不经后端）：
curl -X POST http://localhost:8181/v1/data/ecos/rbac \
  -H "Content-Type: application/json" \
  -d '{"input":{"action":"scenario:write","subject":{"userId":"u-1","role":"dept_user"}}}'
```

**C. 策略热更新**
- `PUT /api/v1/policy-engine/policies/{name}`（`PolicyEngineController.java:47-59`）→ 后端把策略文本写到**后端进程本地策略目录**（`OpaPolicyService.updatePolicy` → `Files.writeString(policyDir.resolve(name+".rego"))`），**不是**写 OPA REST API、也不直接写容器卷 — `OpaPolicyService.java:303-320`。
- ⚠ **生效前提（重要风险点）**：后端策略目录必须与 OPA 容器挂载目录指向同一处（经 `ECOS_OPA_POLICY_DIR` 环境变量统一指向 `ecos-docker/opa-policies/`）。dev 下 `OpaPolicyDirResolver` 会把 classpath 策略解包到临时目录（`${java.io.tmpdir}/ecos-opa-<random>/`），与容器卷**不是同一目录** ⇒ 此时 PUT 热更**不会**落到 OPA，改了白改。目录解析优先级：① `ECOS_OPA_POLICY_DIR` 环境变量 > ② 显式配置 `opa.policy-dir` > ③ classpath 解包临时目录 — `OpaPolicyDirResolver.java:33-68,81-127`。
- 生产改策略的可靠路径：**直接改 `ecos-docker/opa-policies/*.rego` 文件 → OPA bundle 模式热加载**（或 `docker restart ecos-opa` 强制重载），改完用 §4A.7-B 的 evaluate 验证。

**D. 新增策略文件的纪律**
1. 包名/文件名合规：`^[a-zA-Z0-9_-]{1,64}$`（**禁点号**），包名形如 `ecos.<name>`
2. 必须 `default allow = false` 兜底（fail-closed）
3. 角色矩阵类规则**先扩详设-01 §4.7.2 矩阵文档再改 rego**（矩阵纪律：禁先实现后补格）
4. 改完必跑 evaluate 验证 ALLOW 与 DENY 两侧用例
5. `some x in ...` 语法在 OPA 0.63 需 `import future.keywords.in`（Rego v1 前非默认），漏了整包 load error 拒载

### 4A.8 OPA 与安全中心的关系

| 关系面 | 说明 |
|:--|:--|
| **安全中心是 OPA 的前端管理/验证入口之一** | `detect` Tab 的「ABAC 策略评估器」(`POST /api/v1/security/policy/evaluate`) 与 policy-engine 的 `POST /evaluate` 共用后端裁决链，最终都会咨询 OPA（前者 policy 常量 `"abac"`，后者可指定 `rbac`/`data_access`） |
| **安全中心 ≠ OPA 唯一通道** | OPA 也被**非 UI** 路径调用：场景状态机迁移、WAgent 发布/提交、LLM 网关外发、AI 护栏——这些不走安全中心页面，但同样过 OPA |
| **fail-closed 一致性** | 安全中心「ABAC 评估器」展示的四态结果 = 后端 `OpaPolicyService` 的真实四态；OPA 挂掉时评估器返回的不是"服务异常"而是 `STATE_UNAVAILABLE`（按拒绝展示），与运行时裁决行为一致 |
| **策略编辑不在安全中心** | 安全中心**没有** rego 在线编辑器；策略文件的改、验、热更是运维动作（§4A.7），前端只提供「评估验证」入口 |
| **审计** | OPA 裁决本身不写审计；触发裁决的业务动作（如 scenario:write）由后端 `AuditAspect`/显式审计写入 `ecos_audit_log`（§八），OPA 只负责"裁决"，审计是裁决调用方的责任 |

## 九、常见问题与排障（FAQ）

| 症状 | 可能原因 | 排查 |
|:--|:--|:--|
| 登录后直接跳 `#/no-access?reason=unavailable` | gateway 或 sysman 未起 / `/auth/me` 5xx | `Test-NetConnection 127.0.0.1 -Port 8080`；看 `_win_tasks/logs/gateway-stdout.log` |
| 登录后 30 秒内偶发被踢回登录页 | 登录宽限期外首个请求 401 | 看是否 access token 过期（15 min）且 refresh 失败 |
| 调 `/api/v1/security/**` 报 403 | 当前用户密级 < L2 | 查用户/角色的 clearance 配置（`SubjectClearanceQueryServiceImpl` 级联） |
| 调 `/api/v1/system/**` 报 403 | 当前用户密级 < L3 | 同上 |
| ABAC 评估恒 DENY | OPA 不可达或策略未加载（fail-closed） | `curl http://localhost:8181/v1/policies` 看 OPA 策略；OPA 无 `/v1/health`（404 正常） |
| 审计列表为空但业务有写操作 | Kafka 未起 → 落 retry 表未回灌 | 查 `docker ps --filter name=ecos-kafka`；查 `ecos_runtime_audit_retry` |
| 新增匿名路径 401 | 未登记 `AnonymousEndpointRegistry` | 把路径加进 Registry，跑 `AnonymousEndpointInventoryTest` |
| 前端安全中心某 Tab 空白 | i18n `ecos_locale` 值非法（非 zh/en）整页白屏 | `localStorage.ecos_locale` 重置为 `zh` 或 `en` 后整页刷新 |
| 强制下线后用户仍能操作 | 黑名单查询异常会 fail-closed 503，但如果 sysman 重启黑名单缓存延迟 | 查 `sys_token_blacklist` 表是否有该 token 记录 |
| OPA 评估恒 DENY/UNAVAILABLE | OPA 零策略启动（compose 漏 `-b /policies`）或策略未加载 | 见 §4A.7-A 查 `/v1/policies`；查 compose `command` 是否带 `-b /policies` |

| CLI 写命令 BLOCKED(exit 2) | 未提供凭据 / L3 命令缺 `--approval-token` | 见 §9A.2 凭据四来源；L3 命令必须显式审批 token（§9A.5） |

## §9A、CLI（ecos-cli）安全机制

> 对象：`tools/ecos-cli/`（Java 17 命令行客户端，唯一入口类 `Cli.java`，分发为 `ecos-cli.jar` + 安装脚本）。CLI 是**除浏览器外的第二条对外访问通道**，所有安全设计围绕「不削弱、不绕过 gateway 安全链」展开。

### 9A.1 设计总原则：CLI 不建第二安全面

CLI **不实现**自己的鉴权/授权逻辑，而是**强制把流量送进 gateway :8080**，复用 §二~§四的全部安全链（JWT 验签 → SecurityConfig → ClearanceInterceptor → security-engine 裁决 → 审计）。CLI 侧的安全机制只解决三件事：**凭据怎么来、怎么不外泄、写操作怎么防误触**。

### 9A.2 认证：凭据四来源，禁匿名，不持久化

- **CLI 无登录命令**（不调 `/api/v1/auth/login`，全工程 grep `login` 0 命中）；token 由用户**外部预先获取**（如浏览器登录后从 localStorage 取、或调登录 API）再注入 CLI — `tools/ecos-cli/README.md:49-53`
- **凭据解析优先级**（`CliOptions.java:172-196`）：
  1. `--token <jwt>`（命令行直给）
  2. 环境变量 `ECOS_TOKEN`
  3. `--token-file <path>`（从文件读）
  4. `--profile <name>` → 读 `~/.config/ecos/cli-<name>.properties`（键 `baseUrl`/`token`）
- **无凭据即拒**：没有任何凭据时，**只读接口也一律 BLOCKED(exit 2)**，禁匿名放行 — `commands/GenericCommandRunner.java:90-95`
- **不持久化**：token 只从上述来源读入、内存持有，请求时注入 `Authorization: Bearer <token>`，CLI 自己不写任何 token 缓存文件 — `HttpTransport.java:127-129`
- **凭据永不回显**：所有输出/日志/报错中的 token 一律脱敏（见 9A.3）

### 9A.3 脱敏：Redactor 统一收口（输出/日志/异常全覆盖）

`Redactor.java:8-46` 是所有对外文本的**唯一脱敏入口**，模式覆盖：
- `Bearer <token>` 头形态
- JWT 三段形态（`eyJ...` 开头）
- key=value / JSON 键：`token / access_token / refresh_token / password / passwd / secret / authorization / api-key / x-api-key / approval-token`（含引号与空格变体）
- URL query `?token=...`
- 兜底：逐字替换当前 `ECOS_TOKEN` 环境变量值（≥8 字符时）

**调用点**（任何对外输出前必经）：`Cli.java:53,90,104`（错误出口）、`EnvelopeMapper.java:147-160`（error.message/hint/原始响应体）、`CliLog.java:73`（本地 jsonl 日志逐字段）、`OutputRenderer.java:34`、`SseReader.java:124`（SSE 流）、`HttpTransport.java:146`（HTTP 异常消息）。

### 9A.4 传输与端口红线

- 默认 base URL = `http://localhost:8080`（明文 HTTP，面向本机 gateway；**生产 TLS 由部署层网关/nginx 终结，CLI 自身无 TLS 配置项**）— `CliOptions.java:24`、`HttpTransport.java:50-54`
- **无** InsecureSkipVerify / TrustAll 之类代码（JDK HttpClient 默认校验证书链）——CLI 不削弱 TLS
- **端口红线**：`--base-url` 指向 service 端口（18081-18090）、调试 boot 端口（19xxx）或存储端口（5432/6379/9092/7687/7474/9000/2181）一律 **USAGE(exit 64) 拒绝** — `CliOptions.java:147-170`。目的：强制流量走 gateway，**绕过 gateway = 绕过鉴权与审计**。
- 超时：默认 30s（可调 1~120s），connectTimeout = min(timeout, 10s)

### 9A.5 写操作保护：审批 token + dry-run + 幂等

命令元数据（name / accessMode / requiresApproval / wired）唯一来源 = classpath `contract/ops.json`（**禁手写 URL**），当前 17 条命令，其中 **3 条为 L3 高危写操作**：`ontology publish` / `knowledge publish` / `action commit` — `OperationRegistry.java:44-108`、`ops.json:692-1117`。

| 保护 | 机制 | 证据 |
|:--|:--|:--|
| L3 审批闸 | `requiresApproval=true` 的命令必须带 `--approval-token`，**缺失即 BLOCKED 不发请求，CLI 不得自签** | `GenericCommandRunner.java:52-56,80-88` |
| dry-run | `--dry-run` 只打印 plannedCall 不发请求 | `README.md:75,80-81` |
| 防误拼变真写 | 未知参数一律 USAGE(64)（`--dry-runn` 不会被吞成真写） | `CliOptions.java:81-92` |
| 幂等键 | 写命令未传 `--idempotency-key` 时自动生成 `cli-<uuid>` 并回显；显式键校验 `[A-Za-z0-9._:-]+` ≤128 字符（防头部注入）；发 `Idempotency-Key` 头 | `IdempotencyKeys.java:19-46`、`HttpTransport.java:124-126` |
| 重试纪律 | **只有显式幂等键才允许写命令自动重试**（自动键仅供人工重放/对账，服务端无从去重）；GET 恒幂等可重试。默认 maxAttempts=3、指数退避 base 200ms 封顶 4s + jitter；可重试 = 传输失败/429/500/502/503/504；**429 且 errorCode=E-WA-BUDGET（预算耗尽）不重试**；尊重 `Retry-After`（秒形态封顶 60s） | `HttpTransport.java:73-90`、`RetryPolicy.java:19-89` |

### 9A.6 追踪与审计

- 每次请求注入 `X-Trace-Id: cli-<uuid>`（可 `--trace-id`/`ECOS_CLI_TRACE_ID` 指定）+ `X-Client: cli`；响应回读 `X-Trace-Id`/`X-Request-Id` — `TraceIds.java:6-9`、`HttpTransport.java:119-120`
- **CLI 侧无显式写审计调用**——审计完全依赖后端：CLI 的每个写命令打到 gateway 后，由 §8.3 的 `AuditAspect`/security-engine 审计链落 `ecos_audit_log`。这正是「强制走 gateway」红线（9A.4）存在的意义。
- 本地日志 `~/.cache/ecos-cli/logs/*.jsonl`：**不落 token、不落请求体、不落响应体**（只记元数据 + traceId），且逐字段过 Redactor — `CliLog.java:73`

### 9A.7 分发与安装面

- 产物 = `target/ecos-cli.jar`（不入库）；`dist/` 只含 `install.ps1`/`install.sh`/`build.sh` + 补全脚本
- `install.ps1` 装到 `~/.ecos-cli/lib/ecos-cli.jar` + 生成 `~/.ecos-cli/bin/ecos.cmd` 包装器，**只提示不自动改 PATH**；要求 JDK 17+ — `dist/install.ps1:1-16,61-105`
- 另有 Dockerfile（多阶段构建，运行镜像非 root、不含凭据），不进 compose 基线 — `README.md:40-47`

### 9A.8 CLI 风险点（管理员须知）

1. **明文 HTTP**：CLI→gateway 默认 `http://localhost:8080`。仅适合本机/内网；跨网段必须由前置网关终结 TLS，CLI 不改。
2. **token 生命周期全由用户管**：CLI 不登录、不刷新，15 分钟 access token 过期后需用户重新获取（§2.1）。自动化脚本里建议用 `--token-file` 指向由外部刷新的文件，而非写死 `ECOS_TOKEN`。
3. **凭据不落盘 ≠ 凭据不泄露**：`--token` 直给会进 shell 历史，生产环境优先用 `--token-file` 或 `--profile`。

## 十、给开发者的扩展指引

| 场景 | 规则 |
|:--|:--|
| 新增 Controller 端点 | 必过三道：①`VersionPrefixRewriteFilter` 前缀映射 ②`SecurityConfig`/Registry permitAll ③`ClearanceInterceptor` 密级豁免（双路径 `/api/v1/` 与 `/api/` 各写一遍） |
| 新增匿名放行 | **只**改 `AnonymousEndpointRegistry`，别改 SecurityConfig 散写 |
| 写业务需要安全裁决 | **禁**在引擎内自建 RLS/脱敏/审计逻辑，一律调 security-engine REST（铁律 §2.4） |
| 新增审计点 | Controller 走 `AuditAspect`（sysman 包自动覆盖 CUD）；非 sysman 包需显式调 `POST /api/v1/audit/log` 或注入 `SecurityAuditService` |
| 新写 security 端点 | 双 `@RequestMapping`（`/api/v1/security/...` 为主 + `/api/security/...` 兼容）；审计接入用 `@Autowired(required=false)` 注 `AuditHashChainService` |
| 涉密钥 | 禁硬编码；走 `KeyManagementService` + `application-*.yml`；禁裸用 `org.jasypt`/`org.bouncycastle`（统一 `crypto/kms` 适配器） |
